# PyrePlus — modular, opt-in Pyre rework (parallel prototype)

> **HANDOFF STATUS (2026-07-23).** The IMGUI → UI Toolkit switch this design was once shelved for is **done** — the whole Laubrary editor toolkit is UI Toolkit (`Laubrary.Zui`, the `Z.*` factory) and every tool window is ported. Per the original shelving note, that means this design was **reconsidered for a UITK world**, not ported verbatim: **Zolumn is dropped** (the UITK toolkit already gives collapsible bordered sections that fold — `ZuiSection`/`ZuiBox` — plus a grow-to-fill column layout and a `Z.Divider`), and the window is built directly on `ZuiAssetWindow<T>` + `Z.*` controls. **Slice 1 is BUILT and committed** (Shape section + renderer + window, rendering one live particle). This document is the brief for **Fable Claude** to continue from there. Everything below is current unless a paragraph says "(SLICE 1, DONE)".

## Purpose

Pyre's `Layer` (`Runtime/Pyre/Layer.cs`) is one flat ~60-field bag mixing placement, population, per-particle shape, and modifiers, all always visible regardless of whether they currently do anything (this session added Fire/Fireball/Matte fields to it, making the point sharper). PyrePlus is a restructured data model + UI, validated as a **parallel prototype — its own asset type, its own renderer, its own window** — so the shipping Pyre tool is **never** put at risk. Folding this back into real `Pyre`/`Layer`/`BlastRenderer`, and ideally emitting real `Pyre` assets from it, is explicit future work, not part of this build.

Open it, hit New, and you get a pulsing soft particle. That is the whole of slice 1.

## The UITK conventions PyrePlus MUST follow (this is the new world)

Read `references/ui-layout-rules.md` in the `laubrary` skill IN FULL before writing UI — it is mandatory, not optional. Then:

- **Every control is a `Z.*` factory and REQUIRES a tooltip.** No raw `EditorGUILayout`/`GUILayout`, no bare labels. Use `Z.Field`, `Z.Row`, `Z.Box`, `Z.Section` (collapsible), `Z.MicroSlider`, `Z.Toggle`/`Z.ToggleButton`, `Z.MiniRadio`/`Z.Segmented`, `Z.EnumDropdown`, `Z.Color`, `Z.Object`, `Z.Value` (the animatable `ZUIValue` control), `Z.Value2D` (the animatable XY pair), `Z.Pad` (plain Vector2). Genuine canvas painting (the preview) stays an `IMGUIContainer` — that is the one sanctioned IMGUI island.
- **Animatable fields are `ZUIValue`, drawn with `Z.Value`/`ZuiValueControl`.** Its Static mode now draws a **MicroSlider** by default — label AND value inside the filled track, no thumb (the fill is the handle), a horizontal-gradient fill. MinMax and Curve modes still use an external label. Turn on `Options.grow` (or `WithGrow()`) so a control fills the row's spare width up to a cap and packed pairs share/reflow — PyrePlus's `Val(...)` already does this. (This is exactly the "use the empty horizontal space" and "label inside the microslider" feedback that drove the current look; keep it.)
- **Plain (non-`ZUIValue`) sliders should also be `Z.MicroSlider` with the label inside**, not `Z.Slider` (which is the vanilla thumbed Unity slider) and not a MicroSlider with an external `Z.Field` label. The convention across Pyre is: label + value INSIDE the microslider track. Pyre's `PackedSlider` helper is the reference.
- **Sections fold.** `Z.Section(title, tooltip)` is a collapsible header that owns its body; `Z.Box(title, tooltip)` is a framed foldable box. Use `Z.Section` for the three top-level sections (Shape / Swarm / Modifiers) and `Z.Box` for sub-groups. The design's "gear panel to opt fields in/out" is NOT needed as its own mechanism — a section that folds, plus a single `Z.Toggle` gating the opt-in fields' visibility (rebuild on toggle), gives the same result far more simply. Prefer that.
- **Every edit records Undo and marks the preview dirty.** Route mutations through a `Dirty(Action)` helper: `Undo.RecordObject(spec, "...")` → apply → `EditorUtility.SetDirty(spec)` → mark the preview dirty. The value controls take an `onBeforeMutate` (record) + `onChanged` (dirty) pair.
- **Do NOT add any menu item beyond `Laubrary/Pyre Plus`.** (Laubrary house rule — no speculative menu items.)
- **Verification (do this, every slice):** flip fields / build a spec **in memory** via `execute_script` (never write a `.asset` from a probe, and never call `AssetDatabase.SaveAssets()` — two assets were silently gutted this way earlier); run `ZuiAudit.Audit(window, out int skipped)` and require **0 findings with skipped==0** (a folded section audits clean falsely — `ZuiAudit.ExpandAll(window)` first); and BAKE frames to a PNG strip and read them back by eye (a scratchpad `CaptureWindow.ps1` does a DPI-aware PrintWindow by window title). For a generator, correctness is visual — "compiles + 0 audit findings" is necessary, not sufficient.

## Plug-in forms (PlusForm) — how a shape becomes ONE file

A layer's look is either a built-in `ShapeForm` enum case (the renderer's if-chain) or a **`PlusForm` object** held in `PyrePlusLayer.form` (`[SerializeReference]`). When `form` is set it wins outright: the renderer dispatches to it once at the top of `RenderLayer` (`RenderFormLayer`), the Shape section shows Fill + Alpha + the form's card, and Size / Position / Border (particle-form features) are hidden. `form == null` is the enum path. The model is the modifier stack's pattern applied to the shape itself: an abstract base in the core (`Runtime/PyrePlus/PlusForm.cs`), subclasses discovered by assembly scan, fields drawn by `ZuiReflect`, Undo through `Undo.RecordObject(spec)`, deep copy by reflection. The core never names a form; a **family** of forms lives in its own asmdef that references the core (the template is `Runtime/PyrePlus/Forms/Kiln/`, `com.Lautaro-Arino.Laubrary.PyrePlus.Forms.Kiln`, home of `InfernoForm` and `ForkBlastForm` — the two enum cases migrated to prove the model; their enum slots are retired but kept so the other ints keep their meaning).

What the base gives a form: `DisplayName`, `Description` (the card's tooltip), `Kind` (WholeLayer is what the renderer dispatches today; PerParticle / Stateful are declared for later), `Prepare(in PlusFormPrepareCtx)` once per frame — `ctx.Eval(value, slot)` resolves an animatable `ZUIValue` through the renderer's single deterministic funnel at the layer's life with an auto-derived field id (`PyrePlusRenderer.FldForm - slot`, so the hand-maintained registry is never touched), `Render(in PlusFormCtx, Color32[] target)` with W/H, life, seed, layerSalt, the layer's fill + alpha, the already-prepared geometry/pixel modifiers, phase/frameIndex, and `swarm` — the renderer's own per-particle instance list (position with live spin/scale applied, own life, spawn life, index, orientation, depth, size/brightness multipliers) or null when the swarm is off. `Clone()` and `ContentHash()` reflect over the form's fields, so neither goes stale when a dial is added. The target is always an isolated transparent scratch — a form may SET pixels; compositing, clip, matte and post happen after it. `PyrePlusRenderer.Hash` is public so every random draw in a form comes from the same seeded function; never `UnityEngine.Random`, never `Time`.

**Recipe — add a form = one file, no shared-file edits:**
1. In a family folder with its own asmdef (copy `Forms/Kiln/`'s asmdef: references `PyrePlus`, `SpriteFx`, `ZuiRuntime`; the core must never reference the family), add `MyForm.cs`: `[Serializable] [PlusFormInfo("My Form", group: "Explosions", icon: "bomb")] public sealed class MyForm : PlusForm`.
2. Dials = public fields with `[Range]` (→ MicroSlider; on a `ZUIValue` → the animatable control's bounds) and `[Tooltip]` (every control needs one). `[PlusSwarmOnly]` hides a dial while the layer's swarm is off; `[ZUIShowIf("field", "Value")]` gates a dial on a sibling. Defaults are the field initializers. Keep a private `[NonSerialized]` snapshot of the evaluated dials.
3. `Prepare`: `_x = ctx.Eval(x, 0); _y = ctx.Eval(y, 1); …` — one slot per animatable dial, never reused.
4. `Render`: read `ctx.fill` (`Evaluate(1 - heat, 0.5f, 0.5f)` is the heat-ramp convention: LEFT end = hottest), multiply by `ctx.alpha`, place one instance per `ctx.swarm[i]` (or one centred when null), derive every random from `PyrePlusRenderer.Hash(ctx.seed, ctx.layerSalt, …)`, honour `ctx.geo` (inverse-warp the sample point) and `ctx.pix` (per lit pixel) if the form can, write `target`. **Render must be re-entrant across worker threads** (see "Threading contract" below): no mutable `static` state, no `UnityEngine.Object` access (textures, sprites, TMP, AssetDatabase), RNG replicas (`PlusPyRandom`, `PlusNumpyRng`) instantiated inside Render/Prepare, never shared. Per-instance scratch (planes, buffers, the Prepare'd dials) is fine — a worker renders on its own clone. A pre-pass shared across frames goes through `PlusPrepassCache` (thread-safe, shared between a form and its clones).
5. Recompile. The picker shows it under its group, its card draws itself, Undo/Dup/Clone/ContentHash work, and the whole window needs zero edits. Verify: cold-vs-warm determinism 0 px, a baked PNG strip looked at, `ZuiAudit` 0 findings.

### Shared capabilities available to every form (Phase 3, wave 1)

Small `public static` libraries in the core, pure functions over `float[]` planes / `Color32[]`, no allocation in inner loops when the caller passes scratch buffers, no `Random`/`Time`. Nothing in the default path calls them — a form opts in, so a layer that does not use them renders byte-identical to before.

- **`PlusFieldOps`** (`Runtime/PyrePlus/PlusFieldOps.cs`) — the pre-shade field toolkit: `GaussianBlur(field,W,H,sigma,scratch)` (separable, edge-clamped), `BoxBlur(field,W,H,radius,passes,scratch)` (running-window, 3 passes ≈ Gaussian), `Smear(src,dst,W,H,angleDeg,lengthPx,taps,falloff)` (N-tap directional), `SmearIIR(field,W,H,angleDeg,decay)` (exponential trail), `Warp(src,dst,W,H,dxPlane,dyPlane,amount)` / `Warp(src,dst,W,H,(x,y)=>Vector2)` (bilinear domain warp), `SampleBilinear`, `Bloom(field,W,H,sigma,gain)`, `MultiplyNoise(field,W,H,cellPx,amount,seed,ox,oy,octaves)`, `MaxInto/AddInto/Lerp/Scale/Clear/Sum`, `ComputeStats(plane,lo) → Stats{peak,mean,q50,q90,q99,litPx}` (Kiln's `stats.json` numbers), `Quantile`, and noise: `ValueNoise2D/3D(x,y[,z],seed,period)` (quintic fade, tileable every `period` lattice cells), `Fbm2D/3D(…,octaves,lacunarity,gain,period)`, `Curl2D` (divergence-free advection direction), `Hash01`. `PyrePlusField` (metaball `Sample`/`Accumulate`/`ThresholdShade`/`SmoothMax`/`AccumulateDomes`/`ReliefLight`/`Noise01`) and its `FieldParticle`/`RampParticle` structs are public too.
- **`PlusShade`** (`PlusShade.cs`) — field → RGBA: (a) `BakeLut(PlusRamp|stops|Gradient|ZuiFill, size) → PlusLut` interpolating RGB in LINEAR light (alpha linear), `PlusLut.Sample(t)`/`Sample32`/`Alpha`, `EvalStops`, `Blend(a,b,u,space)`, `SrgbToLinear/LinearToSrgb`; (b) `Banded(t, Color32[] bands)` / `Banded(t, thresholds, colors)` (no interpolation) and `Quantise(t, steps)` (Kiln's `steps`); (c) `DualRamp(lutA, lutB, t, w, lo, hi)` (smoothstep crossfade in linear light — the soot family) and `Palette2D(na, nb, cells).Sample(a, b)`; (d) `AdditiveEmissive(lr,lg,lb,k,blowout,alphaGain)` per-channel `1−exp(−k·L)` with white blow-out, also as a whole-plane overload. Ramp convention everywhere: **t = 0 is the cold edge, t = 1 the hottest core**.
- **`PlusRamp`** — a `[Serializable]` ramp (`List<PlusRampStop> stops` of pos + Color-with-alpha, `space`) a form holds as a public field; ZuiReflect draws it as a box of stop cards (nested plain classes are now drawn generically). **`PlusRampPresets.Ember()` / `EmberSoot()`** ship the gen-7 Fork Blast ramps verbatim (10 stops, linear light, opacity ceiling 0.18 → 1.0); a preset test checks the baked LUT against the contract's own 256-entry LUT within one 8-bit step. A port's ramps go there, never on a default gradient. Unity `Gradient` is NOT the carrier because it caps at 8 colour keys.
- **`PlusClipStats`** (`PlusClipStats.cs`) — field statistics over the WHOLE CLIP, computed once: `Get(cache, ctx, form, sampleFrames, lo, (life, buf) => accumulate)` prepares the form at each sampled life through the real Eval funnel, pools the lit values of every sampled frame, returns `Result{frames, perFrame[], pooled, litPxMax}`, restores the current frame's dials, and is cached by spec hash. **Never normalise per frame** — the ForkBlast post-mortem is the worked example; if the source fitted a constant, port the fitter at clip level or freeze it as a dial.
- **`PlusSupersample`** (`PlusSupersample.cs`) — `Render(ctx, k, renderAt, target)` renders into a `W·k × H·k` scratch (`ctx.WithSize`, swarm positions scaled) and `Downsample`s with a premultiplied box filter (no dark fringe); k ≤ 1 renders straight.
- **`PlusPrepassCache<T>`** (`PlusPrepassCache.cs`) — `cache.Get(ctx, form, () => ExpensiveSetup(), extraHash)` returns the same object every frame until `form.ContentHash()` or the spec's W/H/frameCount/seed/layerSalt changes (keyed by form identity in a `ConditionalWeakTable`, the fire harness's invalidation without replay). Deterministic by construction: `build` reads only the ctx and the form's fields.
- **Swarm hand-off** — `ctx.swarm[i]` carries `x, y` (live spin + scale applied), `own` (die-together honoured), `spawnLife`, `index`, `orientDeg`, `zNorm`, `sizeMul` (depth shading × scale-by-index, exactly as `RenderSwarm` folds it), `brightMul` for every instance, alive or not. `PlusFormCtx` also has `frameCount`, `LifeOfFrame(i)`, `PrepareCtxAt(life)` and `WithSize(w, h)`.

- **`PlusFieldOps.GradientNoise3Periodic(x,y,z,px,py,pz,perm)`** — classic 3-D Perlin gradient noise (12 edge gradients, quintic fade), −1..1, periodic on INTEGER periods per axis with the wrap on the lattice index, over a caller-supplied doubled 512-entry permutation table (the Kiln flame agents' `pnoise3`; `PlusTorch.PermTable` builds numpy's `permutation(256)` exactly). **`PlusRampPresets.Torch*`** — the Flame agent2 banded palettes (hot / ember / white / rim / gold) as the contract's stepped stops, sRGB, plus `TorchTop(name)` (each palette's top threshold in heat units).

- **`PlusFieldOps.SmearShiftX(field,W,H,taps,decay,normalise,scratch)`** (whole-pixel −x geometric-weight smear, zero-filled; the Kiln "speed smudge") and **`PlusFieldOps.BinomialBlur(field,W,H,passes,scratch)`** (zero-padded [¼ ½ ¼] separable soften). **`PlusRampPresets.Orb*`** — the Energy Projectile agent's five signatures (ember / frost / gold / toxin / volt), sRGB, 8 stops, `Orb(name)` by Kiln name.

- **`PlusSupersample.Downsample(float[] pr, pg, pb, pa, W2, H2, k, target, W, H, flipY)`** — the float-plane overload: premultiplied colour + alpha planes box-averaged and quantised ONCE (the Color32 overload rounds each supersample first, which loses a speck under 0.5/255 before it can add up; Plasma Bloom `ashfall` is made of such specks).
- **`PlusForm.UsesFill`** (virtual, default true) — a form whose colour is its own ramps returns false and the window omits the Fill row (Text's Colour-row precedent: no dead control).
- **`PlusRampPresets.Plasma*`** — the Energy Explosion agent's five palettes (ion / cryo / volt / toxin / flare), sRGB, 6 stops, `Plasma(name)` by Kiln name.
- **`PlusNumpyRng`** (`Forms/Kiln/PlusNumpyRng.cs`, family assembly) — numpy's `default_rng(int)` stream bit-for-bit (SeedSequence pool 4 → PCG64 XSL-RR → `random()`, `random(n)`, `shuffle()` via `random_interval`). A Kiln port whose source fixes its populations / lattices with numpy draws uses it to get the SAME picture, not a statistically equivalent one; seeded from the spec seed + layer salt only, so the determinism contract holds. Verified against recorded numpy values in `PlasmaBloomTests`.

### Modifier support for forms (all three kinds, for free)

| Modifier kind | Legacy shapes (Disc …) | Plug-in forms | How |
|---|---|---|---|
| **Geometry** (Wobble, Rotate, Scale, Skew, Turbulence, Curl, RingWave, PointBlast, Sunburst, PulseRings, Profile, Ground, Sphere, Smudge, PinWarp …) | ✅ per sample, around each particle | ✅ post-render, around the layer centre (`PlusFormWarp`, T-0058) | `GeometryModifier.InverseWarp` is an inverse map of the sample position. A per-pixel-sampled shape folds it into every sample; a field form has no sample position, so after `Render` the renderer inverse-maps every destination pixel of the finished layer buffer through the stack and resamples the source. Conventions = `PlusInferno`'s per-sample loop: canvas-pixel offsets from the centre (y-up), `GeoCtx(W/2, H/2, centre 0, radius min(W,H)/2)`, highest `WarpPass` first, the renderer's per-frame `phase`. **Nearest** sampling (identity-equivalent stacks are byte-identical, hard edges survive); outside the canvas reads transparent. Published parity planes (`IPlusFieldPublisher`) go through the same integer map, so dumps stay aligned with the frame. Skipped entirely when the layer has no geometry modifiers — the default path is the untouched code. |
| **Pixel** | ✅ | ✅ (the form applies `ctx.pix` per lit pixel) | unchanged |
| **Post** | ✅ | ✅ (renderer, after the layer) | unchanged |

**The `HandlesGeometry` rule:** forms get geometry modifiers for free; override `PlusForm.HandlesGeometry => true` ONLY if you apply `ctx.geo` per sample yourself (Inferno does — its containment test reads the warped point, which a post-warp cannot reproduce), otherwise the renderer would warp you twice. A form that returns true and ignores `ctx.geo` simply gets no geometry modifiers.

**Layer-centre vs per-instance:** the Disc path warps each swarm particle around its OWN centre (`GeoCtx.center` = the particle, `radius` = its radius); the generic pass warps the whole layer buffer once around the canvas centre — "wobble the layer", which is what a field form's swarm reads as anyway (one accumulated field). A per-instance warp for swarming forms is a possible later refinement, not built.

## Determinism contract (non-negotiable — the renderer's whole point)

`PyrePlusRenderer` mirrors `BlastRenderer`'s contract exactly: **pure, static, every random value derived from a seeded `System.Random` keyed by `(seed, particleIndex, fieldId, …)` — never `UnityEngine.Random`, never `Time`**, so preview, bake and runtime produce **byte-identical** output from the same inputs, and any frame renders on its own (no state carried between frames). `Eval(ZUIValue, life, seed, particleIndex, fieldId)` in the renderer is the single funnel for this — a MinMax field becomes a per-particle random draw, a Curve field reads the envelope at that particle's own life, a Static field is the value. **Verify determinism per slice:** render a frame cold, render it again after a forward pass, compare — must be 0 differing pixels. (`PyreNoise` in `Runtime/Pyre/PyreModifiers.cs` is `internal` and NOT reachable from PyrePlus — write your own hash/value-noise if you need noise; the renderer already has a `Hash`.)

## Threading contract (T-0060 — the preview fills on every core)

Because every frame renders standalone, `PlusFrameFill` (`Runtime/PyrePlus/PlusFrameFill.cs`) renders the frames of one clip on `ProcessorCount - 1` dedicated worker threads and the bytes are identical to a serial loop (tested: five-layer spec, 0 px over 9 runs and three worker counts; the live cache textures vs `RenderFrame` 0 px). What makes that legal, and what every renderer edit and every form must keep true:

- **Renderer per-thread state is `[ThreadStatic]`:** `_layerSalt`, `_textReady`, the `ComputeSpawns` scratch lists. Never add a plain mutable `static` to the per-frame path; `static readonly` tables and resolve-once reflection handles (`volatile` flag) are fine.
- **Workers render on their own deep clone of the spec** (`Object.Instantiate`, main thread, `HideAndDontSave`, destroyed when the fill is disposed). So a form's instance fields — planes, scratch buffers, the snapshot `Prepare` stores — need no locking; `Prepare`/`Render` are never called concurrently on the same instance. Modifier instances (their `Prepare` state) are cloned along.
- **Shared pre-passes:** `PlusPrepassCache` is thread-safe (immutable snapshot per entry, build under the entry's lock — N workers missing at once build ONCE) and keys by `PlusForm.PrepassIdentity`: a render clone is linked to its origin (`SharePrepassWith`), so the Plasma fit / clip stats the main thread's first frame computed are reused by every worker. A duplicated layer (the editor's `Clone`) is NOT linked — its own entry, as before.
- **Serial-only layers** (`PyrePlusRenderer.IsParallelSafe(spec, out reason)`): Fire / Fireball / an enabled simulation modifier (replay harnesses step N-1 → N, keyed by layer), Text (TMP atlas + AssetDatabase auto-pick — checked on `shapeForm` even when a plug-in form is set, because the loop bakes the atlas before the form dispatch), Sprite and any Fill with a Sprite texture (`GetPixels32`), Playback3D, and an installed `PlusFormDebug.FieldSink`. Any such layer makes the whole spec fall back to the serial fill; the Kiln forms are all parallel-safe. A port must not introduce a new main-thread dependency — bake it on the main thread into plain data first (the LUT idiom) or it joins this list.
- **Thread-safe Unity APIs the path relies on:** `Gradient.Evaluate` / `AnimationCurve.Evaluate` (thread-safe in Unity's bindings; exercised by the test on worker threads), `Mathf`, `Color32`, `System.Random`, `Debug.Log`. `Texture2D` never leaves the main thread: workers return `Color32[]`, the editor uploads.
- **Cancellation:** a fill is cancelled between frames; an in-flight frame finishes and is discarded. The editor replaces the fill object on every invalidation — its queue is never drained again, so a stale frame cannot land (the object is the generation id) — and starts no new fan-out while a cancelled one's workers are still mid-frame (a dial drag never piles up threads). Specs under `ParallelWorthMs` (100 ms of remaining serial work) stay serial: the threads' start-up and the one-tick result latency outweigh the gain.
- GIF export still renders serially through `RenderFrame` (untouched).

Measured (12-core machine, 11 workers, 128 px × 24 frames): Arc Burst / Lichten serial 8.7 s → parallel 0.93 s renderer-only; in the live window the fill went from 10.3 s wall (T-0059) to 1.1–1.5 s. Plasma Bloom 2.7 s → 0.21 s renderer-only (the live fill is ~1.5 s because the 1 s fit pre-pass runs with the first, main-thread frame). A 64 px Disc clip (2 ms) stays serial.

## Per-layer preview cache (T-0061 — hide/show/reorder recomposite; a dial re-renders one layer)

The editor's frame cache (`PyrePlusWindow.FrameCache.cs`) no longer stores frames — it stores LAYERS. Each layer's rendered buffer for each frame lives in a content-keyed LRU store (`PlusLayerCache`, 64 MB, never evicting the layers of the spec being filled) and frames are COMPOSITED from those buffers (`PyrePlusRenderer.ComposeFrame`). The renderer was factored so there is one per-layer code path for the bake and the cache (`PyrePlusRenderer.Layers.cs`): `PlanFrame(spec, f)` decides, without rendering, what every layer does in that frame (active / role / clip / luma matte / heightmap consumer / fast path / background-fused); `RenderLayerBody` is the one body every path runs (form or particles, border rim, the layer's own posts, the sim slot); `FrameComposer.Apply` folds a finished layer into the frame (matte write, luma arm, matte apply + clip + Over, deferred border) and `Finish` runs the deferred borders and the spec-level posts. `RenderFrame` itself = `PlanFrame` → `RenderLayerBody` (target = the frame buffer on the fast path, a fresh buffer otherwise) → `Apply` → `Finish`, and its bytes did not change (the whole suite, parity dumps included, is green). `RenderLayerFrame` / `AccumulateChannel` / `ComposeFrame` are the public pieces the cache uses; `PlusLayerFill` runs "render layer L of frame F" and "compose frame F" jobs on worker threads with the same clone/cancel discipline as `PlusFrameFill` (which remains for whole-frame parallel renders).

**Keys (`PlusLayerKey`).** A layer's buffers are keyed by a 64-bit FNV over: every Unity-serialized field of the layer except `enabled` / `name` / `shapeAdvanced` (ZUIValues, fills, gradients, curves, the modifier stack, the sim slot, the plug-in form via `PlusForm.ContentHash`); the layer's INDEX (the renderer's layer salt is the index, every seeded draw reads it — a moved layer renders differently and must re-render, a layer that stays put while others are hidden does not); the spec's canvas / frameCount / seed; the spec's global GEOMETRY and PIXEL modifiers with their list positions (they wrap every layer's stack and their Eval ids depend on list position). Per frame a buffer carries a VARIANT: the background hash when the buffer is background-fused, and for a heightmap consumer the keys of the active writers below it on its channel. NOT in any key: visibility, list order beyond the index, spec-level POST modifiers (applied after compositing), clip channels and the luma matte (applied at composite time from the matte layers' own cached buffers — editing a matte layer re-renders that matte layer alone). Nulls hash as what Unity writes on serialization (empty string / list, a default instance of a plain `[Serializable]` class, "no object" for a Unity reference) and owners' `ISerializationCallbackReceiver.OnAfterDeserialize` runs before hashing (ZuiFill seeds its companions there), so a layer built in memory keys like the asset it becomes across undo snapshots and reloads; the one residue is a Gradient / AnimationCurve that is null in memory (a `new ZuiFill(color)` Solid), which Unity materialises on the first serialization — a brand-new layer re-keys once at its first undo or reload.

**Consequences, measured live (12 cores, 11 workers, Lichten + Plasma Bloom + Disc swarm + Inferno at 128 px × 24; before = T-0060, where every one of these re-rendered all 96 layer-frames, 1.7–1.9 s wall):** first fill 96 layer-frames, 12.2 s of rendering in 1.8 s wall (unchanged); hide a layer 0 renders / 25–60 ms; show it 0 / 20–60 ms; edit a Disc dial 24 renders (the Disc only), 36 ms; edit a Lichten dial 24 renders, 1.6–1.8 s (that layer IS the cost); swap two adjacent layers 48 renders (the two whose index changed), 430 ms; move a layer from bottom to top 72 renders (every index shifted); undo any of those 0 renders / 50–70 ms; redo 0; add or edit a spec-level post 0 renders / 50–60 ms; a dial drag on Lichten restarts per step with 72 hits each time; scrub to an unrendered frame after a Lichten edit 330 ms (one layer-frame + the composite, vs a whole frame before). Live cache textures vs `RenderFrame`: 0 px on all 24 frames when every layer is one the renderer isolates (forms, posts over content, clips, mattes, borders, sims); with the plain Disc swarm (a fast-path layer) in the stack, 3413 of 393 216 px differ by at most 2 in alpha and 2/255 in premultiplied colour — the quantisation described next.

**The fast path and exactness.** A plain Draw layer (enum form, no post over earlier content, no clip / luma matte / border / sim) paints its particles straight into the frame; `Over` is straight-alpha with a byte quantisation per step, so that layer's isolated buffer composited afterwards cannot be byte-identical wherever the frame beneath it is not transparent. Where the frame beneath IS transparent its bytes are copied verbatim (exact); the first fast-path layer over a VISIBLE background is cached FUSED with the background (variant = background hash) so a post on it sees bg + layer exactly as the bake does (a semantic difference, not rounding — never allowed to drift); elsewhere premultiplied colour and alpha move by at most a couple of steps (the straight colour of a near-transparent pixel can read further off because dividing by a tiny alpha amplifies a 1/255 step). The bake (`RenderFrame`) keeps the fast path and its bytes; the tests pin both the exact cases (0 px) and the quantisation bound (`Assets/Tests/PyrePlus/PlusLayerCacheTests.cs`).

## Burst-boosting a form (T-0062 — Arc Burst's rasteriser; the recipe for the next one)

Arc Burst at 128 px spent ~90 % of a frame in two per-pixel loops (`ArcField.Seg` + `Put`: ~37k strokes × ~200 px bboxes × three transcendentals on Lichten). The form now renders the same picture through one Burst kernel, and the way it was done is the recipe for any other form whose time is in a rasteriser rather than in its geometry:

1. **Measure first, and take the bit-exact managed wins before touching Burst.** A `Stopwatch` table of `RenderFrame` per layout/preset at the canvas that matters (all ten Arc layouts, frames 0..23 averaged, plus an FNV over the frames so "unchanged" is provable). For Arc Burst two exact changes halved every layout before any Burst: a **skip test** (the composite is a pure maximum, so a pixel whose planes already sit at or above the most this stroke could deposit — bounded by monotone tables sampled below the true argument and widened by 1e-5 — is never computed) and a **bbox for `Blob`** (outside the profile's largest radius the soft edge clamps to exactly 0). Keep exact `Math.Exp` / `Math.Pow` in this step; a LUT is a float change and belongs with the Burst switch, where drift is accepted once. Gotcha met here: Mono evaluates `Math.Pow(d * invW, 1.7)` with the float product promoted to double UNROUNDED, while storing it in a float local first rounds it — a last-bit change that reached the bytes of one layout. So "arithmetic-only" refactors are not automatically exact under Mono either; the FNV table is what tells you.
2. **Collector + kernel.** The geometry stays managed and untouched. The field object that used to rasterise immediately (`ArcField`) becomes a collector: `Seg` / `Blob` append blittable records (`ArcSegRec`: endpoints in plane pixels, `invW`, amp, opa, the bbox already clipped — computed in managed double exactly as before; `ArcBlobRec`: centre, radius, profile offset into a shared `double[]` pool, soft / edge / hole). One `[BurstCompile(FloatMode = FloatMode.Strict, FloatPrecision = FloatPrecision.High, CompileSynchronously = true)]` static method (`ArcRaster.Run`) sweeps all records into the E / A planes with maximum compositing. Records are per-thread grow-only pools (`[ThreadStatic]`, the `PlusSupersample` idiom) — a form renders one frame per thread, and 37k records would otherwise be 1.6 MB of garbage per frame. Marshalling is `fixed` pointers over the existing `float[]` planes and the pools (`allowUnsafeCode` on the family asmdef) — zero copies, and no `NativeArray` lifetime to dispose on a `[SerializeReference]` form that has no teardown hook.
3. **Flush where order matters, nowhere else.** Maximum deposits commute, so the only ordering constraints are the full-plane passes that happen BETWEEN deposits inside a draw (`Bloom`, `FadeAngular`, `Hollow`, `ScaleAlpha`) — each calls `Flush()` first, and the form flushes before its bloom. Anything else (a blob after a stroke, a swarm instance after another) needs no flush.
4. **The kernel is the only path.** Burst's exp / pow are not bit-identical to Mono's C-runtime calls (and Mono rounds float sub-expressions differently, see 1), so a managed twin selectable at runtime would make preview, bake and tests disagree by a last bit depending on a menu toggle. There is no managed `Seg` / `Put` any more. `CompileSynchronously` means the first call blocks on the compile instead of running a frame on the fallback; in the editor Burst compiles direct-call methods during the domain reload, so no stall was measurable after a reload (Cage frame 3: 5.6 / 5.8 / 6.4 ms for the first three calls). With Jobs ▸ Burst ▸ Enable Compilation OFF the same source runs under Mono — correct, several times slower — and `ArcRaster.CheckEnabled` logs one warning per session.
5. **Off the main thread.** Forms render on dedicated worker threads with spec clones (T-0060) and `JobHandle.Schedule` is main-thread-only, so the kernel is a `[BurstCompile]` static method reached by Burst direct call on the calling thread — no job struct, no `JobHandle`. Parallelism stays across frames (one worker = one frame); inside the kernel the records run serially. A row-parallel `IJobParallelFor` would be valid (maximum is order-independent) but would need the job system, i.e. the main thread.
6. **Asmdef.** `Unity.Burst`, `Unity.Collections`, `Unity.Mathematics` references go on the FAMILY asmdef (`PyrePlus.Forms.Kiln.asmdef`), never on the PyrePlus core — the legacy paths keep their byte-identity baselines trivially (Disc FNV 1EA483FD unchanged), and `allowUnsafeCode` only where the pointer marshalling lives.
7. **Re-parity and re-baseline.** Run `PlusParityDump.FromContract` + `SetContractParam("draw", …)` + `Dump` + `Compare` on every contract draw, record every stage per draw in the task log, and look at the contact sheets. Arc Burst after the switch: all ten PASS, IoU 1.000, field MAD ≤ 1.5e-6, Pearson ≥ 0.99999999998, pixel rgb MAD ≤ 0.083, alpha MAD ≤ 7.2e-4. Four layouts (Bolt, Terminal, Stipple, Pinch) stayed byte-identical to the managed output; six moved by a last bit (the exp/pow drift). Any in-repo hash of the form's bytes is re-recorded with a comment saying why; the parallel-fill (0 px serial vs parallel) and cold-vs-warm tests stay as they are — Burst is deterministic run-to-run on one machine, and the kernel has no shared state. Cross-CPU caveat: Burst's CPU-feature dispatch can in principle pick different math paths on another machine; a desktop-vs-laptop strip diff is the check if that ever matters.

Measured (`RenderFrame`, 128 px, average of 24 frames, warm): Lichten 356 → 180 (managed wins) → **77 ms**; Bolt 156 → 82 → 30; Pinch 122 → 61 → 23; Terminal 54 → 26 → 17; Lattice 46 → 17 → 10; Stipple 46 → 24 → 12; Weave 35 → 21 → 12; Core 31 → 18 → 12; Crown 23 → 13 → 7; Cage 18 → 11 → 8. Lichten + swarm 4 + Wobble/Tint/Bloom, 12 frames: serial 1563 ms, 8-worker fill 275 ms, 0 px apart.

## Remaining work

### SLICE 2 — Swarm (the big one)

A single top-level `Z.Toggle` "Swarm" gates the whole section (off = exactly one particle, the current behaviour; the section's other controls are hidden — rebuild on toggle). When on:

- **Mandatory:** `count` (int, min 2) — an ordinary field.
- **Spawn mode** (`Z.Segmented`/`MiniRadio`): **Area** | **Path**.
- **Shape kind** (both modes): **Circle | Triangle | Square | Pentagon | Hexagon**, plus **Custom** (Path only). This is a regular polygon by side count (Circle = ∞ sides). The original design pointed at `PolygonRadiusFactor`/`BandSides` in `BlastRenderer.cs` as reusable, but **those exact symbols may have drifted or never landed — grep the current `Runtime/Pyre/BlastRenderer.cs` for the Rosing (`ScatterMode.Rosing`) placement math before assuming; if it isn't there, write the polygon boundary math fresh** (a point-in-regular-polygon test and a random-point-in-polygon are both short). Custom = a hand-drawn polyline authored via `Z.Value2D` in animate-over-time (Curve) mode (click to add points, point order is time) and/or click-to-add on the preview canvas.
- **Area:** each particle is a uniformly-random point inside the chosen shape's boundary (generalise the existing random-in-disc to the polygon boundary). No progress/spawn-point concept.
- **Path:** placement is a **spawn point travelling along the shape**, positioned by a **`progress` ZUIValue** (Static/MinMax/Curve, 0→1 around the shape, 0 = start, 1 = end/once-around). Because `progress` is an authored envelope it can ease/hold/rewind; **each particle samples `progress` at its OWN spawn frame and keeps that position for its whole life** (a spawn-time snapshot, not a shared live value) — so particles born while `progress` moves slowly cluster, and fast-moving ones spread. Spawn *timing* is a plain even distribution across the swarm's life window.
- **Shared shape transform**, applied to the whole Area/Path shape: **Position** (`Z.Value2D`), **Scale** (`ZUIValue`, with an optional discrete-step snap — evaluate then round to the nearest step so placements land on fixed radii), **Rotation 2D** (`ZUIValue` degrees), **Rotation 3D** (pitch + yaw, two `ZUIValue`s — a pseudo-3D tilt: rotate the shape's points in 3D, project, and scale/brighten by depth so nearer parts render bigger/brighter). The original design cited `RotatePitchYaw`/`roseZ`/`zSizeInfluence` in `BlastRenderer.cs`; **those names may not exist as written — the pseudo-3D lighting/normal math in `BlastRenderer.cs` (search for the `lx/ly/lz` normal-dot-light block) is the style to mirror, but expect to write the tilt+project fresh.**
- **The crucial snapshot rule:** each particle's placement is computed against a **snapshot of the shape transform at THAT particle's spawn frame**, NOT the live transform — otherwise a growing/orbiting shape retroactively slides every already-placed particle instead of leaving a trail. (Pyre makes exactly this split deliberately: `ringExpand` is live so a ring visibly grows, but `spawnRadius`/`ringStartAngle` are spawn-time-snapshot so placed shapes don't slide — read those comments in `BlastRenderer.cs`'s scatter section for the reasoning.) This is the single most important thing to get right in Swarm.
- **Preview authoring overlay:** while editing Swarm, draw the active shape over the canvas plus a dot at every particle's ACTUAL computed spawn location (not just the outline), and make Custom points / the shape's position handle draggable. Mirror the gizmo-interaction style in Pyre's own `Editor/Pyre/PyreWindow.Preview.cs` (the MetaBlob orb markers, Pin-warp handles, Curl-vortex handles: `Handle*`/`Draw*Markers` methods) — click-to-add / drag / right-click-to-remove, mutation on mouse-up, wrapped in Undo.

### SLICE 3 — Modifiers

Reuses `PyreModifier` **directly** — its contract has NO `Pyre`/`Layer` coupling in any signature, so `PyrePlus.asmdef` already references `Pyre` and the `[SerializeReference] List<PyreModifier> modifiers` field is already on the spec. The four kinds and their apply points (all in `Runtime/Pyre/PyreModifiers.cs`):
- `PyreModifier.Prepare(Func<ZUIValue,int,float> eval)` — call before applying, passing an eval closure that resolves the modifier's own animatable fields (mirror how `BlastRenderer` builds that closure).
- `GeometryModifier.InverseWarp(Vector2 off, float phase, in GeoCtx ctx)` — a coordinate warp applied when sampling each pixel's source position.
- `PixelModifier.ApplyPixel(ref Color col, ref float alpha, in PixelInfo info)` — per-pixel colour/alpha (return false to drop the pixel).
- `PostModifier.Apply(Color32[] buf, int W, int H)` — a whole-buffer pass (Bloom, Outline, **Kaleidoscope** — new this session, mirrors a layer into N arms, a good demo for PyrePlus).
Apply them exactly as `BlastRenderer` does (study its per-layer modifier application: geometry warps folded into the sample position, pixel modifiers per lit pixel, post modifiers over the finished buffer). The UI is the same enable/reorder/"+ Add modifier" loop Pyre already draws — reuse Pyre's editor pattern (`Editor/Pyre/PyreWindow.Modifiers.cs` — the `GenericMenu` "+Add" flow and the per-modifier bodies) rather than reinventing it; the shared drag-reorder grip is `ZuiReorder` in the toolkit.

### Opt-in Shape fields (small, do alongside Swarm or after)

- **Position** — the particle's own path after birth, on its own life clock — `Z.Value2D` in Curve (animate-over-time) mode.
- **2D spin** — one `ZUIValue` of degrees, the particle's own pixels rotating in place (2D; the 3D tilt belongs to the swarm shape transform).
Gate both behind a single "advanced" toggle in the Shape section (rebuild on toggle) rather than a gear panel.
