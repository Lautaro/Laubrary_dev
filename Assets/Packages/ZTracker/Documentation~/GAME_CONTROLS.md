# Game controls

Call these methods on a playing `ZTrackerPlayback` from the main thread. Each returns whether the request was accepted for delivery, not whether the speaker has already played it. The existing SAP command pipe transfers fixed-size records; the renderer never resolves strings or touches game objects. A command takes effect after delivery at an audio block boundary unless a row boundary is specified below. Output buffering still separates rendering from what the listener hears; use `Clock.TryGetHeard` for gameplay tied to audible rows.

| Method | Behavior |
| --- | --- |
| `SetTempo(float bpm)` | Accepts 32–999 BPM. Last queued value wins, beginning at the next row. Current row duration is unchanged. This is a persistent override above authored tempo commands and lanes; authored values continue advancing beneath it. Authored transport-stop commands still stop. |
| `ClearTempoOverride()` | Removes the override at the next row, restoring the then-current authored tempo, including intervening authored changes. |
| `SetTrackTranspose(int track, int semitones)` | Sets an additive offset from −120 through +120 semitones for all active and future voices on this track. Zero restores authored pitch. |
| `SetTrackDetune(int track, float cents)` | Sets an independent additive offset from −1200 through +1200 cents. It composes with transposition, authored fine tuning, macros, per-note envelopes and modulation. |
| `SetCommandParameter(string uid, float normalized, int track = -1)` | Resolves an authored dynamic command definition by its stable `uid`, not its two-character display ID. Accepts 0–1 within the definition's declared range. Instrument-effect definitions need the sequencer track index because each track owns a separate effect instance. Other scopes use their definition's target. |

Pitch offsets are applied to rendering after note/sample selection. They do not rewrite authored cells, alter drum mapping or change the pitch values in note callbacks. A game excludes drums by leaving their track at zero. Set transposition and detune separately so a health detune can be cleared without clearing a progression's semitone offset. Both members of a paired sample receive the offsets. Extreme combined pitch still uses the engine's existing bounded-pitch diagnostics.

Stable command writes follow the existing evaluator: track controls ramp over 5 ms; instrument/macros/effect settings ramp over 10 ms in four-sample slices. Later authored commands or automation can replace these writes. Dynamic tempo writes are exceptional: they wait for row entry, follow that row's authored timing writes and remain below a persistent `SetTempo` override. Pending writes to one definition coalesce to the last value. Invalid IDs, unsupported targets and nonfinite/out-of-range inputs are refused without rebuilding the song. Compiled indices are private to each preparation; resolve again on each send rather than caching across refresh.

Play, Stop and Seek clear game pitch offsets and the tempo override. A compatible live refresh preserves them and pending dynamic tempo writes. Pause/resume preserve them. A full replacement uses its own fresh defaults. Resetting these controls does not mutate saved assets.

`TrackerCommand.SetTempo`, `ClearTempoOverride`, `SetTrackTranspose` and `SetTrackDetune` expose the same fixed-size requests for lower-level consumers. `TrackerPreparedSong.TryCommandParameter` resolves the stable definition on the main thread; `TrackerOffline.SetCommandParameter` provides the same resolution for deterministic rendering.

Run `Laubrary.ZTracker.Engine.TrackerGameControlCheck.Execute()` through editor eval for scoped checks. It creates and destroys in-memory fixtures, does not open a device or window and does not force collection. It checks row timestamps across three block sizes, override precedence and clearing, effect ramp/output, active/future/excluded-track pitch, sample pairs, macro composition, refresh/reset and rejected inputs.

## Immediate bounded note retrigger

`playback.RetriggerNote(track, instrument, note, velocity)` queues a fresh attack on the track's first note column. Unlike ordinary `PlayNote`, it cuts that column's previous held voices and release tails before starting the new group, regardless of the instrument's new-note action or legato. Layers and unison within the new group are retained, so mashing does not accumulate groups. Other columns and tracks are unaffected. Authored assets are untouched. The audio command is fixed-size and allocates nothing; lower-level clients set `TrackerCommandKind.RetriggerNote` on an `Audition` command.

The Boolean return means the valid command was queued; invalid indices/pitch/velocity and a full command queue return false. The chosen instrument must map the requested pitch and the track must be audible. Attack begins at the next audio command boundary, plus normal output buffering. Requests in the same audio boundary execute in order with note events for each; the last attack wins, so sub-buffer bursts do not imply distinct audible durations. A hard restart can click on a waveform discontinuity; this is deliberate retrigger behavior. Call `ReleaseNote(track)` to start the instrument's normal release envelope; a later retrigger cuts that tail too.

`TrackerRetriggerCheck.Execute()` checks 512 attacks with eight rendered frames between each (6000/second at 48 kHz), all three new-note actions and 64/333/1024 partitions. It checks every note event, pitch/cohort replacement, peak voice count and completed release. It opens no devices or windows and creates no saved assets.

## Tape rewind

Set `ZTrackerPlayer.rewindHistorySeconds = 30` before `Play()`, or pass `rewindHistorySeconds: 30` to `ZTrackerPlayback.TryPlay`. Lower-level consumers call `TrackerPreparedSong.EnableRewindHistory(30)` before publication. Zero is the default and allocates no history. The valid enabled range is 1–120 seconds; 30 seconds of stereo floats at 48 kHz uses 11.52 MB. The buffer is owned and retired by the prepared song under the same native lifetime rules as its other storage.

`playback.RequestRewind(3f)` queues a rewind of the actual post-master stereo mix from this pass of the current pattern. It does not reverse individual source samples or reconstruct earlier notes. In the first 0.5 seconds, playback speed falls from 1 to 0.5 and gain falls to 0.5; the remaining 2.5 seconds traverses the captured history in reverse, ending exactly on its first frame. Resampling is linear and changes pitch with speed, like tape. The renderer then seeks to row zero of the order that was active at the request and resumes normal playback. Rewind durations from 0.1 through 10 seconds are supported; the slowdown takes the smaller of 0.5 seconds and one quarter of the requested duration. The endpoint is sample-exact from audio-thread receipt; device buffering adds the ordinary speaker latency.

History starts at each actual pattern start and is bounded. A request refuses when history is disabled, fewer than two frames are available, the start is missing, the buffer has filled, or there is not enough free capacity for the slowdown. It never silently rewinds to a later point. A short history is valid: the forward slowdown captures more real mix before reversing. During slowdown the source renderer runs ahead at its normal rate to supply the slowed mix; its musical callbacks are suppressed and the song clock reports unavailable, so game code must use rewind status instead of treating that ahead-of-tape source position as audible.

Read `playback.RewindStatus` for a coherent published snapshot: `phase` (Idle, Slowing, Reversing), `result`, `Progress`, `CanRewind`, `HistorySeconds`, `completed` and `refused` counters. `playback.IsRewinding` is the phase convenience property. Engine callbacks `RewindStarted`, `RewindCompleted` and `RewindRefused` report audio-thread transitions; a refusal carries its `TrackerRewindResult` in the event payload. The bool request result means queued, not completed. State can change before the request reaches audio, so the audio thread revalidates and its status/events are authoritative. `LastError` explains a refusal detected on the main thread.

A repeated request while active refuses without restarting the effect. Pause/resume freezes/continues its progress, so paused wall time is excluded. Play, Stop and Seek cancel and clear history. A compatible Refresh uses fresh independently owned storage, cancels an active rewind and waits until the next pattern start to record a complete pass; no multi-megabyte copy runs on the audio thread. Completion uses normal seek semantics and clears game tempo/transposition/detune controls; the game should reapply its active modules after completion. Saved assets are never changed.

`Laubrary.ZTracker.Engine.TrackerRewindCheck.Execute()` checks actual mixed stereo samples, 64/333/1024 partitions, the exact three-second endpoint and resumed first samples, empty/exhausted/short history, repeat requests, pause, same-order landing after a pattern crossing, cancellation/refresh and native ownership. It opens no devices/windows, writes no assets and does not force collection.

## Reverse row sequencing

`playback.RequestReverseRows(3f)` is a separate transport from tape rewind. It needs no recorded history. On audio-thread receipt it cuts held voices, retriggers the current row N from its start, visits N−1 through 1, then triggers row zero once and resumes forward in the same order. Requests on row zero refuse with `AtPatternStart`. Normal note-on, note-off, note delay, tick effects and per-row events apply to each visited row; ticks and audio always advance forward within it. This is a new performance of those rows, not reconstruction of their previous sound. Instrument memory, non-timing commands and effects follow traversal order.

The schedule fits the requested duration exactly in audio frames, from 0.1 through 10 seconds, excluding pauses. Its relative traversal rate falls from 1 to 0.5 during the smaller of 0.5 seconds and one quarter of the duration, then stays at 0.5. Row boundaries divide the integrated rate into equal distances and are rounded to samples. Because a fixed deadline and absolute song BPM cannot both be preserved, this schedule stretches or compresses row durations to fit; the clock's BPM describes each scheduled row's actual duration. Master gain falls from 1 to 0.5 during that initial interval, holds, and returns to normal at landing. Individual sample pitch does not follow the traversal speed. A duration too short to give every visited row at least one frame refuses explicitly.

Authored BPM, lines-per-beat, ticks-per-line, stop, break and hold commands cannot alter the reverse schedule. The entry lines-per-beat and ticks-per-line stay fixed. Timing automation and pending typed tempo-definition writes do not execute during the trip; those definition writes are discarded when authored defaults are restored at landing. Non-timing automation evaluates at each visited row and moves forward through that row, so jumping to the preceding row can change its target. Parameter envelopes, macros, modulation, sample cursors and effect state continue forward. Direct game tempo changes remain stored but do not change reverse timing.

On completion, voices/effects and authored parameter defaults reset and the same order's row zero applies its authoring. Game `SetTempo` override, track semitones/cents and trigger/output mute gates survive, including edits received during the trip. In particular a game-gated lead cannot leak a row-zero trigger before the main thread reapplies controls. Other direct parameter/fader changes should be reapplied if the game still wants them. This landing is direct; it does not silently replay earlier orders or follow their flow commands. Explicit Play/Stop/Seek retain their ordinary reset behavior, and tape rewind retains its existing semantics.

Read `playback.RowReverseStatus` for `active`, `result`, `order`, `startRow`, `currentRow`, `elapsedFrames`, `totalFrames`, `sampleRate`, `Progress`, `Direction`, and monotonic `completed`, `refused` and `cancelled` counters. `playback.IsReversingRows` is a convenience property. Lower-level consumers use `TrackerCommand.RequestReverseRows`, `TrackerOffline.RowReverseStatus`, and engine events `RowReverseStarted`, `RowReverseCompleted`, `RowReverseRefused`. The boolean request result means queued, with `LastError` for a main-thread refusal; audio-thread status is authoritative. Snapshot counters are preferable to assuming an immediately idle status means completion, because the request may still be queued. A repeated request or either reverse mode requested while the other is active refuses without replacing the active operation. Pause freezes progress; Play, Stop, valid Seek and Refresh cancel, incrementing `cancelled` once. A compatible refresh resumes forward from the current row remainder and restores authored timing at the next row.

Musical callbacks remain enabled during reverse row sequencing. Native events and row anchors expose `TrackerPlaybackDirection`; mapped `ZTrackerEventData.direction` and `ZTrackerSongPosition.Direction` are −1 for descending rows and +1 for forward. Transport sample timestamps stay monotonic, row anchors remain in the clock history after landing, and consumers must retain queued reverse events until their heard timestamp arrives. Within-row `RowFraction`, elapsed samples and ticks increase normally; use Direction when comparing row indices or scheduling release. `ZTrackerAccents.NextEventRow(..., direction: -1)` finds the next lower note/Off row, falling back to row zero; accent judging excludes adjacent orders in reverse and measures signed distance along traversal. The clock can report unavailable if the requested heard sample predates the bounded 64-anchor history, rather than inventing a location. Tape history is invalidated on direction entry and starts a fresh forward pass at landing.

Run `Laubrary.ZTracker.Engine.TrackerRowReverseCheck.Execute()` directly through editor eval for scoped offline checks, and rerun `TrackerRewindCheck.Execute()` for the independent tape regression. These checks open no devices/windows, create no saved assets and do not force collection. Live event consumers and visual use-case switching still need their separate game integration checks.

The exact sample partition proof uses modern authored mixing. Imported `native-v0` compatibility mixing retains its existing voice-count normalization over caller-sized slices; overlapping release tails can therefore differ across buffer sizes in that compatibility path, during ordinary or reverse sequencing. Reverse row deadlines and event/clock boundaries remain sample-exact there. This feature does not change that legacy sound policy or the tape renderer.
## Live editor observation

The model editor automatically observes `ZTrackerPlayback.Current` only when `SourceSong` is the same authored song asset. It never drains the game's events or changes the asset to reflect runtime controls. Play, play-from-cursor and stop-preview controls are disabled during game-owned playback (including keyboard Play), with a tooltip explaining ownership. Closing the editor leaves the game stream running.

The existing transport line shows the heard order/row and BPM, pending next-row tempo, pending typed parameter writes, reverse/tape progress, pause and the selected track's additive game pitch. Pattern headers show live voice activity (including release tails), `G` for gated triggers, `M` for output mute and nonzero game pitch offsets; their tooltips spell out the complete state. Authored mixer/instrument controls retain their authored values. These offsets are not a replacement for authored instrument/envelope/macro tuning. Tape replays recorded master audio, so voice counts and the last sequenced row are not a per-track meter or tape read-head position; the row highlight is suppressed during tape playback.

`TrackerSapGenerator.TryReadTrack(int, out TrackerTrackReadout)` and the playback facade's equivalent return version-checked POD copies. `TrackerClockHead` adds BPM, requested tempo, pending flags/count, order/row and the published track count. Head and track snapshots share a native publication version; each track carries its block number for callers requiring a matching block. They consume nothing and allocate nothing. Storage is allocated with the event ring on the control thread and freed by the same owner; compatible refresh preserves it. A low-level structural `SwapPrepared` to more tracks than the initial song exposes only the initial track capacity (`head.trackCount`); use a fresh playback for a complete structurally different song. The normal public facade creates fresh playback for song changes.

The editor polls every 30 ms. The measurable target is at most 100 ms from a native block's publication to visible readout on a responsive, visible editor; suspended/stalled editor frames cannot satisfy a wall-clock guarantee. Heard row/BPM additionally include configured audio output latency by design. `ObservedLiveBlock`, `LiveReadoutObservedAt`, `LiveReadoutMaxPollGapMs` and `LiveReadoutLagTargetMs` expose observation evidence. The deterministic `TrackerLiveReadoutCheck.Execute()` checks publication, tempo pending/application, track controls, activity, bounds, pause, reverse/tape, stop, event independence and authored-data preservation at 64/333/1024-frame partitions. It does not measure repaint latency; the live editor probe and visual walk must verify that separately.
