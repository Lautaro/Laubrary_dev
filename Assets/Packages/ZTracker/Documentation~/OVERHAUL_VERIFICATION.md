## Paste Insert (2026-10-13, T-0594)

Paste Insert sits beside Paste in the Pattern tool column (rows-plus icon) and on Ctrl+Shift+V, next to Ctrl+C / Ctrl+X / Ctrl+V. It works on the columns the clipboard lands on: from the cursor row down, those columns move down by the clipboard's height, rows pushed past the end are dropped and counted, then the clipboard is pasted into the gap; one Undo step. Moved values are read from a copy taken before any write, because a command's identifier and its value are two fields over one cell (the first implementation lost the moved values exactly there, caught by the check). Automation lanes belong to a track rather than a column, so a track's automation points move with it only when the paste covers every visible column of that track; a paste into some of a track's columns leaves its automation in place. The dropped count shows on the window's status line ("⚠ Paste Insert dropped 2 rows pushed past the pattern end."), and also counts dropped automation points and copied rows that did not fit; it clears at the next cursor move. Hidden sub-columns (for example a pan value whose column is not shown) do not move, matching what Copy and Paste already do with hidden fields.

## FX columns: count, +N expander and stacked commands (2026-10-13, T-0597)

The model already stored up to eight commands per row per track, one per FX column, so stacking needed no model change and no migration: the column count only decides what is shown. A playing command stored beyond the shown columns keeps playing (the compiler never looked at the count); its row gets an amber "+N" (N = commands hidden on that row) in a gutter after the track, and the header gets "+N" (N = columns to add). ## P5 allocation guard counts only its own render (2026-10-13, T-0605)

Cause, reproduced before fixing: the guard compared the editor-wide count of rendered audio blocks before and after its own 64 renders. With the owner's ZTracker window open, its preview renderer adds about 50 blocks a second to the same count, so whenever one of those landed inside the measured loop the check saw 65. Measured with the window open: 200 trials of the old count, 15 wrong; the same 200 trials counted by the engine's own render counter, 0 wrong. The guard now reads the started song's own completed-render counter (one per block it rendered) and checks after every block that the render ran as compiled Burst code (the engine's own witness), with the same 0-bytes allocation requirement; its failure message now names the measured bytes, blocks and managed blocks.

Verified by probe: compilation clean; P5 commands 30/0 three times in a row with the owner's window and its preview running (`MEASURE p5RenderAllocatedBytes=0 nativeBlocks=64 managedBlocksDelta=0` each time).
