## What is left, and why (read before picking this up)

**A2, the event half — NOT started, on purpose.** "The weapon slot names a fire event" means `Zoe.weapons` (a `List<WeaponDef>`) becomes a list of SLOTS carrying `{ def, fireEventId }`, which is an **asset-schema migration** on a field that four runtime/editor files read. A half-applied schema migration is the one failure mode that can cost real authored data (see the `serializereference-data-loss-hazard` memory), so it wants a clean run of its own rather than the tail of a long one. Also still open from A2: retiring `WeaponDef.muzzle`/`muzzleLayerId`/`muzzleEventName` in favour of an ordinary effect entry at a MetaPoint, and the re-fire policy (Queue/Restart/Ignore/Overlap, with the effect list and the body laumination probably wanting different answers). `Restart-at-zone` needs zone knowledge the event does not have yet.

**What A2 DID deliver (built + probe-verified):** the muzzle POSITION chain the design doc specifies — MetaLayer point on the current frame → nearest frame that has it painted → the weapon's own offset. `ZonedAnimationPlayer.TryGetMetaPointNearest` + `IAnimatedView.TryGetMetaPointNearest` + a `MuzzleTracker` added per weapon slot at equip time. This is what removes the live fragility §5 complains about: firing no longer depends on anyone having painted the muzzle layer, because the painted point now only answers WHERE. Verified in Play mode on Hero: while `Idle` plays nothing resolves and the muzzle sits at its offset (-0.56, 1.47); while `Shoot` plays it resolves to (-0.02, 3.13) and the muzzle transform matches.

**A4 (directional laumination sets) and A5 (Clip → Laumination rename + the OutBurner sync) — NOT started.** Both are large: A4 adds a first-class set type with mirroring to `LauminaryVersion` and re-points locomotion at it; A5 is a package-wide rename that must be batched with the pending consumer sync so consumers migrate once. Neither was touched, so neither is in a half-state.
