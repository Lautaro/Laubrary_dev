## 0. Corrections to assumptions in the task statement

- **There is no `LauAsset` base class.** "LauAsset" is a duck-typed predicate (`Editor/AssetKit/LauAssetHook.cs`, `IsAssetReference`): any `ScriptableObject` that is in a `Laubrary.*` namespace, OR implements `Laubrary.PreviewKit.IVisualPreview`, OR has an opener/creator registered in `LauAssetEditors`. A new LauAsset is just a `ScriptableObject` in namespace `Laubrary.GoreLab`.
- **New editor windows are UI Toolkit, not IMGUI.** `ZUIWindow`/`LaubraryAssetWindow<T>` (IMGUI) are legacy. New tools extend `ZuiWindow` (`Zui/Toolkit/ZuiWindow.cs`, override `BuildUI(VisualElement root)`) or `ZuiAssetWindow<T>` (`Editor/AssetKit/ZuiAssetWindow.cs`, override `BuildAsset(VisualElement root, T asset)`). The skill's `references/zui.md` top section and `references/ui-layout-rules.md` say so explicitly. The preview stage is a UITK `VisualElement` with `ZuiPanZoom` + a `Painter2D` overlay (MetaMapper's `MetaStage` is the model); a raw `IMGUIContainer` island is still sanctioned for bespoke canvas painting (Pyre keeps one).
- **ZUI has no tab control.** Existing "tabs" are a `Z.MiniRadio`/`Z.Segmented` across the top that sets a field and calls `Rebuild()` (`Editor/Rulesets/RulesEditorWindow.cs:38-70`), or a row of `ZS.Toggle` (Zounds). ui-rules.md 8b ("tabs, one group at a time; the tab IS the mode") is the rule; `Z.Segmented` is the closest factory. If a real tab strip is wanted, adding `Z.Tabs` to ZUI (and documenting it in `references/zui.md` in the same change) is the sanctioned route.
- **There is no `ZoeCombat` folder.** `Runtime/ZoeCombat.meta` is an empty leftover; the Zoe pixel-perfect hit filter is `Runtime/Zoetrope/SpriteAlphaHitFilter.cs` (added by `ZoeSpawner` when `Zoe.pixelPerfectHits`). `Runtime/LauminaryCombat/LauminaryHitFilter.cs` is the meta-layer variant.
- **`Combat2D.DamageType` exists but nothing carries it.** `DamageInfo` (`Runtime/Combat2D/DamageInfo.cs`) has amount, source, faction, point, direction, crit, and no type. Nothing in `Runtime/` reads `DamageType`. See section 2 and Open Questions.
- **The CLAUDE.md demo rule overrides the skill's `authoring.md` §8.** authoring.md still says a `[MenuItem("Laubrary/<Tool>/Build Demo Scene")]` builder is the deliverable; the project CLAUDE.md ("Demos — ship SCENES, not scripts that build scenes") says the opposite and is the newer, binding rule. Follow CLAUDE.md.

## 1. LauAsset / AssetKit

**What makes a LauAsset.** `LauAssetHook.IsAssetReference(Type t)`: `ScriptableObject` AND (`IVisualPreview` OR registered in `LauAssetEditors` OR namespace starts with `Laubrary`). Being one buys: chip-style fields with thumbnails wherever a field of that type is drawn (`LauAssetElement`), the shared picker popup (`LauAssetBrowser`, TypeCache-backed so unregistered types still appear), and a browser grid in any `ZuiAssetWindow<T>`.

**Conventions seen across every Runtime type:**
- `[CreateAssetMenu(menuName = "Laubrary/<Tool>/<Thing>", fileName = "<Thing>")]` (e.g. `Runtime/Zoetrope/Zoe.cs:12` `"Laubrary/Zoetrope/Zoe"`, `Runtime/Chunks/ChunkSpec.cs:18` `"Laubrary/Chunks/Chunk Spec"`). This is the Assets ▸ Create menu, not the top `Laubrary/` menu, so it does not violate the "no unrequested menu items" rule.
- Implement `IVisualPreview` (`Runtime/PreviewKit/IVisualPreview.cs`): `Texture2D RenderPreviewTexture()`, `bool CanAnimatePreview`, `float PreviewFps`, `void UpdateAnimatedPreview(Texture2D tex, double time)`. Must call the same renderer the tool's live preview uses (authoring.md §7, §10). A browser of a type without it shows a "NO PREVIEW" nag cell. Use `PreviewKit.PreviewTex.CropSprite(sprite)` / `PreviewTex.BlitInto(tex, sprite)` (they cope with non-readable textures).
- Tools ship ZERO assets. Authored assets live in the host project (`Assets/<Tool>/...`); `ZuiAssetWindow<T>.DefaultFolder` decides where New lands. `LauAssetHook.DefaultFolderFor` falls back to `Assets/<TypeNameNoSpaces>`. Demo assets are committed files under `Assets/Demos/<Tool>Demo/`.
- Register open/create in an `[InitializeOnLoad]` static class in the Editor asmdef, e.g. `Editor/BackSplash/BackSplashEditorLink.cs:15`: `LauAssetEditors.RegisterOpen<BackSplash>(BackSplashWindow.OpenFor);` and optionally `LauAssetEditors.RegisterCreate<T>((name, folder) => ...)`.
- CRUD for editors: `AssetLibrary<T>` (`Editor/AssetKit/AssetLibrary.cs`): `Enumerate(folder=null)`, `FindGuids`, `Create(name, folder)`, `Duplicate`, `Rename`, `Delete`. `AssetFolders.EnsureFolder("Assets/A/B")`.

**Browser/editor window.** `ZuiAssetWindow<T>` gives toolbar (assign / New / Duplicate / Rename / Delete / Browse), a thumbnail browser, New/Duplicate undo and a Delete confirm. Override points (`Editor/AssetKit/ZuiAssetWindow.cs:55-84`): `BuildAsset(root, asset)` (abstract), `TypeLabel`, `DefaultFolder`, `NewAssetName`, `RenderThumbnail`, `AnimateThumbnails`/`UpdateAnimatedThumbnail`, `OnAssetChanged`, `InitializeNewAsset`, `AutoInsertTagsSection` (default true: inserts a LauTag section). Reference implementations: `ChoreographerWindow`, `PyreWindow`, `ChunkWindow`.

**Lock design, as it affects a new type.** Nothing is built (`LAUASSET_LOCK_DESIGN.md`, `LAUASSET_LOCK_DECISIONS.md`). The design keeps lock flags in a GUID-keyed side table and seals with `EditorJsonUtility.ToJson`, so a new type needs no field or base class. Two things to keep it lock-friendly: (1) do NOT store sub-assets in the sidecar `.asset` (`AddObjectToAsset` of baked textures); the seal format captures one object only and the guard refuses or ignores sub-assets; keep wound textures runtime-only. (2) `[SerializeReference]` is allowed (heavily used) but carries the known "managed refs null out against a broken assembly; never save from probes" hazard; keep `[MovedFrom]` discipline if a wound-recipe type is ever renamed.

**Smallest correct sidecar that points at a Zoe without the Zoe pointing back.** The Zoe has no field for it and no code in Zoetrope references the GoreLab assembly; the dependency is one-way (GoreLab → Zoetrope).

```csharp
using System.Collections.Generic;
using UnityEngine;
using Laubrary.Zoetrope;
using Laubrary.Launimator;

namespace Laubrary.GoreLab
{
    [CreateAssetMenu(menuName = "Laubrary/GoreLab/Gore Rig", fileName = "GoreRig")]
    public class GoreRig : ScriptableObject, Laubrary.PreviewKit.IVisualPreview
    {
        [Tooltip("The character this rig adds wounds to. The character does not know this rig exists.")]
        public Zoe zoe;
        [Tooltip("Used instead of a Zoe when the rig targets a bare animation.")]
        public LauminaryVersion reel;

        public List<GoreMemberDef> members = new List<GoreMemberDef>();   // head ball, torso box, ...
        public List<GoreFrameTags> frames = new List<GoreFrameTags>();    // one per drawn sprite frame

        [SerializeReference] public List<IWoundRecipe> recipes = new List<IWoundRecipe>();  // modular kinds

        // IVisualPreview: show the target's first frame with the member shapes over it, via the SAME
        // drawing code the GoreLab window's stage uses (rule: never a second render path).
        public Texture2D RenderPreviewTexture() { /* ... */ return null; }
        public bool CanAnimatePreview => false;
        public float PreviewFps => 0f;
        public void UpdateAnimatedPreview(Texture2D tex, double time) { }
    }
}
```

Key the per-frame data by the drawn `Sprite` reference (plus the laumination name and frame index for display/validation), not by clip name strings alone: the runtime knows which `Sprite` is on screen and that answer is identical for a Zoe and a bare Reel (see section 2).

**Finding every sidecar for a given Zoe/Reel.** Editor only: `AssetLibrary<GoreRig>.Enumerate().Where(r => r.zoe == zoe)` (loads every rig; fine, LauAsset counts are small), or the cheaper `AssetDatabase.FindAssets("t:GoreRig")` + `AssetDatabase.GetDependencies(rigPath, false)` containing the Zoe's path. At runtime there is no asset database: the live component must be handed its rig explicitly (serialized field on the component, or passed by the spawner). Do not add a lookup into Zoetrope.

## 2. Zoetrope / Zoe: structure, spawning, display, facing, damage

**Asset.** `Zoe` (`Runtime/Zoetrope/Zoe.cs`) is a single `ScriptableObject` (no ZoeVersion class; versioning lives in Launimator's `LauminaryVersion`). Fields: `displayName`, `maxHealth`, `faction`, `invulnerableAfterHit`, `[SerializeReference] ICharacterView view` (default `SpriteView`), `deathDisposal`, `deathLinger`, `pixelPerfectHits`, `locomotion`, `motionPose`, `hit`/`death` (`ReactionFx`), `events` (`List<NamedReaction>`), `brain`, `playerController`, `aiming`, `loadout`, `weapons`, `cues`, `meta` (`MetaMapData`, local units). `Zoe` implements `IVisualPreview` by asking `view as IPreviewableView`.

**Generated sibling file.** Saving a Zoe writes `<ZoeName>.states.cs` next to it (`Editor/Zoetrope/ZoeStateNamesGenerator.cs`), e.g. `Assets/Zoetrope/Hero.states.cs`. Commit it with the Zoe; it joins whatever asmdef owns the folder (a Zoe in `Assets/Demos/` joins `com.Lautaro-Arino.Laubrary.Demos`).

**Spawning.** No prefab: `ZoeSpawner.SpawnCharacter(Zoe def, Vector3 pos, Transform parent = null, LayerMask projectileBlockers = default)` (`Runtime/Zoetrope/ZoeSpawner.cs:15`) builds one GameObject: `view.Build(go)` → `AnimationArbiter` → cues → `MotionStateSource` → motion pose (if `def.motionPose.IsAuthored`, via `IMotionPoseHost.BindMotionPose`) or locomotion → `Health` (maxHealth, then `Revive()`) → `Combatant` → kinematic `Rigidbody2D` (interpolated) → trigger `BoxCollider2D` sized to the view → `Hurtbox` → `SpriteAlphaHitFilter` (if pixelPerfectHits) → `ReactionFxPlayer` → `ZoeState` → loadout / brain / weapons / player controller. Returns the root GameObject. The demo spawner pattern is `Assets/Demos/ProtoGuyDemo/ProtoGuySpawner.cs` (one line in `Start`).

**Display for a single-sheet character.** Use `ZonedLauminaryView` (`Runtime/ZoetropeLaunimator/ZonedLauminaryView.cs`; fields `version`, `idleClip`, `height`). Its `Build` adds `ZonedAnimationPlayer` (which `RequireComponent`s the `SpriteRenderer` on the root), `CueRelay`, `AnimatedViewRelay`. So the character is ONE `SpriteRenderer` on the root GameObject (unless the laumination uses `spriteLayers`, then the base renderer is disabled and child renderers named `layer:<id>` draw instead; the imp has none). Composite characters (`CompositeLauminaryView`) put parts on child GameObjects; out of scope for the imp.

**What is showing, readable every frame** (`Runtime/Launimator/ZonedAnimationPlayer.cs`): `CurrentClip` (laumination name), `CurrentFrame` (int), `CurrentSprite`, `flipX` (public bool, the authoritative mirror flag), `IsPlaying`, `version`. Events: `OnFrameEntered(int)` (every frame entry), `OnFrameEvent(string,int)`, `OnComplete`, `OnMetaLayerReached`. `IAnimatedView` (on `AnimatedViewRelay`) forwards `OnFrameEntered`/`OnFrameEvent`/`CurrentFrame`. `IResolvedFacing` (on `MotionPoseAnimator`) gives the drawn facing angle.

**Order of writes (this is what a sprite-swapping sidecar must respect):**
- `ZonedAnimationPlayer.Update()` → `Tick` → applies `_sr.flipX = flipX` FIRST, then advances, then `PushSprite()` writes `_sr.sprite = _anim.frames[_i]` (every Update while playing; lines 278-296, 416-439).
- `MotionPoseAnimator.LateUpdate()` (default order) resolves the direction, writes `FlipX` through `IFlippableView` (→ `player.flipX`, applied to the renderer on the NEXT Update) and may call `Play`/`EnterAtFrame`.
- Only `[DefaultExecutionOrder]` uses in the package: RulesHost -2000, SceneDirector -999, SmartStats -100, `FreeAimRotateAimSpec` 100. Nothing runs late in LateUpdate.

So a sidecar can replace the displayed sprite cleanly from `LateUpdate` with a late order, e.g. `[DefaultExecutionOrder(10000)]`: read `player.CurrentSprite`, `player.CurrentClip`, `player.CurrentFrame`, `player.flipX`, write `sr.sprite = wounded` and `sr.flipX = player.flipX` (writing flipX too removes the one-frame lag where the renderer still has last frame's flip). Next Update the player overwrites the sprite with the clean frame, and the sidecar's LateUpdate swaps it again before render. No Zoe or Launimator change needed. Key the lookup on `CurrentSprite` (an instance-keyed `Dictionary<Sprite, FrameTags>` built once from the rig), which works identically for a Zoe and a bare Reel. Respect hidden states: when `ReactionFxPlayer` blanks the body (`IAnimatedView.Hide()`, clip-less death) or `sr.enabled == false`, do nothing.

**8-direction facing and mirroring.** Direction sets live on the `LauminaryVersion`: `List<LauminationSet> sets` (`Runtime/Launimator/LauminationSet.cs`). For the imp: `directionMode = DirectionMode.Members`, `mirrorBuiltIn = true`, `framePivot (0.5, 0)`, members `{angleDegrees, laumination, pivotOverride, zoneName}`. Convention: 0° = up (+Y, i.e. the BACK view for a top-down walker), increasing clockwise; 180° = facing the camera. The Zoe picks the set by name through `Zoe.motionPose.rules` (`MotionPoseRule { condition = Always, setName = "Walk8" }`, channel `Heading`), and `MotionPoseAnimator` resolves `(set, angle) → (laumination, FlipX)` through `LauminationSetResolver.Resolve` and writes the flip via `IFlippableView` (render-time `SpriteRenderer.flipX`, no separate clips).

**Mirror gotcha that decides how the imp must be authored.** `LauminationSetResolver.NearestMember` (`Runtime/Launimator/LauminationSetResolver.cs:195-248`) mirrors ONLY when no authored member has an angle above 180°, i.e. the authored members must face the RIGHT half (0..180), and requests in 180..360 are served by `flipX = true` of member `360 − θ`. The retail imp's drawn side columns face LEFT (GoreLab: column 1 front-side forward ≈ (−0.71, 0, 0.71), column 2 side (−1, 0, 0), column 3 back-side (−0.71, 0, −0.71)). Authoring them at 225/270/315 disables mirroring entirely (the resolver then picks nearest of 0/180 for a right-facing request). Therefore the right-facing members must be horizontally flipped copies of columns 1-3: commit flipped PNGs (or bake with `FrameRef.transform.flipX`, but see section 3 for why baking is risky). Member angles: col 0 front = 180, col 1 flipped = 135, col 2 flipped = 90, col 3 flipped = 45, col 4 back = 0. Their GoreLab tags must be mirrored on import (x → w−1−x, negate x of `u3`/`f3`, mirror the mask indices); GoreLab's own rule for the derived directions is "a mirrored direction is a rotation: mirror the pixels and tag vectors, do NOT mirror the wound" (GoreLab CLAUDE.md 2026-10-03 entry), which carries over unchanged.

**Damage path** (`Runtime/Combat2D/`): `Combat.TryDamage(Hurtbox target, Faction attackerFaction, GameObject attackerObj, float damage, Vector2 point, out DamageInfo info, GameObject striker = null)` runs faction check → every `IHitFilter` on the target (`SpriteAlphaHitFilter.ConfirmHit` maps the world point to a sprite pixel and checks alpha) → `Hurtbox.ReceiveHit(info)` (× `damageMultiplier`) → `Health.ApplyDamage`. `Health` raises `event Action<DamageInfo> Damaged`, `Died`, `Healed`, `Revived` (plus UnityEvents). `TryDamage` derives `direction` from `attackerObj`'s position, so with a null attacker the direction is zero.

For a mouse-driven demo: `var col = Physics2D.OverlapPoint(world); var hb = Combat.FindHurtbox(col);` then either `Combat.TryDamage(hb, null, null, dmg, world, out _)` (honours the pixel filter, no direction) or `hb.ReceiveHit(new DamageInfo(dmg, null, null, world, dragDir))` (carries the drag direction, skips filters). The GoreLab live component should subscribe to `Health.Damaged` (it has `point` and `direction`) AND expose a direct `ApplyWound(...)` for callers that need a damage kind or a 3D shot direction, which `DamageInfo` cannot carry. Keep the imp alive in the demo with a high `maxHealth` and `Health.Revive()` on Reset, or `Health.invulnerable` (note: invulnerable also suppresses `Damaged`; check `Health.ApplyDamage` before relying on it).

**Palette-rule tension (read before designing the hook).** CLAUDE.md "Zoe palette" forbids "bolting a bespoke 'play this on hit' component onto the character" and `Editor/Zoetrope/ZoePaletteBypassAudit.cs` greps for `ChunkPool.Get(`, `.PlayClip(`, etc. Package code under `Packages/Laubrary/` is exempt from the scan, so a GoreLab runtime component in the package will not be flagged, but a demo script calling `ChunkPool.Get(` directly will be. The owner's "additive, the Zoe must not know" requirement is in direct tension with the palette rule's intent; record this as a deliberate, owner-requested exception (Open Question 1) rather than silently contradicting CLAUDE.md. The palette-respecting alternative is an `IEffect` (`Runtime/Zoetrope/IEffect.cs`, `void Apply(EventContext ctx)`, `EventContext` has `HitPosition`, `Direction`, `Renderer`, `View`, `FlipX`) added to the Zoe's Hit reaction list; that makes the Zoe know, so it is the opposite of what was asked.

## 3. Launimator: storage, frames, building the imp

**Data model** (`Runtime/Launimator/Lauminary.cs`, `LauminaryVersion.cs`). `Lauminary` (identity: `lauminaryId`, `lauminaryName`, `latestVersion`, `pixelsPerUnit`) owns versions; `LauminaryVersion` (the thing a view references) holds `List<Laumination> animations` and `List<LauminationSet> sets` (+ generated `prefab`/`controller`). A `Laumination` holds `name`, `fps`, `recipe` (`List<FrameRef>`: source texture GUID + cell rect + pivot + `CellTransform`), `events`, `frames` (`List<Sprite>`, what actually plays), optional `spriteLayers`, `atlas`, `clip`, `metaLayers`, `zones`. "Reel/ReelVersion" are the old names (`[MovedFrom]`/`[FormerlySerializedAs]` still map them). Pivots: each baked frame shares `framePivot` (default bottom-centre); with loose sprites the pivot is the sprite importer's own.

**Two ways to build the imp, and which to use.**
1. *Repo path*: `LauminaryRepo.CreateLauminary(name, ppu)` (`Editor/Launimator/LauminaryRepo.cs:30`, folder `Assets/Launimator/Lauminaries/<Name>_<id8>/`), then `LauminaryRepo.SaveAnimationToDraft(c, new Laumination { name, fps, recipe })`, which re-bakes via `AtlasBaker.Bake` (per-frame source GUIDs allowed; it auto-sets `isReadable`). `Editor/Launimator/SelfTest.cs:62-130` is a complete worked example. **But** `UNITY_DEV_GUIDE.md` (Testing → "Never exercise a SAVE/REBUILD path against real user data") records that `SaveAnimationToDraft → RebuildDraft → BuildVersionAssets` re-bakes EVERY atlas of the lauminary and has corrupted a real character (frames merged). Avoid for anything you care about, and never call it on an existing asset to "test".
2. *Hand-built version, no bake* (recommended; exactly how ProtoGuy is made). `Assets/Demos/ProtoGuyDemo/Lauminaries/ProtoGuyLegs.asset` is a bare `LauminaryVersion` (`versionNumber: 0`, empty `recipe`, no parent `Lauminary`) whose animations' `frames` reference loose per-direction PNG sprites in `Assets/Demos/ProtoGuyDemo/Sprites/LegsWalk/...`, with a `Members` set `LegsIdle16`. Do the same for the imp from an ephemeral scratchpad script run through `unity command eval_file`, then delete the script:

```csharp
// eval_file body (sketch). Copy PNGs into Assets/Demos/GoreLabDemo/Sprites/ first; cols 1-3 also as
// horizontally flipped copies (e.g. Walk_d135_f0.png) because members must face RIGHT (section 2).
var v = ScriptableObject.CreateInstance<Laubrary.Launimator.LauminaryVersion>();
int[] angle = { 180, 135, 90, 45, 0 };                       // col 0..4 (cols 1-3 = flipped copies)
var set = new Laubrary.Launimator.LauminationSet { name = "Walk8",
    directionMode = Laubrary.Launimator.DirectionMode.Members, mirrorBuiltIn = true };
for (int col = 0; col < 5; col++) {
    var anim = new Laubrary.Launimator.Laumination { name = "Walk_" + angle[col], fps = 6f };
    for (int row = 0; row < 4; row++)
        anim.frames.Add(AssetDatabase.LoadAssetAtPath<Sprite>($"{dir}/Walk_{angle[col]}_f{row}.png"));
    v.animations.Add(anim);
    set.members.Add(new Laubrary.Launimator.LauminationSetMember { angleDegrees = angle[col], laumination = anim });
}
v.sets.Add(set);
AssetDatabase.CreateAsset(v, "Assets/Demos/GoreLabDemo/Imp Walk.asset");
// Then a Zoe: view = new ZonedLauminaryView { version = v, idleClip = "Walk_180" },
// motionPose.rules = { new MotionPoseRule { condition = MotionCondition.Always, setName = "Walk8" } }.
```

Caveat: a member holds its own `Laumination` by value (`[Serializable]` class, Unity serializes it inline), so the set duplicates each animation's data; ProtoGuy accepts this. The death row (retail row 8, `r8_0..r8_4`, single direction) can be added as a plain animation `Death` and wired as `Zoe.death.clip` if the demo wants a death.

**Importer settings for the PNGs** (copy `Assets/Demos/ProtoGuyDemo/Sprites/LegsIdle/Legs-E.png.meta`): `textureType: 8` (Sprite), `spriteMode: 1` (Single), `spritePixelsToUnits: 16` (project `PixelScaleProjectSettings.pixelsPerUnit = 16`, target 320×200, reference human 32 px; the imp frames are 30-49 px wide, 46-60 px tall, so about 3.5 units tall), `filterMode: 0` (Point), `textureCompression: 0` (None), `enableMipMap: 0`, `isReadable: 1` (GoreLab bakes from source pixels; ProtoGuy already has it on). Pivot: GoreLab treats frames as bottom-aligned and horizontally centred (`retail.json` has no Doom offsets, only sheet boxes). Use a custom pivot `(floor(w/2)/w, 0)` rather than `alignment: BottomCenter` so odd-width frames land on a whole pixel and the feet do not shimmer by half a pixel between frames; make the GoreLab tag→sprite conversion use the SAME centring rule. Source files: `D:\CODEZ\GoreLab\web\assets\retail\r{row}_{col}.png` (walk rows 0-3, columns 0-4; `retail.json` lives at `web\assets\retail.json`, not inside `retail\`). Name committed copies by angle and frame, not by sheet row/col.

**Existing directional demos to copy.** ProtoGuy (`Assets/Demos/ProtoGuyDemo/`, a composite two-part 16-way player with `Members` sets `LegsIdle16`, `LegsWalk3`, `UpperAim16`) is the only direction-set example. There is no 8-direction single-sheet enemy yet; the imp will be the first.

## 4. Editor window pattern

**Closest models, and what to take from each.**
- **MetaMapper** (`Editor/MetaMapper/MetaMapperWindow.cs` 945 lines + `MetaStage.cs` 1065 + `MetaEditSession.cs`): the per-frame tagging workflow. `Z.Split("metamapper", 300f, left, right)` layout (line 446), a frame strip (`BuildFrameStrip`, line 727), and `MetaStage`: checkerboard behind the art, the image as a child with a `Painter2D` overlay child kept in front, a self-explaining guide label, `ZuiPanZoom` for wheel-zoom-to-pointer and middle-drag pan with the degenerate-geometry guard, a gesture enum (`MoveMark, AimMark, Paint, Erase, DrawShape, MoveShape, ResizeShape`) and a clean statement of the three coordinate spaces (map +y up, texture px +y up, GUI +y down, the flip lives only in the stage). It also shows the subject-provider seam (`MetaSubjectProviders.RegisterOther(typeof(Zoe), ...)` in `Editor/Zoetrope/ZoeMetaSubject.cs`) for turning a Zoe into "a picture plus frames" without the window knowing Zoe.
- **Chunks** (`Editor/Chunks/ChunkWindow*.cs`, a `ZuiAssetWindow<ChunkSpec>` split into partial-class cards plus `ChunkPreviewSim.cs`): how to lay out a modular list of `[SerializeReference]` capability cards (the model for modular wound recipes), card colours/state, a deterministic live preview that mirrors the runtime RNG stream.
- **Pyre** (`Editor/Pyre/PyreWindow*.cs`): the UITK mutation helpers to copy: every control's `onBeforeMutate: () => Undo.RecordObject(spec, "Edit ...")` and `MarkDirty()`; a targeted `RebuildLeft()` on structural change; a sanctioned `IMGUIContainer` preview island. Also `Editor/Rulesets/RulesEditorWindow.cs` for the minimal "segmented control as tabs + `Rebuild()`" pattern.

**Undo.** `ZuiWindow` auto-`Rebuild()`s on undo/redo. Record before mutating: `Undo.RecordObject(rig, "Move head")` inside each gesture's first mutation, `Undo.RegisterCreatedObjectUndo` for created assets, collapse a drag into one group (`Undo.GetCurrentGroup` / `CollapseUndoOperations`). `ZuiValueControl`/`Z.Value`/`Z.Value2D` take `onBeforeMutate` for exactly this. View state (zoom, active tab, fold) is not undoable; key it per instance. ui-rules.md §8 asks asset editors for visible Undo/Redo buttons as well as shortcuts (GoreLab's web editor has them).

**Mechanical UI audit.** UITK: `ZuiAudit.ExpandAll(window)` then `ZuiAudit.Audit(window, out foldedSkipped)` (namespace `Laubrary.Zui`), only authoritative with the window open at real size and `foldedSkipped == 0`; menu `Laubrary/Audit Focused Editor Window` (with `Laubrary/Toggle Editor UI Recording` for IMGUI windows). It does not catch enum-as-dropdown, bare numeric fields, row-packing waste, redundant titles or missing tooltips; those are read-the-code checks against ui-rules.md. Factory choices that are checked by review: enums → `Z.MiniRadio`/`Z.Segmented` (never `Z.EnumDropdown`), bounded scalars → `Z.MicroSlider`, bools → `Z.Toggle`/`Z.ToggleButton`, X/Y spatial → `Z.Value2D`/`Z.Pad`, a 3D direction → `Z.Direction3D(yaw, pitch, distance, tooltip, onChanged, options)` (a draggable lit sphere; a candidate for the member "up/forward" controls), view-option toggles over a picture → one `Z.SegmentedMulti`, captured boxes → `Z.BoxKeyed`, every factory takes a tooltip. Pixel-exact image drawing in an IMGUI island → `Z.PixelFit`/`Z.DrawPixels` (fractional-DPI trap).

## 5. Flying pieces and blood: Chunks (and Pyre)

**Fit: yes, with one caveat.** Chunks has no public "spawn this sprite" call, but a piece is a pooled `Chunk` whose `SpriteRenderer.sprite` can be ANY sprite, including one built at runtime with `Sprite.Create`. Physics, spin, pseudo-3D tumble, floor bounce/settle, size/alpha/colour over life are all in `Chunk` + its `DebrisScatter` config. The canonical spawn loop is `DebrisScatter.Fire` (`Runtime/Chunks/Capabilities/DebrisScatter.cs:251-358`). A GoreLab piece copies its inner block:

```csharp
var chunk = ChunkPool.Get();                       // pooled, has a SpriteRenderer
var sr = chunk.GetComponent<SpriteRenderer>();
sr.sprite = pieceSprite;                           // Sprite.Create(tex, rect, pivot, ppu 16), tex FilterMode.Point
sr.sortingOrder = bodyOrder + 1;                   // or a Layering.LayerSpec slot; ChunkEmitter.DefaultSortingOrder = 500
chunk.transform.SetParent(null); chunk.transform.position = worldPos;
float unit = Mathf.Max(pieceSprite.bounds.size.x, pieceSprite.bounds.size.y);
chunk.Init(scatterCfg, velocity, angularDegPerSec, life, worldSize: unit /* = scale 1, pixel exact */,
           Color.white, animation: null, tumble: false, owner: null, trailModifier: null,
           hitsModifier: null, pixelExact: true);
System.Action done = null;
done = () => { chunk.Finished -= done; ChunkPool.Release(chunk); Object.Destroy(pieceSprite.texture); Object.Destroy(pieceSprite); };
chunk.Finished += done;
```

`scatterCfg` is a `DebrisScatter` instance (a `[Serializable]` subclass of the abstract `ChunkCapability`; construct with `new` or take it from a committed `ChunkSpec` asset) supplying `gravity`, `drag`, `useFloor`/`floorY` (a WORLD Y, so for a standing character set it to the feet Y at spawn), `bounciness`, `floorFriction`, `restOnFloor`, `sizeOverLife`, `alphaOverLife`, `colorOverLife`, `tumble*`. Caveats: `Init` reads the scatter every frame (`Chunk.Update` dies if it is null), so keep it alive; the runtime texture/sprite must be destroyed on `Finished` (the pool reuses the GameObject, not your texture). `SampledChunkSprites.Sample/SampleAt(Sprite source, RectInt cut, ...)` already cuts a rectangle out of a sprite into a chunk sprite with tint/edge modifiers; it is rectangle-based, so arbitrary pixel sets still need GoreLab's own texture.

**Blood droplets.** Use a committed `ChunkSpec` asset (Squares visual, red palette, tiny sizes, high gravity, floor on) and `Chunks.Burst(worldPos, spec, tintPalette, directionDeg)` (`Runtime/Chunks/ChunkEmitter.cs:91-104`, static class `Laubrary.Chunks.Chunks`), or `ChunkEmitter.SpawnBurst`. Chunks has no creeping/pooling liquid: the prototype's crawl-down-the-body and floor-pool behaviour must stay GoreLab's own (baked into the body texture), with Chunks only for airborne drops and gibs. Pyre (`PyreBlastPool.Get()` → set `spec`/`fps`/`loop` → `Finished` → `Play()`, worked example `Runtime/ZoetropePyre/SpawnPyreFx.cs`) is for a baked splash/burst animation; optional.

## 8. Things that will bite

- **"Member" already means something in Launimator.** `LauminationSetMember` is one direction entry of a direction set ("members" in every Launimator doc and tooltip). A GoreLab "member" (head ball, torso box) in the same window as direction sets will confuse readers and code search. Use a distinct type name (e.g. `GoreMember`/`GorePart`) and say "body member" in UI text, or pick another word; `ZoeBodyPart` is also taken (composite part).
- **Do not name a class `GoreLab` inside namespace `Laubrary.GoreLab`.** ZUI documents the trap: a class named like its namespace's last segment gets shadowed by the namespace in sibling `Laubrary.*` namespaces (why the UITK factory is `Z`, not `Zui`). No `Gore*`/`Wound*` types or namespaces exist anywhere in the project, so there is no other collision.
- **Mirror only works for right-facing authored members** (section 2). Getting this wrong produces an imp that never shows its left side, with no error.
- **Coordinate conventions differ three ways.** GoreLab tags: sprite-local, origin top-left, y down, z toward viewer. Unity sprite pixels / MetaMapper map space: origin bottom-left, y up. Launimator angles: 0° = up, clockwise. Convert once, in one helper. World ↔ sprite pixel with pivot, PPU, transform and flipX is already written: `Laubrary.MetaMapper.MetaMapSprite.ToMap(Sprite, Transform, bool flipX, Vector3 world)` and `ToWorld(...)` (`Runtime/MetaMapper/MetaMapSprite.cs`), lifted verbatim from `ZonedAnimationPlayer.PixelToWorld`; reuse, do not write a fourth copy.
- **Sprite pivots must match the prototype's placement rule** (bottom-aligned, horizontally centred) or every tag is off by the centring difference; odd widths need the floor rule from section 3 on both sides.
- **`SpriteAlphaHitFilter` caches alpha per sprite instance ID in static dictionaries and never evicts** (`Runtime/Zoetrope/SpriteAlphaHitFilter.cs:34-90`, inference from the field shapes). If the live component swaps in a NEW runtime `Sprite` per bake, physics hits will read the wounded sprite (holes become misses, probably desirable) but the cache grows by one entry per bake. Reuse one texture/sprite per frame slot (rewrite pixels in place with `SetPixels32` + `Apply`) instead of creating new sprites per wound.
- **Readable textures.** Baking needs source pixels. `isReadable: 1` on the imp PNGs (ProtoGuy has it) or a pixel copy via `PreviewTex.CropSprite` (works on non-readable textures but costs a GPU readback). The editor should check readability of a rig's frames and offer to fix it, the way `AtlasBaker.TryGetPixels` auto-sets it.
- **Runtime sprite lifetime.** Every runtime `Texture2D`/`Sprite` (wounded frames, flying pieces) must be destroyed by its owner; `ChunkPool` reuses GameObjects only.
- **Death and disposal.** `ZoeState` disposes the body after a death clip or `deathLinger` (`Zoe.deathDisposal`); `ReactionFxPlayer` may `Hide()` the view on a clip-less death. The live component must stop swapping when the renderer is disabled/blank and must not resurrect a hidden body. In the demo, keep the imp from dying (high `maxHealth`, `Revive()` on Reset).
- **`AnimationArbiter` owns who plays what.** Hurt/death reactions preempt locomotion through it. GoreLab must never call `PlayClip` (and the bypass audit flags `.PlayClip(` outside the package).
- **Undo + SerializeReference + probes.** Never save assets from probe scripts; `[SerializeReference]` lists null out if a type fails to load (project memory "serializereference-data-loss-hazard"). Give every `IWoundRecipe` implementation `[Serializable]` and keep type names stable (use `[MovedFrom]` on rename).
- **Hand-written files and `.meta`.** Unity generates a `.meta` (random GUID) on import for any new file; commit it with the file. If a script writes an `.asset` that references a sprite, run `AssetDatabase.ImportAsset`/`Refresh` first so the referenced sprite has its GUID. Never hand-edit or duplicate GUIDs; copying a ProtoGuy `.meta` to get importer settings means changing its `guid:` line (or, better, set the importer through `TextureImporter` in the eval script and `SaveAndReimport()`).
- **Odin / VInspector.** Odin is not installed. `Assets/vTabs/` (an editor tab helper with its own asmdef) is present and does not touch inspectors. No interference expected.
- **Draw order.** No generic y-sort component exists in this tree (OutBurner keeps its own). A spawned Zoe's renderer is at sorting order 0 on the default layer; Chunks default to order 500 (`ChunkEmitter.DefaultSortingOrder`); `Layering.LayerSpec` (`Runtime/Layering/LayerSpec.cs`) is the shared "named slot → sortingOrder" resolver if the rig wants authored slots for pieces/blood.
- **Generated `.states.cs`.** Creating the imp Zoe through script still triggers the generator on save; commit the file it writes.
- **Coplay targeting.** This worktree's editor has the same `productName` as the other Laubrary Dev worktrees; always verify `Application.dataPath` resolves under `D:\Unity\Laubrary Dev - GoreLab` before trusting a compile check.
- **UI work gate.** Read `D:\AgentGuide\ui-rules.md` in full, the "UI in Unity" section of `D:\Unity\UNITY_DEV_GUIDE.md`, and the skill's `references/ui-layout-rules.md` before touching the window or the demo HUD; run `ZuiAudit`, do the leftover audit (ui-rules §7) and the Handover Walk (§10) before calling it ready.

## (a) Recommended integration design

1. **Assemblies:** `Runtime/GoreLab/` → `com.Lautaro-Arino.Laubrary.GoreLab` (refs: Zoetrope, Zoetrope.Launimator, Launimator, Combat2D, Chunks, PreviewKit, MetaMapper, Pooling, Unity.Burst/Collections/Mathematics; `allowUnsafeCode: false`). `Editor/GoreLab/` → `com.Lautaro-Arino.Laubrary.GoreLab.Editor` (refs: the runtime asmdef plus Zui.Editor, ZUI.Editor, ZuiRuntime, AssetKit.Editor, PreviewKit, Launimator, Zoetrope). Tests in `Assets/Tests/GoreLab/`. Nothing else references GoreLab, so Zoe/Reel stay ignorant.
2. **Sidecar LauAsset `GoreRig`** (namespace `Laubrary.GoreLab`, `CreateAssetMenu("Laubrary/GoreLab/Gore Rig")`, `IVisualPreview`): a `Zoe zoe` OR `LauminaryVersion reel` target, a list of body-member definitions (kind ball/box, name), per-drawn-frame tags keyed by the frame's `Sprite` (centre, radii, depth, squareness, up3, forward3, nudge, behind/exempt masks per member, no-head flag), and `[SerializeReference] List<IWoundRecipe>` with default style settings. No sub-assets.
3. **Frame enumeration** from the target: Zoe → `view as ZonedLauminaryView`/`LauminaryView` → `version` → `animations[].frames` (and `sets[].members[].laumination.frames`, de-duplicated by `Sprite`). Mirrored directions are not stored: they are derived at runtime from the drawn frame plus `flipX`, using GoreLab's "mirror pixels and tag vectors, not the wound" rule.
4. **Pure cut engine** in plain C# (no UnityEngine types in the core math; `Color32[]`/`int` grids), a straight port of `cut3d.js` (removers: planes and capsules in member coordinates, groups, superellipsoid box), validated against `GORELAB_GOLDEN.json` by reflection-run tests. One deterministic function used by the editor preview, the IVisualPreview thumbnail and the runtime (authoring.md §7).
5. **Modular wound kinds:** `public interface IWoundRecipe { string DisplayName { get; } void AddRemovers(in WoundRequest req, List<Remover> into); }` with `[Serializable]` implementations (Slice, Bullet straight-on, Shotgun cone, Remove head) each in its own file; the editor discovers them via `TypeCache.GetTypesDerivedFrom<IWoundRecipe>()` and draws an "Add" menu (`Z.Menu`), exactly the Chunks capability-card model. A game adds a new kind by writing one class, no GoreLab edit.
6. **Damage kind selection:** a wound request carries a recipe reference (or index into the rig's list) chosen by the caller; optionally map `Combat2D.DamageType` assets to recipes in the rig (`List<(DamageType, recipe)>`), which works once `DamageInfo` carries a type (Open Question 2).
7. **Live component `GoreBody`** (package runtime, `[DefaultExecutionOrder(10000)]`, added by the game/spawner next to `ZoeSpawner.SpawnCharacter`'s result, holding a `GoreRig`): caches the `ZonedAnimationPlayer`/`LauminaryPlayer` and `SpriteRenderer`; subscribes to `Health.Damaged` (point + direction) and exposes `ApplyWound(WoundRequest)` and `ResetWounds()`; keeps the session's remover list; bakes lazily (the frame on screen plus the next, per GoreLab's research plan, with a per-frame ms budget later) into one reusable `Texture2D`/`Sprite` per drawn frame slot; in `LateUpdate` swaps `sr.sprite` (and restates `sr.flipX` from the player) when a baked version of `player.CurrentSprite` exists; does nothing when the renderer is disabled or hidden.
8. **Hit mapping:** world point → sprite pixel via `MetaMapSprite.ToMap(sprite, transform, flipX, world)`, then to GoreLab top-left coordinates; shot direction from `DamageInfo.direction` or the caller.
9. **Flying pieces:** the newest group's changed pixels become runtime sprites spawned as pooled `Chunk`s (`ChunkPool.Get()` + `Chunk.Init` with a rig-owned `DebrisScatter` config, `floorY` = feet Y), released and texture-destroyed on `Finished`. Airborne blood and gibs via `Chunks.Burst` with a committed red `ChunkSpec`. Creeping blood and stains stay GoreLab's own, baked into the body texture.
10. **Editor window `GoreLabWindow : ZuiAssetWindow<GoreRig>`**, menu `Laubrary/GoreLab` (the only menu item): `Z.Split` with controls left and a UITK stage right copied from `MetaStage` (checkerboard, image child, `Painter2D` overlay in front, `ZuiPanZoom`), a frame strip copied from `MetaMapperWindow.BuildFrameStrip` grouped by direction set member with mirrored directions shown read-only, and a `Z.Segmented` tab row (Shape, Rotate, Paint, Frame, Play) where the tab is the mode, matching the web prototype and ui-rules 8b.
11. **Undo:** every gesture records `Undo.RecordObject(rig, ...)` once at gesture start (Pyre's `onBeforeMutate` pattern), collapsed per drag; visible Undo/Redo icon buttons plus Ctrl+Z/Y; `ZuiWindow` rebuilds on undo automatically.
12. **Editor-side lookup:** "which rigs target this Zoe" = `AssetLibrary<GoreRig>.Enumerate().Where(r => r.zoe == z)`, used only inside the GoreLab window (e.g. an "Open rig for selected Zoe" path); register `LauAssetEditors.RegisterOpen<GoreRig>(GoreLabWindow.OpenFor)` in an `[InitializeOnLoad]` link class. The Zoe window gets nothing.
13. **Imp assets:** commit PNG copies (cols 1-3 as flipped copies) with Point/no-compression/readable/PPU 16/custom bottom pivot importer settings; a hand-built `LauminaryVersion` with five `Walk_<angle>` animations and a `Members` set `Walk8` (angles 180/135/90/45/0, `mirrorBuiltIn`), built by an ephemeral `eval_file` script (never `LauminaryRepo.SaveAnimationToDraft`); a `Zoe` with `ZonedLauminaryView` and an `Always → Walk8` motion pose; import the user's tags from `GORELAB_USER_TAGS.json` into the rig (mirroring cols 1-3).
14. **Demo scene** `Assets/Demos/GoreLabDemo/GoreLabDemo.unity`: ProtoGuy-style camera (PixelPerfectCamera + PixelScaleCamera, size 6.25), a spawner that spawns the imp, attaches `GoreBody`, and turns it with `MotionPoseAnimator.SetPoseOverride`; a demo input script (Input System `Mouse.current`) that turns a click/drag into `GoreBody.ApplyWound` / `Hurtbox.ReceiveHit` with the drag direction; a `ZuiRuntime` panel (`Zui.Panel` + `ZuiStack`) with direction arrows, damage-kind toggles and Reset wounds. Committed scene, no builder.
