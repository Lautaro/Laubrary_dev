# GoreLab port: fidelity and usability review

Reviewer: fidelity and usability reviewer, 2026-10-04. Branch `feat/gorelab`, project `D:\Unity\Laubrary Dev - GoreLab`. Compared against the web prototype in `D:\CODEZ\GoreLab` (its dated log, the Member tagging editor, the algorithm specification section 11). Nothing in the repo was changed; the temporary rig and screenshots made for this review were deleted and the editor was left out of Play mode. `git status` after the review is identical to before it.

## 1. Verdict

The engine came over faithfully and the game side works: all 14 golden tests pass, the demo imps take every damage type, the wound stays on the same spot of the body as the imp walks and turns (mirrored directions behave as a rotation, not a reflection), Reset restores every imp, and repeated wound/reset cycles do not grow the number of textures. The authoring window is a clean, recognisable translation of the prototype's tabbed editor (same five tabs, marquee shapes that never get replaced by a stray drag, U/F trackball dots, Default orientation and the orientation warning, two paint layers, red/amber frame status in Test, real undo/redo), and its first-run path is good: New rig, pick the character, and the 32 drawn frames appear grouped by direction with the three mirrored directions listed read-only. But a person could not comfortably SET EVERYTHING UP with it today, for two reasons. First, a real bug: on any frame that has never been tagged, the shape you drag out is invisible (and the Test tab treats the frame as not set up) until you step to another frame and back, which is every frame of a new rig. Second, the speed tools the owner actually tags with (Carry, Carry all, Auto-tag, Same shape on all) are absent, so an 8-direction, 4-frame character means drawing and adjusting about 40 shapes by hand from scratch. Getting a wounded character into a game also requires writing code; nothing in the tool says so or helps.

## 3. Usability findings, worst first

Walked cold in the real editor: opened the window from its menu (Laubrary > GoreLab), created a new rig, pointed it at the demo imp, drew a head and torso on the first frame with real pointer events sent to the window, tagged a head on the Front-side direction, painted, switched to Test and sliced the head, stepped to an untagged frame, undid and redid. Every screen was captured from the window itself and looked at.

1. **The first shape on a new frame is invisible (bug, blocks).** What I did: on a fresh rig, Shape tab, dragged a box over the head on Front 1. What happened: the data was written (the strip got a check mark, the guide text disappeared, the Squareness slider became active) but the stage showed no outline, no sphere, no highlight, and the torso box drawn next was equally invisible. Only after stepping to another frame and back did both appear. Cause, in plain terms: the window remembers the shown frame's tag record at the moment you select the frame; on a frame that has no record yet, the first edit creates one, but the stage keeps drawing from the old empty reference. The same stale reference makes the Test tab report the frame as "not set up" until you re-select it. Because every frame of a new rig starts with no record, a user meets this on every single frame, and while dragging they see nothing at all, so a marquee cannot even be aimed. Suggestion: when the window creates a frame's record, point the shown frame at it (one line), and add a test that draws a shape on an untagged frame and checks the stage sees it.
2. **No speed tools for tagging dozens of frames (annoys a lot).** The imp needs 5 drawn directions x 4 frames x 2 members = 40 shapes. In the port each one is a fresh marquee plus whatever moving, resizing, squareness and depth adjustment it needs, frame by frame; nothing copies a shape forward, and nothing guesses a starting shape. The prototype gets this down to a few clicks per direction (Auto-tag puts a rough head on every frame, then a torso below it; Carry all moves a checked shape through the rest of a direction by matching pixels; Same shape on all copies size and squareness). Suggestion: at minimum a "Copy to next frame" and "Copy to all frames of this direction" (same position, size, orientation, masks), then Auto-tag, then pixel-matching Carry.
3. **Getting it into a game requires code, and the tool never says so (blocks a non-coder).** A character is spawned at run time from its Zoe asset, so there is no prefab to drop the wound component on; the demo adds it in code after spawning and calls the wound function from its own mouse script. Nothing in the window, the rig, or its tooltips tells the user that a character needs this component, which rig to give it, or that wounds only happen when game code (or, optionally, the Health damage hook, off by default) asks for them. The demo also builds fresh damage types in code, so settings tuned on the rig's Test tab do not reach it. Suggestion: let the rig (or the Zoe) declare "attach gore at spawn" so the spawner adds the component itself, turn the Health hook into the visible default with the rig's chosen damage type, and make the demo use the rig's own damage-type list.
4. **Test tab bullets do not match the game's bullets (misleading).** The Test tab says it uses "the game's own cut engine", but it skips the rule that places a bullet where most frames of the direction will show it, and it skips the wound counter that decides which member a bullet hits. A test bullet can therefore vanish on the next frame where the game's would not, or hit the torso where the game hits the head. Suggestion: pass the same two inputs the running character passes.
5. **You cannot see which thumbnail is selected, and "done" only covers one member.** The selected frame in the strip looks exactly like the others (checked in a zoomed screenshot). The check marks and the direction badge (check / ellipsis) describe only the member currently chosen, so to know whether a frame is fully set up you switch members and scan again; there is no "this frame is missing its torso" view. Suggestion: a visible selection frame on the thumbnail, and two small dots per thumbnail (head, torso) so completeness reads at a glance for both.
6. **Test is a still picture.** To check a wound across the walk you click through 4 frames x 8 directions by hand (the wound does persist across them, which is good). The prototype plays the walk and lets you turn the walker. Suggestion: a Play toggle in the Test tab that cycles the direction's frames at the walk speed, and left/right to turn.
7. **No Target choice.** With two members, a slice near the neck may go to the torso or the head by the "crosses most" rule and you cannot force it; the prototype had Auto / Head / Torso. Suggestion: a three-way segmented control in the Test tab (the recipes already support it).
8. **Damage-type settings render badly.** The section headings inside a damage type's settings ("Swipe", "Which side flies") are drawn as small blue chips floating in the middle of the field rows instead of as dividers above them (visible in the Test tab screenshot). Suggestion: give dividers a full row in that flowing layout.
9. **Chrome above the tool eats space.** The generic asset header (picker, New, Browse, Duplicate, Rename, Delete) plus an asset "Tags" block take about three rows before the tool starts; the frame strip has a vertical scroll arrow it does not need. Minor against ui-rules 8b.
10. **Small things.** Undo/Redo never grey out. The Animation (bare version) field stays visible after a Character is chosen, although only one is used. Painted "Behind" pixels are nearly invisible on a brown sprite at full paint opacity (a contrasting outline or a stronger colour would help). No fly-direction arrow during a test drag. On the demo, after Remove head on the back view, a few dark-red pixels float in the air above the neck where the head's outline was; this is probably the engine's known rim behaviour at the very edge of the head shape (spec 14.5) and may look the same in the prototype, but it reads as a mistake in the game.

The window's automated audit (missing tooltips, controls off-screen, stretched or over-wide controls) reported zero findings on all five tabs; every control I hovered in the dump had a tooltip describing its effect.

## 4. What the owner's prototype workflow loses in Unity today

In the prototype the owner tags a whole 8-direction walk in a few minutes: Auto-tag drops a rough head on all 20 drawn frames, a second Auto-tag adds a torso under each, then per direction they fix frame 1 and Carry all pushes it through frames 2 to 4 by matching pixels (rotating the 3D vectors with the pose), with a match percentage to warn when the guess is poor; Same shape on all evens out sizes. Then they press Play, the imp walks, they turn it with the arrows and shoot it, seeing red borders on any frame that is not ready. In Unity today every one of those 40 shapes is drawn by hand from an empty frame (and, because of bug 1, drawn blind), there is no motion test inside the editor (stepping frames by hand, or entering Play mode with a scene and code of their own), there is no Target choice, and the masks have to be repainted on every frame because nothing carries them. Estimated effect: the same character goes from a few minutes of checking to something like an hour of drawing, with more inconsistency between frames (which is exactly what made bullets vanish in the prototype's own history).

## 5. What I would build next

1. Fix the invisible-first-shape bug and add a regression test for "draw on an untagged frame, the stage shows it, Test accepts the frame".
2. Frame speed tools in the Frame tab: Copy to next frame / to the rest of this direction (shape, orientation and both masks), then Auto-tag for head and torso, then the prototype's pixel-matching Carry with its match percentage. Each one undoable.
3. A playing Test tab: walk the direction's frames, turn with left/right, a Target choice, the fly-direction arrow, and the same bullet-placement inputs the game uses; plus a way for a spawned character to get its gore component and rig without the user writing code.

## 6. Verified and not verified

Verified by probe: 14 of 14 GoreLab golden tests pass (run by reflection; this covers the two named test classes only, not a Test Runner suite). Undo/redo of two marquee shapes. Each demo damage type returns success on an imp (one Slice on the back-side imp missed and correctly reported "nothing visible changed"). Reset clears wounds on all imps. Three wound/reset cycles left the editor's texture count unchanged (1046). Window audit: zero findings on all tabs (one folded section skipped per tab, eight on Test). No errors in the console from GoreLab.

Verified by eye (screenshots of the real window and the game view): new-rig empty state; frames appearing grouped by direction after choosing the character; invisible first shape and its appearance after re-selecting; sphere wireframe with U/F/E/W marks; Front-side default orientation; Paint, Frame and Rotate tabs; a Test slice on the head; red border on an untagged frame; demo imps before wounds, right after, a moment later on another walk frame, and after Reset.

Not verified: no human has dragged in this window; all drags were synthetic pointer events sent to the window. Ctrl+Z / Ctrl+Y keys were not pressed (Undo was invoked through Unity's undo directly). The demo's on-screen panel and its mouse driving were not exercised (the camera capture does not include the panel). The wounded imps were not compared pixel-for-pixel with the prototype for the same cut on the same sprite; the floating rim pixels after Remove head are unconfirmed as prototype behaviour. Shotgun cone, Cut and torso slices were seen only at game-view scale. Behaviour with a Zoe whose view is not a Launimator one, or with a rig targeting a bare animation version, was not tried. Phone-width and docked-window layouts were not checked.
