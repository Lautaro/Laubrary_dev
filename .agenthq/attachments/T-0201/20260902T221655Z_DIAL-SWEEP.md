## What this table is, and what it is not

**The failure it hunts.** Every control the window shows writes into the document and then asks the preview to
repaint. The preview reads THROUGH a frame cache, so an edit that does not also invalidate that cache repaints
the frame rendered before the edit: the dial moves, the picture does not. That is the owner's report, verbatim —
"I change every dial to its minimum, NO CHANGE AT ALL" and "didn't make any difference until I disabled and
re-enabled Auto Exposure" (an unrelated edit that DID invalidate, releasing every held-back edit at once).

**How it is tested.** For a set of scratch documents covering every node kind — each primitive, each solid, a
bag, each of the nine hosted PyreForms, both stateful simulations, all sixteen hosted Pyre legacy shapes, plus
fill / border / height / mask / swarm / effects / lights — every serialized field in the document graph is moved
to a different value, the caches are invalidated exactly as `ShaperWindow.AfterEdit` does, and the frame is
rendered twice: once through the preview's own cache and once COLD, with no cache and no buffer pool. The two
must agree. They are compared on the document's BUSIEST frame, not frame 0, because a burst generator paints
nothing at frame 0 and would report its whole dial set inert for the probe's own reason.

`ZUIValue` dials are swept as controls rather than as fields: a static-value move and a curve-envelope move,
because a dial's off-mode fields are inert by construction and its ENVELOPE is the edit a hand-written cache key
most easily misses.

**NO EFFECT is not a failure verdict.** It says this dial did not move THIS document's picture. A Rect dial on
an Ellipse, a strip dial on a solid fill and a Curve range while the dial is Static are all honestly inert. The
grouped table at the end is the one to read: a BLOCK with zero moved dials is the finding, not a row.

## Findings that are NOT invalidation, and whose they are

**Every hosted generator's own dials are inert inside Shaper, and the generator is not at fault.** With the
invalidation contract clean (0 stale across 29,023 controls), the nine PyreForms, both simulations and all
sixteen hosted Pyre layers still show ZERO of their own dials moving Shaper's picture, while the SAME
documents' transform, shell, swarm and canvas dials all move it. `generator-source-check.md` beside this file
asks the layer below: each form's own raster is between 45,000 and 573,000 covered pixels and MOVES when one of
its dials moves. So the picture is lost between the source's raster and Shaper's composite paint, not in the
generator and not in the cache. The one exception is `TestDiscForm`, whose single radius dial changes coverage
and does come through — which is the tell: what survives the bridge is COVERAGE, and what is dropped is
everything the generator says about colour and energy.

Owner: **T-0202** (`Runtime/PyreShaper`, "a hosted Pyre generator paints what Pyre paints"). The trail for it:
`ShaperCompiler.cs:971` bakes the source with the current dials on every render; `ShaperFillResolver.cs:433`
attaches that bake as the owner's `compositeAlbedo`; `ShaperEvaluator.FillCompositeAlbedoTile` paints it.

**A document built in memory shifts once, the first time a layer key is taken.** `ShaperLayerKey.MixValue`
deliberately runs each object's `OnAfterDeserialize`, and that is where a dial block promotes its legacy float
into a dial (`ShaperNode.cs:117-125`), guarded by a `dialsPromoted` flag it then sets. An authored asset is
promoted the moment it loads, so this is invisible in the window; only an object that has never been through
Unity's serializer — which is what a probe builds — can still be waiting for it. Verified rather than assumed:
after the promotion settles, 29,023 further comparisons agreed.
