# DotGen — behaviour checklist (W0.2)

Acceptance rows for every control, range, default, formula and interaction of the POC (`POC-DotFoundry-Specification.md`, normative for maths/ranges/defaults, and `POC-DotFoundry.html`, the behavioural reference — its whole `<script>` was read; line numbers below cite that file). Where the two disagree, the ruling follows `DOTGEN-DESIGN-DECISIONS.md`: HTML wins for visible behaviour, spec wins for maths — see **Discrepancies**. DotGen mapping cites the card/section names from design-decisions §4.

Every default-demo dot/area count in §S below was **not** hand-derived — it was computed by transcribing the exact pure functions from the HTML (`hash`, `xform`/`invform`, `shapeInside`, `makeArea`, `genBase`, `selectorWeight`, `warpCenters`, `applyMutators`, `build`, plus the id-generating `rid`/`defaultGen`/`demo`) into a standalone Node script and running the real §20 `demo()` state through the real `build()` logic. The script is `dotgen_demo_counts.js` (scratchpad); its printed generator ids (`gen_1`, `gen_5`, `gen_b`) matched the hand-traced `rid()` counter sequence, cross-confirming the transcription.

Columns: **#** · **Area** · **Behaviour** (one testable sentence) · **Source** (spec § / HTML function+line) · **DotGen mapping** · **Verify** (probe / eye / probe+eye).

## Discrepancies (HTML vs spec)

Per `DOTGEN-DESIGN-DECISIONS.md`: **HTML wins for visible behaviour, spec wins for maths.** Every formula I checked across §§5–11 (Grid, Box Row, Radial Grid, Margin, Gradient, Random, Nudge, Warp/points, Warp/lines, Cull, Fill Drawer target/gradient math) matched the spec pseudocode term-for-term in the HTML — I found **no maths discrepancies**. The disagreements found are all about *when defaults get applied* and *what exists in the HTML but isn't yet mentioned in the spec's newer requirement*:

**D-1 — §8.12: does switching Placement method preserve or recreate?**

**Ruling: the HTML PRESERVES — it is one shared config object per generator's `placement`, never recreated per type.**

Evidence:
- `defaultGen` (HTML L51) builds a generator's placement as `placementDefaults({id:rid('place'), type:'grid', cols, rows, gapX, gapY, skewX, skewY, rotation, offsetX, offsetY, ...})`. `placementDefaults` (HTML L50) unconditionally back-fills **every Box Row field** (`boxWidthMin/Max`, `boxHeightBasis`, `boxHeightMin/Max`, `boxAspectMin/Max`, `boxOverflow`, `boxGap`, `boxPadding`, `boxAlign`, `boxSeed`) onto that same object at creation time, regardless of the placement's current `type`. So a Grid placement is already carrying full Box Row data from the moment it's created.
- The Method dropdown (HTML L106, `placementBody`, the `row('Method', selectCtl(p.type, ..., 'type', 'placement', null, true))` line) is bound through the fully generic handler in `bindInspector` (HTML L125): `const o=getTarget(el.dataset.scope,el.dataset.index); ...; o[key]=v;`. For `scope==='placement'`, `getTarget` (HTML L124) returns `g.placement` — the single existing object. Switching Method therefore executes literally `g.placement.type = 'boxRow'` (or `'grid'`/`'radial'`) and nothing else — no new object, no field reset, no re-init call of any kind.
- **Consequence for Grid ↔ Box Row:** switching between these two preserves every previously-entered value on both sides, because both sets of fields already coexist on the one object (Box Row fields via `placementDefaults`, Grid fields as the object's own literal properties). Confirmed by inspection — there is no code path that clears or reinitializes either set.
- **Consequence for Radial Grid:** the radial-only fields (`rings`, `dots`, `minRadius`, `maxRadius`, `direction`, `spacingCurve`, `densityScale`, `phase`, `includeCenter`) are **not** part of `placementDefaults`'s back-fill list, so a placement object that started life as Grid has none of them until the user's own runtime session first switches Method to Radial. At that moment `p.rings` etc. are `undefined`; `placementBody`'s radial branch (HTML L106) still renders `range(p.rings,1,14,1,'rings','placement')`, i.e. `<input type="range" value="undefined">`. HTML5's own range-input fallback (not the app's code) then substitutes some in-range default the browser computes — **not** the spec §8.3 registered defaults (Rings 3, Base dots/ring 7, Inner radius 18, Outer radius 88, Ring spacing curve 0, Outer density scale 45, Phase 8, Center dot on). The one place those §8.3 defaults are actually produced is the hardcoded `demo()` bootstrap (HTML L54), which builds `rings.placement` as a **brand-new** object (`rings.placement={id:rid('place'),type:'radial',rings:3,dots:7,...}`) — a special-cased authoring path, not the live Method-switch handler every user actually drives.
- The shared field name `rotation` (used by both Grid's "Grid rotation" and Radial Grid's "Rotation") carries over correctly either way, since it's the same underlying property.

**Net:** spec §8.3's "MUST initialize a newly selected Radial Grid type" is true only inside the demo bootstrap, not in the interactive app the spec otherwise treats as the behavioural reference — this is a genuine spec-vs-HTML disagreement, not just an ambiguity. Per the design-decisions ruling ("HTML wins for visible behaviour, spec wins for maths"), I'm treating *which fields survive a switch* as the visible-behaviour axis (HTML wins → **preserve**) and *what a never-touched field should read* as the maths/data-model axis (spec wins → **must resolve to the registered default, not `undefined`/browser fallback**). Combined, this is exactly what design-decisions §8.12 already proposes and what DotGen should build: a per-generator `List<DotPlacement> placementBank` (one instance per registered type, `Activator.CreateInstance`-backed) so (a) switching to a type it has visited before restores its prior edits (matches the HTML's actual preserve behaviour for Grid↔Box Row), and (b) switching to a type for the first time gets that type's real registered defaults immediately (fixes the HTML's `undefined`-field gap, which C#'s field initializers give for free — there is no such thing as an uninitialized struct field the way JS leaves `p.rings` undefined).

**D-2 — §14 double-click slider reset is confirmed absent from the HTML, exactly as the spec itself frames it.** Not a disagreement to resolve — spec §14.1 explicitly says this is "required even though the current HTML reference does not yet implement it," and I verified that framing is accurate: there is no `dblclick`/`ondblclick` binding anywhere on a `<input type="range">` (HTML — the only `ondblclick` in the whole file is `viewport.ondblclick=fitView` at L139, on the preview canvas, unrelated). Ruling: build it per spec §14/§14.1 in full (B-163..B-165).

**D-3 — "New seed" uses `Math.random()`, not `hash01`.** HTML L133: `state.seed=Math.floor(Math.random()*999999)`. This is a one-shot UI convenience picking the *input* to the deterministic pipeline, not part of evaluation itself, so it isn't a maths discrepancy in the pipeline sense — but it does collide with the programme rule "no `UnityEngine.Random`/`System.Random` in the DotGen assemblies" (`PROGRAMME_RULES.md`). Flagging for W1.2/W2.1: the "New seed" button needs a non-`System.Random` source for its one-off pick (e.g. a tick-count-seeded `hash01` draw, or `Guid.NewGuid().GetHashCode()`), not a design contradiction to resolve here — just don't reach for `System.Random` when wiring the button.

**D-4 — internal JS codes vs. the spec's/UI's display names.** Not behavioural discrepancies, just naming to get right in DotGen's C# enums (use the display text as the enum member name, never the JS internal string): Cull `mode:'inside'`="Cull selected", `mode:'outside'`="Cull unselected" (HTML L108); Drawer cell shape `cellShape:'square'`="Rectangle" (same convention as Generator Area's own `shape:'square'`="Rectangle", HTML L51); Warp `force:'pull'`="Pull / cluster", `force:'push'`="Push / disperse"; Radial `direction:'center'`="Center → edge", `direction:'edge'`="Edge → center"; Box Row `boxAlign:'bottom'/'center'/'top'` = "Bottom / grow upward" / "Centre" / "Top / grow downward"; Drawer `target:'areas'/'cells'` = "Generator areas"/"Placement cells"; `selection:'selected'/'inverse'` = "Selected"/"Inverse". None change behaviour; all are direct 1:1 renames.

**D-5 — Box Row's height-slider range compromise is a DotGen-only deviation from both sources, already decided, not left open.** Spec §8.2's table and the HTML (`range(p.boxHeightMin,1,p.boxOverflow?1000:100,1,...)`, L106) agree with each other exactly (dynamic max 1000 vs 100 depending on Grow-outside-area). `DOTGEN-DESIGN-DECISIONS.md` §2 deliberately widens this to a single static `[Range(1,1000)]` field because Unity's `[Range]` attribute can't be conditional, relying on evaluation-time clamping to make the wide range harmless when Grow-outside-area is off. Recorded here only because the task asked for every HTML/spec mismatch; this one isn't a mismatch between HTML and spec, it's a documented Laubrary-side compromise against both.
