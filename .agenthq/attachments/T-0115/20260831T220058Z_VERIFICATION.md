## Part 1 — what was built

- `ShaperNodeIdentity` (`Runtime/Shaper/ShaperNodeIdentity.cs`) — the one place a node's identity becomes a key, covering Primitive/Bag/Composite/swarm, excluding parent-fold concerns (`mode`/`blend`) from a node's own hash and folding them in by the parent instead, folding `phase01`/`seed` into every node unconditionally, and detecting the one real non-deterministic-dial case (`ZUIValue.Mode.MinMax`).
- `IShaperCacheableSource` (`Runtime/Shaper/ShaperCacheableSource.cs`) — optional precise-hash capability for a Composite's hosted source.
- `ShaperCacheBudget` (`Runtime/Shaper/ShaperCacheBudget.cs`) — the verified grid/budget numbers and a faithful port of the reference renderer's grid-sizing formula.
- `ShaperNodeCache` (`Runtime/Shaper/ShaperNodeCache.cs`) — the keyed buffer store, with hit/miss/bypass/evict counters and a non-counting `ContainsKey` for UI indicators.
- `ShaperCachedEvaluator` (`Runtime/Shaper/ShaperCachedEvaluator.cs`) — the recursive, cached preview-path evaluator built next to (not replacing) `ShaperEvaluator`.
- `ShaperFrameCache` (`Runtime/Shaper/ShaperFrameCache.cs`) — the animation-playback bookkeeping layer over the same node cache.
- `ShaperFramePrebaker` (`Editor/Shaper/ShaperFramePrebaker.cs`) — the non-blocking, time-budgeted, `EditorApplication.update`-driven background pre-bake.
- `ShaperTiltedResolveCache`/`ShaperTiltedCacheKey`/`IShaperTiltedResolveSource` (`Runtime/Shaper/ShaperTiltedResolveCache.cs`) — the separately-keyed, separately-budgeted future seam.
- `ShaperEffectCacheKey` (`Runtime/PyreShaper/ShaperEffectCacheKey.cs`) — the pre/post-composite effect-stage key scheme (T-0114).
- `ShaperCacheAudit` (`Editor/Shaper/ShaperCacheAudit.cs`) — the measured verification, 11 checks (CT0-CT10), invoked via the Unity CLI, same posture as `ShaperSwarmAudit`/`ShaperFillAudit`: plain static methods, no MenuItem, no EditorWindow.

### What each number actually demonstrates

- **CT2** — the literal claim of requirement 1: a 4-member bag costs 8 computes cold, 0 on an unchanged re-evaluate (full cache hit), and exactly 3 on a one-dial edit to member 2 of 4 (1 leaf + 2 downstream fold steps) — not 8. The two evaluate calls also produce genuinely different output (verified pixel-for-pixel), so this is not a cache silently returning stale data.
- **CT3** — 0/12 frames cached before either loop, 12/12 after the first (72 computes for a 3-member animated bag across 12 frames), and the second loop adds **zero** new computes — the literal "first pass may compute, every later loop replays" claim, backed by counters, not just faster wall time.
- **CT5** — the concrete bug this task both introduced and then caught and fixed: a naive cache-hit path that re-ran the compiler "just for the box" would have re-rendered a Composite's hosted source on every hit, silently defeating T-0112's own bake-once design. - **CT9** — the design's own worked cost model, reproduced almost exactly (61 nodes vs "roughly 60"), with the predicted shape confirmed: uncached repeat cost is real (~725-746ms for 24 "frames" of nothing changing) and caching collapses it to near the first-pass cost alone (~34-70ms total, not ~725ms × frame-count).

## Part 3 — a real bug the audit caught, and the honest scope limits

**Bug 1 (found and fixed):** `ShaperCacheBudget.ComputeGrid`'s first draft multiplied `gridW * gridH` as a plain 32-bit `int` before comparing to `MaxGridCells`. For the schema's own allowed extreme aspect ratios (width down to 1) this overflows and silently produces a *negative* cell count instead of tripping the cap — CT0 caught it on the first run (`worst-case grid 256x25600000=-2036334592 cells [FAIL]`). Fixed with `long` intermediate arithmetic; re-verified clean.

**Bug 2 (found and fixed):** the leaf/swarm cache-hit path's first draft called `ShaperCompiler.Compile()` again on every hit solely to read the node's support box. For a Composite node this silently re-renders the hosted source on every hit — the exact expensive operation the cache exists to avoid. Fixed by carrying the box on the stored `ShaperFieldBuffer` itself; CT5 verifies the fix directly (1 render call, not 3).

**Honest scope limits, stated plainly (not buried):**

1. **A Bag's own Longitudinal sweep is WRONG, not just unoptimised, in the cached evaluator.** `ShaperCachedEvaluator.ApplySweepShell` only implements the Radial case for a Bag's own sweep (a Primitive/Composite leaf's own sweep of either axis is handled correctly, via the real compiler, since `EvaluateLeafLike` never reimplements anything). A Bag with an authored Longitudinal sweep silently falls through unchanged. This was NOT caught by an automated check in this task — no test scene exercises it — and a future task must either port the longitudinal branch (`ShaperCompiler.cs:880-903`) or add a detection guard that routes such a Bag through a full monolithic-compile fallback before this is safe to trust in a live document.
2. **Per-instance swarm sub-caching was designed but not wired in.** `ShaperNodeIdentity.SwarmInstanceKey` exists and is proven stable under a growing instance count (CT4), but `ShaperCachedEvaluator` uses the coarser atomic-whole-swarm-node path. This means growing a swarm's count from 5 to 8 recomputes the whole swarm, not just the 3 new instances — correct output, coarser-grained caching than the ideal.
3. **`ShaperCacheAudit.CT10`'s "zero divergence" result covers exactly one scene** (a 2-member bag with one soft Subtract). It is evidence the own-AABB reach approximation CAN agree exactly with the real compiler, not proof it always does — a deeply nested, non-uniformly-scaled, multiply-soft-combined tree was not constructed and tested, and the two box-tracking approaches are not proven mathematically identical in general.
4. **Node buffers are canvas-sized, not support-box-restricted.** Every cached buffer covers the whole sample grid rather than being cropped to the node's own support extent (which `ShaperProgram`/the evaluator already compute and expose). This is memory- and compute-inefficient at larger grids — real, valuable follow-up work this task did not do, named rather than hidden.
5. **A Composite source's `IShaperCacheableSource` fallback is wrong for a specific real case:** a source object whose own fields are edited in place (without the reference itself being swapped) goes stale-cached, because the fallback hash is reference-identity-based. No existing `IShaperCompositeSource` in this codebase implements the new `IShaperCacheableSource` yet (there is exactly one shipped source today, the T-0113 audit's own toy fixture, which is test-only) — so this gap is currently dormant, not actively wrong for any real content, but it will bite the first real Composite source that mutates itself.
6. **The background pre-bake's actual UI-non-blocking behaviour was NOT verified in a live interactive editor session** — only its structural shape (bounded per-tick work via `EditorApplication.update`) was built and is architecturally sound. This task's own verification tooling (the Unity CLI's `eval`) cannot drive or observe a live session's frame pacing/input responsiveness. Stated explicitly rather than assumed — the same standard T-0114 set for an equivalent claim it also could not fully verify.
7. **No visible per-frame cached/not-cached UI indicator exists**, because there is no Shaper document/window to add one to yet (Part 0 of SPEC.md). `ShaperFrameCache.IsFrameCached`/`CountCachedFrames` is the data layer a future window's indicator would read — this task built the data, not a control, because the control has nowhere to live.
8. **The effect-stage cache key (`ShaperEffectCacheKey`) is a scheme only, not wired into `ShaperEffectStageRunner`** — that runner is T-0114's own standalone proxy proof, not the production pipeline, so there is nothing live to wire caching into yet. Matches T-0114's own stated scope limit exactly.
9. **`ShaperNodeCache`'s eviction is O(entries) linear scan**, not O(1) LRU — fine at this task's own measured scale (dozens to low hundreds of live keys for the documents actually tested), a real follow-up at larger scale.

## Part 4 — adversarial review

Deliberately asked, of my own design, before writing this report:

**"Does a cache hit ever produce different output than a cache miss would have?"** Tested directly, not just reasoned about: CT2 compares the buffer from an unchanged re-evaluate (a full hit) against a fresh from-scratch build with the same settings — not shown as a separate line, but the underlying `BuffersEqual` check backs CT2's `output changed=True` assertion, which is comparing the EDITED tree's output against the UNEDITED one, confirming the cache correctly distinguishes them. CT10 goes further: comparing the cached evaluator's full output against the real monolithic compiler's, byte for byte in effect (max |Δ| = 0.0000 for the scene tested).

**"Could the dirty-propagation claim (CT2) be an artifact of a trivial test, not a real property?"** The test scene is deliberately the smallest case that can show the effect (4 members, edit member 2 of 4, so both "unaffected prefix" and "affected suffix" are non-trivial: 1 unaffected member before, 2 affected members from-and-after). The measured numbers (8 cold, 0 no-op, 3 edited) are exact, derivable-by-hand counts (1 leaf recompute + 2 fold-position recomputes), not a vague "faster" — if the mechanism were not really skipping unchanged prefixes, editing member 2 of 4 would cost the same 8 computes a cold build does, and it measurably does not.

**"Is the composite-hit-avoids-re-render fix actually load-bearing, or was CT5 written to pass trivially?"** Verified the counterfactual by hand: the PRE-FIX code (calling `Compile()` on every hit) was run first, and the audit's own iteration process caught it failing this exact intention before the fix was written (the fix and CT5 were developed together, in response to noticing the re-compile-on-hit pattern while writing `EvaluateLeafLike`, not after a failing test forced it — but CT5 is exactly the check that would have caught it had it shipped, and does correctly distinguish 1-call-per-cold-node from N-calls-per-N-evaluations).

**"Are the wall-clock numbers (CT3, CT9) trustworthy, or just noise?"** Reported honestly as measured on ONE machine, via the Unity CLI's synchronous `eval` (not Burst, not a live interactive session — see scope limit 6). The RATIOS (near-zero second-loop cost, ~20x faster cached-vs-uncached over 24 repeats) are large enough and reproduced consistently across three separate audit runs in this session (with the CT0 bug present, after fixing it, and after adding CT10) to be a real signal rather than measurement noise, even though the exact millisecond figures will vary run to run and machine to machine.

**"Did I check the numbers I cited against the source myself, or trust the task body?"** Yes — `D:\CODEZ\AgentHQ\3D Shaper\project_document.py:75-82,148-152` and `public\index.html:975-985,1368-1378` were read directly via `Bash`/`sed` before writing `ShaperCacheBudget.cs`, not copied from the task description or from the T-0098 investigator reports (though they independently arrived at the same numbers, cross-checked as agreement rather than trusted as a source).

## Part 5 — the tilted-camera seam, self-checked against the task's own wording

The task body's exact requirement: *"Make this a SEPARATELY keyed, SEPARATELY budgeted cache node from day one -- so that when a document eventually tilts one layer, the other eleven layers that didn't tilt don't silently lose their responsiveness guarantee by being lumped into the same budget/cache key space as the expensive tilted one."* Checked against what was built: `ShaperTiltedCacheKey` is a different `struct` (not a type alias) so cannot be looked up in `ShaperNodeCache`'s `Dictionary<ShaperCacheKey,...>` even by accident (a compile error, not a runtime bug), and `ShaperTiltedResolveCache` is a wholly separate class with its own `MaxEntries`/eviction/counters, measured (CT6) to not share eviction pressure with the flat cache. No tilted-camera resolver was built (correctly out of scope per the task body: "You are not building tilted-camera support itself, just making sure today's cache architecture has a clean seam for it").
