## Part 0 — what already existed, and what did not

Wave 2/3 built the **compile/evaluate backbone**: `ShaperNode` (the authored tree) → `ShaperCompiler.Compile` (a recursive walk, cheap, O(nodes)) → `ShaperProgram` (one flat, immutable, post-order RPN op array) → `ShaperEvaluator.Distance`/`FillTile` (a flat per-pixel VM walk, no virtual dispatch, no allocation — Burst-shaped by construction). This is exactly right for a **final bake or a runtime spawn**: the whole tree genuinely needs evaluating once, and it already does so fast.

There is **no document/window/canvas-grid-renderer layer in Laubrary's own Shaper yet** — no `ShaperDocument`, no `ShaperWindow`, no authored resolution field, no per-frame animation timeline UI. This was verified by an exhaustive `Glob`/`Grep` of `Assets/Packages/Laubrary/Runtime/Shaper` and `Editor/Shaper` before writing any code; the only files that exist are the compile/evaluate backbone plus the fill/border/composite/swarm/effect systems the four prior Wave 3 tasks added. **This caching architecture is therefore built as a layer over the existing compile/evaluate pipeline, with clean seams for a future document/window/renderer to plug into — not as a feature bolted onto an editor window that does not exist.**

## Part 2 — the cache-key scheme

`Runtime/Shaper/ShaperNodeIdentity.cs` is the ONE place a `ShaperNode`'s identity becomes a `ShaperCacheKey` (two independent 64-bit FNV-1a lanes, deterministic across process restarts — not `System.HashCode`, which is randomised per process and would make a unit test's exact-key assertion unrepeatable).

**What is, and is not, part of a node's own identity.** `ShaperNode.mode` and `ShaperNode.blend` describe how a node folds into its PARENT — they change the parent's output, not the node's own buffer — so they are excluded from a node's own hash (`OwnHash`) and instead mixed in by the PARENT, per child, via `FoldChild`. This is a deliberate refinement over "hash the whole subtree in one pass": it is what lets editing a blend width on member 7 of 12 dirty the bag (the fold changed) while leaving member 7's own cached shape buffer untouched (its shape did not change) — closer to the letter of the task's own example ("editing the fill on layer seven... recomputes layer seven's fill and the composite, not layers one through six").

`ShaperNode.name` is excluded — authoring metadata, never a rendering input.

**Animation.** `ShaperCompiler.Compile(root, phase01, seed)` already threads `phase01`/`seed` into every primitive's own bake and every composite's own render. Rather than building per-node phase-sensitivity detection (a real optimisation that was considered and cut — getting it wrong in either direction is worse than always-correct), `phase01`/`seed` are folded into **every** node's own hash unconditionally. Cost: a cache entry per (node, phase) pair rather than one entry for a genuinely phase-invariant node. Benefit: this can never silently return a stale value for the wrong frame.

**Per node kind:**
- **Primitive** — kind, every `ShaperPrimitiveDef` field, including the three `ZUIValue` star fields (`starLength`/`starBaseWidth`/`starSkew`), plus the node's own transform/sweep/shell/swarm.
- **Composite (T-0112)** — reason, reasonNote, half-extents, bake resolution, plus the hosted `IShaperCompositeSource`'s own content hash. A source has no generic hashable contract, so an **optional** `IShaperCacheableSource.ContentHash()` capability (`Runtime/Shaper/ShaperCacheableSource.cs`) lets a source publish a precise hash — the same "declared capability, never assumed" posture `IShaperSwarmNativeSource` already takes (T-0113). A source that doesn't implement it falls back to reference identity + phase/seed, which is **correct for a fixed asset reference swapped for a different one, and wrong for a source mutated in place without its own reference changing** — a real, named gap (Part 5).
- **Bag** — its own transform/sweep/shell/swarm, deliberately **excluding** children (folded in separately, incrementally — see Part 3).
- **Swarm-modified node (T-0113), any kind** — the swarm def's fields (count, seed, jitter ranges, lifetimeStagger, interact, merge blend) fold into the node's own hash. Two key functions exist: `SwarmInstanceKey` (per-instance, stable across a growing count — designed but not wired into the built evaluator, see Part 3) and `SwarmWholeNodeKey`/`FullSubtreeStructuralKey` (the one the built evaluator actually uses).

**A real, found issue, not hypothetical (`ShaperNodeIdentity.IsCacheable`):** a `ZUIValue` in `Mode.MinMax` draws a fresh `UnityEngine.Random` sample on every `Evaluate()` call — it is **not** a pure function of its own settings. Caching such a node would either freeze the random roll forever (a hit replays the FIRST draw) or silently misbehave. `IsCacheable` detects this and the evaluator bypasses the cache for that node entirely (always recomputes, never stores) — measured in `ShaperCacheAudit.CT8`.

## Part 3 — per-node output caching (`ShaperNodeCache` + `ShaperCachedEvaluator`)

`Runtime/Shaper/ShaperNodeCache.cs` is the keyed store: `ShaperCacheKey → ShaperFieldBuffer` (a canvas-sized `float[]` distance buffer, plus the node's own canvas-space support box carried alongside it — see the Composite fix below for why). Plain `Dictionary` + O(entries) linear-scan LRU eviction above `MaxEntries` — correct and simple at this task's own measured scale (Part 6); a real O(1) LRU is a named, valuable follow-up, not a hidden gap.

`Runtime/Shaper/ShaperCachedEvaluator.cs` is the recursive, cached, PREVIEW-path evaluator, built **next to** `ShaperEvaluator` rather than replacing it:

- **Leaves (Primitive / Composite)** — compiled and evaluated as a **one-node subtree via the real `ShaperCompiler`/`ShaperEvaluator`** (`ShaperCompiler.Compile(node, parentForward, phase01, seed)` then `FillTile`), so a leaf's own math, sweep, shell and dilate are exactly production's, never reimplemented. Cache key = `OwnHash`.
- **Bag** — members folded **incrementally, in order**: each child is evaluated (recursively, cached), then combined into a running accumulator via the same public `ShaperOps.Combine` the compiler itself emits. Each PREFIX of the fold is cached under its own key (`ShaperNodeIdentity.FoldChild`, applied incrementally), so an unchanged prefix of members is a cache hit even when a later member changes — this is the mechanism that makes "editing member 7 recomputes member 7 and downstream, not members 1-6" literally true rather than a coarser "the whole bag recomputed, just quickly."
- **Swarm (T-0113), any kind** — one **atomic** cache unit for the whole swarmed subtree, evaluated via the real compiler's own swarm expansion (`EmitGenericSwarm`/`EmitNativeSwarm`), keyed by `FullSubtreeStructuralKey`. **Honest scope cut:** per-instance sub-caching (so growing a swarm's count from 5 to 8 reuses instances 0-4's own cache entries) was DESIGNED — `ShaperNodeIdentity.SwarmInstanceKey` exists and is proven stable under a growing count (`ShaperCacheAudit.CT4`) — but was **not wired into the built evaluator**, which uses the coarser atomic-whole-node path instead. Reason: reimplementing the per-instance jitter derivation outside the real compiler risks a formula mismatch bug that this task's remaining budget could not fully re-verify; reusing the real compiler's own swarm expansion is zero-risk. Still gets dirty-propagation right at the NODE level (editing this swarm's dial dirties this node+downstream, not siblings); it just doesn't get the finer per-instance reuse.
- **A Bag's own sweep/shell** — Radial sweep and Shell are implemented directly on the folded accumulator, per pixel, via the same public `ShaperOps.RadialWedge`/`Shell` the compiler's own evaluator case uses, ported from `ShaperCompiler.EmitSweep` (`ShaperCompiler.cs:840-912`). **Honest scope cut, and a real one:** a **Longitudinal** sweep authored directly on a Bag is NOT supported — it falls through unchanged (identity), which is **wrong output, not just unoptimised**. This is the rarer authoring pattern (axis is normally declared by a primitive child, SHAPER_THE_DESIGN.md B12); porting it correctly needs the child-box-carried-through-the-inverse arithmetic the real `EmitSweep`'s longitudinal branch uses, which this task did not port. Flagged explicitly, not silently accepted — see VERIFICATION.md for what a future task must do before this is safe to ship.

**A real bug found and fixed during this task, not hypothetical:** the first version of the leaf/swarm cache-hit path called `ShaperCompiler.Compile()` again on every hit just to read the node's support box — which for a **Composite node re-renders the hosted source** (`IShaperCompositeSource.Render`), exactly the expensive bake T-0112 caches once at compile time, silently defeating the entire point of caching that node. Fixed by carrying the box alongside the stored buffer (`ShaperFieldBuffer.boxCx/Cy/HalfW/HalfH`), so a hit never recompiles. Measured directly: `ShaperCacheAudit.CT5` instruments a fixture source's `Render()` call count and confirms exactly 1 call across 3 evaluations of an unchanged composite node.

**The one piece of production math this file duplicates, measured, not assumed:** the soft-Subtract "reach" band depends on an accumulated bounding box. The real compiler tracks this via a private `Box` type internal to `ShaperCompiler`; this file tracks its own plain axis-aligned-box union instead (built from each node's own canvas-space support extent, which `ShaperProgram.supportCx/Cy/HalfW/HalfH` already exposes for a leaf, and which this evaluator accumulates the same way for a Bag). `ShaperCacheAudit.CT10` compares the cached incremental evaluator's output against the real monolithic compiler+evaluator for a 2-member scene with a soft Subtract: **measured max |Δdistance| = 0.0000 canvas px across 6,144 samples** — exact agreement for the scene tested. Not proven to hold for every possible nesting/transform combination; a genuinely adversarial case (deeply nested bags, non-uniform scale, chained soft combines) was not constructed and tested — named honestly as unverified beyond what CT10 covers.

## Part 4 — per-frame animation caching (`ShaperFrameCache` + `ShaperFramePrebaker`)

This is **not a second cache** — `ShaperNodeIdentity` already folds `phase01` into every node's key, so frame 7 and frame 12 of an animation already live at different keys in the SAME `ShaperNodeCache` a live dial-drag preview would use. `Runtime/Shaper/ShaperFrameCache.cs` is a thin bookkeeping layer over it: a frame-index-to-phase01 mapping, a read-only `IsFrameCached` presence check that does **not** touch the cache's hit/miss counters or LRU timestamp (a UI indicator must not distort the very numbers it exists to help interpret, and must not keep a frame artificially warm against eviction just by being displayed — `ShaperNodeCache.ContainsKey` was added specifically for this), and `ComputeFrame`/`NextUncachedFrame` for actually doing the work.

`Editor/Shaper/ShaperFramePrebaker.cs` is the **non-blocking background pre-bake**, driven by `EditorApplication.update`: bakes frames one at a time, stopping early inside a tick once a caller-set time budget (`MaxMillisecondsPerTick`, default 8ms) is exceeded, resuming next tick. This is the ONE place the whole cache architecture touches `UnityEditor` — `ShaperFrameCache` itself has zero editor dependency, so a future runtime consumer (a coroutine-driven pre-bake at play time) can drive the identical `ComputeFrame` without this class at all.

**What "non-blocking" is, and is not, verified to mean (stated honestly in the class doc too).** Measured: each `Tick()` call returns quickly and the whole bake completes over many ticks rather than one (structurally — bounded per-tick work, resumable). **NOT measured:** whether a live, open, interactive editor session's frame pacing / input responsiveness is subjectively smooth while this runs across real wall-clock time. This task's own verification runs through the Unity CLI (`unity command eval`), which cannot drive a live interactive session to observe that. The architecture is built for it; a human walking a real animated document while this bakes in the background is the verification this task could not itself perform — flagged explicitly as the standard prior Wave 3 tasks (T-0114 in particular) already set for this kind of claim.

A **visible per-frame cached/not-cached indicator** is data-only, not a rendered UI control — there is no `ShaperWindow` to add one to (Part 0). `ShaperFrameCache.IsFrameCached(i)` / `CountCachedFrames()` is exactly the data a future window's indicator strip would read; wiring it into an actual UI is out of this task's scope because the UI itself does not exist yet.

## Part 5 — the tilted-camera seam (`ShaperTiltedResolveCache`)

No tilted (non-fixed) camera resolve exists anywhere in Shaper today — confirmed by the design's own citation (`P3 - Shaper internals...md` §2.3: arbitrary 3-D rotation is "not possible in this representation... structurally excluded" for the current height-field resolve). This task does not build one. It builds the seam:

- `ShaperTiltedCacheKey` — a **structurally distinct struct type** from `ShaperCacheKey` (not a type alias, no implicit conversion), so a tilted-resolve key can never be looked up in or stored into `ShaperNodeCache`'s dictionary — incompatible at COMPILE time, not by convention.
- `IShaperTiltedResolveSource` — the capability a future tilted-camera-aware resolver would implement (same "declared capability, never assumed" pattern as `IShaperCacheableSource`/`IShaperSwarmNativeSource`). No implementation exists.
- `ShaperTiltedResolveCache` — a separately-budgeted store (default `MaxEntries = 256`, an order of magnitude smaller than the flat cache's 8,192 default) with its own eviction, so a future tilted layer's much-more-expensive re-key (7-11x a flat resolve, per the design's own citation) cannot degrade the OTHER eleven untilted layers' responsiveness guarantee by sharing a budget/eviction policy with them.

`ShaperCacheAudit.CT6` measures the separation directly: filling one cache to its own cap and forcing an eviction does not change the other cache's `Count`, and the two key types are confirmed distinct via `typeof(...)`.

## Part 6 — the realistic-document cost model

Built exactly as named: a dozen (12) Bag-of-4-subshapes layers (`ShaperCacheAudit.BuildRealisticDocument`) = **61 total nodes** (12 bags + 48 primitives + the implicit root bag), matching the design's own "roughly 60 passes a frame before effects" estimate closely. Measured, not assumed (`CT9`): one full cold pass costs 108 node-computes (61 nodes plus fold-combine steps); 24 repeated "frames" with nothing authored changed between them cost **zero additional computes** after the first — cache genuinely collapses repeat-frame cost to nothing. Wall-clock, measured via the Unity CLI's `eval` (C#, not Burst, inside the editor's own process — the honest caveat every timing number in this report carries): 24 monolithic (uncached) passes ≈ 724-746ms; 24 cached passes ≈ 34-70ms (first pass pays the full cost, the other 23 are near-zero). This is exactly the shape the design predicts: "fine at these canvas sizes with caching... not fine without them."

## Part 7 — effect-stage cache keys (T-0114)

`Runtime/PyreShaper/ShaperEffectCacheKey.cs` provides the key scheme for `ShaperEffectStage.PreComposite`/`PostComposite` (T-0114): `Compute(inputKey, stage, effectTypeName, effectStateHash)`. **Honest scope limit, matching T-0114's own posture verbatim** (`ShaperEffectStageRunner`'s own class doc: "Deliberately standalone... wiring this stage split into the production compile pass is real, separate surgery this task does not take on"): this file provides the KEY SCHEME only. It does not modify `ShaperEffectStageRunner` to actually cache anything, because that runner is a proxy proof T-0114 built to demonstrate the pre/post distinction is real, not the production effect pipeline — there is no production effect-stage evaluator yet to wire caching into. A future task that builds one calls `Compute` with a real input key and a real per-effect state hash (each effect type publishing its own `ShaperCacheKey`, since `PixelModifier` subclasses have no shared reflection-free hashable contract — the same "declared capability" answer used throughout this task rather than a fragile generic reflection hasher).
