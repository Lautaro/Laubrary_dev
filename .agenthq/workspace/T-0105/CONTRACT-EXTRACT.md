# T-0105 contract extract — what binds the shape stage

**Distilled from BUFFER_CONTRACT.md (T-0102), SHAPE-TREE-RULES.md (T-0103) and SHAPER_THE_DESIGN.md (T-0098), 2026-08-30.** This is the binding spec for a first shape-engine implementation. Fills, borders, lights, extrusion/bevel, Tapestry, swarms, caching and UI are out of scope and are not extracted here except where a shape-stage rule references them for context. Every clause below carries its rule ID; treat the ID as the citation to put in code comments.

---

## A. The node contract

**BC-1.1 — block call, not per-point.** "A generator MUST be able to fill any rectangular tile of the sample grid, given only that tile's origin and size, by writing into flat arrays of primitive numbers supplied by the host. A generator MUST NOT be invoked once per sample through a managed callback, virtual method or delegate." A shape node is asked to fill a rectangular tile `(x0, y0, w, h)` of the sample grid in one call, writing `w` contiguous values per row for `h` rows into host-supplied flat arrays (BC-1.2) — never "what is at 4,7?" through a per-sample callback. The tile MAY be the whole grid; per BC-1.2 the generator must not be able to tell the difference (tile independence, BC-1.6, is the conformance test — bit-identical output whether rendered as one tile or a prime-sized decomposition).

**BC-2.1 — the output is a sampled function, not a picture.** "A shape node's output is defined as a function evaluated at a point in the node's own local space. The published sheets are that function *sampled*, never the shape's definition. No stage before the resolve may read the screen-space neighbours of an intermediate buffer." So the per-tile call still evaluates a point-wise implicit field at each grid sample within the tile; BC-1's block shape is the *calling convention*, BC-2's implicit-field rule is the *semantics* of what gets computed per sample.

**What is returned — coverage is mandatory, everything else is declared-optional.** Design C3: "Every shape node publishes, per pixel: **coverage** — soft and unbounded, a fog rather than a stencil; optionally **height**; optionally a set of **named quantities** it declares." BC-3.1 makes the same point as the closed vocabulary: "A shape node declares which it publishes." Coverage is not one of the nine declared-optional quantities — it is the one thing every node, primitive or bag, always publishes (SHAPE-TREE-RULES R5: "Every node publishes coverage, and a *consumer* names the node it reads"). `edgeDistance` (signed distance) is optional and is what lets a node combine in the distance domain (R6) rather than the coverage-only domain.

**Both a distance and a coverage exist, and they are different quantities with different obligations.** `edgeDistance` (BC-3.3 #3) is the signed field a primitive MAY publish; `coverage` (BC-3.3 #1) is what every node MUST publish. R6: "A generator declares which domain it combines in. One that can publish a signed field combines in the distance domain and gets the full blend width. One that publishes only a fog declares itself **coverage-only**." And: "Combining happens on signed distance, not on coverage… coverage is derived from the combined distance at the end." **Gap, not resolved by these three documents:** none of the three specifies the actual smoothing kernel/width used to turn a *single primitive's own* final signed distance into its 0..1 coverage value (i.e. the base antialiasing step). R6 only specifies the *combine*-time smoothing (the two-knob blend width/profile, `smoothMinShaped`, applied when merging two operands' distances). The primitive→coverage conversion at the leaf, and the final combined-distance→coverage conversion at the top of a fold, are asserted to happen but the transfer function is not given anywhere in Wave 1. Flag this for the implementer to either propose (e.g. a one-pixel-wide smoothstep in canvas units) or ask about before locking it in code.

**Sign convention.** BC-3.3 #3: "**signed**, layer-local units. **Negative inside, positive outside, zero on the boundary** (the standard SDF convention, and the reference app's own…)." Pyre's *existing* `BorderInsideDistance` is the opposite polarity (grows inward, unsigned) — BC-3.3 explicitly calls this out as a defect the new convention corrects, not a precedent to follow.

**Coordinate frame and units.** BC-3.3: "Coordinate frame for every one of them is the **layer's own local space**, right-handed, +Y up, origin at the layer's own origin. Not the screen. Not flipped." Units for a leaf primitive are its own local units; R2 then requires every node to rescale its *published* distance into canvas pixels on the way back up the tree by multiplying by `minStretch(M)` at each transform level ("Every node publishes its distance rescaled into canvas pixels… **this is the rule that makes everything else compose**"), specifically so R6's pixel-authored blend width means the same thing regardless of nesting depth or scale. See G.5 for the one place this interacts awkwardly with BC-3.3's flatter wording.

**What "publishes coverage" requires concretely — BC-3.7, publishing hygiene, six clauses, each fixing a named defect in today's code:**
- **BC-3.7a — declared, not discovered:** the published set is declared statically before any render; the host allocates only declared, requested sheets.
- **BC-3.7b — always available, never debug-gated:** if declared and requested, a sheet is produced in normal operation (today's planes exist only under a debug sink — forbidden going forward).
- **BC-3.7c — non-destructive:** "Publishing hands over a view, not ownership. A sheet is readable any number of times by any number of consumers" (today's `PublishFields` nulls its own fields on hand-off — forbidden).
- **BC-3.7d — one coordinate frame:** BC-3.3's frame, for every quantity, from every generator, no exceptions.
- **BC-3.7e — one definition per name:** "`coverage` means occupancy at the sample, before any layer-alpha multiply and before any style curve. A form whose internal alpha is something else converts, or declares `coverage` unpublished."
- **BC-3.7f — host-allocated, host-owned:** the generator never allocates, replaces, resizes or frees a sheet.

## B. The nine named per-pixel quantities (BC-3.3)

All nine are the **shape node's** responsibility to publish (declared per-node); nothing here comes from fill, border, or any later stage — those are consumers only, per BC-3.2 ("A shape publishes no colour at all, ever"). BC-3.2 also carves out three things a fill is handed that are **not sheets and not shape responsibility**: the instance index and its own life (per-instance scalars in the parameter block), the document clock, and the shape-local sample coordinate (it *is* the sampling point, returned by the resolve query, BC-2.2).

| # | Quantity | Status | Existed today? |
|---|---|---|---|
| 1 | `coverage` | Partial promotion, conversion work | 4 of 9 composites publish an "alpha" plane, debug-gated, 3 frames, 4 incompatible definitions |
| 2 | `height` | New as a published quantity | Existed only as a cross-layer matte channel derived from finished-pixel luminance; never published by a shape |
| 3 | `edgeDistance` | Partial promotion, semantic change (unsigned→signed, polarity flips) | Only as `BorderInsideDistance`, unsigned, chamfer-approximate, opposite sign convention |
| 4 | `heat` | Promotion | Published as `"H"` by 6 forms |
| 5 | `density` | **New as a distinct quantity** (BC-3.4 decision) | Did not exist separately — `"H"` doubled as both heat and density |
| 6 | `soot` | Promotion, narrow | Published as `"T"` by only 2 form families |
| 7 | `depth` | **New construction** | No plane by this name/meaning; identically zero until extrusion exists (T-0109) |
| 8 | `age` | **New construction** | No per-pixel age exists anywhere (per-*instance* age exists and is a different thing) |
| 9 | `surfaceDirection` | **New construction — and mandatory** (BC-3.6) | Published by nothing; computed-and-immediately-collapsed-to-a-scalar in five places today |

**Marked "does not exist yet" outright:** `depth`, `age`, `surfaceDirection` (all "New construction"); `density` is new *as a distinct quantity* (BC-3.4). `coverage`, `height`, `edgeDistance` are partial promotions requiring conversion work, not new construction, but also not drop-in ports. `heat` and `soot` are the closest to already-existing.

## C. The tree rules a shape engine must implement now

**R1 — combine modes.** Three modes exist, not four: "Add, Subtract, Intersect — each with the blend width of R6… Intersect is new: neither tool has it today." The combine mode lives **on the member**, not the bag: "A bag holds an ordered list of children; each child carries its own mode. The bag itself carries no mode." Fold order is authored data and immutable: "**No stage may reorder a bag's members.** Not to batch the additive ones, not to group by generator, not to improve cache locality, not to skip ahead." Direction: "The bottom of the list is evaluated first and is the base of the silhouette; each member above it applies onto the accumulated result." The leading-non-Add rule: "The accumulator starts empty, so a bottom-most member set to Add gives itself, and a bottom-most member set to Subtract or Intersect gives nothing… our addition is not a change of behaviour, it is **a UI flag**: a leading non-Add member is marked with the reason shown." Implementation note: use an explicit empty-accumulator sentinel, not a magic large number (3D Shaper's `1e6` is called out as a latent collision risk).

**R2 — the transform block.** Components: "translate, rotate, scale, skew, **origin**." Exact composition order, quoted: **"composed `T · P · R · S · K · P⁻¹`, and apply it by transforming the sample point down the tree rather than transforming the shape up it."** (T=translate, P=pivot/origin translate, R=rotate, S=scale, K=skew, P⁻¹=inverse pivot.) Inverse point-chaining: the block's sample points are pushed down through each node's inverse matrix; every primitive still answers over a plain run of points in its own local space — this is required to stay compatible with BC-1's block-fill contract (rasterising-and-resampling each child instead would break both BC-1 and the bound composition below). Pitch/yaw are explicitly excluded from this transform: "Pyre's `shapePitch`/`shapeYaw` bake a perspective scalar and belong to B7's extrusion and resolve stage. The shape tree's transform is strictly 2D affine." Distance rescale: "Only the sample point travels down in local space. Every node publishes its distance rescaled into canvas pixels, by multiplying by `minStretch(M)` — the *smallest* singular value of the linear part of its matrix — at each level on the way back up." `minStretch`, not `maxStretch`, because it is the conservative (never-overstate) choice; `maxStretch(M)` is reserved for the support-extent box only (a different, new, second declaration — see D). Singular-matrix rule: "A singular transform publishes nothing… A member whose linear part has a determinant below epsilon publishes empty coverage and is flagged." A bag itself also carries a transform applied to the whole assembly before reaching members.

**R5 — every node publishes coverage.** "There is no mask role. **Every node publishes coverage**, and a *consumer* names the node it reads." This is what dissolves the old writer/consumer mask exclusivity: coverage references are cheap (shape-stage-only dependency), luminance references are expensive (depend on the full resolve — fill, border, pre-composite). Two independent orders exist and must not be confused: the **fold order** (authored, immutable, what R1 protects) versus the **resolve order** (topological over the reference DAG, governs *when* each node's coverage is computed) — "R1's prohibition on reordering binds the fold order only, and says nothing about the resolve order." A cycle in the reference graph must be refused at edit time with the offending edge named.

## D. The Lipschitz / bound rule

**Corrected assertion form, quoted exactly (BC-4.2):** "The multiplier belongs on the *true* side: **`reportedDistance ≤ declaredBound × trueDistance`**, i.e. the primitive promises never to over-state by more than its declared factor, and the march's safe step is **`reportedDistance / declaredBound`** — which is exactly the one division B7 prices the whole guarantee at." The prior (wrong) draft asserted `declaredBound × reportedDistance ≥ trueDistance`, which BC-4.2 calls vacuous: since the only defect is *over*-estimation, `reportedDistance ≥ trueDistance` already holds by construction, so multiplying the reported side by any bound ≥ 1 only makes a true inequality truer — a primitive that over-states by 50× would pass a declared bound of 1.5 just as easily as one that over-states by 1.5×.

**What the bound means.** BC-2.6: "Every primitive MUST declare a bound on how far it may over-state its own edge distance, and every transform and combination MUST compose those bounds." It is a *ratio*, carries no spatial information (R2 is explicit that a support-extent box cannot be derived from it — it's a separate, second, new declaration). Cost if declared at authoring time: "one number carried per node and one division — on the order of twenty lines." Cost if retrofitted: "the only remaining safe march costs roughly forty times as much."

**How a transform node composes its child's bound.** Because R2's `minStretch` rescale already absorbs the transform's effect on distance, the bound passes through **unchanged**: "a member publishes `bound_child` — the same number — and a bag publishes the maximum over its members." I.e. a transform node does not inflate the bound at all; it is identity on the bound value (the rescale is what keeps it sound), which R2 states explicitly is *why* the rescaling belongs in R2 rather than R6.

**How each combine mode composes children's bounds.** The rule stated in R2 is: **"a bag publishes the maximum over its members."** R6 confirms this rule survives soft combining too, and shows why with an algebraic argument: differentiating the soft-min expression `smoothMinShaped` gives weights on its two arguments that are non-negative and sum to exactly one for every profile setting `n` — a convex combination — so "the gradient magnitude of the result never exceeds the larger of its inputs'. Hard min, max and negation preserve the same property. So R2's rule — a bag publishes the maximum bound over its members — holds through soft combines as well as hard ones, for every profile setting." This applies uniformly across Add, Subtract and Intersect (hard or soft) — the docs do not give a *different* composition rule per mode; max-over-members is the one rule for all of them.

**Safe march step.** `reportedDistance / declaredBound` (BC-4.2, quoted above) — this is the one division the whole guarantee is priced at (B7/BC-1.4: a tilted resolve using this scheme costs "roughly seven to eleven times a flat one," measured on the simplest case; curved tops, bevels and the stepped-profile family cost more or, for stepped profiles, cannot be bounded at all — B7/BC-2.6 flags that family as a known exception requiring its own treatment in the extrusion task, T-0109, not this one).

**`subtractSoft` needing an explicit rather than derived bound.** **Not found as a rule in any of the three documents — the documents state the opposite.** R6 explicitly proves the max-over-members composition "holds through soft combines as well as hard ones, for every profile setting," and separately proves "a Subtract member never enlarges a bag's box even with a soft seam" (the analogous statement for the support-extent, R7). Nowhere is a soft/hard distinction made for the *bound* specifically, and nowhere does the text call for `subtractSoft` to declare its own bound independent of the derived max-over-members rule. If T-0105's own task brief asserts this requirement, flag it back as a discrepancy against SHAPE-TREE-RULES R6/R2 (see G) rather than silently implementing an undocumented exception.

## E. B12 — sweep and shell

Verbatim from the design: **"Both are cheap, both are universal, and — importantly — neither requires touching any primitive's formula. They are two operators applied to the finished shape:**
- **Sweep** — keep only a wedge of the shape, from a start angle across an extent. At full extent nothing is removed. This is your arc control.
- **Shell** — keep only a band at a given distance from the surface, discarding the interior. At its identity setting it does nothing. This is your 'remove from the middle outwards', and it gives you rings, tubes, frames and, combined with sweep, actual arcs."

They are explicitly operators on the *finished* shape (post-combine, applied to the resolved node), not per-primitive formula changes — "neither requires touching any primitive's formula."

**Identity settings are bit-identical, quoted:** "Applied as operators, **all eight primitives gain both at once, and at their identity settings the output is bit-for-bit what it is today.**" I.e. sweep at full angular extent and shell at its no-op setting must reproduce today's un-swept, un-shelled primitive output exactly — this is a literal bit-identity requirement, not "looks the same."

**Shell vs. the naive scaled-copy alternative.** The design deliberately rejects "subtract a scaled-down copy of the shape from itself" (what the existing Ring's inner-radius actually does) in favor of Shell, because a scaled copy gives non-uniform wall thickness on non-radially-symmetric shapes ("thick at the ends and thin in the middle") whereas Shell keeps constant wall thickness. Note this as a real behavioral difference from Ring's existing inner-radius control, to be treated as a new/different feature, not a rename.

**A primitive declares whether its sweep runs around it or along its length.** Quoted: "The one genuinely awkward family is the long thin *primitives* — the capsule, the line, the streak shape — where sweeping by angle around the centre produces a meaningless bowtie… The fix is one line in the design: **each primitive declares whether its sweep runs around it or along it.** Hub-shaped things sweep angularly; line-shaped things sweep along their length. Same two controls, same UI, sensible result either way." This is a per-primitive declared boolean/enum, analogous in spirit to the per-primitive bound (BC-2.6) and support-extent (R2/R7) declarations — a third thing every primitive must state about itself.

**One side note not to miss:** "shelling changes what 'inside' means for everything downstream. A shelled dome becomes a tube. That is almost certainly what you want, but it falls out of the maths rather than being chosen, so it should be tested deliberately rather than discovered" — i.e. edgeDistance / coverage semantics for consumers (fill, border) must be re-verified against a shelled node, not assumed to carry over unchanged, even though that's a downstream (non-shape-stage) concern.

## F. Explicit prohibitions

- **BC-1.1:** a generator "MUST NOT be invoked once per sample through a managed callback, virtual method or delegate."
- **BC-1.3, Burst-hostility list — named illegal today's-code patterns, do not port the shape of any of these:** per-pixel virtual dispatch (`ApplyPixel`, `InverseWarp`); per-pixel dereference of a managed object holding a `Gradient`; reflection with boxing in the frame path (`Invoke(post, new object[]{...})`); `new System.Random(...)` or `[ThreadStatic]` state inside a generator's inner loop (a job kernel cannot address either); per-layer per-frame buffer allocation (`new Color32[...]`, `.Clone()`, `new float[...]`). Also: "No delegate crosses the boundary" (BC-1.2) — a value funnel must be evaluated *into* the parameter block up front, never called from inside the per-tile loop.
- **BC-2.1:** "No stage before the resolve may read the screen-space neighbours of an intermediate buffer." (Neighbourhood work in the shape's *own* declared domain is legal per BC-2.4; neighbourhood work on an intermediate screen-space buffer is not.)
- **R1:** "No stage may reorder a bag's members. Not to batch the additive ones, not to group by generator, not to improve cache locality, not to skip ahead." Fold order is part of the document's meaning and part of every cache key.
- **BC-3.1:** a consumer needing an unpublished quantity is "greyed out with the reason shown — never hidden, never silently inert." (A UI/consumer-side rule, but binds how a shape node must expose its declared set.)
- **BC-3.3 / vocabulary closure:** "The vocabulary of named per-pixel quantities is closed at nine… Extending the vocabulary is a design decision requiring a new task, not a new string literal." Private, non-vocabulary values a generator computes internally (today's `ramp_t`, `rim_mix`, `C`) "may not be given vocabulary-looking names," and no standard fill may depend on them.
- **BC-3.7f:** "the generator never allocates, replaces, resizes or frees a sheet" — sheets are host-owned.
- **BC-2.3 API-shape prohibition:** "A caller MUST NOT be able to tell that v1 only handles one direction by the shape of what it calls." I.e. do not build a straight-down-only entry point alongside/instead of the general ray-query signature — implement the general signature now, specialise only the body.

## G. Contradictions

1. **Combine-mode count.** Design B2/C3: four modes ("add, cut out, keep only the overlap, blend softly"). SHAPE-TREE-RULES R1/R6: three modes (Add/Subtract/Intersect) plus a blend-width/profile dial applicable to any of them — "'Blend softly' becomes a property every mode has rather than a fourth mode." **Flagged by SHAPE-TREE-RULES itself as departure #1**, reversible "at the cost of inheriting the overload or reinventing it." **Governs: R1/R6** — it is the later, argued, Wave-1-locked decision, and the design's own four-mode wording is pre-investigation.

2. **Masking mechanism.** Design C2: "Masking is unchanged in principle from today: a layer may contribute its silhouette to a shared channel and a later layer may read it." SHAPE-TREE-RULES R5: drops the role enum and the shared mutable channel entirely in favor of per-node coverage planes and consumer-side references. **Flagged by SHAPE-TREE-RULES itself as departure #2**, and R5 additionally says: "This is the largest departure in the document, and no owner ruling exists on it," offering an explicit cheaper fallback (keep the role enum, permit combined draw-plus-write, fix only read-before-write ordering) "in case this is more change than wanted." **Governs, provisionally: R5's full version** — it is the one item in this whole extract where the authoring document itself says owner sign-off is outstanding; a shape engine built against R5 should still expect this could be walked back to the fallback and should not hardwire the DAG-reference model somewhere that a role-enum revert would be expensive to unwind.

3. **"Every node is a pass over the canvas."** Design B2 ("every node is a pass over the canvas — which is what the caching rules in B9 exist to contain") and B9's own phrasing treat a node as an unconditional full-canvas pass. SHAPE-TREE-RULES R7 corrects this: "a node costs one pass over the pixels it can affect" (bounded by a new, separate support-extent declaration), calling the premise "not true today, and should not become true." **Flagged as departure #3, called a correction rather than a disagreement. Governs: R7** — explicitly the more accurate reading of both the current code and the intended cost model, and it is what makes the support-extent declaration (§D) a hard requirement rather than optional.

4. **Units/frame for published distance at the point of publication.** BC-3.3 states the coordinate frame for every quantity (including `edgeDistance`, `height`) is "the layer's own local space… in layer-local units," with no mention of a rescale. R2 (written to close exactly the composition question BC-3.3 didn't yet address) requires every node to rescale its published distance into **canvas pixels** via `minStretch(M)` on the way up through each transform, specifically because a pixel-authored blend width (R6) would otherwise mean nothing under nesting/scale. These are not stated as being in tension by either document, but read literally they use different unit language for the same published value. **Governs: R2's canvas-pixel rescale** at every node's publish boundary — R2 was written later in the same Wave specifically to reconcile transform composition with BC-3.3's vocabulary, cites the composition requirement as its explicit reason, and BC-3.3 predates the tree/transform mechanics entirely (T-0102 authored before T-0103 closed B2/C3's open questions). Implementer should treat "layer-local units" in BC-3.3 as meaning "canvas pixels once rescaled per R2," not as a separate, un-rescaled convention.

5. **`subtractSoft` bound (task-brief vs. source documents).** The T-0105 brief handed to this distiller asks specifically what the buffer contract says about `subtractSoft` needing an *explicit* rather than *derived* bound. No such requirement exists in any of the three documents — R6 proves the opposite (derived max-over-members composition holds for all combine modes, soft or hard, per §D). **Governs: the documents as written** — treat this as either a misremembered detail in the brief or a requirement introduced somewhere outside these three files; do not implement an undocumented special case for `subtractSoft` without checking back, since adding one would silently contradict R6's proven composition rule.
