## Design assumptions that are FALSE

1. **`WrapRow` is NOT a shared `Z.*` factory.** `DOTGEN-DESIGN-DECISIONS.md` §6 lists it in the same breath as `Z.HGroup`/`Z.Row` ("`WrapRow`/`Z.HGroup`/`Z.Row`") as if it were part of the ZUI toolkit surface to inventory. It is a **private 5-line helper local to one window**: `Assets/Packages/Laubrary/Editor/Launimator/LauminationBuilderWindow.cs:400-405` — `private static VisualElement WrapRow(params VisualElement[] children) => { var row = Z.Row(children); row.style.flexWrap = Wrap.Wrap; return row; }`. There is no `Z.WrapRow`. DotGen must either write the same two-line pattern inline wherever it needs a wrapping row, or (better, since two other tools would want it too) add a real `Z.WrapRow(...)` to `Zui/Toolkit/Zui.cs` and note it in `zui.md`. Not a blocker — trivial to add — but the design doc's phrasing implies a control that does not exist.

2. **DotGen's Editor asmdef table names a reference set that does not match what "copy `PyreEditor.asmdef`'s reference list" actually produces.** §1's Editor-folder row says: "references the runtime asmdef, **ZUI.Editor**, ZuiRuntime, AssetKit editor, BackSplash editor, **PreviewKit** — copy `Editor/Pyre/PyreEditor.asmdef`'s reference list and prune." The real file, `Assets/Packages/Laubrary/Editor/Pyre/PyreEditor.asmdef`, has this exact `references` array: `com.Lautaro-Arino.Laubrary.SpriteFx`, `com.Lautaro-Arino.Laubrary.Pyre`, `com.Lautaro-Arino.Laubrary.AssetKit.Editor`, `com.Lautaro-Arino.Laubrary.Zui.Editor`, `com.Lautaro-Arino.Laubrary.ZuiRuntime`, `com.Lautaro-Arino.Laubrary.BackSplash`, `com.Lautaro-Arino.Laubrary.BackSplash.Editor`, `Unity.TextMeshPro` — it references **`com.Lautaro-Arino.Laubrary.Zui.Editor`** (the UI Toolkit `Z.*` factory assembly), **never the bare `"ZUI.Editor"`** (the legacy IMGUI assembly), and it has **no direct `PreviewKit` reference at all** (PreviewKit reaches it transitively through `AssetKit.Editor`, which itself references `com.Lautaro-Arino.Laubrary.PreviewKit` — see `Assets/Packages/Laubrary/Editor/AssetKit/AssetKit.Editor.asmdef`). Pyre is fully UI-Toolkit-native (confirmed: `zui.md:30`, "Migrated tools so far: … and Pyre (fully native control surface)"), so it never needs the legacy IMGUI assembly at all. DotGen, being built the same way ("Use ZUI in the same way that Pyre is made"), should copy Pyre's ACTUAL list — i.e. drop the design doc's literal "ZUI.Editor" reference and either add PreviewKit directly (harmless, more explicit) or rely on the AssetKit.Editor transitive reference like Pyre does. See Q8 below for the exact list DotGen needs.

3. **Pyre (`Runtime/Pyre/Pyre.cs`) does not itself implement `IVisualPreview`**, despite the design doc using "the same class-named-as-tool shape as `Laubrary.Pyre.Pyre`" as the model for DotGen's asset class, which is asked to "Implement `IVisualPreview`". `Pyre.cs:1182` is `public partial class Pyre : ScriptableObject` with no `IVisualPreview` in its base list, and there is no `RenderPreviewTexture`/`CanAnimatePreview`/`UpdateAnimatedPreview` anywhere in `Runtime/Pyre/`. Pyre instead uses the OLDER per-window pattern: `PyreWindow` (editor) overrides `RenderThumbnail`/`AnimateThumbnails`/`UpdateAnimatedThumbnail` (`Editor/Pyre/PyreWindow.cs:40,45,52`) — exactly the pattern `IVisualPreview.cs`'s own doc comment (`Runtime/PreviewKit/IVisualPreview.cs:5-7`) says the interface exists to REPLACE. Real (if partly stubbed) `IVisualPreview` implementers to copy instead: `TextSplash` (`Runtime/TextSplash/TextSplash.cs:655,992-997` — implements the interface but `RenderPreviewTexture()` returns `null`, i.e. not yet wired to a real render), and `ChunkSpec`/`Zoe`/`Tileset`/`Prop`/`LevelTile`/`AmmoDef`/`WeaponDef`/`LauminaryVersion` (grep hits, not read in depth here — worth a closer look by W1.1 for a fully-wired example before designing DotGen's own).

## 1. `ZuiReflect` (`Zui/Toolkit/ZuiReflect.cs`)

- **`[Range]` float** → `Zui/Toolkit/ZuiReflect.cs:322-330`: bounded → `Z.MicroSlider(nice, (float)v, range.min, range.max, tip, nv => Set(nv), opt.ControlWidth, showValue: true)`; unbounded → `Z.Field(nice, tip, Z.Float(...))`.
- **`[Range]` int** → `ZuiReflect.cs:332-339`: same shape, `decimals: 0`, setter rounds with `Mathf.RoundToInt`.
- **`defaultValue` is NOT passed** in either call (confirmed: the 8th positional param of `Z.MicroSlider`, `float? defaultValue = null`, is simply omitted at both call sites, so it stays `null`). This means **double-click reset currently does nothing** for any field ZuiReflect draws — `ZuiMicroSlider`'s reset only fires `if (e.clickCount == 2 && _default.HasValue)` (`Zui/Toolkit/ZuiMicroSlider.cs:180`), and `_default` is `null` here. This is exactly the open question `DOTGEN-DESIGN-DECISIONS.md` §4 flagged ("W0.1 checks whether ZuiReflect already does") — **answer: it does not.** W1.2 must add a `defaultValue:` argument at `ZuiReflect.cs:328-329` (float) and `:337-338` (int) — and also the wrapped-float fallback at `:472-473` — computed from a fresh `Activator.CreateInstance(owner.GetType())` instance's same field, per §4's plan. There is no existing helper that does this; W1.2 is greenfield here.
- **`[Tooltip]`** → `ZuiReflect.TooltipAttributeOf` (`ZuiReflect.cs:737-741`), read via `Attribute.GetCustomAttribute(field, typeof(TooltipAttribute))`. Precedence in `BuildField`: `opt.TooltipFor?.Invoke(field) ?? TooltipAttributeOf(field) ?? "<generated fallback>"` (`ZuiReflect.cs:286-287`).
- **Enums** → `ZuiReflect.EnumControl` (`ZuiReflect.cs:48-74`). Non-`[Flags]` enums always render as **`Z.MiniRadio(sel, labels, tooltip, onChanged, wrap: true)`** (`:71-73`) — **there is no Segmented-vs-MiniRadio option-count threshold in ZuiReflect**; it is unconditionally a wrapped MiniRadio regardless of how many members the enum has. `[Flags]` enums render as `Z.SegmentedMulti` over the single-bit members (`:56-68`). The design doc's blanket rule ("Z.Segmented for ≤3 options on one line, Z.MiniRadio otherwise", §4) is **not what ZuiReflect does today** — it applies only to controls DotGen hand-builds itself (e.g. the Placement Method switch, which the design doc already says is hand-built: "Method (Z.MiniRadio over the registry)"). Any enum field left to a reflected module card (Selectors/Mutators/Drawers bodies) will always come out as wrapped MiniRadio, never Segmented, unless W1.2/W2.2 changes `EnumControl` to add a length check.
- **bool** → `Z.Toggle(nice, tip, (bool)v, nv => Set(nv))` (`ZuiReflect.cs:341-342`).
- **Color** → `Z.Field(nice, tip, Z.Color((Color)v, tip, nv => Set(nv), 110f))` (`ZuiReflect.cs:356-357`) — confirms `Z.Color` exists (see Q4).
- **string** → `Z.Field(nice, tip, Z.TextInput((string)v ?? "", tip, nv => Set(nv), opt.ControlWidth))` (`ZuiReflect.cs:344-345`).
- **`[ZUIShowIf("field", "Value1", "Value2", ...)]`** → attribute defined at `Zui/Scripts/Runtime/ZUIShowIf.cs:28-42`, global namespace (no `using` needed). Value-name syntax: `Values` compared against the sibling field's `.ToString()`, case-insensitively (`ZUIShowIf.cs:34`; enums by member name, bools "True"/"False"). Gating logic lives in `ZuiReflect.VisibleNow` (`ZuiReflect.cs:174-184`) and **fails OPEN** — an attribute naming a field that no longer exists shows the control rather than hiding it (`ZuiReflect.cs:173,179`). Redraw hook: `ZuiReflect.IsGate`/`s_gateCache` (`ZuiReflect.cs:186-201`) records which field names are read by some `[ZUIShowIf]` on the type; `BuildField`'s internal `Set()` calls `opt.OnStructureChanged?.Invoke()` whenever the edited field is itself a gate (`ZuiReflect.cs:298-300`) — so the HOST only has to supply `Options.OnStructureChanged`, which every module-card host already needs for its own add/remove/reorder rebuilds.
- **`[SerializeReference]` lists**: `ZuiReflect.cs` has **no special-case handling** for a `List<T>` where `T` is an abstract/polymorphic `[SerializeReference]` base type. Its generic `List<>` branch (`ZuiReflect.cs:519-520` → `BuildList`, `:540-637`) calls `Activator.CreateInstance(elemType)` for a null/new element (`:610`, `:630-631`), which **throws for an abstract element type**. A SINGLE polymorphic `[SerializeReference]` field (not a list) is handled by a different class, `ZuiManagedRef` (`Zui/Toolkit/ZuiManagedRef.cs`), which works off `SerializedProperty` (needs a `SerializedObject`, not raw reflection) and shows a header (fold caret + title + a type-switch button popping a `Z.Menu` — `ZuiManagedRef.cs:97-117`) over a caller-filled body. **This confirms DotGen's own plan is correct**: `DOTGEN-DESIGN-DECISIONS.md` §4 already has Selectors/Mutators/Drawers built as hand-rolled card lists with their own `+ Selector`/`+ Mutator`/`+ Fill drawer` `ZuiMenu` (see Q6), NOT drawn through `ZuiReflect.BuildList` — that plan sidesteps the gap. `ZuiReflect.BuildFields`/`FlowFields` are still the right call for the FIELDS *inside* one already-resolved concrete module (e.g. a `GridPlacement`'s own scalar fields), just not for the polymorphic list membership itself.
- **`Options`** (`ZuiReflect.cs:96-119`): `OnBeforeChange` (the `Undo.RecordObject` hook, fired inside `Set()` before the field write, `:294`), `OnChanged` (fired after, `:296`), `OnStructureChanged` (list/gate rebuild hook), `TooltipFor`, `Skip`, `FloatWrapperProperty`, `ConfigureValue` (per-field `ZUIValue` tuning), `ControlWidth` (default `150f`, `:118`). **There is no "label width" option** — labels auto-align per scope via `ZuiLabelAlign` (confirmed by `ui-layout-rules.md:97`; not something `ZuiReflect.Options` exposes).
- **One Undo per drag**: `Options.OnBeforeChange` is called on EVERY pointer-move during a drag (via `ZuiMicroSlider.SetValue` → `_onChanged` → `ZuiReflect`'s `Set()` → `opt.OnBeforeChange?.Invoke()`, `ZuiMicroSlider.cs:111` + `ZuiReflect.cs:294`), so `Undo.RecordObject` genuinely fires many times per drag. It still collapses into ONE visible Undo step because the CONTROL itself brackets the whole pointer-down-to-up gesture in `ZuiUndoGesture.Begin()`/`End(group)` (`ZuiMicroSlider.cs:155-169`, calling `Zui/Toolkit/ZuiUndoGesture.cs:19-32`, which does `Undo.IncrementCurrentGroup()` on begin and `Undo.CollapseUndoOperations(group)` on end) — so a host gets "one Undo per drag" FOR FREE from any ZUI drag control; it does not need to suppress repeated `OnBeforeChange` calls itself. Worked host wiring to copy: `Editor/Pyre/PyreWindow.Modifiers.cs:327-334`, `ModifierDrawerOptions(PyreModifier m, Action rebuild)` → `OnBeforeChange = () => Undo.RecordObject(spec, "Edit Pyre Plus modifier")`, `OnChanged = () => { EditorUtility.SetDirty(spec); MarkDirty(); }`, `OnStructureChanged = rebuild`.

## 3. `ZuiFill` (`Zui/Scripts/Runtime/ZuiFill.cs`) + `ZuiFillControl`/`Z.Fill`

- **Two-colour linear spatial gradient with an angle: YES, directly.** `ZuiFill.Mode.Linear` (`ZuiFill.cs:29`) + `public Gradient gradient` (a `[SerializeReference] ZuiGradient gradientAnim` companion also exists but a plain 2-key `Gradient` is enough for "two colours") + `public float angleDeg` (`:78`, "Linear: rotation of the fill axis, in degrees") + `public Vector2 center`/`centerXAnim`/`centerYAnim` (`:94,105-107`) + `public float zoom` (the gradient's spatial SIZE, `:89`) + `public FillSpace space` / `FillFit fit` (`:111,114`). `ZuiFill` itself is in the **global namespace** (no `namespace` block in the file) and has **no `UnityEditor` dependency** — safe to call from DotGen's Runtime assembly.
- **Per-pixel evaluation API**: `public Color Evaluate(float life, float u, float v)` — `ZuiFill.cs:167`. `life` is a 0..1 over-life clock (DotGen can pass a constant, e.g. `0f`, for a still). **`u`/`v` are in `-1..1`**, NOT `-0.5..0.5` — DotGen's POC-derived "local −0.5..0.5 space, half-diagonal-extent rule" must be converted before calling `Evaluate`, either by hand (multiply by 2) or via the companion helper `public Vector2 Normalize(Vector2 p, Vector2 origin, Vector2 half)` (`ZuiFill.cs:125-134`), which already implements exactly this kind of box-to-`-1..1` mapping (`FillFit.Uniform` divides both axes by `Mathf.Max(half.x, half.y)` — a "largest half-extent" rule closely matching a half-diagonal-extent convention; `FillFit.Stretch` divides per-axis). **Conclusion for the design decision's open question**: (b) DOES have a clean per-pixel API, so DotGen's renderer can call `fill.Evaluate(life, u, v)` directly (via `Normalize`/`NormalizeUV` for the box mapping) — the `DotGenFillEval` fallback helper described as a contingency in §2 is **not needed**.
- **Solid mode** ignores gradient/angle entirely and returns `color` (`ZuiFill.cs:173-174`) — this is DotGen's Flat case.
- **Pyre's `backgroundFill` per-pixel evaluation** — `Runtime/Pyre/PyreRenderer.Layers.cs:124-143`, `PaintBackground(Color32[] buf, Pyre spec, int W, int H, float life)`: for every `(x,y)` in the full `W×H` buffer, `v = (y+0.5)/H*2-1` (`:130`), `u = (x+0.5)/W*2-1` (`:134`), then `buf[rowBase+x] = (Color32)spec.backgroundFill.Evaluate(life, u, v)` (`:135`). This maps the WHOLE frame independently per axis into `-1..1` (equivalent to `FillFit.Stretch` over the full canvas, not a half-diagonal/uniform circle rule) — a simpler convention than what the POC/DotGen wants for a per-shape fill; DotGen's own renderer needs its own mapping (half-diagonal, per generator-area box) rather than copying this exact formula verbatim, though the "evaluate once per pixel, call `.Evaluate(life,u,v)`" SHAPE is identical.
- **`Z.Fill`**: `public static ZuiFillControl Fill(string label, ZuiFill fill, string tooltip, Action onChanged, Action onBeforeMutate, ZuiFillControl.Options options = null)` — `Zui/Toolkit/Zui.cs:885-892`, constructs `new ZuiFillControl(label, fill, options, tooltip)`. The control's mode-switch menu (`ZuiFillControl.cs:584-587`, `AddFillItem(menu, "Solid colour", ..., ZuiFill.Mode.Solid)` / `"Linear gradient"` / `"Radial gradient"`) maps 1:1 onto DotGen's planned Flat/Gradient split — DotGen's Fill drawer card should embed `Z.Fill(...)` directly rather than hand-rolling a colour-pair UI, exactly as `DOTGEN-DESIGN-DECISIONS.md` §2 already plans.
- **Recommendation** (concrete): DotGen's `DotDrawer.Fill` field is a `ZuiFill fill` (+ `List<ZuiFill> fills` for the random-from-list drawer variant per §2); the card draws it with `Z.Fill(...)`; DotGen's renderer, per target shape, computes `origin` (shape centre) and `half` (the POC's half-diagonal-extent value) in its own local units, calls `fill.Normalize(point, origin, half)` to get `(u,v)` in `-1..1`, then `fill.Evaluate(0f, u, v)` (DotGen is a still picture — `life` is always `0f`/irrelevant unless a future runtime player is added per §8.7).
