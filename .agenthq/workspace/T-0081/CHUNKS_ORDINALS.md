## Task 2 — D-06: stale/unresolved `layerName` shows nothing latched

This defect's ONE occurrence inside my scope is `ChunkWindow.Layers.cs`'s `BuildLayerAssignRow` (the "Modules" box radio, used by every module row — Splash/Fragments/Pyre Spawn/Formation and every blast group). Neither `ChunkWindow.Timeline.cs` nor `ChunkWindow.PyreMotion.cs` contains a layer-slot picker at all (Timeline schedules WHEN things fire, not WHERE they draw; PyreMotion has no depth concept), so D-06 does not recur in either of those two files — confirmed by grepping both for `layerName`/`MiniRadio` (no hits).

What changed, mirroring `ChunkWindow.Slicer.cs`'s `BuildSlicerLayerPick` (read-only, lines ~226-244) exactly:
- Slicer's shape: build a LOCAL copy of the declared slot names, and if the stored value doesn't resolve (`IndexOf < 0`), append it to that local copy (`"(none)"` if blank, the raw stored string otherwise) and select that appended entry — so the radio shows the true stored state instead of nothing.
- Applied the same shape in `BuildLayerAssignRow`: a new `radioNames`/`radioSel` pair, separate from the real `names`/`sel` the rest of the function still uses. When `sel < 0` and the stack has at least one declared slot, `radioNames = names + ["(none)" or cur]` and `radioSel` points at that new last entry. The `Z.MiniRadio` call now renders `radioNames`/`radioSel` instead of the bare `names`/`sel`.
- **One deliberate improvement over Slicer's literal pattern, not asked for but a straightforward safety fix**: Slicer's setter is `m.layerName = options[v]` unconditionally, which means re-clicking the synthetic `"(none)"` entry when the module was previously blank would write the literal string `"(none)"` into the asset. My version guards this: the click handler returns early (no-op) when `i >= names.Count`, i.e. when the synthetic entry itself is clicked again — only a REAL declared slot index reaches `set(...)`. This does not change what the user sees (the synthetic entry was already selected; clicking it again is visually a no-op either way) — it only prevents a latent write-the-placeholder-text bug that exists in the Slicer file today (I did not touch Slicer — it's read-only — so that latent bug still lives there; flagging it for the PM as a possible follow-up, not something I fixed).
- The real stack (`c.layers.layers`, i.e. `names`) is never mutated by this — `radioNames` is a fresh `List<string>` built per-row, per-rebuild. `resolved`, `blank`, and the "New slot…"/"+ Add…" fix-button logic further down the same method still read `sel` (the real, unaugmented resolution), not `radioSel` — confirmed by re-reading lines ~531-556 after the edit: a stale value still correctly offers "+ Add "<name>"" / the fix-button flow, exactly as before. Only the RADIO's own rendering changed.
