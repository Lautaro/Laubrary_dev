# T-0081 — a chunk asset's thumbnail now says what the chunk does

Single file changed: `D:\UNITY\Laubrary Dev\Assets\Packages\Laubrary\Runtime\Chunks\ChunkSpec.cs`. No serialized field was added, removed or renamed; no other file was touched; nothing was compiled or run (no Unity editor access by design — see "Not verified" at the end).

## What was wrong

`RenderPreviewTexture()` consulted only the legacy fields (`animationSource`, `sampleSource`, `sprites`) and then fell through to `ProceduralSwatch()`, which drew 14 squares of a fixed size from a fixed seed (17). It was structurally blind to every Chunks 2.0 module — `fragmentSlicer`, `particleSplash`, `pyreSpawn`, `blastGroups` — which is where a modern spec's whole identity lives. Consequence: every art-less spec rendered a byte-identical scatter varying only by `colorOverLife`, and `Floating Disc Blowup` — whose identity is a Floating Disc shattering in front of three layered blasts — rendered as generic white squares.

## The new precedence chain, and why it is in this order

Resolved in exactly one place, the new private `ResolvePreviewSource(out IVisualPreview animated, out Sprite still)`, deliberately mirroring the "one place decides precedence" discipline that `FragmentSlicerModule.ResolveSource()` already establishes in this module.

1. **Animated chunk content** — `animationSource as IChunkAnimation as IVisualPreview`. Top because this is literally what every individual chunk plays; if it is set, nothing else is a more accurate picture of the burst. Unchanged from the previous behaviour, so no existing spec's thumbnail regresses.
2. **What the Fragment Slicer cuts apart** — `fragmentSlicer.sourceVisual` when it implements `IVisualPreview`, otherwise `fragmentSlicer.ResolveSource()` as a still. Second because for a "**X** blows up" recipe, **X** is the answer to "what is this chunk?" — the blasts are the staging, the thing coming apart is the subject. This is the tier that fixes the flagship asset. The animated source is preferred over the raw sprite because it can also drive the animated thumbnail; when it exists but cannot render itself, this tier sets BOTH outputs so the still (its own first frame, via the slicer's own resolver) is still available as a fallback.
3. **Authored debris art** — `sampleSource`, then the first non-null entry in `sprites`. Third and unchanged in relative order, because the brief is right that this path was already correct for a plain debris spec. (Only refinement: `sprites` now takes the first *non-null* entry rather than blindly `sprites[0]`, so one empty leading slot no longer costs the whole thumbnail.)
4. **The Particle Splash sprite** — `particleSplash.sprite` when that module is enabled. Fourth: a splash-only spec has real art authored on it, and showing it beats a swatch.
5. **The blast** — first enabled group's `source`, else that group's first non-null `pool` entry, scanning `pyreSpawn` first and then `blastGroups` in authored order. Last of the real tiers because a blast is what happens *around* the subject; for a pure-blast spec (tiers 2–4 empty) it IS the effect, and that is exactly when it wins.
6. **`ProceduralSwatch()`** — the never-blank floor, now spec-derived (below).

Two rules run through the whole chain. **A module only contributes when it is `enabled`**, so a thumbnail can only ever show something the burst will actually produce — a dormant, half-authored module cannot lie about the effect. **Nothing in the chain is random**: tier 5 pointedly does not call `PyreSpawnModule.PickSpawner()`, which rolls a die across the pool and would make the thumbnail change on every rebuild.

## Per-asset hand-trace, all four surviving demo specs

Traced by reading each `.asset`'s YAML directly against the new code. `Sparks`, `WallDebris` and `SampledDebris` are pre-Chunks-2.0 serializations: their YAML contains no module fields at all, so every module deserializes to its C# field-initializer instance with `enabled = false`.

**`Assets\Demos\ChunksDemo\Sparks.asset`** — `animationSource` absent, `fragmentSlicer.enabled` false, `sampleSource` absent, `sprites: []`, `particleSplash.enabled` false, `pyreSpawn.enabled` false, `blastGroups` empty. Lands on **tier 6, the swatch**, with `IsComposedEffect` false so no glow. Seed = FNV-1a("Sparks"). `countMin 12 / countMax 22` → 17 pieces. `spreadDeg 180`, `directionDeg 90` → a full ring. `sizeMin 0.06 / sizeMax 0.16` → 2–3 px squares. **The user sees:** a dense full-circle spray of many fine warm-cream→orange grains.

**`Assets\Demos\ChunksDemo\WallDebris.asset`** — identical structure, same tier. Lands on **tier 6, the swatch**, no glow. Seed = FNV-1a("WallDebris"). `countMin 8 / countMax 14` → 11 pieces. `spreadDeg 32`, `directionDeg 60` → every piece confined to a 28°–92° wedge, i.e. a tight diagonal jet up and to the right. `sizeMin 0.1 / sizeMax 0.24` → 2–4 px squares. **The user sees:** a sparse, clearly *directional* jet of pale-blue→slate shards. Distinct from `Sparks` on four axes now (tint, count, piece size, and above all the silhouette: wedge vs ring), where before it differed on tint alone.

**`Assets\Demos\ChunksDemo\SampledDebris.asset`** — `sampleSource: {fileID: 0}` (genuinely null in the asset; `ChunksDemoSpawner.cs:77` assigns it at runtime from `DemoSprites`, so there is no authored art to show and no way to show one), `animationSource: {fileID: 0}`, no module fields. Lands on **tier 6, the swatch**, no glow. Seed = FNV-1a("SampledDebris"). `countMin 10 / countMax 18` → 14 pieces. `spreadDeg 180` → a ring. `sizeMin 0.35 / sizeMax 0.6` → **5–7 px** squares. **The user sees:** a coarse rubble field of big chunky white blocks. Same ring silhouette as `Sparks` but roughly triple the piece size and a different colour and arrangement — reads as "big slabs" against Sparks' "fine grit". This is the weakest of the four differentiations and the one worth a look by eye.

**`Assets\Demos\ChunksDemo\Floating Disc Blowup.asset`** — `animationSource: {fileID: 0}` → tier 1 skipped. `fragmentSlicer.enabled: 1`, `fragmentSlicer.sourceVisual` = guid `df6d774acf094b948b983102c9ef9a34` = `Assets\Zoetrope\Floating Disc.asset`, a `Laubrary.Zoetrope.Zoe`, which implements `IVisualPreview` (`Runtime\Zoetrope\Zoe.cs:13`) as well as `IChunkAnimation` (`Runtime\Zoetrope\ZoeChunkAnimation.cs:26`). **Tier 2 wins**: `animated` = the Zoe, `still` = its first frame as a backstop. **The user sees:** the actual Floating Disc artwork — and because `Zoe.CanAnimatePreview` is `PreviewSprites().Length > 1`, a browser that animates thumbnails will play the Disc's own animation at `Zoe.PreviewFps`. Its three blasts (`pyreSpawn.source` = `Old School Explo 2 Plus`, two `blastGroups` entries = `Proper Blast`) are correctly *not* what the thumbnail shows; they are what happens around the subject. Note this asset has `countMin/countMax: 0` — it emits no plain debris at all, so under the old code it was drawing a swatch of debris it does not even throw.

**No two of the four land on the same branch with the same appearance.** Three land on the swatch but with different seeds, different piece counts, different piece sizes and (for `WallDebris`) a different silhouette; the fourth leaves the swatch entirely for real artwork.

## How determinism is preserved

The original guarantee came from a literal `17`, which is also precisely what made every spec look the same — one constant carrying both properties. The fix derives the constant from the spec instead of dropping it. `SwatchSeed()` is a hand-rolled FNV-1a over `name` (the asset's own file name), **not** `string.GetHashCode()`, which is randomised per process on some .NET runtimes and would have reshuffled thumbnails between editor sessions — reintroducing the exact flicker the fixed seed existed to prevent. The result is masked to a positive int (`& 0x7fffffff`) because `System.Random(int.MinValue)` is a trap. Every other input to the swatch (`countMin/Max`, `sizeMin/Max`, `directionDeg`, `spreadDeg`, `colorOverLife`) is serialized authored data, so a given asset renders byte-identically on every rebuild; only renaming the asset — a deliberate act, not a rebuild — changes its scatter. Tiers 1–5 are likewise fully deterministic: no `Random`, no `PickSpawner()`, list scans in authored order.

## How the never-blank guarantee is preserved

Four separate places, all deliberate. (a) `RenderPreviewTexture()` treats a delegate that returns `null` (an unbuilt Zoe, a zero-frame blast) as if it had never been picked, falling through to the still and then to the swatch, so a broken delegate can never surface as a blank square. (b) `SpriteToTexture()` still returns `null` for a non-readable texture and that `null` is still absorbed by `?? ProceduralSwatch()`. (c) The swatch clamps its piece count to a minimum of 3 even for a zero-count spec, so a pure-blast recipe (`Floating Disc Blowup` has `count 0/0`) cannot produce an empty canvas. (d) The swatch forces `c.a = 1f` on every square: a gradient authored fully transparent would previously have painted an invisible scatter, which is a blank thumbnail by another route (the per-chunk alpha ramp is `alphaOverLife` anyway, not this gradient, so nothing truthful is lost). `RenderPreviewTexture()` therefore has no `null` return path at all any more.

The texture-ownership rule is also intact: nothing is cached and no reference to a returned texture is retained. The swatch allocates a fresh `Texture2D` per call; a delegated texture is the delegate's own fresh allocation, handed straight to the caller. `ChunkSpec` holds no field pointing at either.

## Fallback swatch — what it now encodes

Kept deliberately small: the goal is "two different chunks look different", not a simulation. It reads five things the spec already knows. **Seed** from the asset name (arrangement). **Piece count** from `(countMin + countMax) / 2`, clamped 3–24. **Piece size** from `sizeMin..sizeMax`, mapped from world units onto a 1–7 px side, so a spec throwing half-unit slabs reads chunky and one throwing 0.06-unit sparks reads as grit. **Silhouette** from `directionDeg` + `spreadDeg`, so a 32° jet no longer looks like a 180° radial burst. **Tint** from `colorOverLife`, as before. Plus one binary marker: a spec where any content-producing module is enabled (`IsComposedEffect`) gets a soft radial glow behind the scatter, so a composed effect that still had no renderable art never reads as an unconfigured debris spec. None of the four demo specs triggers the glow (three are plain debris; the fourth never reaches the swatch), so it is exercised only by other library assets.

## The animated-preview trio

This was a real latent inconsistency, now closed. `CanAnimatePreview`, `PreviewFps` and `UpdateAnimatedPreview` previously delegated to `AnimationSource` while `RenderPreviewTexture` had its own logic; all four now call `ResolvePreviewSource` and use the single `animated` delegate it returns. Without this, `Floating Disc Blowup` would have shown the Disc's still frame from tier 2 while the trio reported "cannot animate" (its `animationSource` is null) — or, in the reverse case, a browser would paint one asset's motion over another asset's still. That second case is not merely cosmetic: `Pyre.UpdateAnimatedPreview` writes frames in with `tex.SetPixels32(frameTex.GetPixels32())`, which throws outright on a size mismatch (`Zoe`'s equivalent uses `PreviewTex.BlitInto`, which refuses a mismatch quietly). A `tex == null` guard was also added to `UpdateAnimatedPreview`.

## Risks the PM must check by eye

1. **`SampledDebris` vs `Sparks` are the closest pair.** Both are full-ring scatters; they are separated by piece size (5–7 px vs 2–3 px), count (14 vs 17), colour (white vs orange) and seed. On a small thumbnail that should read clearly as "big rubble" vs "fine grit", but it is the one pairing where I would want a human's eye on the actual browser grid.
2. **`Floating Disc Blowup` depends on `Zoe.PreviewSprites()` returning frames in edit mode.** It is the same path Zoetrope's own browser uses, so it should be fine, but if that Zoe has no built view the thumbnail degrades: first to the Zoe's own first frame as a still, then to a glowing composed swatch. Confirm it actually shows the Disc.
3. **Residual trio hole, pre-existing and not regressed.** If a delegate reports `CanAnimatePreview == true` but its `RenderPreviewTexture()` returns `null`, `RenderPreviewTexture` correctly falls back to a 32×32 swatch while the trio still animates from the delegate — and `Pyre`'s implementation would then throw on the size mismatch. For both real implementations this cannot happen (`Pyre` returns null only when it has no frames, i.e. `CanAnimatePreview` is already false; likewise `Zoe`), and the old code had the identical shape, so I left it rather than adding a per-repaint `try/catch` that would mask genuine errors. Worth knowing if a third `IVisualPreview` implementation is ever added.
4. **Piece-size mapping constants** (`0.05`–`0.5` world units → 1.5–7 px) are a judgement call tuned against the four demo specs' ranges. A library spec authored far outside that window will simply clamp to 1 px or 7 px, which is fine but flat.
5. **Renaming a chunk asset reshuffles its swatch arrangement.** Intended and documented in the code, but it means a rename visibly changes the thumbnail of an art-less spec. Using the GUID instead would avoid it but requires `AssetDatabase`, which is editor-only and cannot be referenced from this Runtime assembly.
