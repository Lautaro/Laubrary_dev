## W2.2 — the card contract

The shell builds the four sections ONCE (in `BuildCards`) and never touches their bodies again. Each owns a body host; the four rebuild methods clear their own host and refill it. **Rebuild a BODY, never the flow.**

```
ZuiSection placementSection  → VisualElement placementHost
ZuiSection selectorsSection  → VisualElement selectorsHost
ZuiSection mutatorsSection   → VisualElement mutatorsHost
ZuiSection drawersSection    → VisualElement drawersHost
```

Entry points — replace these four bodies and nothing else:

```csharp
void RebuildPlacement()
void RebuildSelectors()
void RebuildMutators()
void RebuildDrawers()
```

All four are called from `RefillSelectionSections()` in that order, then `MarkDirty()`. They are called on load, on selection change, after add / duplicate / delete / reorder, and after a reset. **Each must tolerate `doc == null`, a null selected generator, and being called twice in a row.**

Gizmo targeting state (window-only, never persisted):

```csharp
string hoveredModuleId;    // set from a card root's PointerEnter/Leave via HoverModule(id) / HoverModule(null)
string selectedModuleId;   // set from a card header click via SelectModule(id); null means "the generator's own area"
void HoverModule(string moduleId);   // repaints the preview when the gizmo mode is Hovered
void SelectModule(string moduleId);  // repaints the preview when the gizmo mode is Selected
```

The shell clears `selectedModuleId` whenever the selected GENERATOR changes, so a stale id can never point into another generator.

Editing helpers already on the window — use these, never mutate the document directly:

```csharp
DotGen doc                                                  // the document (may be null)
void Dirty(Action apply, string label = "Edit DotGen")      // RecordObject -> apply -> SetDirty -> invalidate
void DirtyRepaintOnly(Action apply, string label = "…")     // for edits that change only how it is looked at
void MarkDirty()                                            // the picture is stale
Action Record(string label)                                 // the onBeforeMutate half for a drag-bracketing control
void Applied()                                              // the commit half of that pair
ZuiMicroSlider Dial(string label, float value, float min, float max, string tooltip,
                    Action<float> set, float defaultValue, int decimals = -1, float width = 150f)
ZuiMicroSlider DialInt(string label, int value, int min, int max, string tooltip,
                       Action<int> set, int defaultValue, float width = 150f)
void RefillSelectionSections()                              // all four bodies + the Generator card
void RebuildTree()                                          // the hierarchy rows
void RefreshChrome()                                        // zoom readout, gizmo readout, legend
```

`ZuiReflect.Options` for a reflected module body, exactly as Pyre wires its modifiers:

```csharp
OnBeforeChange     = Record("Edit DotGen")
OnChanged          = Applied
OnStructureChanged = <the card's own rebuild>   // a [ZUIShowIf] gate changed, so the body must redraw
```

`ZuiMicroSlider` brackets its own drag (`ZuiUndoGesture`), so one drag is one undo step for free, and `ZuiReflect` now passes the type default so a double-click restores it (T-0227). No extra wiring.

Ids are minted by the DOCUMENT, never by a module: `doc.NewId("place" | "sel" | "mut" | "draw")`. A new instance comes from `DotModuleRegistry.Create(entry)`, which sets its default name and leaves the id blank.

## W2.3 — the gizmo hook

`DotGenWindow.Preview.cs` declares

```csharp
partial void DrawGizmos(Rect frame, float scale);
```

and calls it on **Repaint only, after the frame texture is blitted**. W2.3 creates `DotGenWindow.Gizmos.cs` containing

```csharp
namespace Laubrary.DotGen.Editor
{
    public partial class DotGenWindow
    {
        partial void DrawGizmos(Rect frame, float scale) { … }
    }
}
```

**This binding was verified live** (a throwaway implementation in a second file compiled and was called on repaint, then deleted). A partial method with no implementation costs nothing — the call is removed by the compiler — which is why the shell ships with no gizmo file at all.

### Coordinate convention — read this before drawing anything

The evaluator works in frame-normalized coordinates: **(0,0) is the frame's TOP-LEFT corner, (1,1) its bottom-right, y increasing DOWNWARD**, matching the reference implementation (which is what makes `DotAnchor.Bottom` grow an area upward). Use the window's own mapping, never your own arithmetic:

```csharp
Vector2 FrameToScreen(float x, float y);   // frame (0..1, y down)  ->  screen points
Vector2 FrameToScreen(Vector2 p);
Rect  frameRect;    // where the unit frame currently sits on screen (square)
float frameScale;   // frameRect.width — points per frame unit; multiply any normalized LENGTH by this
```

`frameRect`/`frameScale` are refreshed on EVERY event, not only on repaint, so a hit test taken during a drag agrees with the last thing drawn.

What to read:

```csharp
DotGenResult Result { get; }   // the last evaluation; null until the preview has repainted once
```

`Result.order` is in hierarchy order; `Result.For(gen)` gives one generator's `areas` / `baseDots` / `finalDots` / `traces`. Never re-run the pipeline from a gizmo — the traces exist so the overlays cost nothing.

Modes come from `doc.gizmoMode` (`Hovered` / `Selected` / `All` / `Off`), targeting from `hoveredModuleId` / `selectedModuleId` / `doc.selectedGeneratorId`. Per POC §13.1 the Generator Area gizmo stays limited to the SELECTED generator even in All mode.

## Decisions made in this task

1. **The renderer was drawing every picture upside down, and I fixed it in the runtime** (`DotGenRenderer.Render(…, Color32[] buf, …)` now ends with `FlipRows`). Measured, not guessed: a root area anchored `Top` evaluates to `cy = 0.25` and rendered into the BOTTOM quarter of the texture, because a `Color32` buffer is read bottom-row-first by both `SetPixels32` and `EncodeToPNG`. Every anchor meant its opposite and the export was mirrored too, so this had to be fixed in the one place both paths share rather than papered over in the preview. Verified after the fix: `Top` → mean texture row 47.5 of 64.
2. **Selection is not an undo step.** `selectedGeneratorId` is document data (the window reopens on it) and is written with `SetDirty` but no `Undo.RecordObject`; recording it would make Ctrl+Z walk back through clicks instead of through changes.
3. **Frame size does not rebuild the section.** No control's range depends on it (the design's "rebuild on commit" was for a derived range, and there is none), so it re-renders live like any other dial; the readout follows because readouts refresh from the evaluation, not from the edit.
4. **"New seed" comes from `DateTime.UtcNow.Ticks % 999999`**, per the brief — no `System.Random`/`UnityEngine.Random` anywhere in the DotGen assemblies.
5. **The wheel-zoom exponent is rescaled to Unity's delta units.** The reference's `exp(-deltaY × 0.0015)` assumes a browser's ~100-per-notch deltas; Unity reports ~3, so the constant is `0.05` — one notch is the same 0.86×/1.16× step it is in the reference. Transliterated, not changed.
6. **A tree row is one row plus a subtle metadata line beneath it**, matching the reference's two-line row, rather than one dense line — at a 360 px pane a placement name plus two counts plus the name does not fit on one line at any depth.
7. **`Reset to demo` carries no ellipsis**, matching the base window's own `Delete`: the confirmation is a courtesy (the reset is undoable), not a second place where the real choice is made.
8. **`WritePng(path)` and `ApplyDemoReset()` are split out of the two dialog-owning commands**, so the write and the restore can be exercised without a modal panel — which is how both were verified here.
