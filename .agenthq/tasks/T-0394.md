## Description

**Owner request (2026-09-21), while separately investigating the "still sub-pixel" thread (T-0390..T-0393, all landed).** A new authoring mode for `PaletteSplash` (`Runtime/Chunks/Capabilities/PaletteSplash.cs`), specified as 4 numbered requirements — treat each as a real spec item, not a suggestion:

1. **Sample real image pixels, not solid color.** Today `PaletteSplash` spawns procedural white `ChunkSprites` shards (1-3px, just fixed in T-0393 to never downscale below native) tinted by a sampled palette COLOR. This request wants an alternative mode where each particle is instead a real 1-5 pixel CROP cut directly out of the source sprite's own texture (like `SampledChunkSprites.Sample`, already used by `DebrisScatter`'s `Sampled` visual — read that as the closest existing precedent) and flung as-is, full detail and all, not reduced to a flat tinted square.

2. **Optional edge masking to transparency.** The sampled crop can optionally have its edges masked out (irregular/rounded alpha falloff instead of a hard rectangle), so a sampled chunk doesn't read as a crisp little rectangle of the source art but as a softer/organic fragment. Needs an author toggle plus presumably a strength/radius dial — design the specific authoring surface, but it must be OFF by default (hard-edged crop) so existing behavior of anything that reuses this code path is unaffected until explicitly turned on.

3. **Sampling radius centered on the hit point, not the whole sprite's footprint.** Today's footprint-based emission (`emitFromFootprint`) picks source pixels from ANYWHERE in the sprite's opaque area. This new mode instead samples only from within an author-set RADIUS around `ctx.Position`/the hit point (in the sprite's own local/texture space) — so the effect reads as a localized "the bullet hit HERE and this patch of pixels came loose," not a spray sourced from random pixels anywhere on the character. Explicitly call out: the radius can extend past the sprite's edge (partially off-canvas hit) or sit fully inside it — both must degrade gracefully (a radius mostly off-canvas should still sample whatever opaque pixels DO fall inside it, and produce nothing silently-broken if literally none do — same "never silently no-op" floor `PaletteSplash`'s own class doc already commits to for its existing tiers).

4. **Optional edge tinting by a named gradient (Rust / Blood / Charred, etc.).** Pixels at or near the edge of the sampled crop (or perhaps the edge of the whole affected radius — decide and document which, this is a real design call) can optionally be tinted by blending toward a gradient/preset color scheme, simulating scorched/wounded edges. Needs: a toggle, a way to pick a preset OR author a custom gradient (check whether `Z.Color`/ZUI gradient authoring already exists in this project before inventing a new one — CLAUDE.md's ZUI section notes `Z.Color` exists and gradient UI has prior art in Pyre's gradient-fill work, search for it), and a blend-strength dial. Named presets (Rust/Blood/Charred) should be a small fixed set of `Gradient`/color-ramp assets or hardcoded default gradients an author can pick from, not something requiring them to hand-author a gradient from scratch every time — but a full custom-gradient override should also remain possible.
