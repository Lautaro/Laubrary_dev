## Description

Step 3 of the build plan from `D:\UNITY\Laubrary Dev\ZOE_PALETTE_BUILD_PLAN.md` (task 3 — read that file and `D:\UNITY\Laubrary Dev\ZOE_PALETTE_TAKE.md` in full before starting; T-0093 depends on this).

The "ask a character to show this named state" mechanism already exists and is already used (`ReactionFxPlayer.Raise`, matched against `Zoe.events` / `NamedReaction` entries via `Zoe.EventNamed`). This task is about making it safe to build the rest of the palette model on top of. Cover, at minimum:

- Generate an always-up-to-date code-side list of a character's valid state names, regenerated automatically when the character asset is saved (not a manually-maintained list) — a rename must not be able to silently go stale.
- A missed/misspelled name request should report loudly what the character *does* have, not fail silently. Some of this already exists (one raise path already warns by name and the editor already badges it) — check what's there before rebuilding it, and close the actual gap, which is that the warning doesn't list available alternatives and a direct code request's failure is easy to miss.
- Make name-matching consistent — state names currently compare case-sensitively while other authored names in the same editor window ignore case; pick one and make it consistent.
- Carry position and facing direction through with a state request (currently a request like the weapon "Fire" raise arrives with no position/direction, so any effect on that row falls back to the character's anchor point instead of the intended location).
- Make the stun setting on a reaction actually get read and obeyed (it currently exists as an authorable field but is silently ignored except in one specific situation).
- Make asking for a state by name always resolve to a whole reaction card (animation + duration + flash + effect list), never just a bare animation clip — there is an existing feature elsewhere in the toolkit that loses exactly this information; do not repeat that mistake here.

Two changes here will be visibly different to existing projects once this ships: effects on a fire state will start landing at the weapon's muzzle instead of the character's center, and a stun value typed into a custom event will start being obeyed for the first time (having never been enforced before, existing authored values haven't been vetted — check them before this reaches other projects).
