## Description

**Owner escalation (2026-09-21), after a screenshot proved tiny sub-pixel specks were still showing up post T-0390..T-0393:** "LOOK! AT THIS POINT JUST SHOW ME YOU CAN MAKE DEBRIS WHERE NO PARTICLE IS SMALLER THAN THE SET PIXEL SIZE!!!! That is your priority now."

**Root cause of what the screenshot showed:** the tiny debris were NOT from `UC4 Zoe Spray.asset` (what T-0390..T-0393 all targeted) — they were from `Assets/Zoetrope/Floating Disc.asset`'s own PRIVATE, hand-authored Hit-reaction `ChunkSpec` (a `DebrisScatter` capability, `visual: Sampled`, `sizeMin: 0.16`, `sizeMax: 0.35`), which has its own authored `sizeOverLife` envelope that shrinks each debris chunk down to ~17% of its base size by roughly a quarter of its lifetime (and very likely further toward the end). 0.16 units × 0.17 ≈ 0.027 units — well under one game pixel (1/16 = 0.0625 units at this project's PPU). This is a DIFFERENT bug from anything T-0390..T-0393 touched: a per-frame runtime shrink, not a static PPU-governance or shape-fitting issue.

**Already fixed, by hand, this session — a hard floor, not a per-recipe toggle:**

`Runtime/Chunks/Chunk.cs`, `ApplyLook(float t)` (the per-frame size/colour/alpha evaluator every `DebrisScatter`-spawned `Chunk` runs): after computing `scaleX`/`scaleY` from `baseScale * sizeMul` (and tumble squash, if active), both axes are now clamped to a hard minimum: `1f / PixelScaleProjectSettings.Instance.pixelsPerUnit`, converted to a local-scale value via the chunk's own native `spriteUnit` (now stored as a field, previously a local-only variable in `Init`). This applies UNCONDITIONALLY, to every `DebrisScatter`-spawned chunk in the whole project, regardless of any recipe's own `sizeOverLife` curve, tumble squash, or authored `sizeMin` — the floor always wins. Uses the PROJECT's global PPU specifically (not any per-capability override), since "one game pixel" is meant as one pixel of the actual game screen, the same floor every PPU-governance fix today already established as the shared reference point.

A parallel, still-in-flight task (T-0394, a new "bullet hole" sampling feature for `PaletteSplash`) was messaged mid-flight to apply the equivalent floor to `PaletteSplash`'s own particle sizing — check whether that has landed by the time you start; if `PaletteSplash.cs` still floors its particle-size roll at `0.1f` instead of `1f` (or an equivalent), flag it, but do NOT fix it yourself if T-0394 is still actively working that file — coordinate via AgentHQ/SendMessage rather than editing over an in-flight parallel task.

**Details:**

That curve drops each debris chunk to about 16.8% of its size by a third of the way through its life and then HOLDS it there for the rest of the life - so a chunk spends roughly three quarters of its existence tiny.

At 16 pixels per unit, one game pixel is 0.0625 units. The recipe's smallest debris was rendering at 0.430 of a pixel, and even its LARGEST debris was rendering at 0.941 of a pixel. So every single chunk this recipe can spawn was sub-pixel, not just the small ones. On top of that, the tumble effect was squashing each chunk's width through literally zero several times a second.

Now there is a hard floor in the code that no recipe, curve or authored value can get under. It only ever pushes a too-small particle UP to one pixel; it never shrinks anything that was already fine - that was checked separately and a full-size chunk comes back completely untouched.
