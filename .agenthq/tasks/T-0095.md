## Description

Step 6 (round 3's step 3 — "the model") of the build plan from `D:\UNITY\Laubrary Dev\ZOE_PALETTE_BUILD_PLAN.md` (task 6). This is the actual new feature this whole design effort has been building toward. Read `D:\UNITY\Laubrary Dev\ZOE_PALETTE_TAKE.md` (round 3) and `D:\UNITY\Laubrary Dev\ZOE_PALETTE_BUILD_PLAN.md` (round 4) in FULL before starting — this task cannot be done correctly from this short description alone, the design docs contain the actual architecture, the rejected alternatives, and why. Depends on T-0090, T-0091, T-0092, T-0094 all landing first (see those tasks and the build plan doc for why).

Scope, at minimum:

1. **The role chip.** A three-way tag on a declared named state: nothing special / this is a hurt look / this is a death look. Defaults to "nothing special" so nothing currently authored changes meaning. This is what makes a state a legal answer to Laubrary's two built-in questions (see point 3). Placement: the chip lives on the data for custom/authored rows; the two currently-built-in hurt and death slots get the equivalent chip drawn for them in the editor rather than stored, so nothing already authored is touched or restructured.
2. **Body-part targeting.** A row declares which part of the character it speaks for — whole body, or a specific part (e.g. upper body vs legs, matching how ProtoGuy is already built as separate top/bottom halves). This is required for a character to show more than one thing at once (walking legs + a firing upper body simultaneously) — without it, that case is inexpressible.
3. **Hurt and death as the top two rows of one unified list**, not restructured or moved data — same underlying storage as today, just uniformly presented alongside custom states in the editor. Laubrary asks "which hurt look?" / "which death look?" (filtered to rows carrying the matching role chip); the game answers with a name. The game never decides *whether* a hurt or death happens — only its appearance, when asked.
4. **Default-plus-override effects.** A card's effects gain exactly one required default plus any number of optional named override slots; the "ask for this state" call may optionally carry an override name, and if it matches a slot, that effect plays instead of the default. (New mechanism from round 4, evaluated against the existing "opaque parcel" proposal in the round 4 doc — read that reasoning before implementing, they solve different problems and both are needed.)
5. Fix the death-linger timer to start when the death animation actually ends, as its own existing description already promises, rather than at the moment of death (currently a long burn-away effect gets cut off).

No default answerer for hurt/death: per the owner's explicit decision in T-0089's question history, a state must never play without gameplay code having explicitly decided it should — do not add any built-in fallback/default-picking behavior, even for the case of "there's only one option."

Constraint carried over from every round of this design conversation: whatever editor-facing changes you make, they must not silently move, rename, or reinterpret any already-authored data — existing assets must load and behave exactly as before this task, gaining only new optional settings.
