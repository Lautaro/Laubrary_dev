## Description

**Not caused by tonight's incident — this was already broken/incomplete before it,
just newly exposed by the compile cascade.** `ZoeEvent.cs`, `ZoeEventPlayer.cs`,
`IZoeEventTrigger.cs` (dated 2026-08-05/06/14 on disk) and `MirageTrigger.cs` are
all untracked files implementing a "uniform Zoe event" model meant to REPLACE the
still-live `ReactionFx`/`ReactionFxPlayer`/`NamedReaction`/`Zoe.hit`/`Zoe.death`
system (see `zoe-event-uniform-model.md` memory — that memory actually claims this
was "BUILT + verified 2026-08-05," which does not match what's on disk: `Zoe.cs`
was never actually migrated to use it, and `ZoeEventPlayer.cs` calls APIs that
don't exist anywhere — `Zoe.Events`, `Zoe.SpawnEvents`, `Zoe.EventFor`,
`ZoeState.BeginDeath`, `ZoeState.ApplyStun`, `IAnimatedView.OnMetaLayerReached`,
`IAnimatedView.CurrentClip`. Either the memory is describing a plan/partial state
that got overstated, or a LATER pass that finished the wiring was itself lost to
some earlier uncommitted-work incident (this project hasn't been committed since
2026-08-05, so there's no way to tell from git history alone).

`ZoeEvent.cs` also duplicated 4 shared types (`FxTriggerType`, `FxPlacementType`,
`FxEntry`, `EventDurationMode`) byte-for-byte from `ReactionFx.cs` — that
duplication has been resolved tonight (removed from `ZoeEvent.cs`, both files now
share `ReactionFx.cs`'s copies), but the deeper "wire ZoeEvent into Zoe.cs and
retire ReactionFx" migration itself was never finished and is NOT part of this
incident's damage.

**Current state**: quarantined (moved to `_Quarantine/ZoeEventSystem/`, not
deleted) to unblock compilation. `ReactionFx.cs`/`ReactionFxPlayer.cs` (the OLD,
still-live system) were restored from HEAD and are what `Zoe.cs`/`NamedReaction.cs`
currently and correctly depend on.
