## Description

Owner wants a faster way to preview audio while working in a Zounds/Klip editor. Right-clicking the editor's Play button should open an overlay popup with in-editor-only audition helpers (these never affect the saved asset, purely a workflow aid):

- **Play on change**: every time a parameter is changed and the user releases the control (e.g. lets go of a slider/drag), the Zound plays automatically.
- **Burst play**: plays the Zound X times with Y duration between each play. Y needs to support three modes: a static fixed time, "time since the last trigger" (fires on a fixed clock regardless of how long the sound itself took), or "time since last finished playing" (dynamic — waits for the previous play to actually finish, then waits Y more before the next).
- **Loop**: press once to start, it keeps playing continuously until pressed again to stop — same as Burst but unbounded, using the same Y timing modes as Burst between repeats.

**Hard requirement, part of this same task, not optional:** whenever a Zounds/Klip editor window is closed, any Zound(s) it has playing or queued via these audition helpers must always be killed — no orphaned playback left running after the editor that started it is gone, under any code path (normal close, Unity domain reload, editor crash-adjacent cases as far as reasonably preventable).

### Q1 — 2026-09-29T08:33:45Z — agent
Burst/Loop gap modes: your three were 'a static fixed time', 'time since the last trigger' and 'time since last finished'. The first two read the same to me, so I built them as three different things: Steady (a fixed rhythm = first play's length + gap, set once), From start (gap counted from the previous play's start, plays may overlap) and From end (gap counted from when the previous play really finished). If 'static' meant something else (e.g. a random gap range vs a fixed one), say which.

PLAN (design settled, building now).

MEASURED FIRST (unity-mcp, audio master-muted, an in-memory Looper that is never added to the library):
- A genuine script reload already silences a playing edit-mode voice by itself: after the reload, 0 audio sources playing, no voice rendering, no errors or warnings in the console. What a reload does NOT do is stop anything that would start the next play afterwards; and the editor windows currently never stop their own Play when they close (neither the Klip nor the Zequence window kills its sound on close).
- The engine's token list is a plain field, so after a reload the engine no longer knows about anything it was playing. So the audition's running state (a Loop, a burst in progress, a queued play) must never be carried across a reload, and everything it started must be killed through the engine's normal stop BEFORE the reload.

TEARDOWN (the hard requirement):
- One audition session per editor window, holding every sound that window started (the plain Play too, not only Burst/Loop) and every queued play.
- Killed on: window closing (both the ordinary close and the disable Unity does before every script reload); a global before-script-reload hook that kills every session regardless of window order; editor quitting; entering or leaving Play mode; and a per-tick sweep that kills a session whose window has gone for any other reason.
- Kill goes through the engine's own stop (silence the audio source and the voice), which is the first stage of the existing stopped-for-sure sequence; the voice's own teardown then follows the existing path. No second teardown path is added.
- Nothing that starts a play is ever saved with the window, so a reload or a restored layout can never resume a Loop.

LOOPER: Burst and Loop are unavailable for a sound that never ends by itself (a Looper, or a Zequence containing one), with the reason on hover. A Looper plays until stopped, so wrapping it would mean inventing a length for each play, and 'from the end' could never fire. Play on change still works (it restarts the Looper).

GAP MODES (interpretation, flagged as a question): Steady = a fixed rhythm set once when the burst starts (the first play's length plus the gap), which does not adapt to later plays; From start = the gap counts from when the previous play started, whatever its length (plays may overlap); From end = the gap counts from when the previous play actually finished.

PLAY ON CHANGE: plays when an edit made in THIS window is committed (a drag released, a click or a typed value accepted), not while dragging; a short settle so a burst of commits plays once; it restarts the sound. Ignored while a Burst or Loop runs (edits are already heard live there).

STATE: gap mode, gap and count are remembered per sound in the editor's own preferences (never in the project or the asset, no undo entry: it is workflow state). Play on change is remembered by the window while it stays open (survives a reload, not a close). Running state is never remembered.

UI: right-click the Play button opens a ZUI overlay card anchored to it: Play on change (toggle); Burst (start/stop), count, gap, gap mode (segmented); Loop (start/stop). Settings keep it open. The Play button reads Stop while anything this window started is playing or queued, and left-click then stops all of it.
