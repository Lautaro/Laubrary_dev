## Description

**Owner-diagnosed bug (2026-09-20), root cause confirmed by reading the code — fix it now, code-only.** Two Pyre Blast cards in a recipe: card A is Single (one point), card B is a Ring pattern (Count 5). No matter which card is dragged above the other in the stack, B's ring visually renders on top of A almost every time — reordering looks like it does nothing.

**Root cause, confirmed:** `Modules/ChunkModules.cs:45` gives each CARD a base sorting order of `sortingOrder + i` where `i` is the card's plain index in the stack — a difference of exactly **1** between neighbouring cards. But `Capabilities/PyreBlast.cs:280-281` (`ctx.OrderFor(LayerName, orderOffset)`, called once per pattern point from the formation runner) gives EACH POINT within one card its own sequential offset on top of that same base — point 0 = `base+0`, point 1 = `base+1`, ... point N-1 = `base+(N-1)`. A 5-point Ring therefore spans 5 consecutive sorting-order values, which is wider than the single-unit gap a two-card reorder produces: swap the cards and the single-point card's new value (`base+1`) still falls inside the ring's own spread (`base+0` .. `base+4`), so most of the ring keeps rendering above it regardless of stack order. Trace `ChunkModuleContext.OrderFor`/`ResolveOrder` (`Modules/ChunkModuleContext.cs:69-83`) to confirm this end to end yourself before changing anything.

**A second, related finding to fix in the same pass:** the Chunks *editor preview* does NOT have this bug — `Editor/ChunkPreviewSim.cs:1035-1037` already reserves **4×** the spacing between cards specifically to leave room for a pattern's own spread (its own comment says so: "without the gap a trail would sort onto its neighbour's own number and the two would interleave unpredictably"). So the editor preview and the real runtime currently DISAGREE on draw order for exactly this kind of recipe — the preview happens to look more correct by accident, not by matching logic. Fix this by making the runtime use the SAME reservation the preview already validated, not by inventing a second formula.

**Fix:**
1. Find the actual maximum point count a single pattern can realistically produce (Ring/Line Count's real clamp/cap — check the pattern/formation code, likely near where `Count` is authored) so the chosen per-card reservation is provably always wide enough, not just "probably enough."
2. Change the per-card base spacing in `ChunkModules.cs` (and anywhere else that assumes `sortingOrder + i` is a safe flat card-to-card step) to reserve enough room per card that no pattern's internal point spread can ever reach into a neighbouring card's band — the preview's `* 4` was clearly not derived from a real bound (its own comment only mentions "a trajectory arc, a trail", not a 5+-point Ring), so verify 4 is actually enough, or pick a value that is and update the preview to match it exactly (both should use ONE shared formula/constant — do not let them diverge again).
3. Verify: reproduce the owner's exact scenario (a Single card + a Ring/Count-5 card) in the Chunks preview AND a real Play-mode/Mirage burst, both orderings, confirm the depth swap now actually happens in both, and confirm they agree with each other.
4. Compile-check; this is code-only (no editor rights) — self-review carefully since you cannot verify in the live editor yourself; the PM will do the live verification.

Editor rights: NO — the owner is actively using the live editor right now testing this exact bug; this task is code-only so it does not contend for it. **Technical details:**
Hand-traced arithmetic, owner's exact scenario (Single card = formation-less single point, Ring card = SpawnFormation Count 5), emitter sortingOrder = ChunkEmitter.DefaultSortingOrder = 500, no Layer Plan (flat fallback branch of ResolveOrder):

Ordering A: Single at stack index 0, Ring at stack index 1.
- Single (i=0): card base = 500 + 0*64 = 500. One point, orderOffset 0 -> OrderFor = 500.
- Ring (i=1): card base = 500 + 1*64 = 564. Points orderOffset 0..4 -> OrderFor = 564,565,566,567,568.
- Single's only value (500) < every one of the Ring's five values (564-568) -> Single draws entirely BEHIND the Ring.

Ordering B: Ring at stack index 0, Single at stack index 1 (cards swapped in the recipe).
- Ring (i=0): card base = 500 + 0*64 = 500. Points -> 500,501,502,503,504.
- Single (i=1): card base = 500 + 1*64 = 564. One point -> 564.
- Single's value (564) > every one of the Ring's five values (500-504) -> Single now draws entirely IN FRONT of the Ring.

So the two orderings now disagree with each other exactly as a stack reorder should -- whichever card is now first draws entirely behind the other, no partial bleed-through. For contrast, the OLD formula (sortingOrder + i, no *CardOrderSpan) on the same scenario: Ordering B gave Ring points 500-504 and Single 501 -- 501 sits INSIDE 500-504, so ring points 502/503/504 kept outdrawing the single card even after it was moved to the front of the stack, which is precisely the owner-reported bug. Span-safety proof: SpawnFormation.MaxCount=64 is now a hard ceiling (Mathf.Clamp, not just Mathf.Max) on formation.count, and SpawnFormation.Resolve's placement loop runs i in 0..n-1 with n=that clamped count, so a card's own point offsets can never exceed 0..63 -- exactly the CardOrderSpan=64-wide band reserved per card (base..base+63), with the next card's base starting at base+64, so no overlap and no tie is possible for any authored or scripted formation.
