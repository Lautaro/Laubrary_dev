## Description

For making it easier to edit and create with the tools any LauAsset is set to be edited and autosaved immediately. This makes it possible to ruin or slightly alter an asset. We need both the freedom to just change things and not have to save each change. 

We also need the possible to protect certain versions of an asset and say "Hey this is what the game should look like atm, it should not be possible to change without a conscious decision". 

Think about it and suggest some ways to handle this. Everything should be opt in and configurable as a project will have different needs in different stages. Perhaps an asset is locked and can be changed freely but at runtime the  locked version will always be used anyway. Or there can be a test mode where runtime in the editor will show it how it is in the editor but the locked version is always available for builds or when the test mode is disabled. In those cases the editors should show a clear read banner stating why what you are doing at the moment may not be what the game shows etc... Lots of details that needs to be thought through here.

**Reply** (2026-08-25T09:40:59Z, agent):
Short answer: the file was never broken - whatever you were reading it in was using the wrong alphabet, and it was AgentHQ itself doing it. That is now fixed.

The long version. A dash like the one in "LauAsset Lock - design proposal" is a special long dash, not a hyphen. On disk it is stored as three bytes. If a program reads those three bytes back using the correct alphabet (UTF-8) it gets one dash. If it uses the old Western-European alphabet instead, it gets three separate characters, and they are always exactly the same three: a-with-a-hat, a euro sign, and a curly quote. That is the string you pasted, character for character. So the moment you see it you already know two things: the original character was a long dash, and something read the file with the wrong alphabet. The same trick explains the other ones you may have seen - a stray sequence where an apostrophe should be, or a mangled accented letter.

What was actually wrong here: when a document is attached to a task, clicking it opens it in a new browser tab. AgentHQ was handing the file over without telling the browser which alphabet to use, so the browser guessed - and on a Western Windows machine it guesses wrong. The page you were on already declares UTF-8, but that does not carry over to a document opened in its own tab. One missing instruction, in one place.

Two things worth knowing:

1. No file of mine has ever actually been damaged by this. I had 350 documents checked byte by byte across the Unity project, AgentHQ, and my own notes - every single one is correctly stored, none is corrupt. It only ever looked wrong on the way to your screen. That matters, because the tempting reaction is to go and "repair" the files, which would be the thing that actually breaks them.

2. It was one place, and it is fixed and confirmed working. The design document now opens in the browser and reads correctly, dashes and all. As a bonus it now displays in the tab instead of forcing a download.

One caveat, since you asked "sometimes": if you open one of these documents in some *other* program - an old text editor, something that assumes the Windows default alphabet - it can still show the same mangling, because that is that program's guess, not mine. If that happens, tell me which program and I will tell you which setting to change. The usual fix is choosing UTF-8 in its encoding menu. Modern editors, VS Code, GitHub and Unity all get it right on their own.
