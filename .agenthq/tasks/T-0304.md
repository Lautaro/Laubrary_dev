## Description

Measured live 2026-09-08 in the Shaper worktree editor (dataPath D:/UNITY/Laubrary Dev - Shaper/Assets), with ONLY the Pyre window open so attribution is unambiguous.

Unity logs `Layout update is struggling to process current layout (consider simplifying to avoid recursive layout): EditorPanelRootElement unity-panel-container (width:820.00, height:546.22)` tens of times a second, CONTINUOUSLY, while the editor sits completely idle. It burns CPU and floods the console, which is how it stayed hidden: it drowns every other message.

MEASURED (errors counted with LogEntries.GetCountsByType after LogEntries.Clear(), then 4-5 s of pure idle):
- Pyre 820x700, dial pane 560 -> 464 errors / 5 s. Pyre 900x700 -> 0.
- Shaper alone at its own 820x520 minimum -> 0. Shaper at 900x700 and 1200x900 -> 0. This is Pyre's.
- It follows the PANE width, not the window. Window held at 1600x900, rebuilding at each pane width:
    520 -> 0 | 530 -> 0 | 540 -> 390 | 550 -> 380 | 560 -> 362 | 570 -> 356 | 580 -> 380 | 600 -> 340 | 620 -> 410 | 640 -> 0 | 660 -> 0 | 760 -> 0 | 900 -> 0.
  The broken band is 540-620px inclusive; 530 and below and 640 and above are silent.
- It needs a Rebuild() and then never stops. Toggling all 28 sections open on an already-built tree at pane 560 is silent (0 errors, scrollbar present). A Rebuild at pane 560 gives 404 / 4 s, and the storm was still running 20 seconds later (410 / 5 s) with nothing touched.
- The user cannot escape it by resizing the window (516 / 5 s after widening the window with the pane still at 560). Dragging the divider out of the band clears it (pane 640 + rebuild -> 0).
- No single card causes it: all 28 sections folded -> 0; each of the 28 opened alone -> 0 every time. It needs the aggregate content, so a per-section bisection cannot name a culprit.

WHY IT MATTERS NOW: it is not T-0299's re-clamp (with leftPaneWidth at its 360 default the clamp never fires and 820x700 is silent). But the clamp is what lands an author in the band: at T-0302's new 820px minimum window, ClampedLeftPaneWidth() returns 820-260 = 560 - the middle of the broken band - for anyone who has ever dragged the divider wide. Pyre at its own documented minimum size is therefore permanently in the storm.

NOT FIXED HERE: the mechanism is the pane's layout as a whole rather than one control, and rule 6 forbids inventing a new one in this programme. Two plausible directions for whoever takes it: (a) find the element whose measured height changes with a ~13px width delta (a vertical scrollbar appearing and disappearing is the classic driver - the flow measured 547.1px wide with the scrollbar and 560.0 without during the storm), or (b) make ClampedLeftPaneWidth avoid the band. Full numbers in workspace/T-0303/A25-SEVENTH-PASS.md section 1.

### 2026-09-08T22:01:54Z — agent — open -> done
CHANGELOG: ZUI: a field stops re-stamping its own height over a sub-pixel rounding difference, which is what put Pyre's dial pane into a permanent layout-recursion storm at pane widths 540-620.

Pyre's dial pane no longer loops in layout at any pane width. The driver was neither the column flow, nor the scrollbar, nor the splitter: it was ONE 22px-tall image inside ONE field.

Z.Field pins a `.zui-field`'s height to what its children need (T-0287/T-0288, the fix for rows painting over each other). Yoga rounds an element's absolute EDGES to the device-pixel grid, so a row's resolved height depends on the fractional y-position it inherits from everything stacked above it - and at this editor's UI scale the gradient control's 22px objective-preview strip resolves to 21.78, leaving the Torch "Colour ramp" field's needed height alternating between 167.111 and 166.667 forever. The stamp's guard was Mathf.Approximately, whose relative epsilon here is ~2e-5, two orders of magnitude below that 0.44px flip, so every layout pass wrote a new height and every write re-ran layout. That is why no single card reproduced it (the aggregate above the ramp sets the fraction) and why it fired only in a narrow band of pane widths (the pane width decides the aggregate).

The stamp now re-writes only when the needed height moves by more than 1.5 layout pixels - the same absolute-tolerance reasoning, and the same constant, Z.Split already documents at Zui.cs:107 for exactly this device-pixel snapping. It is above rounding at any editor UI scale and two orders of magnitude below the 16-20px overflows the stamp exists to prevent.

ClampedLeftPaneWidth() is untouched: at the 820px minimum window the pane still lands at 560, that width is simply no longer a bad one.
