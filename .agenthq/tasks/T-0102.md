## Description

Three things to write down and agree before a line is written, because all three are expensive to retrofit. (1) Generators fill flat numeric arrays for a block of the canvas; they are never asked per pixel through a managed callback - this is what makes Burst possible later rather than a rewrite (design B9). (2) The shape stage's published output is defined as an implicit field sampled at a depth, and no stage except the final resolve may read screen-space neighbours - this is what keeps 3D rotation possible without building it (design B7). (3) The definitive list of named per-pixel quantities a shape may publish (coverage, height, edge distance, heat, density, soot, depth, age, surface direction), with which are genuinely already produced and which are new construction - note that age and surface direction are published by nothing today, and only 4 of the 9 imported effects publish coverage at all.

Three amendments to the above, from the 3D-rotation investigation behind design B7 (as rewritten). On (1): note this clause is stronger than an optimisation hedge - a tilted resolve costs roughly seven to eleven times a flat one, which is inside a responsive budget in Burst-compiled code over flat arrays and outside it in ordinary managed code with per-pixel calls. If item (2)'s door is ever to be walked through, item (1) is its precondition. On (2): make this testable rather than aspirational - specify the resolve stage as "given a ray, return every layer the ray passes through and the depth and local coordinates of each surface it crosses", and ship its v1 implementation as the trivial closed form for a straight-down orthographic ray, which is algebraically identical to today's point sample and costs exactly the same. Recording EVERY layer the ray passes through rather than only the front-most hit is what makes the occluded-outline coverage bitmap fall out for free instead of needing a re-march per outlined layer later. Before Wave 2 closes, render one deliberately tilted frame through the general path and keep it as a conformance artefact - not as a feature, as proof the door is still open. That requirement is stated here and DONE in T-0109, which is where extrusion lands and therefore the first task that can tilt an actual solid rather than a zero-thickness sheet; this task closes long before it can be satisfied, so do not treat it as satisfiable here. A rule with no test has already decayed twice in this codebase: T-0107's border stage, gated to 6 of 29 generators, and T-0114's picture-rect call, which is never called anywhere. On (3): "surface direction" is the quantity that makes item (2) real, so it is not optional - the shading stage must receive a normal published by the shape, never derive one by differencing the depth buffer itself. Today's tool derives it by finite difference with two hand-tuned constants (a 0.65 slope scale and a 1.4 flattening term); publish both as named dials of the height-field implementation so a later true-gradient normal has a calibration target rather than a memory of how it used to look.

The authoritative design is the "Shaper - the design" tab of this group's planning document (also at D:\UNITY\Laubrary Dev\.agenthq\workspace\T-0098\SHAPER_THE_DESIGN.md). Read it before starting. **Details:**
WHAT IT SETTLES

1. How a generator is asked to draw. It is handed a rectangle of the picture and fills in plain rows of numbers for it, rather than being asked about one dot at a time. This is the thing that keeps the fast-maths option open later instead of turning it into a rewrite.

2. What a shape's output actually is. A rule you can ask at any point in space, not a flat picture of heights - which is what keeps the door open to turning shapes in 3D later. The general question is written down now and answered in the cheap straight-down-only way for the first version, so it costs nothing today.

3. The complete list of the nine things a shape can say about each dot - how much shape is here, how tall, how far from the edge, how hot, how dense, how sooty, how deep, how old, and which way the surface faces - each marked honestly as either something that already exists or something that has to be built.

Each rule also gets a specific automatic test, because the document found two rules in this same project that were once someone's day-one constraint and quietly stopped applying. It also corrects two numbers the task brief itself quoted, and refuses to pretend a promise it cannot keep: one required test needs a feature that does not exist yet.

NOT YET VERIFIED: nothing here was run. It is a paper contract by design - that is what the task asked for - so the tests it specifies are described, not written. Whether they are practical to implement is judged, not measured.

NOT DECIDED HERE, ON PURPOSE: five open questions are listed at the end and handed to the tasks that can actually answer them, rather than being guessed at now.

HOW TO USE THIS: read Part 0 first - it is a one-page summary plus the list of things that turned out not to be true. Then read only the rule you care about. Every rule has a short number so a later task can point at it.
