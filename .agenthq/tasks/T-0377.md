How the Play-mode runs were driven (no human at the keyboard): Windows `SendInput` scancode key events for the number keys and Space (Fire), and `SendInput` absolute mouse moves with MOUSEEVENTF_VIRTUALDESK for aim. Two gotchas worth recording for the next task: (1) `SetCursorPos` does not reach the Input System at all — it produces no raw-input event, so the game's aim never moves, while `Input.mousePosition` does update, which makes it look like it worked; `SendInput` is required, and without VIRTUALDESK on a two-monitor desktop the cursor lands at half the intended x. (2) Reading `Mouse.current.position` from a CLI `eval` returns (0,0) even while the game is aiming correctly — the eval runs against the editor's input state, not the player's; read `Combatant.aimDirection` instead. Keyboard focus was taken with `EditorWindow.FocusWindowIfItsOpen(typeof(GameView))`, as T-0374 found. Aim also had to be computed from the MUZZLE, not the character: the gun sits on a rotating arm about two units out, so a cursor that points the character at the disc sends the shot about a unit over it.
