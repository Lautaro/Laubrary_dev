## Description

Found by T-0284's Views-bar walk, measured on the live Shaper window.

**What happens.** `ZuiViewBar` offers: a dropdown of saved views, **Update** (overwrite the selected view), **Delete view**, a name field and **Save as**. Applying a view happens ONLY through `_picker.RegisterValueChangedCallback` (`Zui/Toolkit/ZuiViewBar.cs:92-96`), so it needs the dropdown's value to CHANGE. Re-selecting the entry that is already selected raises no ChangeEvent, so nothing is applied.

**Measured, on the Shaper window, two saved views:**
- picked the other view -> cards open went 0/9 -> 7/9 (a view really does apply);
- folded every card by hand -> 0/9;
- re-picked the SAME view from the dropdown -> still 0/9 (nothing happened);
- switched away and back -> 7/9 again.

**Why it matters.** `SaveInto` leaves the picker showing the name it just saved, so immediately after "Save as" the bar already displays the view you are in. Rearrange the window and there is no gesture that puts it back: with exactly ONE saved view — the first-run case — restoring it is impossible through the bar. The workaround (save a second throwaway view and toggle between them) is not discoverable.

**Not fixed under T-0284** because the fix is a NEW control (an Apply/Restore button beside Update), which the harmony programme forbids (RULES.md rule 6). Shared control: Pyre's window has the same bar and the same gap.

Suggested shape when the owner wants it: one button, "Apply", next to Update, calling the existing private `ApplyPreset(_picker.value)`. No new concept — it is the gesture the dropdown already performs, made reachable when the value does not change.
