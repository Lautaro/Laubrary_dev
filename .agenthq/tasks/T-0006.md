## Description

Depends on T-0003 (vector data type) and T-0001 (the standalone ZUI vector control, so there's something proven to reuse or reference for interaction feel — see the open question below). Wire actual authoring: the user clicks/drags on the animation canvas to place and adjust a vector MetaLayer's per-frame value.

**Current authoring surface (confirmed by reading `Editor/Launimator/LauminationBuilderWindow.cs` this session):** the MetaLayer panel chrome (layer list, add/remove, colour, brush size) is UITK/ZUI. **But the actual paint canvas is raw IMGUI** (`DrawMetaEditor`) — this matches the project's own documented exception for genuinely bespoke canvas painting. Mouse interaction (`HandleMetaPaint`) is classic `Event.current`/`EventType.MouseDown|Drag|Up` — left-drag paints, right-drag erases, middle-drag pans.

**Open question, flagged rather than pre-decided** (the research this session deliberately did not pick an answer — use your judgment once you're in the code, but the IMGUI-extension path is very likely the lower-risk one and the one to try first): should the vector-drag gesture (click sets origin, drag sets direction/length, release commits) be built as a NEW branch inside the EXISTING `HandleMetaPaint` IMGUI function (the more natural sibling to the current paint/erase/pan gestures, less invasive), OR should it embed the new `ZuiVectorEditor`/`ZuiDial` control (T-0001) as a UITK overlay hosted inside the IMGUI canvas (more code reuse from T-0001/T-0002's work, but embedding UITK inside an IMGUI `GUI.BeginClip` region is real extra complexity that doesn't exist anywhere else in this codebase yet)? If genuinely unclear once you're looking at the real code, log a Question on this task rather than guessing silently — this is exactly the kind of judgment call worth a user check-in given it sets the pattern for any FUTURE metalayer-authoring gesture too.

**What "done" looks like regardless of which path:**
- A user can add a Vector-mode MetaLayer, click on the canvas to set the origin, drag to set direction (and length, if the layer allows it per T-0003's layer-level setting), and see the arrow rendered live.
- The per-frame numeric input boxes the user asked for ("ui should provide options to ses input boxes for the params") are available somewhere in the panel — reuse T-0002's toggle-visibility pattern if that's already built by the time you get here, otherwise a plain toggle is fine as a placeholder.
- Existing Point/Shape layer authoring is completely unaffected.
