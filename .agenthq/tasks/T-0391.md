## Description

**Owner report (2026-09-21), comparing UC4's Hit-reaction splash against Flying Disc/ProtoGuy's own art:** "The debris from the hits have really small pixels though. I don't think they are following the global setting are they?"

**Root cause, found and fixed by hand this session (verify + commit, this is a sibling of T-0390, not the same file):**

The capability that fires on Hit is `PaletteSplash` ("Disc spray" in `Assets/Demos/ChunksDemo/UseCases/UC4 Zoe Spray.asset`), NOT `DebrisScatter`. Unlike `DebrisScatter` (T-0383) and `FragmentFracture` (T-0390), `PaletteSplash` had **no project-pixel-scale integration whatsoever** — a flat authored `pixelsPerUnit` field defaulting to **32**, entirely disconnected from `PixelScaleProjectSettings`. The real asset, `UC4 Zoe Spray.asset`, has `pixelsPerUnit: 32` serialized — exactly double the project's actual Pixel Scale of 16 — so every splash particle rendered at HALF its intended physical size. This is a distinct, previously-undiscovered bug from T-0390's (that one was a measured no-op on the real asset; this one is real and confirmed by the numbers straight from the asset file).

**Already changed, by hand, this session (verify these compile and behave correctly; do not re-derive them):**
1. `Runtime/Chunks/Capabilities/PaletteSplash.cs` — renamed `pixelsPerUnit` → `pixelsPerUnitOverride` (with `[FormerlySerializedAs("pixelsPerUnit")]`, a REAL rename this time, not a copy-paste error like T-0390 had), added `useProjectPixelScale` (bool, default true) + `EffectivePixelsPerUnit`, exact mirror of `DebrisScatter`/`FragmentFracture`. `Fire()` now reads `ppu = Mathf.Max(1f, EffectivePixelsPerUnit)` instead of the raw field.
   - **Important, do not "fix" this:** a SEPARATE `ppu` read at line ~235 (`TrySamplePixels`, `source.pixelsPerUnit`) is deliberately UNCHANGED — that one reads the SOURCE SPRITE's own PPU to convert its pixel grid into world-space footprint-emission offsets (analogous to `FragmentCutter.BuildPieces`'s `pivotPx`/`ppu`), which is a correct, different use of "ppu" from the OUTPUT particle-sizing one this task fixes. Confirm you understand which is which before touching anything.
2. `Editor/Chunks/ChunkWindow.PaletteSplashCard.cs` — added the same "Use project pixel scale" toggle + override field + live-readout UI as `DebrisScatterCard`/`FragmentFractureCard`.
3. `Editor/Chunks/ChunkPreviewSim.cs` line ~568 — the standalone editor preview's own splash-sizing code read `s.pixelsPerUnit` directly (now renamed away, so this was a real compile-break risk) — updated to `s.EffectivePixelsPerUnit`. The OTHER two `pixelsPerUnit` reads in this file (~1218, ~1435) are on a plain `Sprite`/`source`, unrelated, correctly left alone.

DEFECT 1 - a hard compile error (CS0117). ChunkSpec.MigrateSplash() still assigned the old field name inside its `new PaletteSplash { ... }` initializer (`pixelsPerUnit = pixelsPerUnit`). It never reached the console only because the editor's first compile of this source happened after I fixed it; proved empirically afterwards by evaluating `new PaletteSplash { pixelsPerUnit = 32f }`, which fails with "'PaletteSplash' does not contain a definition for 'pixelsPerUnit'". DEFECT 2 - the fix was a RUNTIME NO-OP, and would have split preview from game. This is the serious one, and it is the same trap T-0390 fell into. ChunkSprites kept ONE flat shard cache built at whatever ppu was requested first in the domain and never rebuilt it, and its Count getter primed that cache with a hardcoded 32 whenever nothing had built it yet. PaletteSplash.Fire reads `ChunkSprites.Get(rng.Next(ChunkSprites.Count), ppu)` - C# evaluates Count BEFORE the call - so every cold domain built the shards at 32 and then ignored the ppu actually passed in. A particle's final world size is targetPx / (the shard sprite's real ppu), because Fire scales by targetPx / nativeShapePx. Measured on a cold cache replaying Fire's own expression order: asking for 16 yielded a sprite at 32, world sizes 0.03125 / 0.09375 for sizePx 1-3 - i.e. exactly the old broken sizes, unchanged. Meanwhile ChunkPreviewSim divides by ppu directly (radius = px / ppu * 0.5f) and WOULD have shown the corrected size, so shipping the 3-file fix as written would have made the editor preview and the running game disagree - worse than the original bug.
   Fix: ChunkSprites is now keyed by ppu. Shapes moved to a ShapeDef[] descriptor table, Count answers from that table and builds nothing, and Ensure(ppu) returns a per-ppu set from a Dictionary<float, Sprite[]> (keeping the existing destroyed-sprite guard, now per set). Re-verified cold: Count = 6 with ZERO cache entries created; asking 16 gives a real 16-ppu sprite and world sizes 0.0625 / 0.1875 - exactly 2x the old and exactly the intended values; 32 gets its own distinct set; re-asking 16 returns the SAME instance, so a recipe mixing two PPUs cannot thrash into per-particle texture allocation. Side benefit: DebrisScatter's T-0383 link now actually reaches the procedural shards it was already passing effectivePpu into.
