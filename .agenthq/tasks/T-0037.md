## Description

Wires `Laubrary.Layering.LayerSpec` (T-0032) into `ChunkSpec` as an ordered list of named, typed slots
(Fragment vs Burst — e.g. `Blast` / `Fragment1` / `Smoke` / `Fragment2` / `Fireball` / `Fragment3`), each
resolving to a real Unity `sortingOrder`. This is what turns the standalone modules (T-0033..T-0036) into one
composed, layered process — the full death-effect example in the design doc's Vision section is the target
proof case.

**Depends on T-0032** (the primitive must exist first). Includes the Layer Stack ZUI panel — drag-reorder via
`ZuiThumbGrid` (already shared between PyrePlus's CherryFraming and the Laumination Builder) — and the Envelope-
style popover context menu for adding a layer. Also where the "possibly a Sorting Layer ZUI picker control" gap
gets resolved or explicitly deferred. See `CHUNKS_OVERHAUL_DESIGN.md` §"Standalone modules" #5 and §"UI
architecture".

You can now author which part of a composed explosion draws in front of which -- name the layers, drag them into the order you want, and assign each effect to one. Before this, everything got one flat depth number and the stacking was whatever happened.
**Details:**
How to use this: open Laubrary -> Chunks and find the "Layer Stack" section. An empty stack means no layering at all, which is exactly how Chunks behaved before -- there is no separate on/off switch, because an empty list already says it. Press add to declare slots (a one-click "standard stack" is offered when it is empty), drag the grip to reorder them, and each switched-on effect below gets a row where you pick its slot. An effect pointing at a slot that no longer exists shows as unresolved with a button to declare it, rather than looking fine and quietly losing its depth when the game runs. Not yet verified: no human has dragged a slot; the fixed widths and how a six-slot picker wraps at real pane width are the first things worth eyeballing.
**Technical details:**
D:\UNITY\Laubrary Dev\Assets\Packages\Laubrary\Editor\Chunks\ChunkWindow.Layers.cs (the only file touched; the runtime primitive is T-0032's LayerSpec, unchanged). Slot rows live in their own host (_lsSlotHost) so ZuiReorder.MakeGrip's child-index maths stays honest; reorder calls LayerSpec.Move inside Dial. Renaming goes through LayerSpec.UniqueName with the slot temporarily blanked so it cannot collide with itself, and CASCADES to every module referencing the old name (RepointModuleLayer) -- otherwise a rename silently orphans modules that then degrade to baseOrder at runtime. Adding uses Z.Menu in the Pyre "+ Add modifier" shape, leading with any slot a module already wants but that is not declared. sortingLayerName is Z.MiniRadio(wrap:true) over SortingLayer.layers with an explicit "(leave alone)" empty-string option and a stale stored value shown as "X (missing)" rather than hidden. Per-module assignment rows are emitted only for ENABLED modules (splash/fragments/pyreSpawn/formation); pyreMotion gets none since it is not an IChunkModule and carries no layerName. baseOrder/step edits refresh the resolved-order readouts in place rather than refilling rows under the field being typed in. THE DESIGN DOC'S OPEN QUESTION "possibly a Sorting Layer ZUI picker control" IS RESOLVED AS CLOSED: Z.MiniRadio over the enumerated layers fits and needs no new ZUI control; the only residual is that ~15 lines of enumerate + sentinel + stale-value handling would be duplicated at a second call site, so a thin Z.SortingLayer wrapper is worth adding WHEN a second tool needs one, not speculatively. The design doc's suggestion of ZuiThumbGrid was rejected in a code comment: it reorders pictures, and a layer slot is a name and a number.
