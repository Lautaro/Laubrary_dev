## Description

**Found by T-0293 (A22 fifth pass) through the Shaper defect it caused; the Shaper call site is fixed, the ZUI-wide trap is not.**

`Z.MiniRadio(..., wrap: true)` stamps `.zui-radio--wrap { flex-wrap: wrap; flex-shrink: 1 }` (`Zui/Toolkit/ZuiToolkit.uss:549`), whose own comment says "a wrapped row is allowed to be as wide as its container and no wider — that is the whole point". That only holds where the radio's width is BOUNDED. Wrapped in a `Z.Field`, it is not: `.zui-field { flex-shrink: 0 }` (`ZuiToolkit.uss:331`). In a COLUMN body the field is still bounded by the container's cross-axis width, so the wrap fires; inside a `Z.Row`/`Z.HGroup` the field keeps its full content width, the radio is never squeezed, and the last option is simply clipped by the enclosing box.

**Measured** on the Shaper Mask card's Quantity radio (4 options: Opacity / Height / Distance from edge / Brightness), left pane at its default width:
- `ZuiHGroup` 336.0 px wide, its `.zui-field` child **367.1** px, the radio **312.0** px
- the Mask `ZuiBox` is 350.2 px, so the `Brightness` button ran to xMax 378.2 against the box's 354.2 — **24.0 px outside**, drawn on screen as `"Brightne"` (capture `shots/a22-mask-clip-coverage-190921.png`)
- fixed by moving that one field out of the `Z.HGroup` into the box body: radio now 280.9 px, two lines, 0 overflowing children, `Brightness` fully legible on its own second line (`shots/a22-mask-fixed-192634.png`)

**Why no probe caught it in four passes:** the archived overflow probe (`workspace/T-0284/overflow-probe.cs`) only ever compares `yMax`. It reports "0 of 745" on exactly the window that was clipping a word. An X-axis companion is in `workspace/T-0293/a22-hov.cs`; consider archiving it beside the Y one.

**Scope of the remaining trap.** Every other wrapping radio in Shaper (Fill `Kind`, Ramp `Quantity`, Swarm `Shape`, Height `Profile`, Height `Bevel`) is added to a box body and wraps correctly, and Pyre's five wrapping radios all measured INSIDE their boxes (Torch's `Flame type`: 247.1 px in a 347.1 px box, 2 lines, 22.7 px clear). So nothing is broken today — but the next author who packs a wrap radio into a row gets the same silent clip.

**Suggested fix:** either let a `Z.Field` shrink when its control can wrap, or have `Z.Row`/`Z.HGroup`/`Z.Field` refuse the combination loudly, or teach `ZuiAudit` to flag a `zui-radio--wrap` whose laid-out width equals its content width inside a row. Shared ZUI, so it needs its own cross-host pass — the same reason T-0290 was filed rather than fixed in place.

CHANGELOG: a Z.Field wrapping a Z.MiniRadio(wrap:true) now gets a new .zui-field--wrap class (flex-shrink:1, min-width:0), stamped automatically from the control's own zui-radio--wrap class, so a wrapping radio packed into a Z.Row/Z.HGroup can actually wrap instead of overflowing past the box that holds it -- fixed ZUI-wide, not just at Shaper's one call site.

Bucket 1 - what changed and why: .zui-field is flex-shrink:0 by design (a slider/toggle field must never be squeezed) -- but that rule silently also stopped a WRAPPING control (MiniRadio built with wrap:true) inside a Z.Row/Z.HGroup from ever wrapping, because the field around it kept its full unshrunk content width forever and the radio was never squeezed enough to break onto a second line. Fixed at the ROOT (Z.Field in Zui.cs), not the USS rule itself, so a bounded control (slider, toggle, non-wrapping radio) is completely unaffected: Z.Field now checks control.ClassListContains("zui-radio--wrap") and, only then, adds a new zui-field--wrap class (ZuiToolkit.uss) carrying flex-shrink:1 and min-width:0. This required NO change at any of Shaper's or Pyre's existing call sites -- every current wrap:true MiniRadio (Fill Kind, Ramp Quantity, Swarm Shape, Height Profile/Bevel, Pyre's five) already lives in a box body (not an HGroup) so gets the new class for free with no behavior change; the fix only matters the moment someone puts one inside a Row/HGroup, which is exactly the trap T-0293 hit once already (Shaper's Mask Quantity field, already fixed at its own call site by that task) and is now closed for every future case, not just that one.
