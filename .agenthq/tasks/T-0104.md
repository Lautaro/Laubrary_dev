## Description

The design says the nine large imported Kiln effects come across as composite generators and should be REFERENCED rather than copied, so that ~10,700 lines of carefully verified ports do not get duplicated and drift. That only holds if the existing plug-in contract is unchanged by the new one. Verify it by taking two of the big effects and checking they satisfy the new contract with no edits. If they do not, the reference-rather-than-copy decision has to be revisited before Wave 3. Note this is in tension with the owner's stated preference to duplicate rather than modify - resolve that explicitly, do not let it pass silently.

**Details:**
What was checked: the design promises that nine large, carefully-verified effects can move into the new tool untouched, which is what lets them be shared instead of copied. We tested that promise on two of them, deliberately picking the two that sit on opposite sides of the design's one genuinely unclear rule.

The result: neither passes untouched, but the failures are small and they barely overlap. One effect needs a three-to-six-line fix so that each flame in a group ages from when it appeared rather than all of them being locked to the same clock - the design already predicted this one. The other needs a single line declaring that it does not take a colour choice - except that the one line, done literally, would hide the only control that colours it, so it needs doing slightly more carefully. Everything else that failed either fails for every effect because the new tool has not been built yet, or does not apply to this kind of effect at all.

On the disagreement: you have said you prefer to duplicate things rather than modify them. For these nine effects specifically, duplicating is the more dangerous choice, and we recommend against it. They are the one part of the codebase that was checked number-by-number against the originals it was ported from, so a copy that quietly drifts would produce no error at all - just a slightly different-looking fire that nobody notices. There is also a technical reason a copy is unsafe: the mechanism that keeps your already-saved files loading correctly when code moves cannot cope with two copies both claiming to be the same thing. The recommendation is the design's own: duplicate the tool, share the effects. Where the new tool genuinely needs an effect to behave differently, put that behind a switch that defaults to today's behaviour, so one shared copy serves both tools and the old one is untouched.

Not yet decided - and this one needs you: the design's single rule for this kind of effect says it 'must publish coverage', and that phrase can mean two different things. Under one meaning five of the nine effects fail on day one; under the other all nine pass. We recommend the permissive reading and explain the cost of it in the report, but it is a judgement call about quality versus universality and it should be made before Wave 3 starts.

Not verified: no timing was measured and Unity was not run - this was a source-level review. One effect is flagged as very likely too slow, from the structure of its code rather than from a measurement.

The full report is attached.
