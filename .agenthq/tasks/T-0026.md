## Description

User's design philosophy, stated directly: **"if 2 assets will only be used together... dont make it into 2
assets for the end user."** ProtoGuy's Legs and Upper are legitimately two separate `Lauminary` assets (they
really are independently-timed, independently-versioned animation sets), but the Lauminary Browser currently
lists them as two completely unrelated rows with no indication they belong together, and the Laumination
Builder can only ever edit one at a time with no way to see the assembled composite result while doing so.

User wants: browsing/picking should treat a composite pair as one conceptual unit; the Builder should let you
switch between parts easily AND see the live combined preview (both parts composed together, the same way
`CompositeZonedPlayer` renders them at runtime) while working on either one.

**Explicit ask: this task is for brainstorming/discussion, not immediate implementation.** Run the discussion
here — append to Questions/Handover Log as it develops — rather than treating it as a spec to build from yet.

## Where the disconnect actually lives (confirmed by reading the code)

`Lauminary`/`LauminaryVersion` (what `LauminaryBrowserWindow` lists) have ZERO concept of composites — a
Lauminary is just "a versioned bag of animations," designed to be a portable, independently-reusable artifact
(see `Lauminary.cs`'s own doc comment: "the portable artifact other projects consume"). The composite
relationship (which parts, how they attach — `parentPartName`, `attachMetaLayerId`) lives entirely on the ZOE
side, in `CompositeLauminaryView.parts` (`Runtime/ZoetropeLaunimator/CompositeLauminaryView.cs`). So the
Browser has no way to know two Lauminaries are related — that knowledge lives one layer up, on a different
asset type entirely, and only exists once some Zoe actually composes them.

## Three shapes discussed so far (cheapest → most invasive)

**A. Lightweight grouping/tagging.** Lauminaries stay fully independent assets; add a link (explicit field or
auto-discovered backlink) so the Browser can group/show them together, and the Builder gets a "preview
composite" mode that pulls in sibling parts' current frames and composes them live (reusing
`CompositeZonedPlayer`'s attach math for editor preview, not just runtime). Cheapest, keeps Lauminaries
reusable/independent, degrades to exactly today's UX for anything ungrouped. **Agent's recommendation: start
here.**

**B. A real composite wrapper asset** ("Rig"?) owning references to N part-Lauminaries + their attach config,
and THAT is what the Browser lists as one row. Closer to "literally one asset" but raises a real question:
attach config currently lives on `ZoeBodyPart` (Zoe-side) — a wrapper asset either duplicates that (risk of
drift between the wrapper's idea of composition and the Zoe's) or attach ownership has to move out of Zoe into
Launimator, a bigger layering change than "make the tool nicer."

**C. Make the rig itself the reusable thing** — a Zoe references a shared composite rig instead of declaring
its own part list, so multiple characters could someday share one skeleton (different textures/parts).
Real architectural upgrade, but answers a question not asked yet (cross-character reuse). Treat as a distinct
future fork if it comes up, not bundled into this.

## Open questions (posed to user, not yet answered)

1. Group membership: explicit authoring (pick "belongs with: X") vs auto-discovered by scanning Zoe assets for
   which Lauminaries their `CompositeLauminaryView` references (showing "used by: ProtoGuy (as Legs)"
   backlinks) — since a torso could in principle pair with more than one legs variant someday?
2. Where does a part's DISPLAY name ("Legs" vs "ProtoGuyLegs") come from — authored on the Lauminary itself, or
   does it stay purely `ZoeBodyPart.name` (same Lauminary could be called something different in two different
   composites)?
3. In the Builder's combined-preview: should sibling parts live-scrub in sync with the one being edited, or sit
   frozen on their own idle frame — given parts are independently-timed today (that's the whole point of
   `CompositeZonedPlayer`, e.g. legs running while torso is mid-shot on a different clip)?

## DIRECTION CONVERGED ON (2026-08-17, second pass) — supersedes options A/B/C above

User wants a robust, future-proof refactor, not a light patch — and landed on a materially better model than
any of A/B/C:

1. **"Zoe is the rig."** No new wrapper asset type. `Zoe.view` (`CompositeLauminaryView.parts`) already fully
   owns "which parts, how they attach" — that's already a rig, it just has no dedicated authoring UI yet.
2. **Legs and Torso become two ANIMATION SETS in the SAME Lauminary, not two separate Lauminary assets.**
   Verified against the actual resolution code — this needs ZERO runtime/schema changes:
   `LauminaryVersion` already holds both `animations` (named clips) and `sets` (`LauminationSet`, e.g.
   `LegsIdle16`/`LegsWalk3`/`UpperAim16`). Playback is driven entirely by each `ZoeBodyPart`'s own
   `MotionPose.rules[].setName` lookup (`MotionPoseResolver.Resolve` → `FindSet(version, rule.setName)`) — NOT
   by which Lauminary asset the part's view happens to reference. So two `ZoeBodyPart`s can point their
   `ZonedLauminaryView.version` at the exact SAME `LauminaryVersion` and each will only ever show its own
   set's animations, because each resolves by set-name independently. Net effect: one shared Lauminary asset
   holding all three sets, ONE row in the Browser — not two unrelated entries.
3. **The Zoe "Rig" authoring surface** (still just a concept, not built) picks, per body part, WHICH set(s) on
   the shared Lauminary drive that part — "composites them based on metadata," i.e. by set name, same lookup
   mechanism that already exists.
4. **Mirage is the combined-preview surface**, not a new Builder preview mode. Confirmed:
   `AssetCacheInvalidation` is a fully general, already-working live-update bus (watches Unity's own
   `ObjectChangeEvents`, so ANY tool's edit to a ScriptableObject fires it automatically — ALREADY used by
   Mirage for exactly this "no restart needed" purpose). The ONE real gap found: `MirageSubject.HandleAssetInvalidated`'s
   relevance check (`Runtime/Mirage/MirageSubject.cs` ~line 103) only treats a change as relevant when
   `asset == zoe` or it's an equipped `WeaponDef` — it does NOT currently check whether the changed asset is a
   `LauminaryVersion` referenced by `zoe.view` (single or composite). That's the actual missing piece for
   "edit in the Builder, watch it update live in Mirage" to work today — not a new pipeline, just widening one
   `if` check to also walk `zoe.view`'s referenced `LauminaryVersion`(s).
5. **UI shape**: `ZoeWindow` needs tabs eventually (Identity/Stats/Look/Reactions could stay the default tab;
   Zoe Events its own tab; Rig/composite-authoring its own tab) — but user explicitly said to WAIT on the tab
   split: "lets allow ui bloating for now untill we know how it should work." Do not build the tab
   architecture yet; keep adding sections to the flat `ZoeWindow.BuildBody` until the real shape is clear.

## WORKFLOW DESIGN (2026-08-17, third pass) — the connection/anchor model, still brainstorm-only

User wants a clear picture of the actual authoring workflow before any building starts. Converged on a model
for how two body parts connect, generalizing the earlier "static" vs "metalayer" split into ONE mechanism with
two interchangeable anchor sources per side:

**A connection = a parent-side anchor + a child-side anchor (each independently either mode below) + one
shared numeric offset applied on top.**

- **Edge anchor**: pick a side of that frame's own TRIMMED content bounding box (Top/Bottom/Left/Right/Center).
  Zero authoring — the point is computed automatically from whatever's currently baked, per frame. Handles the
  common "stack these vertically" case (exactly Legs/Torso) with just a dropdown + offset defaulting to
  (0,0).
- **MetaLayer anchor**: pick a named painted point (per-frame, e.g. "Waist") — for content that genuinely
  shifts through the animation (a walk cycle's weight shift). This is the mechanism already built for T-0021.
- Both modes carry the SAME offset field for fine-tuning; "fixed manual offset" is NOT a separate third mode
  (explicitly rejected in this pass) — it's just Edge-mode with a non-zero offset. Two modes, not three.
- **One anchor point per connection** (not multiple) — explicit user decision. A future two-point/rigid
  connection is not ruled out architecturally, just not designed now.

**Visualization**: schematic only — boxes representing each part's frame + a dot for the connection point, NO
animated sprite content (that's Mirage's job entirely, kept out of this view on purpose). Agent's addition,
not yet confirmed with user: since trimmed-bbox size can differ per direction/frame, this schematic view
likely still needs a frame/direction SCRUBBER even though it never plays animation — so a bad alignment on one
specific direction is visible before ever opening Mirage. Not yet explicitly agreed, worth confirming.

**Live-verified on ProtoGuy** (real regression, not just compile-clean):
- Configured Upper's connection: `parentAnchor` = Edge/Top (on Legs), `childAnchor` = Edge/Bottom (on Upper),
  offset (0,0).
- First attempt showed a real, visible gap — root-caused: the T-0025 migration deliberately used
  `fixedFrame=true` (byte-exact reproduction including the ORIGINAL transparent canvas padding) specifically to
  avoid the AtlasBaker repeated-overwrite bug (T-0024). `Sprite.bounds` for an untrimmed, padded sprite reflects
  the padded canvas, not the visible character — so Edge/Top-Bottom pinned padding-to-padding, not
  content-to-content.
- Fix: re-baked BOTH Lauminaries with auto-trim (`fixedFrame=false`) using the SAME safe batched-rebuild
  approach from T-0025 (now that the real T-0024 bug — repeated same-path overwrite/reimport, not auto-trim
  math — is understood and avoided). Verified byte-exact non-transparent pixel count match against the
  original source for both Legs (13227px) and Upper (5350px) before trusting it.
- Re-tested: Edge/Top ↔ Edge/Bottom with offset (0,0) now produces a correctly stacked, gapless character —
  screenshot-verified idle AND walking (W held, real queued Input System event). Zero manual tuning needed —
  arguably better than the old hand-measured `upperYOffset = 1.4375f` constant it replaces, since it's now
  derived from real content bounds instead of a guessed number.
- `ProtoGuySpawner.upperYOffset` hack removed entirely; also fixed a latent bug in the same method
  (`transform.Find("Legs/Upper")` → `transform.Find("Upper")`) — composite parts are now ALWAYS flat children
  of the spawned root (never Transform-nested under each other), since the new system repositions by anchor
  every frame instead of by Transform hierarchy; the old nested-path lookup would have silently found nothing.
