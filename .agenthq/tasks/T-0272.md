Bucket 2 (fixed in this task, self-reviewed + compiled clean, not yet Play-tested since Play mode is out of scope): a real bug in Runtime/PyreShaper/FireCompositeSource.cs and FireballCompositeSource.cs. Pyre's own RenderFireLayer/RenderFireballLayer (PyreRenderer.cs:408, PyreRenderer.cs:765) hash the FireSim/FireballSim's own RNG seed as Hash(spec.seed, layerSalt, 0, 0) before ever stepping the grid; the two composite sources' Step() methods were handing the sim the RAW un-hashed dial-eval seed instead, so the turbulence/cellular field a hosted flame stepped genuinely diverged from Pyre's from the very first step, even though every dial and every FireParams/FireballParams field matched exactly (verified field-by-field via reflection). Fixed by hashing the sim's own seed argument with PyreRenderer.Hash(sd, PyreShaperSimSupport.LayerSalt, 0, 0) in both Step() methods (FireCompositeSource.cs:236, FireballCompositeSource.cs:144), leaving dial evaluation on the raw seed unchanged (matching Pyre's own FireParamsAt/FireballParamsAt, which also use the raw seed). Verified by reflecting into a fresh FireSim's own private heat[] grid after replaying frames 0..4 through Pyre's real FireParamsAt + the bridge's own Step() side by side with the corrected seed: 0/4096 cells differ, maxDelta 0 -- the simulation state is now bit-identical when params match, confirming the seed was the whole cause of the state divergence.

Bucket 3 (measured, explained, left as-is -- not a bug, an existing documented design choice, no owner decision needed): the two SIMULATION composite sources (FireCompositeSource, FireballCompositeSource -- 'Simulation Fire'/'Simulation Fireball' in the table, distinct from the two LEGACY shapes of the same name) still show large per-pixel colour differences at the mid frame after the seed fix, even though sim state and coverage counts now match almost exactly (Fireball 163->163 coverage, Fire 52->51). Root cause, confirmed by inspection: Pyre's own Fire/Fireball dispatch paints the sim through 'layer.shapeFill != null ? layer.shapeFill.gradient : null' (PyreRenderer.cs:437, PyreRenderer.cs:797) -- the LAYER's generic Shape Fill, the same default every other hosted shape uses. FireCompositeSource.ramp and FireballCompositeSource.ramp (FireCompositeSource.cs:146, FireballCompositeSource.cs:72) instead default to PyreShaperSimSupport.DefaultRamp(), an explicit conversion of Pyre's 'Ember' ramp preset -- a deliberate authored choice, documented in both files' own doc comments ('converted from Pyre's own Ember preset... rather than by hand-typing a second set of stops... a null ramp would make the sim render pure white and read as a broken generator'). This is why my reference (a bare PyreLayer with shapeForm=Fire, generic default fill) and the composite source (Ember-preset ramp) paint different colours over an otherwise near-identical flame shape -- it is the same gap T-0202 already flagged and left as 'Remaining: Simulation Fire, Simulation Fireball' rather than a regression introduced since. It is not something the bridge got WRONG relative to a spec Pyre defines (Pyre itself hands Fire no special default ramp; the composite source's own default is simply a nicer starting point than a blank/whatever-generic-fill would give), so I left it as authored rather than reverting a deliberate UX default without the owner asking for it. If a future task wants byte parity here too, the fix is a one-line default change (ramp = new PyreLayer().shapeFill.gradient) traded against a worse-looking out-of-the-box flame -- worth a real decision, not a silent revert.
