Important prior-art finding from T-0089 round 4 (verify it's still accurate before relying on it): every weapon shot **already** asks a character to show a named state today — `WeaponMuzzleCue.cs` (around lines 140-143) already wires `ProjectileWeapon.Fired` and `HitscanFired` to `ReactionFxPlayer.Raise(FireEventId)`, where `FireEventId` (around line 53) is the fixed string `"Fire"`. This covers both held/projectile weapons and hitscan weapons. The actual work: let game code participate in choosing which name gets requested at the moment a shot fires, instead of it always being the fixed `"Fire"` name — so a lazer weapon can make that become "Shooting Lazer" instead, based on what the game knows about the currently equipped weapon and any active powerup. This is expected to be a small, targeted change to existing firing code, not a new module.

Confirm coverage across control schemes: this was verified against the top-down/twin-stick path specifically. A different perspective (platformer, light-gun) reuses the same aim/fire modules per project documentation, but that hasn't been independently confirmed — check it as part of this task.

### 2026-08-26T13:58:02Z — agent — todo -> done
Your game code can now decide which named look a shot asks the character to show, instead of every weapon always asking for the same fixed one. A laser weapon or an active powerup can make the same trigger pull ask for a different look.
**Details:**
How to use this: put a small component on the character that answers the question 'which look should this shot show?'. It is asked at the moment a shot goes out, so it can look at whatever your game knows right then — which weapon is equipped, which powerup is running. If nothing answers, nothing is asked for; there is deliberately no silent fall back to a default look, because a hidden default is exactly the kind of thing that makes a character show something nobody asked it to.

Also fixed in the same pass: a multi-pellet weapon like a shotgun used to ask for its firing look once per pellet, so a five-pellet shot fired its effects five times. It now asks once per shot.

Not verified: the case where a shot is a hitscan (an instant beam rather than a travelling bullet) was confirmed by reading the code rather than by running it — nothing in the toolkit currently calls that path at all, which is itself worth knowing.

This change is not committed to version control yet.
