## Description

Found while verifying T-0383 (which fixed `Pyre.pixelsPerUnit`/`MirageView.displayPixelsPerUnit` drifting from the project's global Pixel Scale setting). Not fixed there — narrower scope, real visual risk to existing authored assets — filed here instead, per the owner's confirmation on T-0383's discussion thread (and independently re-verified by the PM's own dimensional analysis before filing this).

**The bug:** `Runtime/Mirage/MirageRig.cs:224-227` (backdrop) and `:231-234` (`ApplyScale`) compute `scale = displayPpu / sourcePpu`. This is inverted. A sprite's own world width is `texWidth / sourcePpu` (that's inherent to how `SpriteRenderer` draws any sprite). To make it APPEAR as if it had been authored at the view's `displayPixelsPerUnit` instead, the extra scale multiplier needs to be `sourcePpu / displayPpu` — the reciprocal of what's there now. Measured live (by T-0383's agent) at display PPU 16: a source at 32 rendered 4x too small, 64 rendered 16x too small, 100 rendered 39x too small. `MirageView`'s own tooltip promises "a 16-PPU Zoe and a 64-PPU Pyre blast render at the same apparent pixel size" — the current formula makes them 16x apart; the corrected one makes them match.

**Why this was invisible until now:** the formula is a no-op whenever `sourcePpu == displayPpu` — which, after T-0383's fix, is true for every Pyre in this project (all resolve to the project's 16). So this bug only bites: (1) a Pyre with `pixelsPerUnitAuto` turned off, (2) an imported background/backdrop sprite whose own import PPU differs from a view's Display PPU, (3) a `MirageView` with a hand-overridden Display PPU. That's a small, identifiable set.

**Fix:** swap the ratio at both sites (`MirageRig.cs:224-227` and `:231-234`) to `sourcePpu / displayPpu`. Small, well-understood change — but it WILL visibly resize content in any existing authored `MirageView` asset that falls into the three categories above, so do a visual pass over those specific assets after the fix (not a blanket re-check of everything) and say what you found, per T-0383's own risk note.
