Fixed, measured and committed as 9515c20e on dev. The whole sub-pixel bug class closed in one audited pass. Four broken sites found: the incident report predicted two, listed a third as 'verify' (it WAS broken), and a fourth was found only by measuring real chunks in Play mode after the first three were already fixed. The owner's own recipe went from 98.77% of chunks rendering below their own texel grid (worst 0.128x = 7.8 source texels crammed into one game pixel) to 0.00%, worst case exactly 1.0000x.
**Details:**
AUDIT DELIVERABLE: .agenthq/workspace/ChunksPixelSize/SCALE_SITE_AUDIT.md -- 11 sites (A-K), verdict + file:line each.
Exhaustive rather than best-effort because the Chunks module writes Transform.localScale in exactly 3 places, calls
Sprite.Create in exactly 3, and Chunk.Init has exactly 1 caller. Every render-size decision must pass through those.

THE FOUR BROKEN SITES
1. DebrisScatter "Sampled": the crop's texel count (samplePxMin/Max, 5-20) and the chunk's on-screen size
   (sizeMin/Max, 0.16-0.35 world) were two independent rolls, and Chunk.Init divided one by the other. Fixed with a
   new DebrisScatter.FitSampleRange(worldSize, ppu, ...) capping the crop at floor(worldSize*ppu) texels, so scale
   >= 1 by construction; Fire now rolls size FIRST. (Predicted by the report.)
2. DebrisScatter "Squares": called ChunkSprites.Get, not GetFitting -- the exact sibling T-0393's own commit message
   recorded as deliberately out of scope. The report listed it as "verify"; it was broken. Now uses GetFitting.
3. ChunkSprites.GetFitting ITSELF: fitted on a shard's WIDTH while Chunk.Init scales by the sprite's LARGER axis, so
   the non-square 2x3 and 3x2 shards passed the fit on their short side while their long side set the scale -- a 2x3
   shard on a 2px target rendered at 1/3 scale. NOT in the incident report; found only by live measurement. Now fits
   on the larger axis, which satisfies BOTH consumers at once (PaletteSplash scales by targetPx/rect.width, a chunk
   by worldSize/max-axis, and width <= max axis <= targetPx), so one rule rather than a per-caller mode.
4. Chunk.ApplyLook's floor: T-0395 had the right idea in the WRONG UNIT. It floored the outer bounding BOX at one
   game pixel, which under-protects an S-texel crop by exactly a factor of S -- the box stops at one pixel while all
   S texels are crushed inside it. Now stated on SCALE, per axis. Fixing the crop size alone would NOT have closed
   this report, because that only guarantees the size at spawn while the tumble re-crushes it every cycle.

T-0395's OWN RECORDED CAVEAT WAS LIVE, NOT THEORETICAL. It said non-square thin-axis starvation "doesn't apply to
anything in the project TODAY". Sampled crops are square, but the procedural 2x3/3x2 shards are not and every
Squares-mode recipe uses them. Measured thinnest live extent before the fix: 0.67 game pixels -- below the one pixel
that floor was supposed to guarantee.

AUTHORED ART IS DELIBERATELY NOT GIVEN THE STRICT FLOOR. Chunk.Init takes a new pixelExact flag, true only for a
sprite the scatter itself built (sampled cut or procedural shard, both now fitted at spawn). A Sprites pool or an
Animated source passes false and keeps the old one-pixel box floor -- silently ENLARGING someone's 32x32 sprite 10x
to "protect" it would be a worse bug than the blur. Additionally gated on baseScale >= 1 so a future visual mode that
forgets to fit degrades to the weaker floor instead of blowing its chunks up.

CONSEQUENCES THE OWNER SHOULD BE TOLD, NOT LEFT TO DISCOVER
- The tumble's width squash is now bounded by how many whole pixels a chunk has to squash into, so a 3-pixel fragment
  barely squashes and reads as a turn through ChunkTumble's shade swing alone (untouched). Unavoidable: a continuous
  |cos| squash of an S-texel crop IS sub-pixel crushing, and no clamp on the outer box can fix internal compression.
  LEVER: widen the Size range for more headroom above scale 1.
- samplePxMin/Max are now an upper bound on DETAIL rather than an absolute size (both tooltips updated). At the
  currently authored size the Floating Disc recipe cuts 2-5 texels instead of 5-20. LEVER: widen Size and the crop
  follows automatically.
- Seeded bursts re-roll. Moving the size draw to the front changes which rolled value lands on which chunk. Stream
  LENGTH and COMPOSITION are unchanged and ChunkPreviewSim.Debris's mirrored draw moved in lockstep, so seeded
  preview<->runtime parity is preserved by construction.

NO AskUserQuestion RAISED, DELIBERATELY. The one candidate fork ("when the crop range and the size range disagree,
which wins?") resolves by analysis rather than preference: target-wins keeps both dials meaningful AND subsumes the
alternative, because widening Size makes the crop follow automatically. Asking would have stalled the task for an
answer an existing dial already provides.

KNOWN, DELIBERATELY UNFIXED (out of scope, zero assets affected): the non-pixelExact fallback floor still uses the
