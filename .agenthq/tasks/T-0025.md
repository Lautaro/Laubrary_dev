## Description

User asked: "I cant find any Laumination to animate. Why doesnt the asset appear in Laumination Browser?"

Root cause: `ProtoGuyLegs.asset`/`ProtoGuyUpper.asset` (`Assets/Demos/ProtoGuyDemo/Lauminaries/`) were built
directly as bare `LauminaryVersion` assets, bypassing the `Lauminary` wrapper + recipe-based authoring pipeline
entirely — no `Lauminary` container ever existed for them (the Browser only lists `Lauminary` assets under
`Assets/Launimator/Lauminaries/`), and every one of their `Laumination.recipe` fields was empty (`recipe: []`)
— frames were populated directly, never through the normal author→bake flow. Even after fixing visibility,
opening either asset in the Builder would have shown zero frames to scrub/paint on, since the Builder's whole
preview is driven by re-baking the recipe (`EnsurePreviewBake()` → `AtlasBaker.BakeInMemory(recipe, ...)`).

## What was done

1. Reconstructed a `recipe` for every animation (`FrameRef` per baked frame, pointing at that frame's own
   original source texture + its exact pixel rect + normalized pivot) — `fixedFrame=true` matching each
   animation's original frame size, to get a literal reproduction rather than an auto-trimmed re-crop.
2. Hit a real bug doing this (see T-0024) — worked around by batching the whole animation list into the draft
   in one `BuildVersionAssets` call instead of one `SaveAnimationToDraft` call per animation.
3. Created real `Lauminary` wrappers — **ProtoGuyLegs** (`Assets/Launimator/Lauminaries/ProtoGuyLegs_6a0fbd2c/`)
   and **ProtoGuyUpper** (`.../ProtoGuyUpper_b1cceb82/`) — each with a proper draft `LauminaryVersion`.
4. Carried over both `LauminationSet`s (`LegsIdle16`+`LegsWalk3` on Legs, `UpperAim16` on Upper) — these embed
   their own independent `Laumination` copies (not references into `.animations`), so a straight clone was
   correct and needed no re-linking.
5. Verified EXACT pixel-content match (not just size) between old and new frames, for all 35 animations (19
   Legs + 16 Upper) — every single frame, byte-for-byte non-transparent-pixel-count identical.
6. Repointed `ProtoGuy.asset`'s two `ZonedLauminaryView.version` references (Legs and Upper body parts) from
   the old bare assets to the new drafts.
7. Full live regression in Play mode: idle pose renders identically, walking (W held) plays `LegsWalk_N`
   correctly with the new data, screenshot-verified — no visual difference from before the migration.

**The old bare assets** (`Assets/Demos/ProtoGuyDemo/Lauminaries/ProtoGuyLegs.asset` /
`ProtoGuyUpper.asset`) were left in place, untouched, unreferenced — not deleted. Safe to remove once the
user's comfortable nothing else points at them (quick grep first).

## What's now possible that wasn't before

- Both Lauminaries show up in the **Lauminary Browser** (`Laubrary/Lauminary Browser`), can be selected,
  versioned, previewed.
- Each animation can be opened in the **Laumination Builder** for real editing — including the new **Copy
  frame / Paste / Paste all** MetaLayer buttons from T-0023, which is what unblocks the actual next task: the
  T-0021 "Waist" alignment-point authoring pass.
