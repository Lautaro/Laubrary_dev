## Description

Found by T-0288, measured on the live Shaper window with a cherry slot's editor popover open.

**What happens.** The popover puts `Min` and `Max` in one `Z.Row` (`zui-row`, a flex-wrap row). At the popover's own width the two 100 px sliders do not fit side by side, so the row wraps them onto two lines -- but the row keeps its ONE-line height, so the control after it is positioned as if the second line were not there.

**Measured** (world bounds, logical px, popover anchored on slot 2 of three):
- `zui-row` at y=842.7, own height **28.9**
- child `ZuiMicroSlider` "Min" 844.9 -> 862.7
- child `ZuiMicroSlider` "Max" 866.7 -> **884.9**
- so the row's content ends 13.3 px below the row's own bottom, and
- `ZuiToggleButton` "MultiFrame" starts at y=**876.4** -- 8.5 px INSIDE the Max slider. Visible in the attached capture: the word MultiFrame sits over the Max track.

**This is T-0287's defect one level up.** T-0287 fixed the same nested-wrap height staleness for `Z.Field` (`Zui/Toolkit/Zui.cs`), and T-0288 fixed the self-locking stamp that fix introduced. Neither reaches `Z.Row`/`Z.HGroup`, which is what wraps here.

**Not fixed under T-0288** because the row is built by the shared `Editor/Pyre/PyreCherryPanel.cs` (a Pyre file, read-only for this programme) and because the general fix belongs in `Z.Row`/`Z.HGroup` in shared ZUI, which needs its own verification pass across Pyre, Chunks and the other hosts -- exactly the reason T-0284 gave for filing T-0287 rather than fixing it inline.

Repro: open Shaper on any document, tick Cherry Framing, press `+ Add slot` three times, right-click a slot card, then run T-0284's `overflow-probe.cs` logic over `rootVisualElement.panel.visualTree` (the popover's scrim is attached ABOVE rootVisualElement, so a walk that starts at rootVisualElement misses it -- that is why three previous passes did not see this).
