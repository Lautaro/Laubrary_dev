A Pyre Blast can now say what colour its blasts come out in, and how solid each one is. Two dials sit beside Scale on the card: Tint, which multiplies onto everything the blast spawns, and Alpha, a band each individual blast draws its own opacity from. That closes the last part of the use case behind this work - one effect asset, several looks: a ring of five can come out as five differently faded, differently coloured blasts of one Pyre, with no second asset authored and no code. The opacity is drawn from the same seeded sequence the angle and the size already come from, so one authored seed still reproduces the whole appearance of a burst exactly.

Colour lives on the recipe's blast rather than on the effect, deliberately: the same Pyre picked into three recipes is ONE asset, so tinting it there would retint the other two. This is the per-use override the recipe was always the right home for.

Existing recipes are unchanged - a blast is white and fully solid unless you say otherwise, and an untouched recipe does not even take an extra draw off its random sequence, so the arrangement a seeded recipe produced yesterday it still produces today.

One correctness bug came with it and is fixed: Pyre's blast players are pooled and handed on to whoever asks next, and nothing ever put the renderer's colour back. Once anything recoloured a player, the next effect to borrow that instance came out in the previous shot's colour - which would have hit you the first time you tinted one blast and wondered why an unrelated explosion elsewhere turned red. A play now always starts from the frames' own colours.

The preview keeps its promise to predict the burst: the discs take the tint and each instance's own alpha, so both dials visibly change the picture, and a white solid blast draws exactly what it drew before.

**Technical details:**
FIELDS ADDED (Runtime/Chunks/Capabilities/PyreBlast.cs)
- Color tint = Color.white; [Range(0,1)] float alphaMin = 1f, alphaMax = 1f - placed between scaleMax and seed.
- ResolveAlpha() mirrors ResolveScale(): it clamps the band and draws from the capability's own _rng, but returns lo WITHOUT drawing when hi <= lo. That skip is what keeps an existing recipe's sequence of angles and sizes bit-identical - only a recipe that authors a band shifts its own later draws.
- Paint(Transform, float) sets new Color(tint.rgb, tint.a * alpha) on every SpriteRenderer under the returned transform, via the non-allocating GetComponentsInChildren(bool, List<T>) into one shared static buffer (a burst spawns dozens). Called in SpawnOne immediately after SpawnEffect returns, before the Trajectory decoration. IChunkEffectSpawner was NOT changed.
- It writes on EVERY spawn, the white default included, on purpose: two blasts in one recipe can share a pool, so skipping the white write would let capability A's red leak into capability B's untinted spawn.

PYRE WAS EDITED - one line, the sanctioned exception (Runtime/Pyre/PyreBlastPlayer.cs)
- Play() now does sr.color = Color.white before re-asking for frames. Checked first: neither Play(), nor PyreBlastPool.Get(), nor PyreDirectSpawn's release handler (which restores scale and rotation) ever touched colour - so the stale-tint bug was real. Ordering is safe: PyreDirectSpawn calls Play() inside SpawnEffect, so Chunks paints AFTER the reset. Chunks' always-write and Pyre's reset each cover what the other cannot: Chunks protects the spawners it paints, Pyre protects the callers it never sees (SpawnPyreFx, PyreChunksFx, Mirage's realize switch).

CARD (Editor/Chunks/ChunkWindow.PyreBlastCard.cs)
- One Z.HGroup added directly after the Scale/On-screen row: Z.Field("Tint") wrapping Z.Color(..., 110f) - the same control and width DebrisScatter's tint colour already uses - and Z.MicroMinMax("Alpha", 0..1, 180f, decimals 2). Both write through Dial (undo recorded, asset dirtied, preview invalidated); neither changes which controls exist, so no card rebuild is needed for them. The Seed tooltip now names opacity alongside picking, angle and size.

PREVIEW (Editor/Chunks/ChunkPreviewSim.cs)
- Blast() multiplies the tint's RGB onto the slot colour the disc already had (Fade() overwrites a guide's alpha from the alpha field and ignores the colour's, so the tint's opacity is folded into the alpha instead) and multiplies the disc's fade by tint.a and by BlastAlpha(b, seed, placement.Index). The flight path takes the tinted colour too; a pending point's ring takes the colour but keeps its full outline alpha, since dimming a not-yet-fired outline by an authored band would hide the placement.
- BlastAlpha hashes the seed with the point's index (stream 613 + index), the same approach BlastRadius takes for scale and design decision 9 takes for the pool pick, because the preview does not walk a pattern in firing order. KNOWN AND PRE-EXISTING: T-0216 filed that a pattern's per-spawn draws depend on FIRING order at runtime while the preview hashes from the index, so which exact value lands on which point can differ between preview and burst. Alpha inherits that caveat exactly as scale and the pool pick already do; the band, the seed and the set of values are the same.
