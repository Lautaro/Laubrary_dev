## Description

Fake light now creates a Light Radious toggle on the UI. This appears there evern if there is no fake light in the stack. This is unacceptable and will cause bloat. We will have more FX modules that need costume preview drawing. Create a pattern where active spriteFX modules can register custom preview visuals that can only draw if that entry is enabled. If there are several of the same type then the type has to have logic for what this means. But most likely each one handles their own visualiser. Perhaps they should add a tiny label that shows which one it is in the index order. This task is to create a better reusable patter, refactor Fake Light to follow it and then make sure that using it will be the choice for next claude in this situation.

### 2026-08-24T07:55:44Z — agent — in_progress -> done
The 'Light radius' button no longer clutters the SpriteFx preview when there is no Fake Light to use it on. Each effect now brings its own preview marker and its own button, which appear only while that effect is actually in the stack and switched on, and vanish with it - so adding more effects that need preview visuals can never pile up permanent buttons again.
**Details:**
What you will see: open a SpriteFx Stack with no Fake Light in it and there is no 'Light radius' button at all. Add a Fake Light and the button appears; switch the light off, delete it, or set it to Directional and the button disappears again. Switch the button on and the preview gains a yellow circle showing the light's reach and an orange dot showing where the light sits.

Several of the same effect: each one gets its own separate button, numbered ('Light radius 1', 'Light radius 2') so you can tell them apart, and hovering a button says which effect it belongs to and where it sits in the stack. Turning one on lights up only that one. An effect that would rather have all of its copies share a single button can now ask for that instead - that choice belongs to the effect, not to the window.

Caveats:

Not verified by a human clicking: the numbered multi-copy case. Everything about it was tested by driving the real code with two and three lights and checking the results, and by looking at the window with a single light, but nobody has sat down and clicked through a stack containing two Fake Lights.

Worth knowing: the circle marks the light's radius setting only. Light height and falloff also affect how far the light visibly carries, so read the circle as where the light is aimed rather than exactly where it stops. The button's tooltip says so.

Worth knowing: the marker is drawn after the whole stack has run, so an effect later in the stack that warps or shifts the picture will move the sprite but not the circle.

Heads up: another automated task was rewriting the same preview window at the same time as this work (its own change replaced the preview's scrub slider with a timeline bar). The two changes coexist and the project compiles cleanly, but that file was still being edited as this finished, so it is worth a look if the preview area seems odd.

Your on/off choices for these markers are deliberately forgotten when the editor reloads scripts. That is on purpose: remembering them turned out to be the thing that made a remembered choice jump to the wrong light.

TWO REAL BUGS WERE FOUND BY REVIEW AND FIXED - do not reintroduce either:
1. Toggle state must key on the effect INSTANCE (ConditionalWeakTable), never on label+ordinal in EditorPrefs. An ordinal is a position among the overlays that currently qualify and is recomputed every Collect, so disabling the middle of three lights makes the third inherit the second's flag. Reorder/delete/mode-flip do the same, and a per-window pref key also bled one asset's choices onto another. Cost: state does not survive a domain reload. That is the accepted trade.
2. The strip must reserve a MINIMUM height and be allowed to shrink horizontally. A fixed height plus flexShrink=0 plus NoWrap looks like the stricter reading of the stable-workspace rule and is the dangerous one - with several overlays it becomes an unshrinkable wide control inside a column allowed to shrink to 0, forcing an h-scrollbar or wrapping the whole column out from beside the preview stage.

REFRESH PATH: structural edits (add/remove/reorder/enable, and any field a [ZUIShowIf] reads - which covers RelightModifier.mode) go SpriteFxStackView.Structural() -> host.Rebuild -> window Rebuild() -> BuildPreview -> fresh Collect. Host.OnChanged -> RefreshOverlays() is the fallback for a future effect gated on a plain value edit; it signature-compares (Overlay reference, Label, Members.Count) and only refills when the set actually differs, so a slider drag does not rebuild controls under the cursor. Undo is already covered by ZuiWindow's Undo.undoRedoPerformed -> Rebuild.

DELIBERATE BEHAVIOUR CHANGE: WantsPreviewOverlay is 'mode == Point' only; the old 'picture size known' condition was dropped. pictureW/padX are set at render time by SpriteFxStack.RunStack, but Collect runs at UI-build time, and Fake Light's OutwardReachPx() is 0 so a light-only stack takes the unpadded path - gating on it would have shipped a toggle that never appears. DrawPreviewOverlay reuses Apply's own 'known ? pictureW : canvas.Width' fallback so the marker cannot drift from what was shaded.
