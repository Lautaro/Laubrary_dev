## Description

When using toggle bar mode there should be three modes. 1. User selection: this is updated when user starts toggling sections. 2. Show all: this is temporary and shows all sections. 3. Show none: also temporary.  The idea with this is that right clicking the "Toggle Bar" radio button takes you through the 3 modes. If user starts changing the setup when in Show all or Show none then that new setup becomes the new mode 1, user selection view. This is a quick way to set up the view that the user wants by starting from show none or show all.

**Details:**
How to use this
1. Put the toggle bar into "Toggle Bar" mode (left-click that button, as before).
2. Right-click the same "Toggle Bar" button to step through: your selection -> show all -> show none -> back to your selection.
3. While a temporary sweep is active, the "Toggle Bar" button turns amber so you can tell at a glance that what you are looking at is not your own arrangement.
4. Click any section button and that instantly becomes your new saved arrangement, and the amber clears. Starting from "show none" and clicking up the handful of sections you want is the quickest way to build a view.

Your arrangement survives switching modes, changing which asset you are editing, and a script recompile. Nothing you set up can be lost by using the sweeps.

Anything that opens the toggle bar gets this automatically - Pyre, Chunks, Mirage, Sprite Fx, Launimator, Cartographer. Nothing else about those tools changed.

Not verified: only Pyre was walked by hand. The other five tools share the identical control, so they get the same behaviour, but no human has clicked through them.

Known cosmetic point, left alone deliberately: the existing green "solo" highlight (right-clicking an individual section button) makes that button 1 pixel bigger on each side, which can nudge the row. That predates this change and fixing it would alter how solo looks, so it was left for you to decide.

Design decisions worth knowing:
- Right-click is wired with `RegisterCallback<PointerDownEvent>` + `e.button == 1` on `_mode.SegmentAt(1)` only — the same pattern T-0076 solo already uses, because Clickable ignores button 1. Not ContextualMenuManipulator, not IMGUI.
- Right-click while in Sections mode only switches INTO Toggle Bar mode and stops; it does not cycle. Deliberate — a first right-click must never destroy an arrangement before the user has seen the gesture do anything.
- State lives in EditorPrefs (`ZuiSectionToggleBar.<prefsKey>.quickView` / `.userSel`), never instance fields, because five of the eight consumers destroy and rebuild the bar on every asset refresh.
- The user selection is keyed BY SECTION LABEL (`Tags=1;Views=0;...`), not by position. Launimator builds its roster conditionally (`Identify Sprites` drops when the left pane collapses, `Meta Layers` appears when the laumination has them), so two different rosters of the same LENGTH exist and a positional set would silently restore the wrong sections. Unknown label on load defaults to OPEN.
- The ctor runs `if (BarMode) ApplyQuickView(Quick)` UNCONDITIONALLY. `ZuiSection.s_open` is a static dictionary wiped by domain reload while the prefs survive; without this, a recompile silently lost the arrangement and the next hand-toggle saved the wrong set over it. Also re-asserts the selection over a solo mask stranded by a mid-solo rebuild (`_solo`/`_preSolo` are instance state).
- `Apply()`'s `!barMode` branch restores the user selection BEFORE clearing the quick-view flag. This was the blocker the review found: a Show none carried out of Toggle Bar mode and back looked like the user's own selection, and the next right-click's `SaveUserSelection()` wrote all-hidden over the real set, unrecoverably.
- Amber cue is colour-only by design (UI guide "Stable workspace"). Measured: `seg1.worldBound` = (x:77.33, y:59.11, w:79.11, h:18.22) and all four border widths = 0/0.889/0.889/0.889 IDENTICAL across all three modes; `innerBar.x` and bar height unchanged too.

Testing note for whoever picks this up: dispatching a synthetic `PointerDownEvent` to a bar that was constructed in the SAME `eval_file` call silently does nothing — `worldBound` has not been laid out yet, so the event does not route. Select the asset in one eval, then act in a second. Two separate false negatives came from this before it was identified.

Open/known, not fixed: (1) `.zui-segmented__solo` (pre-existing T-0076, ZuiToolkit.uss) bumps all four border widths 1px->2px on a bar whose root sets `flexWrap = Wrap.Wrap`, so a solo can re-wrap the row — same hazard the quickview rule avoids; left alone as out of scope for T-0085. (2) The amber outline is three-sided because `.zui-segmented__seg` sets `border-left-width: 0` for non-first segments; verified acceptable by eye, and adding the left border would change geometry.
