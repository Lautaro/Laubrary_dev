## Description

The three performance requirements, treated as architecture rather than optimisation (design B9). Every node caches its output keyed by a hash of its own settings and its children's hashes, so editing a dial dirties that node and everything downstream and only that - the failure mode to design against is recomputing the whole document on every mouse-move. Each node also caches per frame, so the first pass through an animation may compute and every later loop replays; add a background pre-bake that does not block the UI and a visible indicator of which frames are cached, so a slow first loop reads as working rather than broken. Canvas sizes measured from the source rather than assumed: the document schema bounds resolution to 32-256 with 96 the default, the renderer clamps 16-256, grid height is derived from the canvas aspect rather than being square, and the whole grid is capped at 68,000 cells. The default 960x640 canvas at resolution 96 therefore gives a 96x64 grid - 6,144 cells - and the true worst case is about 68,000. Budget against 6,144 typical and 68,000 worst, not against "64 square"; the budget is still generous provided work is not repeated. Cost model is one pass per node per frame - a dozen layers each holding a bag of four sub-shapes is around sixty passes a frame before effects, which is fine with caching and not fine without it.

If a tilted or otherwise non-fixed camera is ever added, its resolve is a per-pixel search rather than a per-pixel evaluation, so its cost is not bounded by the shape's area the way today's is. Make it a separately keyed, separately budgeted cache node from the start, so a document that tilts one layer does not silently lose the responsiveness guarantee for the eleven layers that did not.

The authoritative design is the "Shaper - the design" tab of this group's planning document (also at D:\UNITY\Laubrary Dev\.agenthq\workspace\T-0098\SHAPER_THE_DESIGN.md). Read it before starting. ### 2026-08-31T22:00:58Z — agent — in_progress -> in_progress
Shaper now has a real caching system built in: when you tweak one dial on one shape, only that shape (and the layers stacked on top of it) redraw -- everything else on the canvas reuses what it already had, instead of the whole picture recalculating every time your mouse moves. Playing an animation also gets faster after the first pass, because each frame is remembered once it's been computed.

[[attach:20260831T220058Z_SPEC.md]] [[attach:20260831T220058Z_VERIFICATION.md]]
**Details:**
This is architecture, not a visible feature -- there is no Shaper editing window yet in this project (it hasn't been built), so nothing looks different on screen. What changed is how the underlying engine works, verified with real measurements rather than just claimed: editing one shape among four costs 3 units of recomputation instead of 8; replaying an already-seen animation frame costs zero new work; a background pre-loader for animation frames is built to run without freezing the editor (its actual smoothness in a live session wasn't able to be tested here, only its design).

Not yet done / known gaps: a less-common authoring shape (sweeping a group of shapes lengthwise, rather than radially) isn't optimized correctly yet and was flagged rather than silently shipped; swarms of repeated shapes cache as one block rather than reusing individual copies when you add more copies; and there's no on-screen indicator yet showing which animation frames are already cached, because there's no window to put it in yet.

How to use this: nothing to operate directly right now -- this becomes visible once a Shaper editing window is built on top of it, at which point dragging a dial should feel instant instead of laggy.

Architecture in one paragraph: ShaperNodeIdentity hashes a node's own settings (excluding mode/blend, which the PARENT folds in per child, and excluding children themselves for a Bag) plus phase01/seed unconditionally. ShaperCachedEvaluator recursively evaluates a tree, reusing ShaperCompiler/ShaperEvaluator for each LEAF (Primitive/Composite) as a one-node mini-subtree so leaf math is never reimplemented, and folds Bag members incrementally with each PREFIX of the fold cached -- this is what makes editing member k of n cost ~(n-k) work, not n. Swarm nodes cache as one atomic unit via the real compiler's own swarm expansion (per-instance sub-caching was designed -- ShaperNodeIdentity.SwarmInstanceKey -- but not wired in, an honest scope cut). ShaperFrameCache is a thin bookkeeping layer over the SAME node cache (phase01 already makes each frame a distinct key) plus a non-blocking EditorApplication.update-driven pre-baker. ShaperTiltedResolveCache is a structurally separate key type + separate budget, a pure seam with no resolver behind it yet.

Two real bugs found and fixed during this task's own adversarial audit: (1) ShaperCacheBudget's grid-cell math overflowed a 32-bit int for extreme aspect ratios, silently producing a negative cell count instead of tripping the 68,000 cap -- fixed with long arithmetic. (2) the cache-hit path originally called ShaperCompiler.Compile() again just to read a node's support box, which for a Composite node re-renders the hosted source on every hit, defeating the whole point of caching it -- fixed by carrying the box on the stored buffer itself. Both are documented in SPEC.md/VERIFICATION.md with the exact before/after audit output.

Honest scope limits (9 total, see VERIFICATION.md Part 3): a Bag's own Longitudinal sweep is WRONG (not just unoptimised) in the cached path -- radial works, longitudinal silently falls through as identity; per-instance swarm sub-caching designed but not wired in; the reach-formula divergence check (CT10) covers exactly one test scene, not proven in general; node buffers are canvas-sized rather than cropped to each node's own support box; a Composite source that mutates its own fields in place (rather than being swapped for a different reference) goes stale-cached under the fallback hash; background pre-bake's real-world non-blocking smoothness wasn't verifiable via the Unity-CLI-only testing this task could run; no visible per-frame indicator exists yet since there's no Shaper window to put one in; the effect-stage cache key is a scheme only, not wired into T-0114's standalone ShaperEffectStageRunner proxy; and ShaperNodeCache's eviction is O(entries) linear scan, not O(1) LRU.
