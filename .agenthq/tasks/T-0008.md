## Description

The user caught two things after T-0007 was first marked done: (1) my "real screenshot" proof of firing was actually a misread of an unrelated overlapping character (see the corrected T-0007 for that), and (2) more importantly — the whole feature had only ever been verified on **Hero** (a single-part Zoe), when the actual point of this feature, given the whole session's context, was to work on **ProtoGuy**, the composite (Torso+Legs) Zoe this session built. "but u know that the task is to set up protoguy right? not hero."

Attempting to wire the vector-muzzle weapon onto ProtoGuy surfaced a REAL, previously-undiscovered bug: `ZoeSpawner.EquipWeaponSlots` always parents a weapon slot under the shooter's ROOT transform. For Hero (single-part, `IAnimatedView` lives on root) this works. For ProtoGuy (composite, `IAnimatedView` lives on the "Upper"/"Legs" CHILD parts, not root) it silently doesn't — `MuzzleTracker`/`MuzzleVectorTracker`'s `GetComponentInParent<IAnimatedView>()` search can never reach a child part from a root-parented weapon slot. No exception, no warning — `HasDirection` just stays false forever, which would have looked exactly like "the feature doesn't work" if tested on ProtoGuy from the start, rather than the actual root cause (a parenting gap that predates this whole feature).

## What was built

- `WeaponDef.attachToPartName` (empty = root, unchanged default for every existing weapon).
- `IPartLookup` (`Runtime/Zoetrope/IPartLookup.cs`) — same optional-capability interface pattern as `IMotionPoseHost`, keeping core Zoetrope free of any Launimator-bridge reference.
- `CompositeZonedPlayer` implements it (`FindPartTransform(name)`).
- `ZoeSpawner.EquipWeaponSlots` resolves the slot's parent via `IPartLookup` when `attachToPartName` is set, falling back to root otherwise (byte-identical behavior for every weapon that doesn't opt in).
- A real `WeaponDef` for ProtoGuy (`Assets/Demos/ProtoGuyDemo/ProtoGuy Gun.asset`, duplicated from Hero's for convenience, `attachToPartName="Upper"`, `muzzleVectorLayerId="MuzzleVec"`), a real authored Vector MetaLayer on ProtoGuy's own `Upper_E` laumination, and the weapon added to `ProtoGuy.asset`'s `weapons` list — so `ProtoGuyDemo.unity` now spawns ProtoGuy WITH a working vector-muzzle weapon by default, no extra setup needed to see it working.
