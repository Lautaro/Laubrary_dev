## Description

User-raised 2026-08-20: "the editor is really struggling… the second loop should run flawlessly, no?" The animated preview (`PyrePlusWindow.Preview.cs`) keeps ONE texture and calls `PyrePlusRenderer.RenderFrameTexture` every time the frame index changes, so looping playback re-renders every frame on every loop and the editor freezes between frames on expensive forms (Arc Burst up to ~380 ms/frame at 128 px). The Strip view already caches every frame (`stripCache`) keyed by `previewDirty` + frameCount/canvas — that is the precedent. Build one shared frame cache for the animated preview and the strip, filled incrementally (current frame first, then a time-budgeted amount per editor tick), invalidated by every authored edit, with a subtle "rendering n/N" readout in the transport while it fills. Renderer untouched; bake/export byte-identical.

Standing rules: autonomous, never stall, commit after each verified milestone, log handovers here.

**Baseline (eval_file, renderer only):** Arc Burst / Lichten, 128 px × 24 frames: first frame 410 ms, 358 ms/frame avg, 518 ms max, **8.6 s per loop — paid on every loop** by the old single-texture preview.
Decisions taken without asking:
- **One cache, new partial `PyrePlusWindow.FrameCache.cs`; `stripCache` removed** — the Strip view reads the same textures. The CherryFraming source-grid thumbnails stay a separate structural-only cache: its textures are bound to UITK tiles as `backgroundImage`, so they must outlive every preview refill (unifying would need a tile-refresh path — not worth the risk here).
- **Textures are stable:** allocated once per (frameCount, canvasSize), `HideAndDontSave`, RGBA32 point-filtered; an edit clears ready flags and renders INTO the same textures (no GPU churn per dial drag). Destroyed on disable / asset change / structural change; rebuilt after a domain reload (fields are null).
- **Playback gating = "play only the ready prefix":** `Tick` only steps onto a cached frame; at the render front it holds `acc` at one beat so it moves the instant the frame lands. For CherryFraming the beat state is snapshotted, `CherryAdvanceOneBeat` runs unchanged, and is rolled back if its pick is not ready. The preview itself never renders during playback; a cache miss in `DrawPreview` (a scrub, or the first repaint after an edit) renders that one frame synchronously — the "current frame first" rule. The fill tick also re-targets the frame on screen first if it is missing (cherry picks / resets move `frame` between ticks).
- **Fill budget 12 ms, ≥ 1 frame per tick, forward from the current frame, wrapping.** Runs paused or playing.
- **Undo / asset switch invalidate via `OnBeforeRebuild`** (ZuiWindow.Rebuild bypasses Dirty; before this, a PAUSED preview kept the pre-undo frame — a latent bug the old per-tick `previewDirty = true` hid while playing).
- **Non-render edits no longer invalidate:** Frame / Strip toggles, loop Delay, `ResetCherryPlayback`, and all 12 CherryFraming sequence edits moved from `Dirty` to `DirtyRepaintOnly` (cherry is preview-only — confirmed the renderer and GIF never read it). Without this every cherry slot edit would re-render the whole clip.
- **Readout:** `Z.Text` (Subtle) `rendering n/N`, fixed 110 px, LAST in the Zoom/Speed/Delay/frame row, `visibility` Hidden when idle (never display — no reflow). Tooltip reads for the current state and carries the last complete fill's wall time + slowest frame (the optional profiling readout — added, cost is two doubles).
- **Zero-cost debug hook kept:** `cacheRenderCount` (an int increment per renderer call) so a probe can prove playback renders nothing.
- GIF export left on the renderer (byte identity untouched). `PyrePlusRenderer` untouched.
