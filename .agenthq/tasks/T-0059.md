## Description

User-raised 2026-08-20: "the editor is really struggling… the second loop should run flawlessly, no?" The animated preview (`PyrePlusWindow.Preview.cs`) keeps ONE texture and calls `PyrePlusRenderer.RenderFrameTexture` every time the frame index changes, so looping playback re-renders every frame on every loop and the editor freezes between frames on expensive forms (Arc Burst up to ~380 ms/frame at 128 px). The Strip view already caches every frame (`stripCache`) keyed by `previewDirty` + frameCount/canvas — that is the precedent. Build one shared frame cache for the animated preview and the strip, filled incrementally (current frame first, then a time-budgeted amount per editor tick), invalidated by every authored edit, with a subtle "rendering n/N" readout in the transport while it fills. Renderer untouched; bake/export byte-identical.

Standing rules: autonomous, never stall, commit after each verified milestone, log handovers here.
