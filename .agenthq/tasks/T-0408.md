## Description

The build task under T-0406. A full audit of the existing engine was done first, and it changes the shape of this job substantially — **for the better, and in one place for the worse.**

### The good news: this is a restructure, not a rewrite

**Every one of the 16 effects already has its per-sample arithmetic written as flat indexed maths over plain float arrays** — no managed collections, no allocation, no exceptions, nothing thrown, in the whole render path. This was deliberate: the code's own header says each node was written so that it would port to C unchanged, and it did exactly that once already when it became a C++ plugin. So the arithmetic does not need porting so much as re-hosting.

**The dispatch is already the right shape too.** Choosing which effect to run is a plain switch on an integer type tag calling plain static routines — no virtual methods, no interfaces, no delegate tables anywhere in the chain. That is precisely what Burst requires, and it is the single piece of the design that needs no change at all.

The 16 effects, with the state each needs: gain and normalise and fade (stateless); limiter, compressor and transient shaper (one or two envelope followers); low-pass and high-pass (a resonant filter, 16 floats); a seven-band equaliser plus cuts (nine chained filters, 144 floats); delay (a stereo ring buffer with feedback and optional ping-pong); reverb (eight comb filters and four all-pass stages per channel, a few thousand floats); flanger and chorus (short modulated delays); phaser (a cascade of swept all-pass stages); bit-crush (quantise and sample-hold); distortion (drive into a soft clipper with tone shaping and a DC blocker).

### The bad news, and it must be faced before any code is written

**There is only ONE copy of this engine, and the offline renderer runs it.** The instruction "the offline renderer stays as-is" cannot be taken literally, because the offline renderer is not a separate implementation — it calls the very same per-sample engine, layout and effect routines that the real-time path calls. That is deliberate: it is how the offline path currently gets its "identical to the real thing" and "allocates nothing" guarantees for free.

So "port the real-time path and leave offline alone" is not achievable as stated. Two ways out, and they are not equivalent:
- **Keep one copy.** Make the shared routines Burst-compatible and have both paths call them. The offline path keeps being identical by construction, because it is running the same code.
- **Keep two copies.** Leave a parallel ordinary-C# version for offline. This reintroduces exactly the duplication the current design exists to avoid, and guarantees eventual drift.

**Decision: keep one copy.** A Burst-compatible static routine is still an ordinary C# method — it can be called directly from ordinary code, and is only machine-compiled when reached through a Burst entry point. So one set of routines taking native buffers serves both callers with no duplication and no job-scheduling machinery on the offline side. This mirrors what a sibling tool in this package already does (see T-0406), and it is the reason that pattern was worth copying.

**A precision caution that comes with that decision, and is easy to miss.** The same source compiled by Burst and compiled normally can still produce slightly different floating-point results, because Burst is free to reorder and vectorise arithmetic. If the two paths must agree exactly, **the aggressive floating-point optimisations must be left off for these routines.** This is a different risk from the one carried over from the C++ work, and it is the one that actually applies now. Decide it explicitly and write it down next to the code, or someone will "optimise" it later and silently break the equivalence.

### What actually has to change

Mechanical, low risk:
- The maths calls go through the general-purpose engine maths helpers rather than the Burst-sanctioned ones. Every call site needs a swap. Most are once per block and cosmetic; one effect rounds **per sample**, so that one matters for speed.
- Two fast approximations for logarithm and exponent reinterpret a float's bits using a general-purpose conversion helper that Burst does not accept. They need the sanctioned bit-reinterpret instead. Small but real, and both the compressor and the transient shaper depend on them at audio rate.
- Two effects read fixed tuning tables held as shared read-only arrays. Either confirm those are acceptable as constant data or inline them. Do not assume.

Structural, where the real work is:
- The layout description is a managed object, but nine tenths of its contents are already flat fixed-capacity arrays of primitives addressed by integer offsets — those convert to native buffers with no change to the offset logic. **Three fields are the exception: they are arrays-of-arrays, one variable-length list per modulator.** Those must be flattened into one shared buffer plus an offset and count per modulator — and the pattern to copy already exists three times over in the same file.
- The per-voice object is a class holding plain arrays, and must become a value type over native buffers. **This is already done** — the new per-voice state container mirrors its fields exactly and is the destination.
- The voice holds references to two managed objects (the decoded audio and the layout). Burst code cannot hold a class reference at all, so these must be passed in as native buffers.
- Cross-thread signalling currently uses low-level volatile reads and writes on integer fields for stop, release, pause and the pitch and gain targets. Burst cannot call those. **This is exactly what the audio framework's own two channels replace** — discrete events through the message channel, per-block streams through the data pipe. This is not extra work; it is the work, and the framework is designed for it.
- Completion events are pushed into a managed ring buffer. That moves to the boundary.
- The source read cursor uses double precision while the effect maths is float throughout. Burst supports both, so this is not a blocker, but mixing them is precisely the kind of seam that produced real bugs last time. **Make a deliberate decision rather than carrying it through unexamined.**

### Where the float-rounding traps actually are

Not evenly spread — concentrated in computations that turn a float product into a buffer length or a read index:
- The delay line's length and its tap position. The code already carries a comment about a previously-fixed off-by-one exactly at the ring wrap, so this is a known-sensitive spot, not a hypothetical one. Test at delay times landing exactly on a whole number of samples.
- **The reverb's comb and all-pass lengths, which are the dangerous ones.** They are computed from a float product and a ceiling, and the same computation is used to decide how much state the voice must allocate. A rounding disagreement here is not an audio artefact — it is a buffer of the wrong size, so a real memory bug. Test at sample rates that do not divide the tuning table's base rate evenly.
- The flanger and chorus modulated-delay lengths and tap reads, same shape; the chorus additionally multiplies the tap by a detune factor, one more chained multiply feeding the same truncation.
- Bit-crush multiplies, rounds and multiplies back on every sample. Lower risk since it only changes a sample value rather than an index, but include it in any numeric comparison.

### T6 — REDESIGNED 2026-09-27 — agent — unchecked
**Do NOT put native buffers in the shared chain layout.** Instead give each voice its own native snapshot of the layout, taken when the voice starts. Reasoning in the Handover Log entry "the obvious conversion would have been a use-after-free" — the original wording of this step described a design that crashes.

**The design part, which is not mechanical:** native buffers must be released explicitly, and layouts are **cached and invalidated wholesale** — so the cache has to dispose what it evicts or the process leaks native memory on every chain edit. The shared empty layout is a separate case: it must live for the whole process and must never be disposed by an invalidation. Settle both before converting a single field; a leak here is invisible in the editor until it is large, and a double-dispose is a hard crash rather than a wrong sound.

**Why this is split from T5b:** doing dynamic sizing and a type change in one step would mean a single large invasive edit whose verification cannot distinguish "sized wrongly" from "released wrongly". Small verified increments have caught two real issues already this session, so the pattern is worth keeping for the riskiest step rather than abandoning at the end.

### 2026-09-27 — agent — the obvious conversion would have been a use-after-free. Design changed.

Checked the assumption behind this step before writing any code, and it does not hold. **Converting the shared chain layout's arrays to native buffers would crash on the audio thread.**

Why: invalidating the layout cache does nothing but drop dictionary entries, and a playing voice holds a direct reference to the layout it started with for its entire life — that is deliberate and documented, so that editing a chain never disturbs sounds already playing. Today this is safe purely because the garbage collector keeps an evicted layout alive as long as a voice still points at it. Native memory has no such protection. So "dispose the layout when the cache evicts it" — the obvious reading of the original plan — frees buffers that a voice is still reading from on the audio thread. That is a use-after-free, not a leak: it produces garbage audio or a hard crash, intermittently, only when a chain is edited while something is playing. It would have been miserable to diagnose later.

Reference counting the layout would fix it, but it adds cross-thread bookkeeping to exactly the path that must stay simple, and the framework's own model points elsewhere.

**The design instead: the layout stays an ordinary managed object, and each voice takes its own native snapshot of it when it starts.** The layout is immutable once built and a voice never needs to see a later version, so a snapshot loses nothing.

Why this is the right shape rather than merely a workaround:
- **The lifetime problem disappears entirely.** A voice owns its snapshot and releases it when the voice ends. Nothing is shared, so nothing can be freed underneath a reader, and the cache can go on simply dropping references.
- **It matches the audio framework's own ownership model.** A generator's real-time struct is handed its native data at creation and releases it through its control half's disposal. Sharing one native buffer between generator instances with independent lifetimes would fight the framework rather than use it.
- The per-voice state container already in place is described as being owned exclusively by one play for the life of that play. Extending that ownership to the layout snapshot is consistent rather than novel.

**The cost, measured rather than hand-waved:** the layout's fixed arrays come to roughly four to five kilobytes at the configured limits (sixteen nodes, about two hundred flat parameters, eight modulators, thirty-two bindings). At sixty-four voices that is a few hundred kilobytes worst case, and the copy happens once when a voice starts, never per block. That is a good trade for removing a whole class of crash.

**A later optimisation, deliberately not done now:** many voices often play the same chain, so one shared native snapshot per layout with proper reference counting would save that memory. Correctness first; the memory is not a problem at these limits, and the sharing version can come later behind the same interface if it ever matters.

### 2026-09-27 — agent — the two errors this conversion always produces, and why compiling matters

The buffer conversion is done and verified — byte-exact on all six renders, and leak-free across seventeen domain reloads. Two compile failures came with it, both systematic rather than accidental. They will recur in every remaining conversion step, so they are written down rather than left to be rediscovered three more times.

**1. A `readonly` field of a struct type cannot be written through its indexer.** With a managed array, `readonly` froze only the reference, so writing elements was fine. A native buffer is a struct, so `readonly` freezes the whole value and every element write is rejected. The fix is simply to drop `readonly` from those fields — it was never protecting the contents anyway, only the identity. Around sixty errors, one cause.

**2. A native buffer's indexer returns a copy, so mutating one field of a struct element in place is rejected.** Code of the form "element dot field equals value" silently becomes "mutate a temporary" in the eyes of the compiler, which correctly refuses it. The fix is to read the element into a local, mutate the local, and write it back once — and the subtle part is any early exit in the middle of that block, which must write back before it leaves. There is no reference-returning accessor on this buffer type to avoid the copy; that exists only on the fixed-capacity list types, which these are not.

### 2026-09-27 — agent — the generator's shape, concretely

Written now, while the conversion steps are in flight, so that building it is assembly rather than exploration. It combines the reference implementation's hosting with this engine's existing state model.

**Two halves, as the framework requires.**

The **cold half** runs on the main thread and may do anything ordinary code can. Its job: take the resolved chain layout, build the native snapshot from it, hand the real-time half its buffers, receive the sample rate from the framework's configure step and pass it in, and release everything on disposal. It is also where a live parameter edit arrives from the editor, and where a stop or release request is turned into a message.

The **hot half** is a value type with no managed references at all, marked for Burst with **synchronous compilation** — not optional, since without it early runs execute as ordinary code and any measurement is meaningless. Its per-block work is exactly what the existing voice already does, in the same order: step the control-rate values, evaluate the modulators and apply their bindings, read the source with pitched interpolation, run the chain, apply output gain, update bookkeeping. **This is not new logic. It is the existing render path with its inputs already native.**

**What it owns, and how little that is.** Three allocations per voice, not one per effect:
- the shared state arena, with each node reading its own region by offset — a filter's history, a delay's ring and a reverb's combs all live in it;
- the layout snapshot;
- its own output buffers, or the framework's supplied buffer if that can be written directly.

Everything else is a scalar or an offset.

**The two cross-thread channels, and which to use for what.** Discrete one-off events — stop hard, release and let the tail ring, pause, resume — go through the message channel. Streams of per-block values — a pitch or gain envelope driven by gameplay, a slider being dragged — go through the data pipe. This is what replaces the volatile integer flags the current voice uses, and it is not extra work: those flags exist only because there was no sanctioned channel. The framework also lets each half declare how eagerly it wants updating, so a voice with no live automation need not be visited every block.

**The one genuinely open question is the audio data**, for the reasons in the entry below. The generator's scope decides it: one generator per *sound* makes owning a copy natural, one per *voice* makes reference counting necessary. **Decide the scope first, then the ownership — not the other way round.**

### 2026-09-27 — agent — Burst rejected the render, and the reason is worth the trip

Marked the render for Burst and asked for strict floating-point. **It compiled as C# and Burst refused it**, with a precise and genuinely useful diagnosis. The attributes have been backed out so the project stays green; this is the finding, not a setback.

**The rejection, in plain terms:** Burst followed the call chain out of the render, into the chain processing, into the reverb's per-block work, into the reverb's *reset*, into its comb-length calculation — and there it hit the effect-descriptor table, whose static setup builds a list of **small anonymous functions that take a managed array**. Burst cannot compile a managed function, so the whole render is refused.

**Why this is the good kind of blocker:** it is a single, specific, named reason, at a single place, and it is exactly the item the original audit flagged and told us not to assume was fine — "two effects read fixed tuning tables held as shared read-only arrays; either confirm those are acceptable as constant data or inline them." They are not fine, and the reason is worse than the tables themselves: the descriptors are built from closures.

**The right fix is not to inline the tables — it is to stop the render asking the question at all.** The reverb's comb and all-pass lengths depend only on the sample rate and a fixed tuning table. They are known when the layout is built, on the main thread, where managed code is entirely welcome. **Precompute them into the layout snapshot and have the reverb read them from there.**

That fix earns its keep twice over, because **it also removes the worst float-rounding trap in this whole port.** The recorded danger was that the reverb's buffer length is computed from a float product and a ceiling, and the *same* computation decides how much state to allocate — so a disagreement between the two is a wrongly-sized buffer and a memory fault rather than a wrong sound. Computing it **once**, on the main thread, and carrying the result makes that disagreement impossible by construction. The trap does not need testing for; it stops existing.

**Worth noting for the remaining effects:** the descriptor table is consulted for state sizes and tail lengths generally, so any other effect whose per-block work reaches into it will fail the same way. The same fix applies wherever it appears: resolve it at build time into the snapshot, never at render time.

**Scanned properly, there are TWO such reaches, not one.** The reverb is the one Burst named, because it stops at the first failure. The flanger/chorus shared code does it too, calling a small static helper on the same type to size its ring buffer. Two other references from the effect code are plain **compile-time constants**, which are inlined and do not drag in the constructor — those are genuinely fine and should be left alone.

**And the exact mechanism is subtler than "the tables are managed data".** The tuning tables themselves are ordinary arrays of integers. The problem is that referencing *any* static member of that type forces Burst to compile the type's **static constructor**, and that constructor is where the descriptor table is assembled out of anonymous functions. So the fix is not about the tables' types at all — it is about not touching that type from the render path, by any route.

### 2026-09-27 — agent — a real fragility found while fixing it: one calculation, two different expressions

Checking whether the precompute was worth doing rather than just relocating the tables, and it is — because the reverb's buffer length is currently computed **twice, in two different shapes**:
- The function that decides how many floats the voice's state arena needs adds the stereo-spread offset for **both** channels.
- The helper the render uses to compute the actual per-channel length adds it for **one** channel only.

**Today this is safe, and safe in the lucky direction:** the sizing over-allocates relative to what the render indexes. Nothing is broken and nothing needs urgent fixing.

**But it is exactly the shape of the trap recorded earlier as the worst in this port.** Two copies of one calculation, in different forms, where one decides an allocation and the other decides the indexes into it. Change either without the other — or "tidy" the sizing to match the render, which looks like an obvious simplification — and it silently becomes a buffer overrun rather than a wrong sound. That is a bug nobody would find by listening.

So the fix is deliberately the larger one: compute these lengths **once**, on the main thread, carry them in the layout, and have both the sizing and the render read that single source. Any remaining margin must be explicit and stated, and never smaller than today's. This is the one place in the port where the goal is not just to preserve behaviour but to remove the possibility of a future mistake.

**Audited the other delay-like effects for the same pattern, and it is THREE places, not one.** All three compute a buffer length in two files:

- **Reverb — divergent, safe by luck.** Described above: the sizing adds the stereo spread for both channels, the render for one. Over-allocates, so safe today.
- **Plain delay — duplicated, currently identical.** The sizing helper and the effect's own reset contain the *same* expression written out twice in two files: clamp the authored maximum time to a range, convert milliseconds to frames with a ceiling, add a small margin. Identical today, so no bug — but two copies, and they read the value from **different places**: the sizing reads the authored parameter array, the reset reads the layout's already-clamped parameter block. They agree only because both happen to clamp to the same range. Remove or widen either clamp and they diverge.
- **Flanger and chorus — duplicated constant.** The maximum modulation depth appears as a bare number in the sizing expression *and again* at the reset call site, in different files. Change one and the buffer is the wrong size, with nothing to catch it.

None of these is a live bug. All three are the same latent trap, and the third is the easiest to trip: a bare literal repeated across files is exactly what somebody "tidies" without realising it sizes an allocation elsewhere.

The precompute fixes the reverb and the modulated delays because those two are what block Burst. **The plain delay does not block Burst** — it reaches the descriptor type only through a compile-time constant — so it is not in that change, and it should be brought onto the same single source of truth as a follow-up rather than left as the odd one out.

### 2026-09-27 — agent — DECIDED: one generator per playing sound. That settles the audio ownership.

The design note above said to decide the generator's scope first, because it determines who owns the decoded audio. Decided.

**One generator per playing sound, attached to the audio source that sound's handler already owns.** The reasons, in order of weight:
- It matches the architecture that already exists rather than fighting it. Each playing sound already has a handler with its own audio source and its own chain state; a generator per sound slots straight into that.
- The alternative — one generator per clip with voices inside it — would mean rebuilding voice allocation, stealing and routing inside the generator, reimplementing machinery the engine already has.
- It is also what the reference implementation does, so the plumbing is known to work in that shape.

**Consequence, accepted: the decoded audio is shared across generators, so it cannot simply be owned by one.** Two ways to serve that, and the first is being taken now:
- **Now: each owner copies the audio it needs.** Wasteful in memory when many voices play one clip, and *trivially* safe — nothing is shared, so nothing can be freed underneath a reader. It unblocks the generator immediately without needing the live-voice registry that does not exist yet.
- **Later: one shared native buffer per cached clip.** Removes the duplication, and requires the registry plus the restored stop-all-voices step before it is safe. That is the sequence recorded above, and it stays in that order.

This is deliberately a two-stage plan rather than holding the generator hostage to a memory optimisation. The correctness argument for stage one is much simpler than for stage two, and stage one is a strict prerequisite for testing anything at all.

### 2026-09-27 — agent — the keystone landed; what remains for the generator is small

The per-block render is now a static function over the state struct, verified byte-exact and leak-free. **This was the hard part of the port, and it is done.** Everything the audio thread does — the control-rate step, modulator evaluation and binding, the pitched source read, the chain, output gain, completion — runs from a value type with the layout passed by readonly reference. Both the existing engine and a generator can call it.

**What that leaves for the generator, concretely:** own a state struct and a layout snapshot, receive the sample rate through the control half's configure step, call this one function per block, and route the two cross-thread channels to what currently arrives as plain parameters. That is plumbing, not engine work. The reference implementation shows the plumbing; this function is the engine.

**Three judgment calls the extraction flagged, worth knowing rather than rediscovering:**
- The published voice state (playing, tailing, stopping, free) is read from outside and written mid-render, so it stayed on the class and is passed in by reference — the same memory word, still written atomically, so behaviour is unchanged. It is genuinely cross-thread and a generator will have to decide where it lives.
- A steal-protection flag sits in a block the code's own comment calls "published on allocation, read-only afterwards", yet the render mutates it every block. The comment is wrong, not the code. Nothing outside reads it today; if a main-thread voice-stealing sweep is ever written, this is the field to re-examine first.
- Buffer sizes were deliberately left at their existing fixed worst-case rather than switched to the size-from-real-need idea the state container's own comment describes. That would change allocation behaviour, which had no place in a behaviour-neutral move. It remains available as a later improvement.

**One consequence for the audio-ownership question:** the decoded audio is now passed into the render as a plain parameter rather than held on the struct. So making it native later is a parameter-type change at a handful of call sites, not a redesign — which makes the deferral cheaper than it looked when it was taken.

**What it confirmed (good news, and most of the feasibility):**
- The generator interfaces can be implemented and **compile in this project**. The whole shape works: the factory interface, the real-time struct marked for Burst with synchronous compilation, the control struct with its configure, dispose, update and message members, the capability properties, the frame-count return.

**The lesson, and it revises something I wrote earlier.** I had recorded the manual context as "the vehicle for the equivalence suite" as though it were free. It is not. Allocating a generator into a context does not connect it to anything, so there is presumably a root output to establish and a correct drive order to follow — and **getting it wrong takes the editor down rather than throwing.** That is a materially different cost profile for an experiment: each wrong guess is an editor restart, not a stack trace.

**What to do about it, concretely:**
- Treat the manual-context route as **unproven** until something actually renders through it. Do not build the equivalence suite on the assumption that it works.
- **RESOLVED 2026-09-27 — the equivalence suite does not need the framework at all. See "the verification problem dissolved" below.** The manual context only matters if the plumbing itself has to be tested offline, which is a much weaker requirement than proving the effects correct.
- Whichever route, **experiment in a throwaway, never in the real code**, and expect crashes rather than errors. That is why this probe existed and why it was worth the restart.

### 2026-09-27 — agent — the verification problem dissolved, and what the real test now is

Extracting the render changed what needs proving, and it is worth being precise because it is easy to keep chasing the old plan.

**The old plan was "render the new path and compare it against the existing engine sample-by-sample."** That made sense while the port was expected to produce a *second* implementation. It no longer is one. There is exactly **one** implementation of the render, and both the existing engine and the coming generator call it. So comparing "the new path" against "the old path" would be comparing the same function against itself — it would pass unconditionally and prove nothing. **Do not build that test; it is vacuous now.**

**What can still genuinely differ is the compiler.** The same source compiled by Burst may reorder and vectorise arithmetic differently from the ordinary compiler. That is the one real remaining correctness risk, and it is exactly what the two-tier tolerance model was written for — exact agreement for sizes, indices and counts, tolerance for anything going through a transcendental.

**So the real test is: the same function, two compilers.** Mark it for Burst, invoke it once through the Burst-compiled path and once directly, and compare.

**The mechanism, because this is the part that is easy to get wrong:** adding the Burst attribute to a method does **not** make an ordinary call to it go through Burst. An ordinary call stays ordinary; the attribute only makes a Burst-compiled version available. Two ways to actually reach it, and the second is far simpler:
- Compile a function pointer to it and invoke through that. Workable, but the render's signature passes several things by reference, so it needs a matching unmanaged delegate declaration and is fiddly.
- **Wrap the call in a tiny job marked for Burst and run it synchronously on the calling thread.** That executes the Burst-compiled code with no scheduling, no threading and no audio involvement, and it is a handful of lines. Compare its output against calling the function directly.

Whichever is used, **force synchronous compilation** or the first invocations run as ordinary code and the comparison silently compares identical things and passes — the same trap the prototype's harness comment warns about, in a different disguise.

**How to get two comparable runs — CORRECTED 2026-09-27, the job idea does not work here.**

The obvious arrangement is a Burst-marked job wrapping the render, switched against a direct call. **It runs into a real obstacle:** a job receives its data as fields, and a job struct is passed by value, so only changes to *native buffer contents* survive the call — plain scalar fields do not. The render mutates a great many scalars on the voice state (live pitch and gain, elapsed and silence counters, the stopping and released flags, the repeat schedule), and all of those would be silently discarded. Putting the whole state into a single-element native buffer to get it back does not rescue it either, because a native container holding a struct that itself holds native containers is rejected by the safety system.

**The simple route instead: Burst's direct-call support.** A static method on a type marked for Burst can be invoked by an ordinary C# call, and Burst redirects that call to the compiled version — no job, no function pointer, no duplicate plumbing, and references and out-parameters behave normally because the signature is unchanged.

**Then get the two runs by toggling Burst itself**, rather than by having two call paths: render the existing baseline probe's six chains with Burst compilation enabled, flip the compiler's own enable switch, render them again, and compare. The switch is genuinely the only difference between the two runs, which is a stronger guarantee than two hand-written paths could give.

Apply the two-tier reading to the result: sizes, indices, counts and frame totals must match **exactly**; sample values of transcendental-using effects get a tolerance.

**And set the floating-point mode deliberately rather than taking the default.** Burst is otherwise free to reorder and contract arithmetic, which is the whole reason the two paths might disagree. Ask for strict floating-point behaviour on these methods, and if that turns out to cost real performance, that is a measured trade to make later — not a default to accept silently at the moment the comparison is being established. That needs no audio device, no mix graph, no manual control context and no player build — which means the crash above blocks nothing that matters. It also makes the existing captured baseline the reference for both sides.

**What the framework plumbing still needs**, separately and much more cheaply: that a generator actually gets called, that audio reaches the output, and that timing holds up under load. Those are answered by running it — a player build and listening — not by a sample comparison. Keeping the two questions apart is the point: one is "is the arithmetic right", the other is "is it wired up and fast enough", and conflating them is what made the earlier plan reach for a mix graph it did not need.

**What proves it works**, in order: it renders the same samples as the existing engine through the framework's manual control context, which can be driven offline with no audio thread and no listening; then the same check with Burst compilation on, where a difference is the compiler's floating-point behaviour rather than the logic; then, and only then, a player build with a small audio buffer to confirm the timing behaviour.

### 2026-09-27 — agent — the source audio is a different problem, and is deliberately deferred

The decoded audio is the last managed thing the render path reads, and it has the *same* cache shape as the layout: clearing or removing an entry only drops a dictionary reference, while a playing voice holds the clip it started with. So converting it naively has the identical use-after-free failure.

**But the fix that worked for the layout does not transfer.** The layout was solved by giving each play its own copy, because a layout is a few kilobytes. Decoded audio is megabytes, and duplicating it per voice — with potentially dozens of voices on one clip — is not a real option.

So this one needs actual shared ownership. The shortlist, for whoever implements it:
- **Reference count the decoded clip.** A voice claims it when it starts and releases it when it ends; the cache disposes an evicted clip only once nothing holds it. Honest and minimal, with one wrinkle worth planning for: a voice frees itself on the audio thread, so the release has to be an interlocked decrement and the actual disposal has to happen later on the main thread. Freeing native memory from the audio callback is not acceptable.
- **Let the generator own its own copy**, which is what the reference implementation does — it loads a clip into a read-only native buffer and releases it when destroyed. Clean for one generator per sound, wasteful if there is one generator per voice, so it depends on how the generator is scoped.
- **Never free until the project closes.** Simplest, and defensible since clips are finite, but it throws away the reclaim the cache exists to provide.
- Pinning the managed array and reading it through a raw pointer avoids the copy entirely, and the research report discusses it — but it is the subtlest option and the least obviously safe, so it should not be the first thing tried.

**Why it is deferred rather than done now:** converting it today buys nothing, because nothing is Burst-compiled yet, and it would commit to an ownership design before the thing that constrains that design — how the generator is scoped, and therefore who naturally owns the audio — exists. The layout was the opposite case: cheap, safe, and on the critical path. This is the right order, not procrastination.

### 2026-09-26T21:45:00Z — agent — open — both decisions settled; the cursor one needs a refinement, with the arithmetic to justify it

**Shared engine copy: confirmed.** One copy, both callers. Proceeding as planned.

**The cursor: unify to float — but NOT as a single float, and this matters.** The instruction is right in intent and I am following it; the literal implementation would ship an audible regression, so here is the arithmetic rather than an assertion.

The cursor holds an **absolute** position in source frames and is advanced every sample. A 32-bit float carries about 24 bits of significand, so the gap between values it can represent grows with magnitude. At 48 kHz that means:
- one second in (48,000 frames): the gap is about 1/256th of a frame. Harmless.
- ten seconds in: about 1/32nd of a frame. The whole-sample advance is still fine, but the *fractional* part — which is what the interpolated read uses to sit between two samples — is now quantised to 32 steps. On pitched material that is audible.
- a hundred seconds in: the gap is half a frame. Interpolation is meaningless.
- about 175 seconds in: the gap reaches one full frame, so a fractional advance **cannot be represented at all.** Pitch goes wrong and playback effectively stalls or steps.

Music tracks, ambience beds and long one-shots live entirely inside the broken range, so this is a real regression and not a theoretical one.

**The fix keeps every bit of the instruction's intent and is strictly better than what is there today: split the cursor into a whole frame index and a fraction between zero and one.** Then:
- All arithmetic in the read path is float. No double anywhere. The mixed-precision seam is genuinely gone, which is what was asked for.
- Precision stops depending on how long the sound is, because the fraction never grows past one — its resolution stays at roughly one part in sixteen million forever. That is **better than the current double-precision version at large positions**, not merely equal to it.
- A whole-number frame index covers about twelve hours of audio at 48 kHz, so the range is a non-issue.
- It is the ordinary technique for sample playback and it suits Burst well, since both halves are simple value types.

The two trim bounds the cursor is compared against get the same representation, so comparisons stay exact. The sample-rate ratio is a value near one that is never accumulated, so it becomes a plain float with no concern. The allocation timestamp is main-thread bookkeeping outside the read path and is left alone.

**Why this is the right moment, exactly as the instruction says:** the change lands during the restructure, which is verified byte-exact against a captured baseline **before** Burst is switched on. So if the split representation changes any output, that shows up while it is still cleanly separable from the compiler's own rounding behaviour. Doing it after Burst goes live would mean two candidate explanations for one discrepancy — which is precisely the situation that made the earlier round of bugs expensive.

**A prediction to record now, so it is not mistaken for a bug later:** this change is *expected* to alter output slightly versus the current baseline, because it genuinely changes the arithmetic — moving from a degrading absolute double to a non-degrading split float. ### 2026-09-26T22:20:00Z — agent — open — first restructuring step done and PROVEN neutral; and one planned step dropped on purpose

**The two fast logarithm and exponent approximations no longer use the general-purpose bit-conversion helper.** They now use the maths library's own bit-reinterpret. This is **provably** behaviour-neutral rather than hopefully so: both forms reinterpret the identical bit pattern with no arithmetic and no rounding. Re-ran the probe and confirmed it — all three whole-render checksums, all three derived buffer sizes, and every one of the probed boundary samples came back **identical to the baseline**. The verification loop therefore works end to end, which matters more than this particular change does.

**I have deliberately dropped the planned sweep of general maths calls to the Burst-specific equivalents, and this is a decision worth understanding rather than a shortcut.**

The plan inherited an assumption that this swap was mechanical and safe. It is not. The general-purpose helpers for sine, cosine, exponent, power and tangent compute in double precision and round to float at the end; the maths-library equivalents work in float throughout. **They give different answers.** So a "mechanical sweep" would silently change the sound of every filter coefficient, every oscillator and the compressor's gain curve, and would invalidate the baseline that every later step is checked against — for no functional gain.

What it would have bought is speed, and the honest accounting is that there is very little to win: of the twenty-one affected call sites, all but two are evaluated **once per block** rather than per sample. Only the oscillator in the flanger and chorus, and the rounding in the bit-crusher, sit in the innermost loop. Two hot sites is a targeted optimisation, not a sweep.

The other reason to keep them: Burst has supported the general-purpose maths helpers for years, so there is no compile blocker forcing the change. If Burst does reject a specific call once the hot path exists, swap that one call and measure it — rather than changing twenty-one things at once and then trying to work out which one moved the output.

**A more fundamental point this raised, which sharpens what "verified" can mean.** Even leaving the calls untouched, Burst is free to map a transcendental function to its own implementation. So **byte-exact agreement between the ordinary-C# path and the Burst path is not guaranteed by anything for effects that use sine, cosine, exponent, power or tangent** — and no amount of careful porting changes that, because it is the compiler's choice, not the code's. The previous native port achieved bit-exactness against a C++ implementation whose maths calls were under its own control; that is a different situation.

So the equivalence model is, deliberately, two-tier:
- **Exact agreement required** for everything structural and integral: buffer sizes, delay tap indices, state offsets, frame and block counts, the zero-allocation property, and the effects that are pure arithmetic with no transcendentals.
- **Tight tolerance, not equality**, for effects whose maths goes through a transcendental — the filters and equaliser coefficients, the oscillator-driven effects, the compressor and limiter gain curves, the reverb damping.

That distinction must be built into the automated equivalence suite from the start. A suite demanding bit-equality everywhere would fail for reasons that are not bugs, and the usual reaction to that is to loosen the tolerance globally — which would then hide a real structural error. Keep the structural checks exact.

### 2026-09-26T23:10:00Z — agent — open — two testing constraints from the prototype's harness that would be very easy to lose

Read the harness rather than just noting it exists, and it carries two pieces of hard-won knowledge written into its own comments. Either one, if forgotten, produces a confident wrong conclusion.

**1. Each pipeline must be measured in its own fresh process. A toggle in one session cannot give a valid reading.**

Unity's managed audio callback runs on one persistent native thread, and once that thread has been attached to the scripting runtime it stays attached **for the life of the process**. So if the old managed-callback path has run at all in a session, any later measurement of the Burst path in that same session is measuring a thread that is already permanently attached — and will show a stutter that has nothing to do with the code under test.

The harness records exactly this happening: on the day the approach was proven, a stutter *was* heard under the Burst pipeline, and the cause was that the legacy pipeline had been exercised first in that same process. Which is precisely why the owner's confirmation was specified as coming from a fresh launch with nothing toggled. **A future session that flips between the two pipelines in one run and concludes the Burst path does not work will have reproduced this trap, not found a bug.** Measure each in its own cold start; treat the legacy control as a separate run, never a toggle.

**2. Naive memory pressure does not force a meaningful collection, and the obvious approach proves nothing.**

The harness deliberately builds around three million small linked objects holding references to each other, rather than simply allocating a lot of bytes. Its comment states the measured reason: the cost of a collection's mark phase is proportional to the number of live **objects and references**, not to the number of bytes — and eight hundred megabytes of plain byte arrays collected in about a millisecond. A pressure test built the obvious way therefore applies almost no pressure, passes trivially, and proves nothing at all.

So reuse this generator rather than writing a new one. It also reports approximate heap size and does a full compacting collection on clear, so the test can be repeated in one session without the heap drifting between runs.

Taken together with the synchronous-compilation point above, the verification has three ways to silently measure nothing: background compilation quietly running managed code, a thread already poisoned by an earlier legacy run, and pressure too weak to cause a real pause. All three are solved in the existing harness. That is a strong argument for reusing it wholesale instead of writing a fresh one.

### 2026-09-27 — agent — the compiler comparison, and the trap that nearly made it a lie

The render now compiles to native code and has been compared against the same function running uncompiled, over the six chains the baseline covers. This is the step the whole restructure existed to make possible, so it is worth recording both what it found and how it very nearly reported a false pass.

**The trap, first, because it generalises.** The comparison was built by putting the compiled render inside a job and running it, which executes compiled code on the calling thread without needing any bridge from uncompiled code. The first version declared that job inside the probe script itself. It reported every chain identical — a perfect result. It was worthless: the probe is compiled on the fly, and the compiler only registers entry points from assemblies built ahead of time, so the job silently ran as ordinary code on both sides of the comparison. **The failure is invisible in the output, because it is the same function either way.** The only reason it was caught is that the compiler leaves a warning saying the entry point is not one it knows, and that warning was looked for rather than assumed absent. Moving the job into the real package assembly made the comparison real, and it immediately stopped passing.

Rule to carry forward: **any claim that two compilers agree must be backed by the compiler's own confirmation that it compiled the thing, not just by matching numbers.** Matching numbers is exactly what a silent fallback produces.

**What the real comparison found.** Three of six chains differ. Two differ by a single unit in the last place of a 32-bit float — one in a reverb, which is a feedback network where a last-place difference persists rather than cancelling, and one in an oscillating modulator. Those need no action.

The third looked alarming: a plain delay differed by about five parts in ten thousand, a thousand times more than the others, starting one sample after the delayed copy arrives. That is far too large to be rounding, so it was treated as a probable defect and tested rather than explained away.

**It is rounding, amplified, and the numbers say so precisely.** The delay's read position is interpolated. The test deliberately places the delay time at an exact whole number of samples and the source has a full-scale impulse sitting exactly where the delayed copy is read — the most sensitive arrangement that could be constructed, chosen originally for exactly that reason. A one-last-place difference in the read position is about nine ten-thousandths of a sample; interpolating that across a step from full scale down to almost nothing turns it into an amplitude difference of five parts in ten thousand.

Three predictions were made before measuring, and all three held:
- against a smooth source, where the signal changes by only about a hundredth per sample instead of by a whole unit, the difference should shrink by roughly seventy times. **Predicted about 1.4 hundred-thousandths, measured 1.27 hundred-thousandths.**
- with the delay time moved off the exact sample boundary, the position no longer straddles an integer and the difference should collapse to a single last-place unit. **It does: fifteen billionths, with either source.**
- the difference should be bounded rather than growing, since nothing feeds it back into itself at that magnitude. **It is — the largest difference over the whole render equals the first one.**

Working backwards from both measurements independently gives the same read-position error of about nine ten-thousandths of a sample, which on a twelve-thousand-sample delay is one last-place unit of a 32-bit float. The arithmetic is not wrong anywhere.

**One real consequence to be aware of, though.** Compiled and uncompiled renders are therefore NOT bit-identical, which means an offline bounce (uncompiled) and live playback (compiled) will differ very slightly. That is inaudible and harmless for a game. If bit-exact agreement between a bounce and live playback is ever wanted, the fix is already available: render the bounce through the same job, which is now a supported public entry point rather than test scaffolding.

**Strict floating-point mode is on** for both the voice and the job, so this is the closest agreement the compiler offers; relaxing it would make the gap larger, not smaller.
