## Description

Fake Light seems to have a bug in that tint seems to affect much more than the radius. Its important that radius is the area that is affected and nothing else since it could otherwise possible color or darken the part of the sprite that is not supposed to be lit by the fake light. Fix this and add a toggleable visible radius indicator that shows the light position and the radius in reference to it.

## Handover Log

### 2026-08-23T19:17:01Z — agent — in_progress -> done
The Fake Light effect no longer bleeds its tint/darkening outside its radius circle, and you can now toggle on a visual guide in the SpriteFx Stack editor's preview that shows exactly where the light sits and how far its radius reaches.
**Details:**
Before this fix, a Fake Light set to a small radius could still faintly tint or darken parts of the sprite far outside that circle, because the light's constant background glow ('ambient') wasn't fading out with distance the way the rest of the light did. Now everything the light does — including that background glow — fades to nothing right at the edge of the radius, so the radius circle is genuinely the whole area affected.

How to use the new indicator: open a SpriteFx Stack asset that has a Fake Light effect in Point mode, and in the Preview section click the new 'Light radius' button next to Play/Reverse. A ring shows the radius and a small dot shows the light's position, drawn right on the preview image. It only appears for a Fake Light in Point mode — Directional lights have no single position or radius to show, so the button does nothing for those.

Not yet verified: only checked in the dedicated 'SpriteFx Stacks' authoring window: this is the one place SpriteFx effects are actually authored/previewed, so no other preview surface needed the indicator.
**Technical details:**
Root cause: Assets/Packages/Laubrary/Runtime/SpriteFx/SpriteFxRelight.cs, SfxRelief.ShadeAt() — the returned `lit` term was `ambient + diffuse*ndl*att + specular*spec*att`; `att` (the point-light distance falloff) only gated diffuse/specular, so `ambient` stayed a flat non-zero floor everywhere regardless of distance. Downstream in RelightModifier.Apply, Tint (`t = tintV * lit`) and Shading both read that leftover `lit` and applied faintly everywhere. Fix: multiply the whole sum by `att` — `(ambient + diffuse*ndl + specular*spec) * att` — so it's exactly 0 outside the radius. Directional lights are unaffected (`att` is hardcoded to 1 for them, so no behavior change there — this is deliberate, a Directional light has no radius concept).

Radius indicator: RelightModifier gained `TryGetPointGizmo(out pixelX, out pixelY, out pixelRadius)`, reusing the exact centre/half/position math from Apply() so the indicator can't drift from what was actually shaded (valid only after Apply has run at least once, since it reads Prepare()'d values and the picture rect SetPicture set). Assets/Packages/Laubrary/Editor/SpriteFx/SpriteFxStackWindow.cs adds a 'Light radius' ZUI ToggleButton (state persisted in EditorPrefs, viewing-preference pattern matching Reverse/Hold-end/Idle-gap) and DrawLightGizmos/DrawLightGizmo/PlotGizmoPixel helpers that alpha-blend a ring + dot straight into the preview's own Color32 buffer, in both the padded and unpadded RenderPreviewAt code paths, right after RunStack/Apply and before uploading to the preview texture. Only draws for enabled RelightModifier instances in Point mode; silently clips at the buffer edge if the light or radius extends past the stage. Verified: (1) a Coplay execute_script numeric probe showing SfxRelief.ShadeAt returns exactly 0 for a point far outside radius (vs the old always-positive ambient floor) and > 0 at the light centre; (2) a PrintWindow-based screenshot of the live SpriteFxStackWindow (using Assets/Hit Glow.asset, a real RelightModifier-using asset already in the project) showing the ring drawn in Point mode, absent when the toggle is off, and absent in Directional mode. Any test asset mutated during verification (Hit Glow.asset's `mode` field, EditorPrefs) was restored afterward. No automated test suite exists for this tool; verification was via the numeric probe + visual screenshots described above.
