## Description

Found by T-0284, measured on the live Shaper window at a 608 px left pane.

**What happens.** On a Composite layer hosting a Pyre form, the form's variant enum is drawn by `ZuiReflect.FlowFields` as a `Z.MiniRadio` row. With five options the row wraps to a second line, but the slot it sits in keeps its one-line height, so the wrapped options are drawn OUTSIDE their own box, on top of whatever follows.

**Measured** with a full-tree scan for elements whose children extend past their own `worldBound` (2 hits per card, one of which is the ScrollView's normal scroll content):
- **Torch** — "Flame type" row is 571x24 and its content is 40 tall: **16 px of overflow**. `Lash` (the fifth option) lands at y=1024 and the "Placement" box header is drawn under it. Visible in the attached capture: the word "Lash" sits over "Placement".
- **Jet** — "Jet type" run overflows by **34 px**.

Orb, Radial Jet, Explosive Jet, Inferno, Fork Blast, Arc Burst, Plasma Bloom, Fire and Fireball were scanned the same way and are clean at this pane width; the defect appears once the option row is wider than the pane, so it will move around as the pane is resized.

**Not fixed under T-0284** because the row is built by the shared reflected-flow layout (`Zui/Toolkit/ZuiReflect.cs`, the `zui-field` slot inside the flow container), not by Shaper, and every reflected card in the package uses it — a height/wrap change there needs its own verification pass across Pyre, Chunks and the other hosts, not a one-line edit inside one generator's audit.

Repro probe: `workspace/T-0284/overflow-probe.cs` (bind any document whose layer hosts a Torch, expand every section, run it).

Fixed the wrap-onto-overflow: a Z.Field row that grows onto a second line (a MiniRadio with wrap:true whose options exceed the row) now stays inside its own slot instead of painting over the next box.

CHANGELOG: ZUI - a wrapped label+control row (a variant radio with more options than fit on one line) now grows the space it reserves to match, instead of painting the wrapped options over whatever came next.

Root cause, measured live on Pyre's Torch "Flame type" row (5 options, wraps 4+1 as Lash overflows by a hair): the field itself (`.zui-field`, built by `Z.Field`) correctly resolved to its full wrapped height (40px) via Yoga - but its parent, the reflected FLOW container (`ZuiReflect.FlowSubset`, itself a flex-wrap row), reported only 24px: the single-line height it had estimated before the control's own internal wrap resolved. Two nested flex-wrap levels (the outer flow, and the MiniRadio's own `.zui-radio--wrap`) is exactly the case Yoga does not reliably re-measure in one pass, so the ancestor's auto-height goes stale and the next box header ("Placement") gets positioned 16px too high - the exact overflow T-0287 (and T-0284 before it) measured for Torch, and 34px for Jet.

Fix in `Zui/Toolkit/Zui.cs`, `Z.Field` (the shared label+control wrapper every reflected field and most hand-authored ZUI rows go through): a `GeometryChangedEvent` callback on the field wrapper stamps an EXPLICIT `style.height` whenever the measured height actually changes. An authoritative height (rather than implicit auto-sizing) correctly re-propagates to the flow container's own auto-height on the next layout pass. The callback is a no-op for the overwhelming majority of fields whose height never changes, and self-corrects both ways (narrower pane forces MORE wrapping -> taller; wider pane -> shorter), so it tracks live resizing rather than fixing a one-time snapshot.

Fixed at the shared `Z.Field` level (not inside `EnumControl`/MiniRadio specifically) because the same nested-wrap mismatch would recur for any other control that grows taller than one line inside the reflected flow, not just enum radios.
