## Description

User observation (2026-08-21): "Having several layers doesn't mean each layer is cached — every time I change a layer or hide/show a layer it has to re-cache everything." True after T-0059/T-0060: the frame cache holds whole composited frames, so any edit throws every frame away. Cache per LAYER per frame instead — each layer's isolated rendered buffer keyed by its own content (plus the few things it reads from elsewhere), then composite the cached layer buffers into frames. Hide/show/reorder = recomposite only; a dial on one layer re-renders that layer only; spec-level post modifiers apply live after compositing. Renderer factored so the full `RenderFrame` and the cached composite share ONE per-layer code path; `RenderFrame` output stays byte-identical (bake/export untouched). Identity tests, live measurements, audit, handover walk.

Standing rules: autonomous, never stall, commit after each verified milestone, log handovers here. Never touch the user's assets (temp probe assets only; the uncommitted `New Pyre Plus§.asset` / deleted `New Pyre Plus.asset` are never added, reverted or committed).

**Finding that shapes the design — the "first-layer fast path" is not first-layer-only and is not reproducible from an isolated buffer.** `needScratch = hasClip || (hasPost && bufDirty) || matteActive || isFire || isFireball || isForm || hasLayerSim || hasBorder`: ANY plain Draw layer (enum form, no post/clip/matte/border/sim) paints its particles straight into the accumulating frame, at any position in the stack. `Over` is straight-alpha with a byte quantisation per step, so "particles onto the frame one by one" and "particles onto transparent, then the whole layer onto the frame" differ by rounding: measured in float32 over all 256×255 (value, alpha) pairs, even the degenerate case "Over onto a fully transparent pixel" returns a different byte for 2695 of 65 280 pairs (255 × a × (1/a) lands at 254.99998). Over a non-transparent destination the two orders are simply different arithmetic. So an exactly byte-identical cached composite is only possible for layers `RenderFrame` already isolates (forms, posts-over-content, clips, mattes, borders, sims) and for fast-path layers wherever the frame beneath them is still fully transparent (the cache copies such pixels verbatim — the exact same bytes the straight draw would have produced).
Decisions taken without asking:
- `RenderFrame` keeps its output byte-for-byte (bake/export/GIF/parity untouched). It is re-expressed through the new per-layer API: `PlanFrame` (which layers are active, their roles, isolation, fast path, base-fuse — a pure function of spec + frame), `RenderLayerBody` (render + border + post + sim into a given target — the one body both paths run), `ApplyLayerFrame` (matte write / luma arm / matte-apply + clip + composite) and `FinishFrame` (deferred borders + spec-level posts). The fast path is "target = the frame buffer" in the same body; the cache path is "target = a fresh buffer".
- Cached composite = `RenderFrame` exactly for every isolated layer and for fast-path layers over transparent pixels; over non-transparent pixels a fast-path layer differs by the rounding above (≤ 1 LSB/channel, never a visible change). A fast-path layer that is the FIRST thing drawn over a VISIBLE background (opaque/any-alpha clear or a background fill) is cached FUSED with the background (its key carries the background hash) so a post modifier on it still sees bg + layer exactly as the bake does — that is a semantic difference, not rounding, so it is not allowed to drift. Tests pin both: 0 px vs an isolate-everything reference, and the ≤ 1 LSB bound vs the plain `RenderFrame`.
- Layer key = 64-bit FNV over every Unity-serialized field of the layer except `enabled`/`name`/`shapeAdvanced` (ZUIValues, fills, gradients, curves, nested modifiers and the form via `PlusForm.ContentHash`), ⊕ the layer's INDEX (the renderer's `_layerSalt` is the index — every seeded draw reads it, so a moved layer legitimately renders differently and must re-render; hide/show never shifts indices), ⊕ canvas/frameCount/seed, ⊕ the spec's global geometry/pixel modifiers with their list indices (they wrap every layer's stack and their seeds depend on list position), ⊕ the background when the buffer is base-fused, ⊕ for a heightmap consumer the keys of the active writers below it on its channel in order (it reads the accumulated channel while rendering). Clip channels and the luma matte are NOT in the key: they are applied at composite time from the cached matte-layer buffers, so editing a matte layer re-renders the matte layer only. Visibility and order are not in the key beyond the index.
- Store: `Dictionary<ulong, LayerEntry>` of `Color32[][]` per frame (+ deferred border planes), LRU by key, default cap 64 MB; toggling off/on, undo of a dial, reorder-back all hit. Frame textures stay as T-0059 left them (one RGBA32 per frame, reused); a frame's texture is (re)composited on the main thread once every active layer-frame it needs is present.
- Fill = `PlusLayerFill` (generalised `PlusFrameFill`): worker threads pull (layer, frame) jobs in on-screen-frame-first order, each with its own spec clone, same cancel/generation discipline; height consumers are rendered after their writers (main thread builds the channel plane). Serial path for parallel-unsafe specs, same per-layer granularity.
- Reorder: the brief expects 0 renders; the index-is-salt rule makes that impossible without changing bake output, so a reorder re-renders exactly the layers whose index changed (an adjacent swap = 2 layers) and recomposites the rest. Logged as a deviation.
