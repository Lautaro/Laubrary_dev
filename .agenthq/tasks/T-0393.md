## Description

**Owner report (2026-09-21), after T-0390/T-0391/T-0392 all landed and recompiled:** "Its still wrong. I see larger debris now, but most are still subpixel size."

**Root cause, found and fixed by hand this session — a FOURTH, distinct bug in the same area, nothing to do with PPU governance:**

`PaletteSplash.Fire()` (`Runtime/Chunks/Capabilities/PaletteSplash.cs`) picks a random procedural shard shape from `ChunkSprites` (native pixel footprints of 1×1 up to 3×3 texels), then scales it so its bounding box matches a randomly-rolled target size (`sizePxMin`/`sizePxMax`, authored as 1–3 "game pixels" on `UC4 Zoe Spray.asset`). The shape pick was **uniformly random, independent of the target size** — so roughly half the time a 2×2 or 3×3 shard got randomly paired with a small target (e.g. 1px), and `localScale` came out below 1 (e.g. 0.33×). That doesn't just make the OVERALL particle small — it shrinks a shard's own multi-texel internal grid to a FRACTION of a game pixel each, so the particle's fine detail renders smaller than the game's actual pixel size: exactly what "sub-pixel" means, and exactly why T-0391's PPU fix (which was real and correctly fixed the outer bounding size) didn't fully fix what the owner is seeing — the OUTER particle size was fixed, but the shard's INTERNAL texel scale, for roughly half of all particles, was never addressed.

**Already changed, by hand, this session (verify + commit; do not re-derive):**

1. `Runtime/Chunks/ChunkSprites.cs` — added `GetFitting(float targetPx, float ppu, int pick)`: chooses only among shards whose native pixel width is `<= targetPx`, so a shard is only ever scaled UP or left 1:1, never shrunk below its own texel grid. Falls back to the smallest (1×1) shard when `targetPx` is below even that (the one case some downscale is genuinely unavoidable, and harmless there since a single texel has nothing internal to subdivide). RNG-agnostic — takes a plain `int pick`, doesn't own or advance any RNG itself.
2. `Runtime/Chunks/Capabilities/PaletteSplash.cs`, `Fire()` — the shard-pick `rng.Next(...)` draw is kept at its EXACT ORIGINAL position in the per-particle RNG stream (same single `NextUInt()` cost regardless of the bound passed — verify this claim against `ChunkRng.Next(int)` in `Runtime/Chunks/Capabilities/ChunkRng.cs`), but its result is now fed into `GetFitting` (called AFTER the target size is rolled) instead of `Get` directly. This is deliberate and load-bearing: reordering or adding/removing an RNG draw here would desync a SEEDED splash's reproducibility between `ChunkPreviewSim`'s preview (a real, recently-learned risk — see T-0391's own commit message) and a real `Fire()`. Confirm this parity actually holds — trace `Editor/Chunks/ChunkPreviewSim.cs`'s `Splash()` method's own `rng.Next(ShapeCount)` call (around line 582) and confirm it still lines up.
3. **Deliberately NOT touched:** `DebrisScatter.cs`'s own `ChunkSprites.Get(...)` call (line ~265, its `Squares` visual mode) has the exact same theoretical risk, but its `sizeMin`/`sizeMax` defaults (0.16–0.35 WORLD UNITS, not "game pixels") sit comfortably above the shards' native pixel sizes at the project's PPU (max native shard is 3px = 0.1875 units at PPU 16), so it is not currently producing a visible symptom. Left alone rather than fixed preemptively, matching this session's established discipline of not fixing what isn't currently broken — but note it as a live latent risk if a future author ever sets DebrisScatter's Squares mode to a much smaller size range.
