## Description

Produce a thorough, standalone vision-and-design-plan document for Shaper's authoring UI. This is a PLANNING deliverable only -- no production code, no ShaperWindow, no changes to the Shaper worktree's runtime (`D:\UNITY\Laubrary Dev - Shaper`). The document is the whole output of this task.

**Method -- mirror the Chunks mock programme's discipline.** Follow the same UI Guide rigor that produced `D:\UNITY\Laubrary Dev\.agenthq\workspace\T-0123\CHUNKS-EDITOR-BLUEPRINT.md`: the absence rule (a surface appears only when something in the current document actually needs it -- never greyed-out-by-default, never permanently present "just in case"), packed rows over one-control-per-line, "label = action" (a control's tooltip and its visible/actual effect must never disagree -- this is the exact defect the Chunks timing model shipped and caught), a stable-workspace rule (nothing the user is looking at may jump because an unrelated part of the tree changed), and Undo designed in from the start. Write findings/decisions as DECIDED vs REQUIRED with a traceability table, same format as the Chunks blueprint.

**ZUI is the control framework -- mandatory, and Pyre is the reference for how.** Every control in the plan must be drawn from ZUI (`this.Button/Slider/Toggle/Label/MiniRadio/SliderRange/Box/...`), the same as Laubrary's other editor tools. Study Pyre's existing shipped editor (`Editor/Pyre/` in the primary `D:\UNITY\Laubrary Dev` project) as the closest existing precedent in this codebase for an effect/layer-stack authoring tool -- its layer list, modifier stack and dial patterns are the best available prior art for what a Shaper UI should feel like. Where the plan needs a control ZUI does not yet have (the Chunks programme already found one gap: a multi-lane timeline), the plan should propose it as an ADDITION to ZUI (so every Laubrary tool gains it), not as a bespoke one-off control -- following this project's standing ZUI-first rule.

**Envelope-first philosophy -- explicit design bias, stated by the owner.** Every authored value in the plan should be treated as a CANDIDATE for changing over time (an envelope/animation curve), and where a value is a plausible envelope candidate, the plan should default to ALLOWING it rather than excluding it. The owner's explicit experience: across prior Laubrary tools, too many parameters have ended up NOT allowed to be envelopes when they arguably should have been, rather than the reverse (too many wrongly allowed). The plan should name, for every major dial/value in Shaper's authored surface, whether it is envelope-eligible, and should treat "not eligible" as the exception requiring a stated reason, not the default.

**Scope -- must account for the full Shaper surface actually built** (Waves 0-3, all committed on branch `feat/shaper`):
- The node tree: Primitive / Bag / Composite (T-0112), arbitrary nesting via breadcrumb navigation (per `SHAPER_THE_DESIGN.md`'s own stated UI principle -- verify this principle against the doc directly).
- All fill kinds: Solid, Gradient, RampByQuantity, Texture (T-0106), IndexedStrip (T-0110), HeightField, TapestrySteel (T-0111), and the palette-quantise stage.
- The border stage (T-0107).
- The light rig (T-0108).
- Extrusion, bevel, Z-offset (T-0109).
- The swarm modifier: generic wrapper vs. native path, which must be SHOWN not hidden per T-0113's own rule, plus the `interact` control's Native-only behavior.
- The effect stage (T-0114): which of the 41 Pyre effects need sheets vs. are buffer-only, pre-composite vs. post-composite placement, padding.
- Caching (T-0115): a visible per-frame cached/not-cached indicator -- T-0115 built the data layer (`ShaperFrameCache.IsFrameCached`/`CountCachedFrames`) with nothing yet to display it.
