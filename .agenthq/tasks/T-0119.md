## Description

Chunks. 
This Laubrary tool is overwhelmingly complex and the UI is massively bloated. 

The goal for UI and all the Laubrary apps should be: 
Allow complexity but ensure minimal cognitive load. 

That means that if a chunk asset is about spawning a single pyre 5 times in a row then the UI that would be needed to show when working with it shouldnt be more than perhaps a list item where 1 pyre is selected in a lauAsset object picker and then some module that exposes parameters for staggering the spawn time. 

I look at the chunk browser and see 5/7 chunks looks like some random test debris. I suspect that these have been made to test out a more complex chunk. That means that there is a massive violation. These are probably sub-assets or private assets. Imagine if each chunk would bloat this list with 3-10 new assets that forms debris or other sub-assets? It would be impossible to work with. 

I have an idea in that when opening an asset perhaps only show the sections (toggled in the sections toggler) that have been used. 

But i suspect the problem is deeeer. The UI is massive with 20 sections at the moment. Obviously many chunks are not going to use that. 

I think we need to rethink this. What chunks will offer to do with in an asset will change alot and most probably increase. I think we are heading in the wrong direction with the UI and underlying data type. Everything has to be modular. Extremely modular. Look at the architecture for the new Pyre spinnoff called Shaper for inspiration. 
Chunks perhaps should be even more modular. The reason is that Struggle to clearly state what the vanilla default use of chunks is. 
Like the smallest usefull user case. 
It wouldnt be "spawn and play a pyre" cause that should be very easy to do without chunks. 

It will probably me more like: 
Spawn several pyres and for each change spawn parameters like: spawn time, position, perhaps scale, alpha or tint.

Spawn pyres and fling them

Spawn specific order of pyres in specifid positions over a timeline

Spawn particle spray based of the sprite of a zoe

Fracture and fling a sprite of a zoe

Those are massively different and they should not be the same function necessarily (obviously there is alot they should share)

So i dont see a reason to give any of them its own section in the UI. They should be modular and have their own UI if their functionality is added to the chunk. 

So what things are truly always a part of a chunk asset? 

Perhaps nothing? I was thinking a timeline. 
And that may be true but a visual UI timeline is only necessary if i want to be very precis with what happens when and set them in relation to each other. 

If the chunk only samples a zoe sprite and spawns a particle shower, there is indeed a timelin in the works. But since what ive asked for, the shower, starts at time 0 a timeline in the ui would do nothing for me. I would want to see a zoe picker and some parameters to show how many particles should spawn, directions, speed, perhaps gravity etc... (btw we never considered having this be a wrapper around the unity particle spawner? not sure that would be a good thing but id like some input on it)

Also, if ther are components in a Chunk that do should appear on a timeline there should (probably) only be one timeline. Comparing different timeline controllers with different data spread over an editor window is a nightmare. 

This task is to thuroughly investigate code and ui of target tool and the referenced blueprint tools and come up with a plan on how we can make Chunks a friendly yet powerful user experience. 

Make this into a task in AgentHQ paste this text as the description and post the result of your research as an attached MD.
