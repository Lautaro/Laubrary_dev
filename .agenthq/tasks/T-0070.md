### 2026-08-23T18:48:20Z — agent — in_progress -> done
The swarm's triangle (and square/pentagon/hexagon) shape fill has been fixed so it now actually looks like the shape it's supposed to fill, instead of leaning lopsided to one side.
**Details:**
When the tool couldn't divide the particle count into a perfectly even grid, it used to just chop off the leftover from one side of whichever row ran out of room -- which is why the triangle's base looked shifted/skewed instead of centered. It now trims evenly from both sides of that row, so the fill stays centered and reads as the intended shape. Not yet checked by eye in the Scene view -- verified numerically (re-ran the exact same placement math the tool uses and confirmed the base row is now centered) and confirmed the project still compiles cleanly, but a human hasn't looked at the corrected triangle rendered live yet.
How to use: no action needed, this applies automatically the next time a Swarm layer with a polygon shape (Triangle/Square/Pentagon/Hexagon) and Area fill mode renders.
**Technical details:**
Root cause: Assets/Packages/Laubrary/Runtime/Pyre/PyreRenderer.cs, GridLayoutPolygon -> NthInsidePolygonGridPoint. The settled density's total inside-cell count is rarely exactly n (only discrete jumps as density grows), and the old code just stopped the row-major scan once it had emitted n points -- silently truncating whichever row crossed the n threshold, from whichever end (left-to-right, or right-to-left under swarmGridReverse) the scan reached first. Reproduced exactly: Triangle, n=18, r=100 settles at density=8 with 20 cells total (2 over) that all happen to land in the base row (y=-37.5), which used to render as x={-62.5,-37.5,-12.5,12.5} (missing the right side entirely) instead of the natural 6-wide row.\nFix: since a regular polygon is convex, a horizontal grid row's inside cells are always one contiguous [lo,hi] run. NthInsidePolygonGridPoint now finds that run directly (instead of testing/collecting every column) and, only on the ONE row where the running total would exceed n, shrinks the run by dropping half the overflow off each end (drop/2 left, remainder right) -- centering it on the shape's own axis of symmetry instead of an arbitrary scan edge. swarmGridReverse's contract (which end of a row is index 0, which end of the grid fills first) is preserved for both the untrimmed and trimmed case. Rows before the overflow are byte-identical to before (verified: for n=18 sides=3, i=0..13 unchanged, only i=14..17 -- the base row -- changed from {-62.5,-37.5,-12.5,12.5} to the centered {-37.5,-12.5,12.5,37.5}).\nVerified two ways: (1) a standalone JS simulation of the exact algorithm before/after, and (2) live via Coplay execute_script + reflection calling the real GridLayoutPolygon in the running Unity editor (Assets/Packages/Laubrary temp script, deleted after use) for both reverse=false and reverse=true -- output matched the simulation exactly. check_compile_errors clean before and after.\nNote on naming: this code is physically still named Pyre/PyreRenderer (namespace Laubrary.Pyre) even though the AgentHQ task tagged it PyrePlus -- per project memory the Pyre-to-PyrePlus rename is a decided-but-not-yet-executed mechanical migration (see todo-retire-pyre-for-pyreplus.md); PyreRenderer.cs is the single source of truth PlaceParticle/RenderSwarm and the editor preview overlay both consume, so there was no separate PyrePlus copy to fix.\nAlso appended a Fixed entry to Assets/Packages/Laubrary/CHANGELOG.md under [Unreleased] describing this in the project's usual style.\nNot done: no human eyeball check of the corrected shape rendered in the Scene/Game view or the editor preview overlay (Unity was available via Coplay for compile-check and reflection calls, but I did not open the PyreWindow/PyrePlus preview and take a screenshot of the fixed output).

Swarm particles dropped into a Triangle, Square, Pentagon, or Hexagon shape now genuinely spread out to look like that shape, evenly, at any particle count -- instead of clumping unevenly the way the last two attempts still did.
**Details:**
Each shape now gets its own proper fill pattern instead of one generic approach forced onto all of them: a triangle fills like a rack of pool balls, a square fills like a tidy grid, a hexagon fills like its own natural honeycomb pattern, and a pentagon (which has no perfectly even way to tile) fills with evenly-sized rings instead of unevenly-sized ones. How to use: no action needed -- this applies automatically the next time a Swarm layer with one of these shapes and Distribution set to 0 renders. Verified: checked by eye against the actual shape outline for three different particle counts on every one of the four shapes, backed by a numeric evenness check (all comfortably even), and confirmed live in the tool on the exact Triangle asset from the bug report. **Technical details:**
File: Assets/Packages/Laubrary/Runtime/Pyre/PyreRenderer.cs. Root cause of both prior rejections: GridLayoutPolygon used ONE generic construction for every polygon kind (first a raster grid, then a single concentric-ring 'dartboard' scaled to the polygon boundary) -- the ring version fixed low-n vertex-landing but still produced visibly uneven density on a Triangle specifically, because scaling a ring's constant radial step by a boundary distance that swings sharply with angle does not preserve equal-area bands. PolygonBoundaryRadius and the old single-purpose GridLayoutPolygon body were deleted as dead code. RingLayoutDisc/RingCounts (Circle/Custom path) are untouched -- not reported broken, out of scope. Call sites at PlaceParticle now pass kind through to GridLayoutPolygon(kind, r, areaSides, n, i, gridReverse). PyreWindow.cs's Distribution tooltip text updated to match.
