## Description

Give Shaper's Solids generator real texture-driven relief SHADING -- ridges catching light, grooves reading as shadow -- by wiring a fill's height (e.g. `HeightField`, from T-0111) into the surface normal used for lighting, scoped to Solids specifically rather than every fill kind at once.

**Context, already established with the owner:** this is deliberately narrower than genuine silhouette-changing carving. Solids is a closed-form analytic generator (six hand-coded shape formulas, no mesh, no vertices), and Shaper's fills are architecturally barred from ever touching a shape's own distance field/silhouette (T-0110's own finding: "a fill is architecturally outside the bound/march system for all five fill kinds"). So this task can only ever make a Solid look carved under lighting, never actually change its outline. That is the intended, agreed scope -- do not attempt to make fills affect Solids' geometry/coverage.

**Why this doesn't exist yet:** `ShaperNormals.cs` (LR-3.3/LR-3.4) deliberately excludes a fill's height delta from the normal provider today, for every generator including Solids -- confirmed directly in T-0110/T-0114/T-0115's own VERIFICATION.md honest-scope-limit sections, not a new discovery. The stated reason at the time: screen-space differencing of paint-authored height would describe the paint's own bumps rather than the true surface, with no apron mechanism to do it cheaply. Read `ShaperNormals.cs`'s LR-3.3/LR-3.4 doc comments yourself and take that reasoning seriously -- if you find a cheap, correct way to do this for Solids specifically (not a general-purpose fix for all five fill kinds), build it; if the same cost/correctness problem applies to Solids too, say so honestly rather than forcing something fragile.

Read `ShaperNormals.cs` (LR-3.3/LR-3.4) and `ShaperSolids.cs` (the `Coverage | EdgeDistance | SurfaceDirection` sheet it already publishes, per `D:\UNITY\Laubrary Dev - Shaper\Assets\Packages\Laubrary\Runtime\Shaper\ShaperSolids.cs:275`) to understand exactly how Solids currently derives its per-pixel normal, and where a fill's `heightDelta` would need to plug in.
