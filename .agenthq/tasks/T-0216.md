Two questions were asked of the Chunks window, mechanically, and both have numbers now.

DOES EVERY AUTHORED VALUE HAVE A CONTROL? 153 of 156 do - 98.1%. The three that do not are the layer plan's own depth numbers: which number the first slot starts at, the gap between slots, and the Unity sorting layer the whole effect lives in. Those were left out on purpose when the card was designed, and that was harmless until this task made the runtime's numbers the truth for what draws in front - now they decide it, and nothing can author them. Filed rather than added, because adding them contradicts an explicit line of the spec.

The answer is trustworthy because it was not obtained by matching names. Each control was DRIVEN - a press and release across a slider's track, a real submit on a toggle - and the recipe diffed to see what moved. A field nothing moves is a miss, and cannot be missed by a bad guess. Because several dials only exist inside a branch, the whole pass runs ten times over ten different states of one recipe holding all nine kinds - every kind added through the window's own menu by a real click. 177 distinct controls were seen; 140 fields were moved through them.

DOES EVERY DIAL CHANGE THE PICTURE? 89 do. 33 do not, and all 33 are now accounted for. Three were defects and are fixed: Rest on floor did nothing at all in the preview (with it off, a settled piece is gone within a beat in the real burst, and the picture kept a floor full of debris); Spin was a dead dial whenever debris is a tumbling sampled cut, because the burst reads Tumble speed instead; and Pixels/unit's tooltip promised it set a chunk's size on screen, which it has never done - it sets the generated sprite's resolution, and Size decides how big the chunk is. The other 30 are honest: a card's own name has nothing to draw, a blast is drawn as a disc so nothing about how it is TURNED can show, damage is a balance number with no picture, and a schematic deliberately does not render a chunk's pixels - that is a texture read that cannot happen sixty times a second.

Three more things came out of the same pass and are fixed. A card can be given a NAME now: it has carried an optional one since the capability stack landed - the upgrade even writes one, from an old blast group's label - and nothing in the window could set or clear it, so a migrated recipe could show a card named for something you could never rename. Every asset picker was showing the PREVIOUS asset's name after a pick, in the window and in the Follow Emitter's inspector alike, until something else happened to redraw it. And the Follow Emitter's Sorting Order field ran off the edge of the inspector at a real pane width, taking a horizontal scrollbar with it.

THE PREVIEW NOW AGREES WITH THE BURST ABOUT DEPTH, and frames itself to the composition rather than to its furthest particle. Anything you did not put in a named slot draws in FRONT of everything slotted, not behind it - that is what the burst does, and the preview had its own rule saying the opposite. And where framing to the whole flight let one fragment still travelling at the end of the clock shrink the first half-second to a speck, the stage now fits about nine tenths of what is on screen at the clock's midpoint, widened only enough to keep the origin and every placement inside.

THE RING BLAST ANOMALY IS EXPLAINED AND FIXED. A pattern's first blast - the one with no delay - really did land off the mark, by an amount that grew the later you looked. It was never a placement error: it was spawned in exactly the right place and then moved one frame before anything could see it, because the thing that flies blasts moved it in the very frame it was handed over, and only the no-delay path hands over mid-frame. Its four neighbours, which arrive from a timer, never got that head start. Flight now begins on the following frame for everything, so a pattern's points all fly from where the recipe puts them. Watched in play mode: all five now match the recipe's own placement exactly.

AND ONE DRAG IS ONE UNDO STEP. Sliders, range sliders, pads and scrub fields used to record a step per twitch of the mouse, so Ctrl+Z after a two-second drag walked back through the drag rather than undoing it. Fixed in the controls themselves, so every Laubrary tool gets it.

SPEC 8.16 - ONE RESOLVER FOR DRAW ORDER
- ChunkModuleContext gains `public static int ResolveOrder(LayerSpec layers, string layerName, int flatOrder, int offset = 0)`; the instance OrderFor now calls it, so there is exactly one implementation.
- ChunkEmitter gains `public const int DefaultSortingOrder = 500`, replacing the literal in three places; the preview assumes it, since a recipe does not know which emitter will fire it.
- ChunkPreviewSim.OrderFor(cap, layers, stackIndex) => ResolveOrder(layers, cap.LayerName, DefaultSortingOrder + stackIndex) * 4. The *4 is the preview's own business: it needs room UNDER each capability for a trajectory arc and a trail (drawn at order-1), and consecutive unslotted capabilities now resolve ONE apart rather than eight, so without the gap a trail would sort onto its neighbour's number and List.Sort is not stable.
- The behavioural consequence, which is the point: unslotted output falls back to emitter.sortingOrder + stackIndex (500, 501, ...) while a slot resolves to LayerSpec.baseOrder + index*step (0, 10, ...), so unslotted draws IN FRONT. The preview said the opposite. Four producer tooltips, LayerPlan's class comment and the slot picker's own wording said the opposite too, and now do not.

SPEC 8.17 - FRAMING
- ChunkPreviewFrame gains `Required` (the extent that must stay inside whatever the fit says); PyreBlast's block records every resolved placement's |pos| + radius into it.
- ChunkPreviewSim.Reach builds ONE frame at the clock's midpoint (includeDisabled: true, as before) and returns max(0.5, max(90th-percentile of every guide's |pos| + radius, Required)). A midpoint with no guides at all falls back to the old whole-clock scan, so a recipe whose output is all early or all late does not open zoomed into empty space.
- Cones are out of the fit entirely and are instead CLAMPED at draw time to 0.46 * min(field width, height) - an aim arrow answers 'which way', not 'how far', so it is the one thing allowed to be cut to fit rather than allowed to push the frame open.
- Measured: Floating Disc Blowup 7.87 -> 5.52, Ring Blast 2.87.

THE RUNTIME FIX
- ChunkModuleRunner.MotionEntry gains `bornFrame`; Move stamps Time.frameCount; Update skips an entry whose bornFrame == Time.frameCount, before ageing it.
- Root cause: SpawnFormationRunner.Fire spawns delay<=0 points INLINE (inside the caller's Update, via PyreBlast.Fire) and the rest from a WaitForSeconds coroutine, which Unity resumes after every Update. A component added mid-frame may have its Update called that same frame, so the inline point was integrated once before anything could observe it and the coroutine points were not. Not a placement error - with the Trajectory disabled the inline point is bit-for-bit on Resolve's answer.
- Smell assessment (fix KEPT): the fix belongs in the runner, but the reason two points could differ is that Fire has TWO DISPATCH PATHS FOR ONE IDEA. A delay of zero is the same event at t=0, not a different kind of event. The second consequence of that split is still live and is filed below.

CARD NAME
- ChunkWindow.Recipe.cs: FillCardBody now leads with IdentityRow(c, cap) - a delayed TextInput for cap.displayName packed with DelayRow where one exists. Delayed because the card's header title is rebuilt from it; the rebuild is RebuildStack (scroll preserved), scheduled a frame later since the field raising it is one of the elements being replaced.

THE THREE DEAD DIALS
- Rest on floor: ChunkPreviewSim.Flight gains `settledAt`; Fly records the step it settled on; Debris skips a piece when !restOnFloor && settled && local > settledAt + 0.05f, matching Chunk.Update's own maxLife = min(maxLife, life + 0.05f). The `rest` parameter was being passed and never read.
- Spin: hidden when cap.UsesSampledDebris && cap.tumble, because DebrisScatter.Fire's `tumbling` flag selects tumbleSpeedMin/Max instead of angularSpeedMin/Max.
- Pixels/unit: tooltip corrected. Chunk.Init derives baseScale = worldSize / spriteUnit, so the sprite's own PPU cancels out and only the Size dial decides world size.

STALE PICKER CHIPS
- LauAssetElement.Build sets ZuiChip's label ONCE at build time and exposes no setter, so a call site that does not rebuild shows the old name after a pick. Fixed at the four Chunks call sites (DebrisScatter Animation, FragmentFracture Source, PyreBlast Blast, Trail Trail source) by routing them through DialAndRebuildCard, and in ChunkFollowEmitterEditor by extracting a FillSpecRow() the pick callback re-runs. The systemic fix - having the chip update itself before invoking onPick - is in AssetKit, outside this task's allowed paths, and is filed below.

SLIDER RANGES

WHAT REMAINS, NUMBERED
1. The Layer Plan card cannot author baseOrder, step or sortingLayerName. Design decision 10 limited the card to name/reorder/remove, which was harmless until 8.16 made those numbers decide whether unslotted output is in front of the plan or behind it. Needs an owner's call, since adding them contradicts the spec as written.
2. A pattern's pool pick, rotation and scale come off the blast's own _rng in FIRING order (immediates first in index order, then the rest in delay order), while the preview hashes from seed + point index per design decision 9. So which alternate lands where can legitimately differ between the picture and the burst. Not a bug either side; it is a decision nobody has made.
3. SpawnFormationRunner.Fire's two dispatch paths for one idea (see the smell assessment). Collapsing them - always through the scheduler, a zero wait resolving immediately - would remove the class rather than the instance.
4. Nothing in the schematic can show how a spawned blast is TURNED: Rotation mode, Fixed angle and Angle range on Pyre Blast, and Face velocity on Trajectory, are five dials with no tell. A short tick from each disc's centre would answer all five.
5. Fragment Fracture's Min area cannot show in the preview, because the cut is approximated as pieces on a ring round the source. Documented in ChunkPreviewSim's header; a real cut is a texture read.
6. LauAssetElement should update its own chip before invoking onPick - it is used by every tool in the package and every one of them has this staleness. Fixed only at the Chunks call sites here (AssetKit is outside this task's paths).
7. ZuiViewBar's preset list is a native DropdownField. A saved-view list is not an enum, so it is not the rulebook's dropdown anti-pattern, but it is the one native control left in that bar.
8. ZuiAudit's foldedSkipped can never reach 0 while ZuiMicroSlider carries a hidden numeric-input field. The useful contract is 'every skipped subtree is a control internal', which needs the enumeration the audit does not print.
9. Trajectory's fixed Life shows in the preview only when the flight is shorter than the blast's own length, so it reads as a dead dial at the defaults. Worth checking with a short life before deciding whether it needs a tell.
10. The Layer Plan's slot-name fields are unlabelled - correct in a list, but nothing tells a reader that the text field IS the slot's name.
11. Two ChunkWindow rows use raw controls with no ZUI equivalent yet: the sprite list is a bound PropertyField, and the sample source / fallback sprite / splash sprite are Z.Object<Sprite>. Both are sanctioned raw islands today; a visual sprite picker would close them.
