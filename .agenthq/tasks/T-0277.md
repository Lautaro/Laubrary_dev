CHANGELOG: Shaper - Posterise now bands every fill kind rather than steel alone; the four ramp Tints, which no authoring action could reach, are gone from the Fill card; and every remaining fill dial that cannot act right now says so on itself instead of doing nothing.

**Eighteen dials T-0265 measured as dead, each read in the engine and then measured in the state the engine says it needs.** Three turned out to be live all along and were being asked the wrong question; one was genuinely broken and is fixed; four could never have worked from the window and are gone; the rest act only under a condition the author can change, and the card now names that condition on the control.

**One dial was actually broken, and it is fixed.** Posterise sits on the shared block of a fill - beside Fade and Height change, drawn once by the card outside the per-kind switch, and described by the engine's own data model as a shared dial. It was sampled inside the steel bake alone and applied inside the steel branch alone, so on eight of the nine kinds it was never even compiled: a user document in this project authors Posterise 13 on a Gradient fill and gets a smooth ramp. The sample moved into the shared block and the banding step after the per-kind switch. Gradient 0 to 1032 pixels, Texture 0 to 214, TapestrySteel unchanged at 1032.

**Three were live, and the sweep was asking them the wrong question.** The strip's Offset wraps, and every value T-0265's sweep tried on it - 16, 1, minus 16, 64 - is a whole number, so all four wrapped to exactly nothing; at 0.5 it moves 1048 pixels. The sprite sheet's Columns and Rows were measured with the Animated toggle off; with it on they move 873 and 446. Fit was measured on a Star and a Pyramid, both of which have a square box, and Fit's only job is to choose one divisor or two; on a 34x13 ellipse it moves 968 pixels. Nothing was fixed for these three, and the card now says what the dial actually does so the next reader does not repeat the question.

**Four colours could not be reached by any authoring action, and the controls are gone.** Tint on Gradient, on Ramp, on Colour over phase, and on Procedural/Noise. Two of them claimed to multiply the sampled ramp colour; none of them does. Each is read by exactly one line in the compiler - the degenerate path taken when that kind's gradient is null, where the fill collapses to a flat solid of that colour - and the gradient is never null: the fill constructs one, and the ramp control has no way to clear it. Measured 0 pixels with a ramp present and 1032 with the field forced to null in code. The fields stay, serialized and still read on that path, so no authored document loses a value; only the control that could never do anything is gone. The same field IS the Ink on Grid and Dots, where it moves 188 pixels, and it stays there.

**The rest act only under a condition, and the condition is now on the control.** Tiles X and Tiles Y are read by the Repeat mapping alone and Mapping defaults to Fit once, so out of the box both were dead - greyed with that sentence, and 819/398 pixels once Mapping is Repeat. Frames is clamped to columns times rows, so on a one-cell grid it can only ever be 1 - greyed until the grid is bigger. The Animated toggle itself changes nothing at a 1x1 grid, which its tooltip now says. The strip's Plain colour shows only where the strip has not reached, and at the default Reach the strip covers the whole shape by construction - greyed at Reach 1, live at 0.2 (596 pixels).

**Height was the misleading one.** Height change said it was "the input the relief shading reads". It is not: every normal provider is forbidden from reading the fill height buffer, and the buffer's only consumer in the shipped engine is the cross-layer depth composite, which decides which LAYER shows through where two overlap. With one layer the whole height path is a no-op - the same edit moves 484 pixels with a second layer present and 0 without one. Height change, the strip's per-slot Height and the height field's Scale are now greyed while the document has fewer than two layers that paint, with that sentence. The one exception is real and is kept: on a Solid, a height-field fill's Scale tilts the surface the light rig shades, because a solid central-differences that one fill kind to perturb its own normal - 671 pixels on a Pyramid with a single layer, and the dial stays live there.

**A fifth thing was found that this card cannot fix, and it is bigger than any dial.** On a SAVED document every child node acquires a phantom fill, because a node's fill is a plain serialized field on a serialize-reference node - the same class of bug as the phantom border. Measured on a two-member bag: in memory the bag's own fill colour moves 1754 pixels; the same document written to disk and re-loaded, 0, because each member is now painted by its own phantom white solid. So on a saved bag the bag's ENTIRE Fill card is dead. It cannot be closed the way the border was: the border had an enabled flag defaulting to false, a fill has no such flag, nothing distinguishes a phantom from an authored plain-white fill, and turning the field into a serialize-reference would change its storage and lose every authored fill in every existing document. It needs an owner decision and a migration.

Also worth knowing: T-0265 read the height field's Scale as flat zero partly because it handed the fill an RGBA texture. The engine reads a height field with GetPixelData<float> and needs an RFloat one; an RGB texture is refused with a diagnostic, but an RGBA one has the right byte count and would be read as garbage floats with no complaint at all.

The per-dial table with before/after pixel counts and file:line is FILL-DIALS.md, which also carries the re-run of T-0265's fill rows on saved documents.
