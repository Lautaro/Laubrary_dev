CHANGELOG: Preview zoom means one thing everywhere: zoom 1 shows a simulated pixel at the size it has in game (4 screen pixels, as on a 1280x800 Steam Deck showing 320x200), zooms are whole numbers, and Fit is a button that writes the zoom it picked into the control - adopted in Pyre, Shaper, Chunks (which gains a zoom control) and Launimator's two canvases.

Zoom used to answer a different question in every tool. Pyre's 1 meant one canvas pixel per GUI point; Shaper's 1 meant "however big this pane happens to make it", so the same number showed a different size after every window resize; Chunks had no zoom at all and always blew the subject up to whatever fitted; Launimator's two zoom fields started at a fit value and at a hardcoded 6. None of them knew how big a pixel is in the game.

There is one rule now, in ZUI, and every pixel preview reads it: at zoom 1 a simulated pixel is drawn at the game's own screen scale - a whole 4x4 block of physical pixels for this project's 320x200-on-1280x800 - snapped so every pixel is an identical block rather than alternately 4 and 5 pixels wide on a scaled display. Zoom 2 is twice that. Nothing is multiplied in behind your back: the picture is never quietly fitted to the pane, and when you do want the whole thing in view you press Fit, which chooses the largest whole zoom that fits AND puts that number in the Zoom box, so what you are looking at is always a number you can read and dial. Chunks' stage, which never had a zoom, still arrives fitted when you pick a subject - the difference is that the fit is now a real zoom number on screen.

The scale comes from the project's Pixel Scale settings when they exist. They do not exist in this worktree (they live on the main copy's dev branch), so every tooltip says so and the reference 4 is used; when the branches meet, the same tooltips will name the project's own numbers with no code change.

**Details:**
How the rule is expressed, and what each tool now does.

ZuiPixelStage (Zui/Toolkit) owns three things nobody should re-derive: what a zoom NUMBER means in device pixels (TargetScale x zoom), where a buffer of a given size lands at that zoom (centred, corner snapped onto a device pixel), and what Fit should answer for a given viewport. It also builds the standard control - a Z.MicroSlider integer 1..16 whose tooltip states what zoom 1 means, plus a Fit button whose press writes its answer into that slider before applying it, so Fit is never an invisible change.

TargetScale is resolved by reflection over the type name Laubrary.PixelScale.PixelScaleProjectSettings, reading its Instance, targetResolution and referenceDisplayResolution, and dividing display height by game height (1280x800 over 320x200 = 4). The type is deliberately NOT copied into this worktree - it lives on the main copy's dev branch and copying it would guarantee a merge conflict. Absent, the fallback is 4 and every zoom tooltip says the project has no settings asset, so a preview never claims to show game size while guessing at the game's scale.

Pyre: DrawPreview now places the frame through ZuiPixelStage instead of computing a point-sized rect around the IMGUI island's centre, and draws it through Z.DrawPixels. swarmZoom - the single mapping every swarm overlay hit test uses - is now read off the placed rect rather than assumed to equal the dial, so the outline, the spawn dots and the drag handles follow the picture wherever the device snap put it. The Playback 3D pixelated sub-mode's hand-rolled floor-to-whole-points fit was replaced by the shared device-pixel fit. The transport's Zoom is the shared control; Fit measures lastPreviewView, the island rect the preview records on every repaint.

Shaper: the stage's image layer used to be stretched over the whole stage with ScaleToFit and then zoomed by a negative percentage inset - which is exactly why zoom 1 meant "whatever this pane implies". It is now absolutely positioned at the placement rect with StretchToFill, and ZoomedCanvasRect (the one rect the image, the frame border, the translate handle and the pivot cross all read) is that same placement. The frame border also picked up a fix in passing: it was drawn at the UN-zoomed fit, so a zoomed preview drew its "canvas edge" somewhere inside the picture. Stage.Zoom is an int now; the window's previewZoom stays a serialized float and is migrated on read, so a value left over from before the rule (3.4, say) arrives as a whole zoom without anything having to be rewritten.

Chunks: the Cut Preview stage gains a Zoom + Fit row. It used to call Z.DrawPixels' fit-largest one-liner, which has no zoom concept at all; it now draws at the dialled zoom. A newly picked subject still arrives fitted (a zero sentinel means "not chosen yet", and the fit is computed against the fixed 200pt stage box, so it can answer before the first repaint and write the number into the slider). Its readout used to print the raw device-pixel factor as "8x" right above a control that would have said 2 - two numbers for the same thing on adjacent lines - so it now reads "19 x 46 px - zoom 2 - 8 screen px each", and its width went from 200 to 300 because the longer line truncated mid-word (measured, not guessed).

Launimator: both zoom fields hold a whole zoom LEVEL now, and everything geometric multiplies by a derived points-per-pixel, so the level is what the user reads and the points stay a display-scaling detail. The sheet canvas's content size is an exact device multiple and its scroll offset is snapped in device space before BeginScrollView, so a 1px marquee outline cannot smear into the art it sits on; the paint editor's clip origin is snapped the same way. Fit for the sheet measures the canvas island's WIDTH only, because the sheet scrolls vertically - which is what the old auto-fit did too, only now the number it chooses is written into the control. The old "Fit" button that just reset a private initialised flag is gone in favour of the shared one.

Two things deliberately left as they are: zoom is preview-only state everywhere (Pyre's on the spec as before, Shaper's and Chunks' and Launimator's on the window), so no Undo was added for it - it survives a rebuild, which is what the card asked for, and a domain reload resets the ones that were never serialized, exactly as before. And nothing in any render path changed: every one of these edits decides how big the same pixels are drawn, never what is drawn.
**Technical details:**
Verification method, because it matters more than the numbers.

InternalEditorUtility.ReadScreenPixel was tried first and rejected: it returns POINT-resolution data (a capture from (40,40) sized 1980x1575 came back covering the entire 1706x960-point desktop), which would have measured the very unit the bug hides in. The captures are PrintWindow with SetProcessDpiAwarenessContext(-4) first, driven from Coplay execute_script (unity-mcp's eval_file wraps its input in a method body, so a class with DllImports cannot be compiled there). Coplay was pointed at the worktree and Application.dataPath verified as D:/UNITY/Laubrary Dev - Shaper/Assets before anything was trusted.

Two rulers, both independent of the code under test:
1. The preview's own canvas-edge frame border, found as the longest uninterrupted run of border-coloured pixels in the capture. Its length in physical pixels divided by the canvas width in simulated pixels is the answer. Pyre 256/64 and 512/64; Shaper 384/96 and 608/152.
2. The GCD of every constant-colour run along scanlines through the picture. At zoom N every simulated pixel must be exactly N x 4 physical pixels, so every run is a whole number of blocks and the GCD is the block size; one pixel a physical pixel wider than its neighbour collapses it to 1. Measured 4 at zoom 1 and 8 at zoom 2 in all four tools.

One trap worth recording: Pyre's first block measurement came back GCD 1. That was not the fix failing - it was Pyre's backdrop, a photograph drawn at its own fractional scale behind the canvas, showing through the flame's partly transparent pixels, so each blended pixel differed from its neighbour. Re-measured against a plain backdrop it is a clean GCD 4 / 8, and the raw histograms show the dominant run was already 4 and 8 in the polluted capture. The backdrop settings object was blanked in memory to take that measurement and then rebuilt field-for-field from the on-disk YAML; the spec's dirty flag was cleared and git diff --stat on Assets/Pyre/New Pyre Plus.asset is unchanged from where it started (127/15, a pre-existing gradient-schema migration), so nothing a probe touched reached disk.
