## Description

T-0408 ported the effect-chain DSP engine to run as compiled native code with no C++ plugin, and verified it exhaustively. **It was never connected to anything.** The owner opened the editor, saw the pre-chain UI with no way to add an effect, and correctly concluded the assignment had been misunderstood: they expected the authoring experience to change too — live editing, no baking step — not a backend swap behind an unchanged UI.

They were right. This task is the integration that makes the engine the product.

## Where the reference lives

**`x/audio-effect-chains-native` in HH2Lab** is the real-time-only architecture: its pooled audio source never plays and its clip is nulled, everything goes through a voice handle, and there is no rendered output file in the path. `x/combat-lab` is the WRONG source — it only has the old bake-based effects, which is what Laubrary Dev already had.

HH2Lab was read strictly read-only, via git plumbing, without switching its branch (it has a live editor open on `x/audio-movement-update`). Reference copies were exported to a scratch folder and read from there.

## What was done

**Playback now goes through the chain, from the sound's ORIGINAL audio, with no rendered file.** The audio source holds no clip; it exists only to carry the sound into the mixer, which is what still gives bus routing, group volume, distance attenuation and 3D position.

**An edit reaches a sound that is already playing.** The authoring UI calls a delivery function on every slider movement; each voice resolves the change against the layout IT started with, deliberately not the sound's current layout, because the edit being delivered may already have rebuilt that.

**The authoring UI exists**, ported from the reference: sixteen effects addable in any order and number, parameter rows generated from the engine's own descriptions, modulators bound onto parameters with depth and operator, a preset library with per-sound overrides, repeat/retrigger, time-stretch, stop-all.

**The old surface is gone and files are no longer written.** The Klip editor had been showing BOTH authoring surfaces with the old one on top — a fixed row of on/off toggles for seven built-in effects — which is exactly what the owner saw. Those seven only worked by being rendered into a file, and each one marked the sound as needing a re-render, which is why the project accumulated a small near-duplicate file per sound per revision. The row is removed and the automatic render is off.

**Nothing authored is lost.** A sound still carrying the old settings has them converted to an equivalent chain on the fly at play time, and a menu action makes that permanent so they become visible and editable.

## Two architecture decisions, made deliberately

**The reference's central voice graph was NOT ported.** It exists because the C++ plugin rendered audio outside Unity's mixer and therefore had to implement its own summing, buses, voice pool, event ring and stall detection. These voices play through an ordinary audio source, so the mixer already provides all of that and concurrency is bounded by the existing source pool. Porting it would have duplicated the mixer for no benefit.

**Rendering was not deleted, only demoted.** The duplicate authoring surface is gone and no file is written automatically, which is the complexity and file-count reduction that was asked for. But bouncing a sound to a file is a working feature with real uses, so it stays as something you ask for rather than something that happens to you. Flagged to the owner in case they want it gone entirely.

## Verified

By automated check, repeatable from the Laubrary menu, and deliberately non-destructive (it builds the sound it tests in memory and never adds it to the library, because the owner is authoring right now):

- the rendered file is bypassed — the audio source has no clip at all
- a chain voice is attached, and knows which sound it plays so an edit can find it
- a play length is worked out despite there being no file to measure
- an editor's (effect, parameter) pair resolves to a real engine slot
- **the audio graph takes the voice in EDIT mode**, so the edit-and-listen loop works without running the game
- **a live parameter change was delivered to the playing voice**

Also confirmed by reading: the browser's own play button already goes through the rewritten path, and the engine is set up to run outside play mode, which is what lets the graph take a voice at all.

## Not verified

**Nobody has heard it.** Every mechanical step between pressing play and the change arriving at the voice is verified; that the result sounds correct is not, and cannot be by an agent.

## Things worth knowing

**A source clip must be imported as Decompress On Load** to go through the chain — Unity will not expose samples otherwise. A sound whose source streams falls back to its rendered file and says why, once per session. The menu check "Can each sound reach the chain" reports this per sound and is the first thing to run if a chain appears to do nothing.

**A tail is accounted for.** A delay or reverb keeps sounding after the source runs out, so the chain's declared decay is added to the play length — otherwise the handler would declare the sound over and recycle its audio source mid-tail, chopping it.

**A sequence now always plays its parts**, never a flattened file of itself. It already had a mode that schedules its parts and lets each play itself, and that mode is now the only one. Preferring a flattened file — which it used to do whenever one existed — became the wrong choice the moment each part gained its own chain, because any such file was produced before those chains existed and playing it would serve a stale mix while appearing to prove the chains do nothing.

## The combined view's flicker, and what it turned out to be (2026-09-27)

The owner reported the combined analyser as too jittery — bars flickering between extremes with nothing affecting them. **The movement was the measurement, not the chain.**

The analyser pushes a test signal through the chain and compares each frequency band before and after. It used continuous noise, so every analysis window saw different samples. In a band an effect has cut deeply, almost nothing of that band survives — so what was actually being measured there was energy leaking in from loud neighbouring frequencies, which changes with every window.

Fixed by driving it with a signal that repeats exactly once per analysis window, so every window sees identical input and anything still moving is genuinely the effect. The analysis window was also widened so low frequencies are resolvable at all, and a band too narrow to resolve now draws a grey stub rather than a number — drawing zero would claim "unaffected" where the honest answer is "too low for this to speak about".

**Checked that this removed noise and not signal**, by sweeping all sixteen effects before and after. Everything that should hold still went to zero movement (a high-pass from 4.4 dB of wobble to none, a distortion from 12 dB to none); everything that genuinely sweeps kept its movement (flanger and phaser unchanged at around 19 dB); and the depth of the effects' actual influence barely moved, so nothing was smoothed away. No display smoothing was used anywhere.

**This overturned a conclusion recorded earlier in this very task.** Delay and reverb had been given the verdict "trust the movement, ignore the average", on the strength of them moving a band by tens of decibels. That movement was mostly the measurement's own noise. Their verdict is corrected to say the settled shape is real but the timing is invisible, and the mistake is written down beside it rather than quietly replaced.

## Layout stability (2026-09-27)

Two standing UI rules were applied to everything built here: text that may be absent, short or long must not change the height of what it sits in, and a redraw must not move a scrollable view. Real breaches were found and fixed — a "re-measuring" line that appeared WHILE a slider was being dragged, shoving the graph up and down under the hand adjusting it; a warning banner that pushed the whole editor down two rows on appearing; and labels that wrapped, so panel height depended on window width.

Enforced by an automated check rather than by looking once: it measures the panel's height in every state at two very different widths. This class of bug only exists BETWEEN two states, so a single screenshot structurally cannot catch it — and the check immediately caught an eighteen-pixel jump that had been missed.

## Edge case found in self-review, recorded rather than fixed

A pooled audio source keeps its chain player between plays, which is deliberate — attaching a fresh one per play would add a component every time a sound started and never remove one. The consequence is that the player remembers only the MOST RECENT sound it was given.

If a sound is still finishing (a long tail, say) when its audio source is recycled for a different sound, an editor edit aimed at the first sound would be delivered to the second. Nothing leaks and nothing crashes — the graph still owns and disposes the earlier voice correctly — but the edit lands on the wrong sound.

Not fixed because it needs the source pool to stop recycling a source whose voice has not finished, which is a change to pooling policy rather than to the chain, and because in practice a source is recycled when its sound is considered over. Worth knowing before trusting a live edit during heavy overlapping playback.

## Visualisation: a chain analyser and live views of the real signal (2026-09-27)

Asked for as an open question — "is it reasonable to see the combined effect of a stacked chain, or do these effects operate in a way that makes a combined figure meaningless?" — with explicit permission to experiment. Both halves were built, and the interesting part is what measurement said about the premise.

**Yes for most effects, and it is measured rather than modelled.** The obvious approach would be to have each effect describe its own contribution and add the descriptions up. That is wrong twice over: some effects have no such description to give, and any description that did exist would be a second implementation free to drift from the one being listened to. So the analyser runs real audio through the real chain, using the offline renderer that shares its code with playback, and compares output with input. Noise rather than an impulse, because several of these effects behave differently depending on level and an impulse would flatter them. A series of windows rather than one number, because a modulated effect is doing something different moment to moment and that movement is usually the whole point.

Verified against known answers before being trusted: a gain of two reads exactly 6.02 dB on every band, a low-pass leaves 150 Hz alone and drops 8 kHz by 35, a high-pass mirrors it, a flanger shows 38 dB of movement.

**The honesty panel is the part worth defending.** It names every effect in the chain and how far to trust its contribution, in four verdicts: shown exactly; shown and moving; shown for this test signal only because its gain depends on level; and shown but manufactured, for a waveshaper or bitcrusher where apparent boost is invented harmonics and reading it as "louder here" is the wrong mental model. An effect added later defaults to unrepresented, because guessing "exact" for something unknown is how a display starts quietly lying.

**Measurement corrected my own classification.** Delay and reverb were classified as showing nothing useful, on the reasoning that their comb structure is far finer than any displayable band so averaging cancels it. The averaging part is true; the conclusion was wrong. Measured across time a delay moved a band by nearly 28 dB and a reverb by nearly 48 — the repeats arriving and the tail decaying, which is worth seeing. They now have their own verdict: trust the movement, ignore the average.

**The live views needed a tap, and two free routes were eliminated first.** Unity's own sample readers return silence for audio produced through a generator, both per-source and at the final mix, because they tap the clip-playback route this engine bypasses. So the engine keeps a rolling copy of its own output, allocated only for voices started while something is looking; otherwise the per-block cost is one check that the buffer does not exist.

## A correction to an earlier claim in this task, and the trap behind it

This task previously recorded that the audio graph "takes the voice in edit mode" and concluded a chain edit could therefore be heard in the editor. **The first half was measured; the second was inferred, and inference was not good enough.** Accepting a voice and asking it for audio are different things.

A first attempt to settle it reported that the graph never renders in edit mode at all — which would have made that conclusion wrong and pushed every audible check into play mode. That result was an artefact of the test: it blocked the main thread for four hundred milliseconds while waiting, and a graph needs the main thread to service it, so the test starved its own subject.

Re-run as two steps with the editor allowed to run in between: three thousand samples written, peak exactly the amplitude of the tone played, frequency read back off the samples matching what went in. **The graph does render in edit mode**, so the original conclusion holds — but it now rests on actual audio instead of on a message being accepted. The wording of the earlier check was corrected to claim only what it shows, and the two-step check is kept, with the blocking trap written down beside it.
