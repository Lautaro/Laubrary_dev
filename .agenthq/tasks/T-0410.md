## Description

T-0408 ported the effect-chain DSP engine to run as compiled native code with no C++ plugin, and verified it exhaustively. **It was never connected to anything.** The owner opened the editor, saw the pre-chain UI with no way to add an effect, and correctly concluded the assignment had been misunderstood: they expected the authoring experience to change too — live editing, no baking step — not a backend swap behind an unchanged UI.

They were right. This task is the integration that makes the engine the product.

## Where the reference lives

**`x/audio-effect-chains-native` in HH2Lab** is the real-time-only architecture: its pooled audio source never plays and its clip is nulled, everything goes through a voice handle, and there is no rendered output file in the path. `x/combat-lab` is the WRONG source — it only has the old bake-based effects, which is what Laubrary Dev already had.

HH2Lab was read strictly read-only, via git plumbing, without switching its branch (it has a live editor open on `x/audio-movement-update`). Reference copies were exported to a scratch folder and read from there.

## What was done

**Playback now goes through the chain, from the sound's ORIGINAL audio, with no rendered file.** The audio source holds no clip; it exists only to carry the sound into the mixer, which is what still gives bus routing, group volume, distance attenuation and 3D position.

**An edit reaches a sound that is already playing.** The authoring UI calls a delivery function on every slider movement; each voice resolves the change against the layout IT started with, deliberately not the sound's current layout, because the edit being delivered may already have rebuilt that.

**The authoring UI exists**, ported from the reference: sixteen effects addable in any order and number, parameter rows generated from the engine's own descriptions, modulators bound onto parameters with depth and operator, a preset library with per-sound overrides, repeat/retrigger, time-stretch, stop-all.

**The old surface is gone and files are no longer written.** The Klip editor had been showing BOTH authoring surfaces with the old one on top — a fixed row of on/off toggles for seven built-in effects — which is exactly what the owner saw. Those seven only worked by being rendered into a file, and each one marked the sound as needing a re-render, which is why the project accumulated a small near-duplicate file per sound per revision. The row is removed and the automatic render is off.

**Nothing authored is lost.** A sound still carrying the old settings has them converted to an equivalent chain on the fly at play time, and a menu action makes that permanent so they become visible and editable.

## Two architecture decisions, made deliberately

**The reference's central voice graph was NOT ported.** It exists because the C++ plugin rendered audio outside Unity's mixer and therefore had to implement its own summing, buses, voice pool, event ring and stall detection. These voices play through an ordinary audio source, so the mixer already provides all of that and concurrency is bounded by the existing source pool. Porting it would have duplicated the mixer for no benefit.

**Rendering was not deleted, only demoted.** The duplicate authoring surface is gone and no file is written automatically, which is the complexity and file-count reduction that was asked for. But bouncing a sound to a file is a working feature with real uses, so it stays as something you ask for rather than something that happens to you. Flagged to the owner in case they want it gone entirely.

## Verified

By automated check, repeatable from the Laubrary menu, and deliberately non-destructive (it builds the sound it tests in memory and never adds it to the library, because the owner is authoring right now):

- the rendered file is bypassed — the audio source has no clip at all
- a chain voice is attached, and knows which sound it plays so an edit can find it
- a play length is worked out despite there being no file to measure
- an editor's (effect, parameter) pair resolves to a real engine slot
- **the audio graph takes the voice in EDIT mode**, so the edit-and-listen loop works without running the game
- **a live parameter change was delivered to the playing voice**

Also confirmed by reading: the browser's own play button already goes through the rewritten path, and the engine is set up to run outside play mode, which is what lets the graph take a voice at all.

## Not verified

**Nobody has heard it.** Every mechanical step between pressing play and the change arriving at the voice is verified; that the result sounds correct is not, and cannot be by an agent.

## Things worth knowing

**A source clip must be imported as Decompress On Load** to go through the chain — Unity will not expose samples otherwise. A sound whose source streams falls back to its rendered file and says why, once per session. The menu check "Can each sound reach the chain" reports this per sound and is the first thing to run if a chain appears to do nothing.

**A tail is accounted for.** A delay or reverb keeps sounding after the source runs out, so the chain's declared decay is added to the play length — otherwise the handler would declare the sound over and recycle its audio source mid-tail, chopping it.

**Zequences need no separate work**: they already had a real-time mode that schedules their children, and each child now goes through the chain. A zequence that still has a rendered file of its own will play that instead; switching those over is a remaining nicety.

## Remaining

- **In flight:** the volume and pitch curves drawn on the waveform still write the sound's legacy fields, which are only honoured when the sound has NO chain — so adding any effect silently disables them. Being rewired onto the equivalent chain modulators.
- The by-ear test.
- Optional: retire a zequence's own rendered file the same way a klip's was.
