## Handover Log

### 2026-08-16T00:00:00Z — agent — in_progress -> done
Turned out to be much bigger than a missing `Priority` const: the ENTIRE
MotionState/AnimationArbiter/MotionPoseAnimator wiring described in
`zoe-movement-motionstate-arbiter-2026-08-14.md` was gone from every TRACKED file
(`ZoeSpawner.cs`, `CompositeZonedPlayer.cs`, `CompositeLauminaryView.cs`, `Zoe.cs`,
`Locomotion.cs`) — only the pure-data/new-untracked pieces (`MotionState.cs`,
`MotionPose.cs`, `MotionPoseAnimator.cs`, `MotionPoseResolver.cs`,
`IMotionPoseHost.cs`) had survived, unreferenced by anything. Rebuilt all of it
tonight, verified live:
- `LocomotionAnimator.Priority` (const, 0f) added back to `Locomotion.cs`.
- `LauminaryVersion.sets` (`List<LauminationSet>`) added back — `MotionPoseResolver`
  needs it to look up a rule's named set.
- `Zoe.motionPose` and `ZoeBodyPart.motionPose` (`MotionPose`, additive/unauthored
  by default) added back to `Zoe.cs` / `CompositeLauminaryView.cs`.
- `AnimatedViewRelay` now implements `IFlippableView` + `IMotionPoseHost` (its
  `BindMotionPose` attaches `AnimationArbiter` + `MotionPoseAnimator` and Binds
  them) — this is what makes both the single-body AND composite-part cases work
  through the same optional-capability pattern the rest of the codebase uses.
- `CompositeZonedPlayer.Build` calls `BindMotionPose` per part after building its
  view.
- `ZoeSpawner.SpawnCharacter` always attaches `MotionStateSource` to the root, and
  prefers `def.motionPose` over `def.locomotion` when authored (exactly mirroring
  the old Locomotion gate, so an unauthored Zoe is unaffected).
- `Laubrary.Demos.asmdef`'s `ZoeCharacter` reference re-added (separate, smaller
  loss, same asmdef-revert mechanism as the rest of this incident).

**The walk-animation bug itself, once this was rebuilt**: `ZoeSpawner.SpawnCharacter`
never set `Rigidbody2D.interpolation` on the spawned Kinematic body (defaults to
`None`). With physics ticking at a fixed 50Hz (`Time.fixedDeltaTime=0.02`) and
rendering at ~184fps in this test, a `MovePosition`-driven Kinematic body only
actually moves `transform.position` on physics ticks — so `MotionStateSource`'s
per-RENDERED-frame velocity sample flickered between the real speed and 0 on the
~73% of frames physics didn't tick that render frame, thrashing the walk/idle
clip. Confirmed via a live probe (`rb.interpolation=None` before the fix) and fixed
by setting `rb.interpolation = RigidbodyInterpolation2D.Interpolate` in
`ZoeSpawner.SpawnCharacter` — a general fix, not ProtoGuy-specific, benefits every
Rigidbody2D-driven Zoe.

**Verified live**: pressed W via a real queued Input System keyboard event, sampled
`ZonedAnimationPlayer.CurrentClip`/`CurrentFrame` 3x over several seconds while
moving — consistently `LegsWalk_N`, frame index progressing/looping (1→6→2), never
reverting to idle. Also captured a mid-walk screenshot (`capture_scene_object`) —
coherent walking pose, correct leg/torso alignment, no visual artifacts. Not yet a
full human Handover Walk (multiple directions, diagonal movement, aim-while-moving)
— that's still worth doing per this project's UI Guide before calling ProtoGuy
fully done, but the specific reported bug (flickering/wrong-order frames) is fixed
and verified.
