A toggle-button bar at the top that shows/hides whole sections (Canvas, Layers, Global Mod, Shape, Swarm, etc.) instead of folding them one by one would be a small, low-risk addition — and yes, it would automatically be available to every other Laubrary tool that already uses this same section layout (Chunks, Larder, Mirage, SpriteFx, Zoetrope, Cabinets), not just PyrePlus, since they all share one underlying piece.
**Details:**
This was a feasibility check — nothing was built yet.

Why it's low-risk: the collapsible sections you see in PyrePlus (and in about 7 other tools) already come from one shared, reusable building block, and a ready-made "row of toggle buttons" control already exists elsewhere in the same toolkit (used today for a different flag-row in Pyre). Adding the toggle bar mostly means pointing that existing button-row control at the existing section open/closed state — it wouldn't be new state to track, and it wouldn't change how any tool that doesn't opt in behaves.

How it would work: each tool that wants the bar would list its own section names once near the top of its window; nothing else about the tool changes. Because it is opt-in per tool, adding it to PyrePlus first and rolling it out to others later is completely safe.

Not yet verified: the exact bar wording/placement, and whether it should sit ABOVE the sections (as asked) or somewhere else in the layout — that's a quick call once you say go.

Recommendation: I'd like the go-ahead to actually build it, starting with PyrePlus's six sections, before touching any other tool.
**Technical details:**
Shared section control: Assets/Packages/Laubrary/Zui/Toolkit/ZuiSection.cs (`Z.Section(...)`). Fold state lives in a static `Dictionary<string,bool> s_open` keyed by title+tooltip, so it survives window rebuilds. Confirmed reuse: 51 `Z.Section(...)` call sites across 13 files / 8 tools — CabinetEditor.cs, ChunkSpecEditor.cs, ChunkWindow.cs + ChunkWindow.Preview.cs, LarderWindow.cs, MirageWindow.cs, PyrePlusWindow.cs + PyrePlusWindow.CherryFraming.cs + PyrePlusWindow.Modifiers.cs, SpriteFxFilterEditor.cs + SpriteFxStackWindow.cs, ZoetropeWindows.cs.

Ready-made bar widget: `ZuiSegmented.Multi(...)` in ZuiSegmented.cs is already a row of independently-latching toggle buttons (used today for Pyre's matte-channel flags) — this IS the toggle-bar UI, it just needs `isOn`/`onToggled` wired to each section's `IsOpen`.

Gap found: unlike its sibling ZuiBox (which raises a `ViewChanged` event on any fold/gear change), ZuiSection has no change-notification hook today, so a toggle bar built as a separate widget wouldn't relight itself if the user folds a section the OLD way (clicking its own header). Fix: add a small optional `Action` callback to ZuiSection, invoked from the same spot `Apply()` runs, mirroring ZuiBox's existing `ViewChanged` idiom — additive, ~15 lines, no call-site changes required for existing users.

Layout safety verified by reading PyrePlusWindow.cs BuildAsset(): its dial stack is one `ZuiColumnFlow` (ZuiColumnFlow.cs) that self-splits 1-4 columns by width; each Build* method (BuildCanvas/BuildLayerList/BuildGlobalModifiers/BuildShape/BuildSwarm/BuildModifiers/BuildImport) adds exactly one top-level unit. Traced `Redistribute()`/`ContiguousSplitByHeight()`: a hidden unit (`style.display = None`) stays in the flow's hierarchy contributing 0 height, so hiding a section via the bar would not break the column height-balancing or leave a visible gap — no ColumnFlow changes needed.

Per-tool wiring note for PyrePlus specifically: some sections are already kept as fields (e.g. `swarmSection`), others are local vars inside their Build* method (e.g. the Canvas section at PyrePlusWindow.cs:643) and would need promoting to fields so a single bar built near `BuildViewBar` (PyrePlusWindow.cs:322) can reference all six.

Effort estimate: ~30-60 min for the one-time ZuiSection hook + doc note; ~15-30 min per tool to wire in (PyrePlus first, 6 sections).
