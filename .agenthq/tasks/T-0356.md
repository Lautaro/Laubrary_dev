**Details:**
Design decisions asked for by the task, both made and documented in the code/CHANGELOG:

1) Does "On screen" keep a manual override? Yes, kept as an escape hatch behind a new Auto toggle (Z.ToggleButton, latches, tooltip per state) - not removed. Two genuine reasons to turn it off: (a) a Blast source this window cannot measure a length for (today only Pyre and PyreSpawnSource are understood - the slider then shows a tooltip saying so and falls back to whatever is typed), and (b) a deliberate pacing choice, e.g. ending the clock before a long trailing fade actually finishes, or holding it open a beat after a short blast. Auto is ON by default for every capability, old and new - a deliberate exception to this codebase's usual "new field defaults to old byte-identical behaviour" convention, because the 0.6s-vs-1.33s+ gap the walk found is a bug nobody would pick on purpose, not an authored value worth preserving.

2) Which alternate's length wins when the pool holds several? The LONGEST measurable one. Sizing to the shortest would make every OTHER alternate's tail overrun its own band on whichever spawn draws it - literally H6's bug again, just moved from "one wrong guess" to "wrong for all but the shortest". Sizing to the longest means only the faster alternates ever finish early inside their band, which already reads as normal elsewhere in this tool (the Life dial does the same thing on purpose); a blast still visibly playing after its band says it's over is the direction that reads as broken, so that's the one ruled out.

How the real length is read (Editor/Chunks/ChunkPyreBlastLength.cs, new file): a directly-picked Pyre -> frameCount / DirectFps (DirectFps = Mathf.Max(1, previewFps), the exact rate PyreChunksDirect.SpawnEffect spawns a one-shot at). A PyreSpawnSource wrapper -> loop ? loopSeconds : frameCount/fps (its own per-use fields). Deliberately NOT read from IChunkAnimation.Fps/Loop - that's Pyre's OTHER Chunks contract (frame handoff for ongoing chunk content) and reports Loop=true unconditionally, which would wrongly claim a one-shot spawn never ends. CherryFrame.ResolveLength (the PM's own suggested lead) was checked and rejected: its header comment says cherry-picking only reorders the EDITOR PREVIEW loop, rendering is untouched, so it describes a loop nobody spawns.

Why this lives in Chunks.Editor and not on PyreBlast itself: PyreBlast (Runtime/Chunks) cannot reference Pyre - Pyre already references Chunks (that's how IChunkEffectSpawner exists at all), so the reverse would be an assembly cycle. Chunks.Editor referencing Pyre's runtime asmdef is one-directional and safe (nothing in Runtime/Pyre ever references an Editor-only asmdef); added com.Lautaro-Arino.Laubrary.Pyre to ChunksEditor.asmdef's references for this.

Syncing behaviour: every explicit edit that can change the answer (picking a Blast, adding/removing/setting an Alternate, toggling Auto) re-syncs blastSeconds inline inside that edit's own Dial() call, riding its existing Undo/dirty/SyncTiming - no extra Undo steps. A second, passive path (SyncAutoBlastSeconds, run once per card build) self-corrects a legacy recipe's stale blastSeconds the moment its Pyre Blast card is next drawn (window open, or that card's own rebuild) without creating its own Undo step - a data-consistency correction, not a user edit, matching how this codebase already treats derived/migrated data. Known, honestly-flagged gap: that passive correction only fires when the card is actually built; it does not watch a picked Pyre asset's frameCount/previewFps changing from OUTSIDE the Chunks window while the card stays unbuilt.
