## Description

**Owner directive (2026-09-20):** offered "make chunk effects previewable in Mirage as intended" as a real path to real-Play-mode verification, alongside T-0374/T-0377's demo-scene rigs. This task checks whether that path already works.

**It's already built, just never exercised.** Every Chunks recipe card already has a "Preview in Mirage" button (`Assets/Packages/Laubrary/Editor/Chunks/ChunkWindow.Preview.cs:217`, wired to `PreviewInMirage(ChunkSpec)` at line 820) that opens `MirageStage.unity`, creates an in-memory-only `MirageView` (never saved as an asset — never `AssetDatabase.CreateAsset`'d), adds the recipe as an entry, and opens the Mirage window for it. The tooltip says: "Chunks only move in Play mode, so press Play once Mirage is up." Every single UC1-UC6 walk (T-0344..T-0349) explicitly skipped testing this ("Mirage handoff was not run... off limits for this programme") because `MirageStage.unity` carries the owner's own uncommitted edits.

**That caution was reasonable but the actual risk has now been traced and is low — confirm this yourself before trusting it, but here's the reasoning:** `EnsureMirageStageOpen()` (`ChunkWindow.Preview.cs:801-818`) calls `SaveCurrentModifiedScenesIfUserWantsTo()` on the CURRENTLY open scene (prompts, cancel-able, leaves that scene alone on cancel) — it does NOT touch or save `MirageStage.unity` itself. It then `OpenScene`s `MirageStage.unity` from disk, which already contains the owner's WIP (git's "uncommitted" just means not yet committed — the file on disk already has the edits saved; opening it doesn't discard anything). Nothing in this call path writes to `MirageStage.unity`. Verify this reasoning against the actual code before relying on it, and if you do anything that WOULD dirty/save `MirageStage.unity`, stop and ask rather than saving over the owner's WIP.

**Do:**
1. Confirm the reasoning above by re-reading `ChunkWindow.Preview.cs:792-830` yourself.
2. Open the Chunks window on a real recipe (e.g. `Assets/Demos/ChunksDemo/UseCases/UC1 Several Pyres.asset` — read-only use, do not edit it) and press "Preview in Mirage."
3. Confirm Mirage opens, the entry appears, and pressing Play actually bursts it in Play mode against a real backdrop.
4. If anything is broken (compile error, doesn't burst, throws), fix it — likely a small, contained bug given the feature already has substantial working code around it. If it's a bigger issue, stop and hand over `blocked` with what you found rather than guessing at a redesign.
5. **Do not save `MirageStage.unity`** at any point — if Unity prompts to save it, cancel/decline and say so in the handover. Exit Play mode cleanly when done.

**Note for the handover:** this tool bursts the recipe DIRECTLY (`view.AddEntry(spec, ...)`), not through a real weapon-hit/`Health`/`ReactionFxPlayer` chain — so it's a strong, reusable check that a recipe looks right in real Play mode against a real backdrop, but it is NOT a substitute for T-0377's real-hit rig for UC4-6 (which specifically need the live-Zoe-sprite-at-death and real-hit-direction behaviour Mirage's direct burst can't exercise). Say this plainly in the handover so nobody conflates "Mirage verified it" with "the real game trigger chain was tested."

**Owner clarification (added after the task was already dispatched, 2026-09-20):** "Preview in mirage should only play the preview and show what it looks like at runtime. It should not have to simulate any kind of interaction." Pressing Unity's own Play button is fine; anything beyond that (a simulated keypress, click, or other gameplay-shaped input) to make the burst actually fire is NOT acceptable as "working as intended." Check specifically whether the burst plays automatically once Mirage is in Play mode. If it does — say so plainly as verified. If it currently needs some extra triggering step, that is a real gap: fix it if small/in-scope (Mirage should auto-play a preview entry on Play start), otherwise stop and hand over `blocked` with a precise description of what's currently required and why — do not quietly verify a simulated-interaction workaround as satisfying this requirement.
