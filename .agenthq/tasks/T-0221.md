### 2026-09-03T08:27:36Z — agent — in_progress -> done
A gradient no longer stops at eight colours, and the thing you use to change colours is now one control instead of two.

The reason there were ever two was single and boring: a ZuiGradient was stored as a UnityEngine.Gradient, which hard-caps at 8 colour keys, while a Pyre ramp has no cap and blends in linear light. So Fill got the nice control that could not hold ten colours, and Pyre kept its own that could. A gradient is now stored as its own stop list with its own blend space -- the same shape a Pyre ramp has -- and a UnityEngine.Gradient is only a format at the edges, subsampled to 8 keys when something genuinely demands one and never in storage.

With the storage the same on both sides, the control follows. The ramp you edit inside every gradient IS the ramp control Pyre already used: double-click the bar to add a stop (it takes the colour already there, so inserting never changes the picture), drag it, right-click to remove, click it for its colour and position, and the Linear Light / sRGB choice sits beside it. The shared star library now stores stops rather than an 8-key gradient, so a palette crosses between a Pyre ramp and a Fill gradient whole -- a 14-stop ramp saved from Orb's Membrane and applied to a Fill gradient arrives as 14 stops, where before six were dropped in transit. Pyre's own ~35 ramp presets reach Shaper exactly now too, Ember's ten stops and its linear-light blending included, instead of the 8-key approximation that path shipped as.

Nothing you have already authored moves. The old gradient stays as the frozen source, an existing asset renders through it exactly as before, and the conversion runs only when an editor opens the field. Measured rather than asserted: the demo document and three authored Pyre assets render to an identical hash before and after their gradients convert, and all 31 Pyre presets survive stop-for-stop.

One thing went the opposite way to the plan, and you should know which way. The task said to put the gradient control at every ramp site; what actually happened is the gradient control adopted the RAMP control's stop editor, because a PyreRamp has nowhere to store the non-destructive Adjust knobs (hue/saturation/brightness/phase) and inventing that storage would change Pyre's authored data. So Pyre's window does not change look -- the before/after screenshots show parity by design -- while gradient sites lose Unity's 8-key field. If you want the Adjust knobs on a raw Pyre ramp too, that needs a decision from you: either those ramps start storing a ZuiGradient (a data change), or the knobs become a one-shot 'recolour every stop' action that rewrites them under a single undo. I did not guess at that.

**Technical details:**
STORAGE. ZuiGradient (Zui/Scripts/Runtime/ZuiGradient.cs) now owns List<ZuiGradientStop> stops + ZuiGradientSpace space (LinearLight=0 / Srgb=1, declared in PyreRampSpace's order so the choice crosses as one index), evaluates itself through EvalRamp (allocation-free, thread-safe, no transforms) and implements IZuiRamp. The legacy Gradient is kept as a private [SerializeField, FormerlySerializedAs("gradient")] field; `gradient` survives as a PROPERTY over ToGradient/SetGradient so all 24 consumer sites still compile and behave. Default space is Srgb, the plain lerp a Gradient performs, which is why a converted gradient is byte-identical.

MIGRATION. EnsureStops() converts at the union of the Gradient's colour AND alpha key positions (linear interpolation reproduces a Blend gradient exactly there). It runs from the editor or an explicit call -- never in OnAfterDeserialize (that would read native Gradient keys on Unity's deserialize thread) and never from Evaluate, so nothing on a render thread can trigger it. Until it runs, EvalRamp reads the legacy Gradient directly: an un-migrated asset renders identically either way.

A FIXED GRADIENT was the one case the probe caught wrong (commit 3d6c0f76). Placing one stop per key and interpolating turns each hard step into a slope -- 816 of 1024 samples wrong. It now emits a stop PAIR per interval carrying that interval's midpoint colour, boundaries as repeated positions (how PyreShade.CollapseSteps already reads a hard edge), plus a leading pair for Unity's own quirk: Fixed reads the NEXT key across an interval but returns the FIRST key's colour at exactly t=0 (measured). 0/1024 after.

CALL SITES CHANGED. ZuiGradientEditor.Source is a ZuiRampControl (was GradientField), constructed with showLibrary:false since the editor's own star sits on the Output row. ZuiRampControl gained that parameter and routes its star through the lossless bridge. ZuiGradientPresetLibrary entries store stops+space with Resolve() converting pre-T-0221 Gradient entries. ZuiGradientPresetPopup trades in ZuiGradient. ZuiRampGradientBridge gained ToZuiGradient/ApplyZuiGradient (lossless, blend mode carried when both types name the same modes) and keeps the Gradient overloads. PyreShaperRampPresets.ToZuiGradient is now exact. ZuiFill.HasGrad and two ShaperFillCompiler null-checks moved to HasRamp -- reading `.gradient` now BUILDS an export, which must not happen per-sample. SpriteFxColorRemap's clone uses ZuiGradient.Clone() (which also copies the animatable companions the old field-by-field copy dropped). Four audit helpers had to stop mutating what the getter returns.

ZuiReflect's exact-type ZuiGradient branch sits BEFORE the IZuiRamp branch, so a reflected ZuiGradient still gets the full gradient control rather than the bare stop editor.
