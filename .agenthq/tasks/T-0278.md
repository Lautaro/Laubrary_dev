**Details:**
Root cause found. Steps/Bevel steps never reach the surface because the ANALYTIC surface-normal derivative — the only channel by which a single-layer document's Height stage can produce a visible pixel, since normalKind defaults to Constant and Height's own buffer feeds nothing but inter-layer depth ordering (ShaperWindow.Sections.cs:262-284, HeightOnlyOrdersLayersReason) — is hard-coded to 0 for the Stepped extrusion technique and the Stepped bevel, regardless of step count:
  - ShaperHeight.cs:615-619 `ExtrusionDerivative`, case Stepped (falls into the same `return 0f` as Flat and Linear).
  - ShaperHeight.cs:682-684 `BevelDerivative`, case Stepped: `default: return 0f`.
The height VALUE does change correctly with steps/bevelSteps — confirmed by direct reflection on the compiled ShaperHeightOp (n=4 vs n=32, bevelN unaffected) — and ShaperHeightCompiler.cs:138-161 samples the dial and clamps it correctly (StepCount/BevelStepCount, ShaperHeight.cs:314/317). But every tread is flat (E is piecewise-constant so its true derivative is 0 within a tread and undefined/infinite only at the zero-measure riser boundary), and nothing in the shading pipeline gives that riser a wall normal — unlike Rounded/Cove/Ogee bevel, whose derivatives correctly diverge to +Infinity at their edge case and are then normalized into a genuine steep-wall normal (ShaperHeight.cs:688-694 comment). So no matter how many steps are authored, every sample's shading normal is identical to Flat's, and the picture cannot move.

This is a genuine engine gap (no riser/wall-normal rendering exists for a stepped profile), not a lost clamp or an ignored branch — RULES.md #6 forbids building new rendering capability in this programme. A prior wave (T-0265, commit cfd161f0) already found the 0-pixel symptom and applied exactly the programme's own prescribed remedy: it absented both dials with InertVal + an explanatory tooltip (ShaperWindow.Sections.cs:1953-1959 Steps, :1976-1981 Bevel steps), correctly gated only by `noDepth` (not by technique/bevel choice, since the gap applies to every profile) and correctly excluded from the animated-dial exemption (DialAlwaysZero only fires on a Static dial, matching InertVal's own no-false-grey rule). Inert() (ShaperWindow.Sections.cs:190-196) genuinely disables the control (`SetEnabled(false)`) and sets the reason as its tooltip — confirmed by reading the implementation, this is not a cosmetic grey.

Re-measured on SAVED, reloaded documents (Rect and Star primitives, technique=Stepped, bevel=Stepped, depth=24, normalKind=Profile — the one configuration where Height CAN reach a pixel), at 3 frames each (0, mid, last): steps 4->32 and bevelSteps 3->16 both diff 0/9216 px on every frame on both shapes, while technique Stepped->Dome (a sanity control proving the height stage and Profile-normal path are genuinely live in this test setup) diffs 9163px (Rect) / 2753px (Star) every frame. Full probe: workspace/T-0278/t0278_saved_probe.cs and its output workspace/T-0278/measurements.txt.
