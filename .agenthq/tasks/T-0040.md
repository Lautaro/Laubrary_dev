### 2026-08-19T13:25:51Z — agent — in_progress -> done
Yes, this is a great idea and it already fits the plan — a paid 3D explosion pack can be captured and turned into pixel-art explosion animations, the same way our in-progress 'Bakery' tool already turns any lit 3D scene into pixel sprites. This task was a design question, so no code was changed; the answer below explains how it would work and what to expect quality-wise.
**Details:**
How these 3D VFX packs work: they are not a fixed video clip — they're a live 3D simulation (particles that spawn, move, fade and change color over a few seconds), built from adjustable settings like speed, size, color, and how long it lasts. That means yes, it is customizable — size, speed, colors, timing can all be tweaked before capturing it.

Could we turn it into pixel art? Yes. The plan is to reuse the same technique our unfinished 'Bakery' tool already proved works: point a camera at the 3D effect, play it, and photograph it frame by frame, then shrink and simplify those photos into a small pixel-art sprite sheet — exactly like a pixel-art game would show an explosion. This is a well-established technique other pixel-art games use.

Would it look good rasterized? Likely yes for the fire and glow parts (bright colors survive shrinking well), but the soft, wispy smoke edges will probably look muddy or noisy unless we add an extra 'simplify to clean pixel shapes' step when converting — that step doesn't exist yet and would need to be built.

Not yet verified: nobody has actually captured this or any other 3D Asset Store explosion pack and looked at the result — this is a design answer, not a demonstrated result. Also, the purchased 3D asset itself can never be bundled inside the shared Laubrary toolkit (licensing) — only the capturing tool can be shared; each project would need to own its own copy of the 3D asset pack to use with it.

How to use this (once built): buy/import the 3D pack into a project, point our capture tool at the explosion prefab instead of a static object, and it plays the explosion once while the camera records it into a pixel sprite sheet — the same output shape our other explosion tool already uses, so it could sit underneath our hand-made procedural explosion effects for extra detail.
**Technical details:**
Directly extends the existing (unported, prototype-stage) Bakery tool — see project memory `bakery-tool.md` and `pyre-tool.md`'s 2026-07-17 'OPEN — rethink shape-creation' note, which already floats exactly this: a baked-3D `Backdrop`/sprite-sequence `LayerShape` sitting as Pyre/PyrePlus's bottom layer, with Pyre's own modifiers (glow, crackle, outline, pixelation/dither post-passes) composited on top.

Key technical delta needed vs. today's Bakery: Bakery currently bakes a TURNTABLE (fixed camera, subject rotates over N frames) via `BakeryStage.unity` + `BakeryStageRenderer`. Capturing a particle-based explosion instead needs a TIME-PLAYBACK bake mode — fixed camera and fixed subject, `ParticleSystem.Simulate(t, true, false)` scrubbed across the pack's own play duration (or `Time.timeScale`-driven real playback captured frame-by-frame), not a rotation sweep. `BakerySpec` would need a `BakeMode {Turntable, Playback}` and a duration/frame-count field instead of (or alongside) `BakeryRotationMode`.

Asset pack itself (Hovl Studio 'Hovl Studio' 3D Fire and Explosions, Asset Store #176981): fetched the store page — description/technical-details sections are SPA-rendered and didn't come through in the static fetch, so this identification of the publisher/pack is from the page's visible metadata (title, publisher 'Hovl Studio', keywords: Explosion/Fire/particles/Shader/Realistic/smoke/detonation), not a read of the full feature list. Hovl Studio's VFX packs are consistently Shuriken `ParticleSystem`-based (not VFX Graph, not baked mocap) with flipbook-textured meshes/planes and additive/alpha shaders — fully exposed via the standard Particle System component (start speed/size/color-over-lifetime/emission), so customization (speed/size/color/duration) is available out of the box without touching any custom scripts, consistent with the answer given above.

Licensing constraint: per this project's own convention (Pyre/Launimator 'ships zero assets'), Laubrary cannot bundle or depend on a paid Asset Store pack — only the Playback-bake capability can be a shared tool feature; the 3D source content stays a per-project, user-owned import.

No code was written for this task — it's a research/design answer. If greenlit, the concrete next step is a `BakeMode.Playback` addition to Bakery's `BakerySpec`/`BakeryStageRenderer`, tested against any locally-available particle-based 3D VFX prefab (doesn't need to be this specific paid pack) before porting Bakery back into the canonical repo.

ROOT CAUSES (found by building the reference rig from the pack's own demo scene and diffing against it):
1. No colour grade. Vefects fire materials use emissive intensity 33-123 and the pack demo scene runs a Volume with Bloom (threshold 1, intensity 1, scatter 0.7) + ACES Tonemapping over an HDR camera. PreviewRenderUtility gets none of that, and a global Volume cannot be put in a preview scene without leaking into every other editor camera - so the grade is now an explicit blit chain (HDR ARGBHalf target + the new shader).
2. Tonemapper choice matters: the one-line Narkowicz ACES fit was tried first and is WRONG here - it tonemaps per channel, so a core measured at RGB (24.9, 14.4, 0.0) stays flat saturated yellow. Only the full ACEScg matrix fit desaturates highlights to white-hot.
3. Tint was assigned into every ParticleSystem main module startColor, replacing the pack authored random-between-two-colours gradients. Now a post-tonemap multiply on the finished image (pre-tonemap it is invisible on anything bright).
4. Cleared to PreviewRenderUtility default grey. Now black with alpha 0, which also lets it composite over the PyrePlus backdrop like every other shape.
5. Simulate was called on nested child systems as well as their parents; withChildren:true already covers them, so children were re-run from t=0 twice (hero prefabs have 5-11 systems). Top-most systems only now.
6. Framing: ParticleSystemRenderer.bounds is wildly oversized on these packs - use real GetParticles positions. And use a ~0.72 PERCENTILE of the spread, not the max, or the smoke column and stray sparks shrink the fire to a dot. Fit must satisfy both axes (the 40 deg FOV is vertical) or a narrow island crops the sides.
7. "Squashed into one line" = the pixel grid was forced SQUARE regardless of the island aspect, then drawn back with ScaleToFit. Long edge takes the requested size, short edge follows the island aspect.

PIXEL QUALITY: one bilinear Blit from 936x576 straight to a 48-cell grid reads only 2x2 of each ~19x19 cell, dropping every spark - now halves progressively. Drawn at a whole-number scale (fractional scale gave cells alternating 7/8 screen px). Optional Colours posterisation pass (playbackPixelLevels, 0 = off).

ROBUSTNESS (from a review pass): try/finally around BeginPreview/render/EndPreview - without it a throwing render leaves the camera targeted at our RT, the utility "begun" and the wrong RT active, after which the rest of the window silently stops rendering; Object.Instantiate instead of PrefabUtility.InstantiatePrefab, which was dropping the VFX into the user ACTIVE SCENE and dirtying it; _BloomTex unbound before its pooled RTs are released; pooled temporaries filterMode restored before release; missing shader cached instead of re-running Shader.Find every repaint. Reviewer findings deliberately NOT acted on: fitCentre.z is hard-zeroed (only matters for a world-space system drifting in +Z), and the shader has no #pragma target (editor-only).

TWO GOTCHAS WORTH KNOWING:
* PreviewRenderUtility with a custom HDR target: you MUST still wrap in BeginPreview/EndPreview (that binds the preview scene and enables the lights - rendering util.camera directly gives a completely black frame), and the substitute target MUST match BeginPreview own target size, not the requested point size. pixelsPerPoint is 2.25 here, so a 416x256 request allocates 936x576; a smaller substitute renders as a hard-edged clipped sub-rect. Also needs a 24-bit depth buffer or URP renders nothing.
* PrintWindow screenshots of an editor window are UNRELIABLE on this multi-monitor setup: content renders at 2.25x but GetWindowRect reports ~1.29x, so you get the top-left ~44% of the window and everything else reads as black/off-centre. This masqueraded as a "preview draws off to the right" bug for several rounds. Use a full-screen CopyFromScreen capture instead.
