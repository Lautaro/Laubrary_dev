## Description

Investigate a fake illumination effect for 2D sprites: using edge detection, a
silhouette/luminosity-derived fake normal, and similar tricks to figure out where and how
much brightness/color to apply to a flat sprite, so it reads as being lit by a nearby light
source without any real lighting/normal-map data authored for it.

Confirmed SpriteFx does NOT already have this — its existing "rim" modifiers (e.g. the
rim-bump/jaggedness shape warp) distort the silhouette's EDGE geometry, they don't do
anything with light/luminosity. This would be new.

Concrete motivating example: a fake point-light placed at a gun's muzzle that illuminates the
gun (and the arm holding it) when a shot fires — a flash of directional brightness/color that
reads as reflecting off the nearby geometry, without any real per-sprite lighting setup.

There's a direct technical precedent worth starting from: the `bevelglow` Kiln agent (Pyre
Edge project, generation 0, `D:\CODEZ\Kiln\projects\Pyre Edge\agents\bevelglow\gen.py`)
already implements exactly the core trick this would need — a fake surface normal derived
from a height field's own local-unit gradient (there: `-sdf` as the height field; here: the
sprite's own alpha/silhouette, or an edge-distance field built from it), shaded against a
light direction/elevation. Worth reading that generator before starting fresh.

Good catch - it is a real defect, not a misunderstanding, and it was in SpriteFx's preview rather than in the Fake light effect.

"Restart after" was labelled like a wait but did not actually wait with the effect OFF. It held the fully-filtered LAST frame of the effect for that whole second. So Duration 0.33 + Restart after 1.00 gave you: ramp up for a third of a second, then sit at full blast for a second, then jump back to the start - which is exactly the "constantly on" you saw. Your expectation was the right one, and it is what the effect does in an actual game: when a pass finishes at runtime the original, unfiltered sprite is put back.

Fixed by splitting that one dial into two, both preview-only and still never saved into the stack asset:

- "Hold end (s)" - the old dial under an honest name. Rests on the filtered last frame so you can see where the effect ended. Same default, and it kept the same saved setting, so your 1.00 is sitting on THIS one right now.
- "Idle gap (s)" - new, defaults to 0. Shows the plain sprite with the effect switched off before looping, matching what ships.

So to get the loop you described: drag your 1.00 off "Hold end" and onto "Idle gap" (leave Hold end at 0, or a small value if you also want a beat on the final frame). Verified in the editor at Duration 0.33 / Hold end 0 / Idle gap 1.0: it runs ~0.33 s, then shows the untouched sprite for exactly 1.00 s, then runs again - and the idle frames are pixel-for-pixel the raw sprite.

Sprites can now be lit by a fake light without anyone drawing or setting up any lighting for them. A new `Fake light` effect works out what shape a sprite is pretending to be from its own pixels, then brightens and darkens it as though a light were nearby — and the case this was asked for works: firing a shot flashes warm light off the gun, the hands and the face, then fades.
**Details:**
How to use this
Open the SpriteFx Stacks tool, add the `Fake light` effect to a stack, and choose where the light comes from: either one fixed direction for the whole picture, or a light you place at a spot near the sprite by dragging a point on a small grid (it also takes typed X/Y numbers). Three options decide what shape the sprite is pretended to have — the default puffs the whole outline into a rounded form, one treats it as a flat card so only the rim catches light, and one uses the brightness already painted into the art. Every dial can be animated across the life of the effect; the muzzle flash is made by animating the `Add` dial up and back down.

Not verified: how it behaves during actual gameplay. It has only been run and looked at inside the editor, on one character sprite.

Not verified: games built for other hardware, such as phones or consoles.

Performance: it does real work every frame. That cost was cut by about a third, but it is still meaningful on large images. Comfortable for character-sized art; worth watching if it is used on very big sprites or on many objects at once.

Pre-existing rough edge, not caused by this: in a narrow window the last dial or two on the effect's row runs past the right edge and gets cut off. The same thing happens to the long-standing Outline effect, so it is a general quirk of how these panels lay out rather than anything new here.

Algorithm: `SpriteFxAuxMap.BuildMap` supplies the height field (EdgeDistanceIn / Alpha / Luma), blurred before differentiation; a clamp-to-edge central difference gives the normal (implicit Z=1, scaled by `relief`); Lambert + Blinn specular with the viewer at (0,0,1). Mirrors `PyreField.ReliefLight` deliberately, including the consumer's `0.35 + light * 1.15` brightness spread — re-implemented rather than referenced because SpriteFx must not depend on Pyre. Direct port of the `bevelglow` Kiln generator's core trick, honouring its two documented gotchas (blur-before-differentiate, clamp-to-edge borders).

FRAMEWORK CHANGE worth knowing: `PostModifier` gained `pictureW/pictureH/padX/padY` + `internal SetPicture(...)`, threaded from both `RunStack` overloads. `PostModifier.Apply` previously received only the PADDED buffer dims, which is fine for every existing PostModifier (all translation-invariant) but wrong for the first one with a canvas-normalised position: an authored light drifted and grew whenever an unrelated outward-reaching effect joined the stack, because `OutwardReach` is summed. `pictureW == 0` means unset and falls back to the handed `W,H`, so Pyre's `PyreRenderer.SetPostContext` reflection path is bit-for-bit unchanged.

Deliberate deviations, with reasons:
- `heightSource` is a purpose-built 3-value `SfxReliefSource` (Silhouette/Slab/Brightness), not the raw 10-value `AuxMapGenerator`. That enum is documented APPEND-ONLY and serialized on every authored `SpriteFxAuxMapGate`, so exposing it here would couple them; `Dark` and `HueProximity` were also actively broken as height fields (with `respectAlpha:false` the transparent surround evaluates to 1.0, making empty space the HIGHEST part of the surface and inverting rim shading); and the 10-wide radio row pushed the default option off-screen at a realistic window width.
- Alpha bleed on the Brightness source is handled by zeroing RGB behind `a == 0` in a copy before BuildMap, NOT by `respectAlpha: true` — that flag is applied after the blur, by which point hidden RGB has already smeared into visible pixels.
- The reflected enum control was left as MiniRadio rather than switched to Segmented: that control is shared by every reflected enum in the package, so changing it is a package-wide UI decision, not a T-0069 fix. The 3-option row was measured to fit.

Measured: allocation 41.7 -> 29.5 bytes/pixel/frame and 10 -> 7 Large Object Heap allocations at 256x256 (dropped the intermediate light buffer; made BuildMap's `sat`/`hue` arrays and per-pixel `RgbToHsv` lazy — verified byte-identical output across all 10 generators). Structurally this effect wants a source-keyed height-field cache, which is the real remaining win; it was deliberately NOT added because `PostModifier.Clone()` relies reflectively on the type holding no shared arrays.

Known-open, all pre-existing and out of scope: `ZuiReflect`'s flow rows clip at the right edge on narrow windows (reproduced on `OutlineModifier`, so not introduced here); `ZuiAudit` could not be made authoritative on this window (`ExpandAll` returned 0 with `foldedSkipped=33`), so UI verification is by screenshot and by measured `VisualElement` bounds instead.

Also still true: `SpriteFxAuxMapGate` remains unconsumed project-wide, and `SimulationModifier` has no case in `RunStack`'s dispatch switch, so `PixelFluidModifier` appears in the Add menu and silently does nothing.

The preview in the SpriteFx Stacks tool was making every looping effect look like it never switched off, and that is fixed. **Details:**
How to use this
In the SpriteFx Stacks tool, beside the preview picture, there are now two pause dials instead of one. Hold end rests on the effect's final frame, still fully applied, so you can see where it finished. **Technical details:**
Files changed by THIS pass: Assets/Packages/Laubrary/Editor/SpriteFx/SpriteFxStackWindow.cs (+63/-22) and Assets/Packages/Laubrary/CHANGELOG.md (+3). Nothing committed, no scene saved, no menu item / window / asset added.

ROOT CAUSE. OnPlayTick treated end-of-pass as a HOLD: on _playProgress >= 1f it pinned progress to exactly 1f, set _previewHeld, and deliberately fell through to RenderPreviewAt(1f, frame) every tick, repainting the fully-filtered life-1 frame for the whole pause. The dial driving it was labelled "Restart after", which reads as a restart delay. Meanwhile the shipped runtime does the opposite: SpriteFxFilter.Update calls Restore() at the end of a pass, which puts the original unfiltered sprite back on the renderer. So preview and runtime disagreed about what "the effect is over" looks like, and the preview was the one lying. Not a maths bug in RelightModifier - the Fake light effect itself was correct.

CHANGE. RestartPause -> HoldEnd, EditorPrefs key deliberately UNCHANGED (Laubrary.SpriteFx.Preview.RestartPause) so an already-tuned value carries over; default 0.35, range 0..2. New IdleGap on key Laubrary.SpriteFx.Preview.IdleGap, default 0f, range 0..2. New fields _previewIdle / _previewIdleLeft, reset in StartPlay. RenderPreviewAt gained ool bypassStack = false, which forces pad = 0 (unpadded path) and skips SpriteFxStack.RunStack / SpriteFxFilter.Apply. Tick is now three-phase: running -> held (filtered, existing repaint-every-tick rationale preserved) -> idle (unfiltered, same repaint rationale) -> running. The old RestartPause == 0 fast path now also routes into idle when IdleGap > 0. Life slider reads 0 during idle.

WHY TWO DIALS RATHER THAN CHANGING THE ONE. The hold behaviour was deliberate and documented in-code (a panel rebuild mid-hold would otherwise repaint at the scrub position, i.e. life 0, and read as the effect switching itself off early). Repurposing the single dial would have silently removed a wanted feature; splitting is strictly additive and IdleGap default 0 makes it a no-op for anyone who does not touch it.

DELIBERATELY NOT DONE: no one-time EditorPrefs migration moving the stored value from HoldEnd to IdleGap. It would have been right for this user and wrong for anyone who genuinely wanted the hold, and encoding one user's intent in a migration is not defensible. The user's 1.01198 is left on HoldEnd and the handover says so explicitly.
