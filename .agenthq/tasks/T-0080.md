## Description

Every Chunks burst today is one-shot: fire once, everything happens at that instant (confirmed in ChunkEmitter.Burst()/SpawnBurst() -- no per-frame follow, no repeat-on-timer anywhere in the class). Needed for the user's use case 3: a Chunk attached to a moving Transform (e.g. a Zoe) that follows it every frame, throws particles backward (opposite to its current travel direction), and spawns a pyre every X seconds, for as long as it's active.

Two existing pieces were checked and confirmed NOT to already cover this: Zoetrope/FxFollowTarget.cs re-tracks one already-spawned effect's position every frame but never spawns anything new on its own; a Chunk Spec's own "Trail" field spawns a puff on a timer but only from an already-flying debris piece (not from an external followed transform), and has no reverse-direction-relative-to-travel option.

New standalone module: a component (sibling to ChunkEmitter, e.g. ChunkFollowEmitter) that takes a Transform to track, repositions its emission point to that transform every frame, computes the transform's current travel direction (frame-to-frame position delta) to spray Particle Splash (T-0033) particles in the reverse of that direction, and fires a Pyre Spawner (T-0034) burst on a repeating interval at the tracked position. Needs the "reversed-relative-motion" primitive the design doc already flags as needed elsewhere (see "New shared primitives" -- originally scoped to a pyre/trail spawn relative to its parent FRAGMENT) generalized so it also works relative to an externally followed transform's velocity, not only a fragment's.

**Depends on T-0033 (Particle Splash) and T-0034 (Pyre Spawner)** for what it repeatedly fires -- must work standalone otherwise (no layering/timeline/Fragment Slicer required). See CHUNKS_OVERHAUL_DESIGN.md (updated with this module as "Standalone modules" #9).

You can now attach a debris source to something that moves -- a character, a missile -- and it will chase it, throw particles out behind it in the direction it came from, and set off an explosion every few seconds while it is active. Everything Chunks did before happened once, at one instant; this one keeps going.
**Details:**
How to use this: drop a Chunk Follow Emitter component on a GameObject, give it a Chunk Spec, and point it at the thing to follow (leave it empty and it follows itself). Its inspector tells you plainly when it will do nothing -- no recipe assigned, or a recipe with neither the splash nor the spawn switched on. One thing to know: for the spray to actually point backwards, the recipe's Particle Splash needs its "Follow Burst Direction" switch on; the inspector says so rather than silently changing your other settings for you. Not yet verified: no human has watched it trail behind a moving character.
**Technical details:**
D:\UNITY\Laubrary Dev\Assets\Packages\Laubrary\Runtime\Chunks\Follow\ChunkFollowEmitter.cs, \Follow\ChunkTravelDirection.cs (new shared primitive), D:\UNITY\Laubrary Dev\Assets\Packages\Laubrary\Editor\Chunks\ChunkFollowEmitterEditor.cs. ChunkTravelDirection API: fields smoothingSeconds/minSpeed; Velocity, Speed, HasDirection, IsMoving, DirectionDeg, ReverseDirectionDeg; Reset(Vector3), Sample(Vector3, float dt); statics ToDegrees/Reverse/Normalize. It is a class not a static function set because the primitive is inherently stateful (last position + EMA + last-good direction); the pure maths half is static. SMOOTHING: exponential moving average with a frame-rate-independent blend factor 1 - Exp(-dt/smoothingSeconds) -- a literal Lerp constant would make aim depend on frame rate -- plus a minSpeed gate below which the last good direction is HELD. That kills two failure modes: angle jitter from meaningless sub-threshold deltas, and Atan2(0,0)==0 snapping a stopped character's aim to due east. LIFETIME: one root container with one ChunkModuleRunner built once in Play(), never per tick, and deliberately a ROOT object that does not move -- parenting it to the target would drag already-spawned debris along and the trail would never fall behind. Stop() tears it down; StopEmitting() lets the tail finish using ChunkEmitter.ContainerLifetime so the number cannot drift. Pooled blasts are correctly NOT parented under it. Per-spawn orderOffset cycles mod 8 so a continuous emitter does not walk sorting order into the thousands. ResetRandom() once in Play(); spawns go through SpawnOne, not Fire, which would reset randomness every tick. PM INTEGRATION: ParticleSplashModule gained an inheritBurstDirection field (plus its UI toggle) so the emitter can aim the spray by putting the reversed travel direction into ChunkModuleContext.DirectionDeg -- without it the splash always used its own fixed angle and "spray backwards" was unreachable. WHY FxFollowTarget does not cover this: it re-positions ONE already-spawned effect so it rides along with a moving source; it never spawns, has no timer, and has no notion of travel direction -- and it is the opposite parenting decision.
