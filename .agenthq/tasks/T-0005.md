## Description

Depends on T-0004 (the runtime read API). This is where the vector MetaLayer actually starts DOING something for real gameplay: supplying projectile spawn position AND direction, not just position.

**⚠️ Architectural correction from the user, 2026-08-16 — read before writing any code:** the Vector MetaLayer is **generic metadata**, not a "projectile direction layer." `MetaLayerMode.Vector` and `TryGetMetaVector`/`TryGetMetaVectorNearest` (T-0003/T-0004) must have ZERO knowledge of weapons, muzzles, or projectiles — they just expose "the vector authored on layer X at the current frame," the same domain-agnostic way `TryGetMetaPoint` already does for points. **The weapon/muzzle system is the CONSUMER that assigns meaning**: it's configured (a field on the weapon def, or similar) with the NAME of a vector layer to look up, calls the generic `TryGetMetaVector(layerName, ...)` API itself, and decides for itself that "origin = spawn position, direction = fire direction, length = ignored." Do NOT build any special-cased "if this layer is a Vector layer, treat it as muzzle direction" branching inside `MuzzleTracker`/`ZonedAnimationPlayer`/anywhere in Launimator — that logic belongs entirely on the weapon-code side (`MuzzleTracker`/`WeaponMuzzleCue`/`ProjectileWeapon`, i.e. Combat2D/Zoetrope), which already knows it's dealing with a weapon; Launimator itself should stay exactly as domain-agnostic about "vector" as it already is about "point." If you already started this task before reading this note, double-check nothing leaked Vector-layer-specific logic into the Launimator side.

**Current architecture (confirmed by reading `MuzzleTracker.cs` and `ProjectileWeapon.cs` this session — this is a real, deliberate design decision, not an oversight, so read the existing doc comments before changing anything):**
- `MuzzleTracker` resolves POSITION only, every `LateUpdate`, via `IAnimatedView.TryGetMetaPointNearest(layerId, ...)`, and moves a Transform. No direction involved today.
- `ProjectileWeapon.TryFireFrom(Vector3 originOverride)` has an explicit doc comment: *"Direction still resolves the normal way (ResolvedAimDirection) — this overrides WHERE the shot originates, not WHICH WAY it goes; aim is a Combatant-level concept independent of wherever the animation draws the muzzle."*
- `ResolvedAimDirection()` reads `Combatant.aimDirection` (or a documented fallback) — never anything animation-authored, today.

**Per the user's own spec, this task changes that FOR THE VECTOR CASE SPECIFICALLY**: "to help with this is like to have... its presented as an arrow... thats how I want to configure metadata for how to handle projectile spawning and trajectory. the vector length would be ignored in this case." So: origin = spawn position, direction = fire direction, length = ignored for this use.

**What to build:**
- A muzzle-direction resolution path parallel to `MuzzleTracker`'s existing position-only one — either extend `MuzzleTracker` itself to also read+apply direction when its target layer is a Vector layer (falling back to today's position-only behavior for Point layers, unchanged), or add a small sibling component — your call, but don't break the existing Point-layer muzzle path, which real assets already depend on.
- A new fire method on `ProjectileWeapon`, e.g. `TryFireFromVector(Vector3 origin, Vector2 direction)` — analogous to the existing `TryFireFrom(Vector3 originOverride)` but ALSO overriding direction, explicitly bypassing `ResolvedAimDirection()` for this call only (existing callers of `TryFireFrom`/plain `Fire` must be completely unaffected — this is a new, additive entry point).
- Wire `WeaponMuzzleCue` (check whether it needs changes to route through the new path when its weapon def is configured to use a vector layer — read the existing file first to see exactly where that decision needs to plug in).

Keep the existing `Combatant.aimDirection`-driven path exactly as-is for every weapon that doesn't opt into a vector muzzle layer — this is purely additive, matching the project's standing convention.
