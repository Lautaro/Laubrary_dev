## Description

Working with backsplash in different editors (mainly PyrePlus) i get the feeling that settings for backsplash assets very often do not stick. I configure a backsplash for a certain pyre asset but next time i open it the backsplash is empty.  Open a new image into backsplash should always have default zoom 1. Check if you can find something that causes it. I want as much of these things as possible to be handled by backsplash and not the consuming editor. That way we can solve these kind of things only once. How many tools uses backsplash?

### 2026-08-16T16:34:12Z — agent — in_progress -> done
Found and fixed the actual gap: Pyre and PyrePlus's backdrop panel never called Undo.RecordObject, unlike every other dial in those windows (Mirage already did). Any later Ctrl+Z elsewhere in the same session could snap the whole spec back past an un-recorded backdrop edit and silently wipe it — that's the "very often doesn't stick" feeling. Also fixed the literal ask: picking a new backdrop image now always resets zoom to 1 (and position to centre) instead of keeping whatever zoom/offset was tuned for the previous image.

Both fixes are centralized in BackSplashZui.Build itself (a new optional `owner` object param) rather than duplicated per editor, per your request — Pyre, PyrePlus and Mirage now all pass their owning asset and get correct Undo+dirty handling for free; a future consumer can't reintroduce the gap by forgetting the boilerplate. 4 tools use BackSplash: Pyre, PyrePlus, Mirage, TextSplash (TextSplash's is a preview-only, non-persisted copy, so it wasn't affected).

Not yet verified: I could not do a full interactive Handover Walk (open the window, click through Recall/Save/undo by hand) — verified via compile-clean + a scripted Undo-semantics probe in the Unity editor instead. Recommend a quick manual pass next time PyrePlus is open: set a backdrop image, tweak a dial, Ctrl+Z once, confirm the backdrop survives.
**Proof of done:**
- [x] Root cause: PyreWindow.Preview.cs / PyrePlusWindow.cs called EditorUtility.SetDirty(spec) for backdrop edits but never Undo.RecordObject(spec, ...) — confirmed via grep (0 Undo.RecordObject calls in the PyrePlus/Pyre backdrop-building code, vs 11/9 elsewhere in those same files, and vs Mirage's BuildBackSplashSection which already had it).
- [x] Fix: BackSplashZui.Build gained an optional `owner` UnityEngine.Object param; its internal Edit() now does Undo.RecordObject(owner) before mutating + EditorUtility.SetDirty(owner) after, for every field (colour/image/position/zoom/tint) and for Recall (BackSplashGUI.ShowRecall also gained an owner param for the same reason).
- [x] PyreWindow.Preview.cs, PyrePlusWindow.cs and MirageWindow.cs updated to pass owner: spec / owner: view, and dropped their own now-redundant Undo/SetDirty boilerplate.
- [x] Zoom-reset fix: BackSplashZui.Build's image-picker callback now sets imageZoom = 1 and imagePos = Vector2.zero whenever a non-null sprite is assigned.
- [x] Verified: check_compile_errors + recompile_status both clean after the change (Unity editor open on this project via Coplay).
- [x] Verified via a throwaway scripted Undo probe run in the live Unity editor (created and deleted, not committed) that an un-recorded field on a ScriptableObject can be swallowed by an unrelated Undo group — confirms the mechanism, though I did not do a full manual click-through of the real window.
