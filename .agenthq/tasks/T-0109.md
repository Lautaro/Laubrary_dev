## Description

Extrusion and bevel are the genuinely new construction in this design - there is exactly one worked instance in Pyre today, welded into the Text generator as eight slabs, plus two unrelated height mechanisms sharing no concept. Also add a real Z offset per layer: the control currently labelled depth is extrusion THICKNESS, and actual Z position is derived from layer order alone. A real Z offset added to the ordering base is a handful of lines and needs no new buffer, since the height field already is the depth buffer (design B7).

State the layer's solid explicitly while defining these, because it costs nothing here and cannot be recovered cheaply later: the extrusion and bevel stages together publish a height as a closed-form function of the shape's own published inside-distance (plus, for the linear technique only, the normalised local coordinates), so the layer is exactly the implicit solid "inside the 2D silhouette, and below that height". Every one of the seven profiles and five bevels is a function of that one number, which is why the whole authoring model survives into a 3D field unchanged and why no primitive has to be re-expressed.

This task carries the other half of T-0105's Lipschitz-bound requirement, and measurement says it is the LARGER half. T-0105 makes every primitive declare a bound on how far it may claim its edge is, and every transform and combine node compose those bounds - but a height profile is not a primitive, not a transform and not a combine node, so it falls through all three, and the profiles over-report far more badly than any primitive does. Measured as the maximum rate of change of height against inside-distance, straight from the reference app's profile code: pyramid 1.00, taper 1.67 at taper 1 but 16.7 at taper 0.1, round 16.4 (the common case), dome 23.1 - against a worst primitive of about 3.1. Round and dome are formally unbounded as inside-distance approaches zero. So the requirement here is: each extrusion profile and each bevel declares how steeply it can change, and that declaration COMPOSES with the shape's own bound - the extruded solid's bound is the composition, not the primitive's, and anything that steps along a ray must use the composed figure. One exception has to be decided rather than numbered: the STEPPED profile (in the extrusion set and in the bevel set alike) is a floor function, so it is a genuine step discontinuity and NO finite bound exists for it at all. It needs either a different treatment - a slope-clamped variant of the profile, or marching a tilted view slab by slab between the steps instead of by distance - or an accepted, explicitly written-down exclusion of stepped from the general path. Do not leave a build agent hunting for a constant that does not exist.

This task also owns the DOING of the tilted conformance frame that T-0102 states on paper. T-0102 requires that "before Wave 2 closes, one deliberately tilted frame is rendered through the general path and kept as a conformance artefact", but T-0102 is a Wave-1 paper task that closes before a line of Wave-2 code is written, so the single mechanism proving the 3D-rotation door stayed open had no owner in the wave that can actually satisfy it. It lands here rather than on T-0105 (the generator task) for a substantive reason: the frame is proof that an EXTRUDED SOLID can be turned, and until extrusion exists there is nothing to tilt but a zero-thickness sheet - T-0105 can render a silhouette, but only this task can render the thing the proof is about. This is also the last spine task before the fills are built on top, which matches "before Wave 2 closes". Concretely: render one deliberately tilted frame of an extruded, bevelled shape through the general resolve, keep it as a committed artefact, and re-render it whenever the resolve changes. It is not a feature and is exposed nowhere in the UI; it is the only evidence that the door is still open, and design B7 openly concedes that a test nobody runs is a weaker guarantee than a path that executes every frame - which is exactly why it needs a home in a task that renders something. Treat T-0102's statement and this paragraph as one requirement in two halves: the paper side there, the doing side here.

Answer one authoring question here even though nothing in v1 renders it: an extruded solid has side walls, and a wall has no "how far in from the outline" value, yet inside-distance is what the bevel band, the border region and the indexed-strip fill are all defined against. Pick one rule now - the wall inherits the rim value it descends from, or the wall carries its own vertical parameterisation, or the wall is a separately paintable surface - and record it. This is the only part of 3D rotation that is a design decision rather than an implementation, so it is the only part that genuinely has to be settled before the fills and borders are built on top of it.
