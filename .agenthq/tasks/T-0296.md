## Description

**Found by T-0293 (A22 fifth pass), measured live.**

`Z.Split(stateKey, initialLeftWidth, left, right)` (`Zui/Toolkit/Zui.cs:77-97`) restores the fixed pane's width from `EditorPrefs["ZUI.Split." + stateKey]` and hands it straight to `TwoPaneSplitView`. Nothing clamps that width to the container, at restore or on resize, so a divider the user legitimately dragged at a wide window survives verbatim into a narrow one.

**Measured, window `minSize` = (820, 520):**
| step | window | left pane | right pane x | Play button inside the window |
|---|---|---|---|---|
| splitter dragged to 1520 | 2100x1150 | 1520.0 | 1524.9 | yes |
| window shrunk to the minimum | **820x520** | **1520.0** | **1524.9** | **NO** |
| window widened again | 2100x1150 | 1520.0 | 1524.9 | yes |

At the minimum the right pane starts 704.9 px outside an 820-px window. The preview stage, the whole transport (Play, Rate, Loop gap, Frame scrub, Strip, Tile size), the filmstrip, Preview backdrop, Cherry Framing and Bake are all off-screen; the outer container has no horizontal scroller (measured `hScrollerVisible=False` on it), and the drag anchor is off-screen too, so there is no way to drag the divider back. The only recovery is to make the window wider again, which a user has no reason to connect to the divider.

With the divider at a normal 360 the same minimum size is clean: left 360.0, right pane at x=364.9 width 451.1, Play inside, and a full-tree overflow scan with EVERY section and box open returns **X overflow 0** and only three `unity-slider__input` +20 px hits, which are UITK scrollbar-thumb internals (`ScrollerSlider`), not Shaper layout.

**Suggested fix:** clamp in `Z.Split` — restore `min(stored, container - minRightPane)` and re-clamp on the container's `GeometryChangedEvent`, so the divider can never park the second pane outside the window. Shared ZUI, so it needs a cross-host pass (Pyre uses its own splitter, `PyreWindow.BuildVerticalSplitter`, and should be checked for the same).

Note for whoever picks this up: T-0293 changed this pref while measuring and set it back to **360**; the exact value it held before that task is not recorded (it measured ~360 by geometry).

CHANGELOG: Zui.cs Z.Split now clamps the fixed pane to the container on restore and on every resize (min left 360px, min right 320px), and re-grows toward the user's real intent when space comes back, instead of parking the right pane off-screen forever.

Bucket 1 - what changed and why: Z.Split (Zui/Toolkit/Zui.cs) restored/dragged the divider with no awareness of the container's own width. Root-caused live: TwoPaneSplitView keeps the fixed pane's width entirely in private internal fields -- it never touches the pane's public inline style.width (confirmed: left.style.width.keyword stayed Undefined throughout while resolvedStyle.width visibly changed) -- so the only way to read or correct it from outside is resolvedStyle, and only after layout has actually settled (a resize can take more than one internal layout pass; reading resolvedStyle synchronously inside the very event that changed it measures a transient size the window is only passing through). Fix: a desiredWidth field (the persisted/dragged intent) is clamped against Max(360, containerWidth-320) on a SCHEDULED recheck (one editor tick later, collapsing repeat GeometryChangedEvents from split/left/right into a single recheck so it converges instead of needing a fixed pass count) and applied via left.style.width. A separate listener adopts a REAL user drag as the new desiredWidth and persists it, using an ABSOLUTE (not Mathf.Approximately) tolerance so it can tell a clamp-forced change from a genuine one despite device-pixel snapping.
