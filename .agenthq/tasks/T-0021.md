## Description

**User request** (paraphrased from conversation): composite Zoe body parts (e.g. ProtoGuy's Legs+Upper) don't
always line up cleanly with a single fixed offset, because each part's sprite sheet was authored/auto-trimmed
independently and doesn't necessarily share a registration point. Proposed fix: paint a "belly button"-style
Point MetaLayer on BOTH the parent part (e.g. Legs, one point per frame across all its clips) and the child
part (e.g. Upper, one point per direction) using the SAME layer name, so the child part is positioned by
lining its own point up with the parent's point — not by moving the child's raw transform origin to the
parent's point (which silently assumes the origin IS the attach point, and breaks the moment either sheet's
trim/recenter differs).

## What was built (implementation done tonight)

`Assets/Packages/Laubrary/Runtime/ZoetropeLaunimator/CompositeZonedPlayer.cs` — the existing per-frame
attach-follow handler (`ZonedAnimationPlayer.OnMetaLayerReached` → move the child part to the parent's named
MetaLayer point) now ALSO checks whether the CHILD part has its own point painted under the same layer name.
If it does, the child is positioned so THAT point lands exactly on the parent's point (two-point stitching);
if it doesn't, behavior is unchanged from before (child's raw origin pins to the parent's point). Purely
additive — no existing composite Zoe's behavior changes unless its child part actually paints a matching
point.

`Assets/Packages/Laubrary/Runtime/ZoetropeLaunimator/CompositeLauminaryView.cs` — `ZoeBodyPart.attachMetaLayerId`'s
tooltip updated to document the two-point behavior.

**Verified**: compiles clean; live regression check in Play mode confirmed ProtoGuy (which currently uses the
plain static-parent attach, `attachMetaLayerId` empty) still renders correctly — the new code path is inert
until a composite Zoe actually opts into it. The two-point math itself was NOT separately unit-tested with a
synthetic asset (would need scripted MetaLayer authoring to set up) — confidence is from code review + the
regression check, not a live proof of the stitching math on real painted data.

## What's NOT done — this is the "you use it" part

1. **Author the actual points**: on `ProtoGuyLegs.asset`, paint a Point MetaLayer (suggested name: "Waist") on
   every frame across `LegsIdle16` (16 frames) and `LegsWalk3` (3 clips × 8 frames = 24 frames) — ~40
   placements total, since the legs' anchor point genuinely shifts through the walk cycle. On
   `ProtoGuyUpper.asset`, paint the same-named point on each of its 16 direction frames (Upper is a single
   static pose per direction, so one placement per frame, no walk-cycle shift).
2. **Wire ProtoGuy's Upper part** to use it: set `ZoeBodyPart.attachMetaLayerId = "Waist"` on ProtoGuy's Upper
   entry (currently empty — static parent-transform attach).
3. **Remove the now-redundant manual offset**: `ProtoGuySpawner.cs`'s `upperYOffset` field/logic (currently a
   single hand-measured constant, 1.4375 units) becomes dead code once the composite view itself positions
   Upper via the meta-layer follow — should be deleted, not left as an inert leftover, once step 2 is
   confirmed working.
4. Human eyeball check that alignment actually holds correctly across all 16 directions AND through the full
   walk cycle (the whole point of doing this per-frame instead of one fixed number) — not yet done, no points
   are painted yet.
