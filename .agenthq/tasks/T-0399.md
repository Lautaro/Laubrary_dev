WHY THOSE NUMBERS: at the project's live PPU of 16 they are exactly 1/16 and 6/16. FitSampleRange cuts at floor(worldSize*ppu) texels and ChunkRng.Range is half-open, so a uniform roll over [1/16, 6/16) lands in the five bands [k/16,(k+1)/16), k=1..5, with exactly equal width. Below 5 texels the authored samplePx 5/20 never binds -- FitSampleRange collapses both ends onto fit, so the texel count is fully determined by the size roll.

MEASURED DISTRIBUTION (the whole risk in this task), 200,000 draws through the real shipped FitSampleRange against the live in-editor asset: S=1 20.04%, S=2 19.90%, S=3 19.98%, S=4 20.02%, S=5 20.07%. Exactly uniform. Twelve simulated bursts at the recipe's own count 15..31 gave 0-7 single-pixel specks and 13-26 multi-pixel blobs each -- a real mix in every burst, not a range that collapses to one end. The fallback (rolling an integer texel target in code) was NOT needed.

T-0397 STILL HOLDS, same 200,000 draws: below-native count 0, texel scale min 1.0000 max 2.0000. The 2.0 upper bound is the honest cost of a continuous size roll against a discrete texel count: S texels can be asked for up to (S+1)/16 world, so texels render at up to (S+1)/S game pixels -- worst at S=1 (a single texel drawn as a 1-2 px square, which has no internal grid to misalign) and tightest at S=5 (1.00-1.20x). All whole-pixel-or-larger, which is what T-0397 actually states. Exact 1:1 for every chunk would need an integer texel target rolled directly: a code change, deliberately not made.
