## Description

**This is the owner's sole active priority as of 2026-09-26.** All other HH2Lab audio work was wound down the same day in favour of this. Branch: `x/zounds-sap` in this project.

### The problem, in plain terms

Unity's ordinary way of letting you generate audio in C# is a callback the audio mixer thread calls to fill each buffer. The moment any code in the project uses that callback, the mixer thread becomes attached to the scripting runtime — and from then on, **any** garbage collection anywhere in the game freezes that thread along with everything else. The audio hardware has a hard deadline for each buffer, so a freeze produces an audible click or dropout. The attachment is permanent once it happens.

Two consequences that shape everything here:
- Removing allocations from the audio path reduces how often this happens but **provably cannot eliminate it**, because the freeze is caused by collections happening anywhere, not by audio allocating.
- **A single leftover use of that callback anywhere in the project re-attaches the thread and silently destroys the benefit for the whole application.** Removing the last use matters as much as adding the replacement.

### The chosen solution

Unity's **Scriptable Audio Pipeline**, shipped in Unity 6.3 (this project is on 6.3, LTS-supported to December 2027). It lets audio processing be written in a restricted subset of C# that the Burst compiler turns into native machine code during the normal build. The mixer thread then calls native code through a plain function pointer, never touching the managed runtime — structurally the same escape a hand-written C++ plugin achieves, but without hand-maintained per-platform binaries. Unity's audio team describes it explicitly as a replacement for that callback "without the hiccups resulting from garbage collection spikes".

Known limits, accepted: no Web platform support; there is not yet a dedicated "effect" extension point, so an effect chain is expressed as a tree of generators where a parent filters its child's output; and if Burst compilation is off (which is normal while debugging in the editor) the code runs as ordinary managed C# and the immunity disappears — **so this can only be proven in a real player build, never in the editor.**

Do **not** adopt DSPGraph — a Unity engineer confirmed it is preview-only, unsupported and permanently unmaintained. SAP is its successor.

### The actual mission

**Rebuild the effect-chain engine that was previously built for the game project — the one that ended up as a C++ plugin — as Burst-compiled generators here, so the capability survives without depending on a hand-written native plugin.**

What "the goodies" means concretely, and what the current stripped-down branch has **lost** and must regain:
- All 16 effects, as a per-voice chain.
- Effects that react while a sound is already playing (a parameter changed live, a modulator moving).
- Retriggering / repeat trains.
- Real-time time-stretch.

What is **not** in scope: the ordinary-C# offline renderer that produces previews and rendered-to-file output stays exactly as it is. This is only about the real-time path.

Reference material: the prior work reached all 16 effects verified, with 58 harness checks and 33 equivalence cases passing bit-exactly against the original managed engine to float-rounding precision. That equivalence suite is the model for how this port should be checked — the new path should be provable against the existing managed engine the same way.

**A specific trap carried forward, and it applies again here.** Chained float arithmetic does not evaluate identically between strictly per-step float rounding and C#'s wider intermediate evaluation. Last time this produced several real bugs: a wrong delay tap position, a buffer length off by one in a reverb stage, and it exposed a genuine pre-existing wraparound bug in a stereo ring buffer. Moving the real-time render from native C++ into Burst-compiled C# is the same category of change, so the same class of mismatch can resurface. Test for it deliberately rather than hoping.

### What "finished" has to mean

From the research report (see Handover Log for the path), in order — **with step 2's premise now already settled, so it is verification of this port rather than a go/no-go gate**:

**Already settled, not to be redone:** that a Burst-compiled generator survives a forced collection cleanly, and that incremental collection is enabled here.

**The port itself.** Separate "the maths" from "the plumbing" first. The per-sample arithmetic transfers nearly as written and usually gets faster under Burst. Everything structural is rewritten: classes become value types, managed arrays become native buffers owned for the life of a voice, and interface-based chaining does not survive at all — it becomes a switch over concrete node types, or the nested generator tree the framework provides. Nesting is confirmed available in this editor version.

**Equivalence, as the definition of correct.** The existing ordinary-C# engine stays in place as the offline renderer, which makes it a live reference implementation. The new real-time path should be checked against it sample-by-sample, the way the previous port was — that is what makes "all 16 effects work" a claim rather than an opinion, and it is what will catch the float-rounding mismatch described above.

**Verification of this port, in a real player build.** Not to re-prove the premise, but because a port can be wrong in its own ways. Two specific things flagged earlier remain valid and still have to be nailed down:
- Run at the **smallest shippable audio buffer**, not the forgiving one this project is currently set to. At the current setting a pass would prove very little.
- **Confirm ahead-of-time compilation is actually configured and actually taking effect**, rather than silently falling back to ordinary managed code — in which case the immunity is simply absent and the test measures nothing. There is no such configuration in this project yet at all.
The editor is not a valid venue for either check.

### 2026-09-26T20:55:00Z — agent — open — the API shape, read off the installed editor, and what it means for the design

Extracted the full audio-generation surface from the editor's own shipped documentation (136 documented members). It maps onto this problem better than the research report implied. The load-bearing facts, in plain terms:

**A processor is a pair of halves, which is exactly the split this port needs.** Each one is written as two value types: a real-time half that runs on the audio thread under Burst, and a control half that is ordinary C# on the main thread and may allocate, read assets and log. They never share memory directly. The real-time half implements a per-block process step; the control half implements configure, update, a message handler and disposal. This is the sanctioned shape for "the arithmetic runs hot, everything that reads authored data stays cold", and it matches how the existing engine is already split between its per-sample renderer and the layout it is handed.

**Two separate communication channels exist, and they serve different purposes.** There is a message send from control to processor — the right vehicle for a discrete event (stop this voice, let its tail ring out, a parameter was just edited). And there is a data pipe with send and available-data halves, usable in both directions — the right vehicle for per-block streams of values. A processor also declares, at creation, how eagerly each half wants updating: always, never, or only when data is waiting. That last option matters for cost: a voice with no live automation need not be visited by the control half every block.

**Nesting is a first-class real-time operation, not a workaround.** The real-time side can invoke another generator instance's process step, handing it a buffer to fill. **That is the whole effect chain mechanism:** a chain node asks its child to render into a buffer, then filters that buffer in place before returning it upward. It confirms the earlier finding at a concrete level — the chain does not need Unity to ship a dedicated effect hook, and it does not need one big monolithic generator either.

**Buffers are spans with a channel count and a frame count, plus a clear operation.** So the per-sample loops keep working on flat float memory, which is what makes the existing arithmetic portable.

**A generator declares whether it is finite and how long it is.** That is how a one-shot clip differs from an endless source, and it is where the existing notion of a sound's duration and tail should land.

**The single most useful discovery: there is a manual control context.** It can be created against a chosen audio format and driven by hand — begin a mix, update, end a mix into a buffer — entirely outside the audio thread. **This is the vehicle for the equivalence suite.** It means the new real-time chain can be rendered deterministically inside a test and compared sample-by-sample against the existing engine, with no player build, no real-time audio and no listening required. Correctness of all 16 effects becomes an automated check rather than an opinion, exactly as the earlier port achieved. Build the port against this from the start rather than retrofitting a test later.

**A design consequence worth stating before anyone writes code.** Because the real-time half must contain no managed objects and no virtual or interface calls, the chain cannot be "a list of effect objects". Two shapes are available and they are not equivalent:
- One generator per effect, nested — each node is its own processor, and the chain is a tree. Cleanest conceptually, gives per-effect lifetime and update settings for free, but pays a process-call and a buffer hand-off per node per block.
- One generator for the whole chain, walking a flat description of nodes and dispatching each by a type tag inside its own loop. Cheaper per block and closer to how the existing engine already works, but reimplements the plumbing nesting would have given.

The existing engine already flattens a chain into node types with state and parameter offsets, and its per-sample code already dispatches on those. **That strongly favours the second shape for the chain interior, with nesting used at the boundary** — one generator per voice, fed by a source, rather than one per effect. Decide this explicitly and record it; it is the difference between reusing the existing arithmetic almost as-is and rewriting the engine's structure for no gain.
