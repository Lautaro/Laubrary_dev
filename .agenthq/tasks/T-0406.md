## Description

**This is the owner's sole active priority as of 2026-09-26.** All other HH2Lab audio work was wound down the same day in favour of this. Branch: `x/zounds-sap` in this project.

### The problem, in plain terms

Unity's ordinary way of letting you generate audio in C# is a callback the audio mixer thread calls to fill each buffer. The moment any code in the project uses that callback, the mixer thread becomes attached to the scripting runtime — and from then on, **any** garbage collection anywhere in the game freezes that thread along with everything else. The audio hardware has a hard deadline for each buffer, so a freeze produces an audible click or dropout. The attachment is permanent once it happens.

Two consequences that shape everything here:
- Removing allocations from the audio path reduces how often this happens but **provably cannot eliminate it**, because the freeze is caused by collections happening anywhere, not by audio allocating.
- **A single leftover use of that callback anywhere in the project re-attaches the thread and silently destroys the benefit for the whole application.** Removing the last use matters as much as adding the replacement.

### The chosen solution

Unity's **Scriptable Audio Pipeline**, shipped in Unity 6.3 (this project is on 6.3, LTS-supported to December 2027). It lets audio processing be written in a restricted subset of C# that the Burst compiler turns into native machine code during the normal build. The mixer thread then calls native code through a plain function pointer, never touching the managed runtime — structurally the same escape a hand-written C++ plugin achieves, but without hand-maintained per-platform binaries. Unity's audio team describes it explicitly as a replacement for that callback "without the hiccups resulting from garbage collection spikes".

Known limits, accepted: no Web platform support; there is not yet a dedicated "effect" extension point, so an effect chain is expressed as a tree of generators where a parent filters its child's output; and if Burst compilation is off (which is normal while debugging in the editor) the code runs as ordinary managed C# and the immunity disappears — **so this can only be proven in a real player build, never in the editor.**

Do **not** adopt DSPGraph — a Unity engineer confirmed it is preview-only, unsupported and permanently unmaintained. SAP is its successor.

### What "finished" has to mean

From the research report (see Handover Log for the path), in order:

**Step 0 — measurement before anything else.** Build a repeatable test that forces a collection at the worst moment and detects audio discontinuities objectively. Record a known-FAILING baseline and a known-PASSING baseline. Without both poles, a "pass" cannot be distinguished from a test that applies no real pressure — which is the single most likely way this whole evaluation goes wrong.

**Step 1 — cheap insurance, correctly labelled.** Confirm incremental collection is on and strip allocations from the audio path. Worth doing regardless. **Must not be reported as a fix** and must not delay the real work.

**Step 2 — the decisive experiment.** One effect, one hardcoded parameter, a trivial source, as a Burst-compiled generator. Its purpose is not the effect; it is to answer one question: does a Burst-compiled generator survive a forced collection without an audible artefact **in a player build**? Include the negative control — with Burst disabled it *should* glitch; if it does not, the test is not applying pressure.

**Step 3 — only if step 2 passes:** port the effect chain properly, separating "the maths" from "the plumbing" first. The per-sample arithmetic transfers nearly as written and usually gets faster. Everything structural is rewritten: classes become value types, managed arrays become native buffers owned for the life of a voice, and interface-based chaining does not survive at all (no virtual calls in the restricted subset) — it becomes either a switch over concrete node types or the nested generator tree.

**Step 4 — retire the native fallback only after the generator path passes in player builds on every shipped platform.** Not before; it is the existence proof that the goal is achievable.

### 2026-09-26T19:45:00Z — agent — open — the API foundation is verified, not assumed

Checked the installed editor's own assemblies and shipped documentation rather than trusting the research report, because the entire plan collapses if the API is not actually in this version. **It is present and documented in this exact editor version.** The concrete surface:

- A factory interface for audio generators, whose job is to create a generator instance, and a matching instance type that is explicitly described as owned by the caller and destroyed through a control context. So voice lifetime is the caller's responsibility, which lines up with the per-play-owns-its-own-state design the new state container already assumes.
- **Creating a generator takes an optional nested format, documented as producing "a nested generator ... to be used from within another processor".** This is the single most important confirmation: the effect chain is meant to be built by nesting generators inside one another, and that capability is real and shipped, not a theoretical workaround. The research report predicted exactly this and it holds.
- A pipe with send and receive halves for passing data between the ordinary-C# control side and the real-time side. This is the sanctioned route for a live parameter edit (a slider drag heard on a playing sound), and it is what the managed voice's new single-voice parameter-push entry point should eventually feed.
- A serializable wrapper around a generator definition, which is likely what lets a chain be authored into an asset.

**Also confirmed present, and must be avoided:** the old graph-based audio package is still shipped in this editor install. A Unity engineer has stated it is preview-only, unsupported and permanently unmaintained. It is the thing most searches surface first, so anyone continuing this work will trip over it — do not use it. The generator interface above is its successor and the correct target.

Practical consequence for planning: because nesting is supported today, the effect chain does not need to wait for Unity to ship a dedicated effect extension point. The known cost of being on this version rather than a later one is extra sample-streaming and decoding plumbing that a later version would remove — worth knowing before someone writes a lot of it.

### 2026-09-26T19:50:00Z — agent — open — project-settings facts for steps 0 and 1

Read from this project's settings, so nobody has to re-derive them:

- **Incremental collection is already switched on.** That is the first item of the plan's step 1, so it is done. Expect nothing from it on its own — it is a frame-rate feature that helps audio only incidentally, and only when buffer headroom is generous.
- **The audio buffer is set to the largest, most forgiving size (1024 samples).** This matters a lot for the validation test and is easy to get wrong: the plan requires the test to run at the *smallest shippable* buffer, where the deadline margin is thinnest. **Testing at the current setting would produce a flattering pass that proves very little.** Whoever runs the test must reduce it deliberately, and should record the value used alongside the result.
- Voice limits are 32 real and 512 virtual, which is the realistic-load figure the test should aim at rather than a single sound.
- **There is no ahead-of-time compilation settings file for Burst in this project at all**, meaning it has never been configured here. Step 2 depends on confirming that the generator really is compiled ahead of time in the player build — if it silently falls back to ordinary managed code, the immunity is absent and the test would be measuring nothing. Configure and verify this explicitly rather than assuming the default is right.

Taken together: step 1 is effectively already satisfied, and the real risk in step 0/2 is running a test that cannot fail. The plan's insistence on a deliberately-failing control case exists for exactly this reason.
