## Description

Found during T-0448. The standalone check build quits with a segmentation fault (exit 139) when Application.Quit is called while a looping Zounds voice plays. The same build quitting with no voice playing exits 0. The log ends with 'Leak Detected: Persistent allocates 41 individual allocations', then the fault; no crash dump was written. Likely a shutdown-ordering problem in the generator's teardown (voice memory versus the audio graph's own disposal), which is deliberately careful already. A shipped game quitting mid-sound would crash on exit.

### 2026-09-28T13:31:59Z — agent — open -> open
Looked at alongside the Looper (T-0473), which makes this case routine.

REPRODUCED on the existing standalone check build (-zoundsGcReport: plays a looping tone, then Application.Quit): exit code 0xC0000005 (access violation) and 'Leak Detected: Persistent allocates 41 individual allocations' - identical to the report. 41 = one voice's native memory (9 state arrays + 30 chain-layout arrays + 1 PCM copy) + its render ticket, i.e. the graph never disposed the voice.

Cause (from the code path, consistent with the evidence): nothing tore voices down at quit except ZoundSapVoiceGenerator.OnDestroy, which at quit runs after the audio graph has begun shutting down - the stopped-for-sure wait passes trivially (nothing renders any more) and control.Destroy then lands on a graph that is going away.

FIX (uncommitted, compiles): SapVoiceRegistry hooks Application.quitting (fires before scene objects are destroyed, while the graph still runs) and tears every live voice down through the existing safe sequence (silence, wait for quiet, destroy -> the graph disposes the voice memory). A Quitting flag then stops OnDestroy from calling into the graph at all.
