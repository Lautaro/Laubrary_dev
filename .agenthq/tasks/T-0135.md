## Description

Follow-up to T-0134: the user clarified the point of the mock is specifically to prove the UI scales to a great number of generators/modifiers, not just to flag the gap. Implemented real solutions, not just a description of the problem:

1. Added search/filter + a capped scrollable body to ZuiMenu (Assets/Packages/Laubrary/Zui/Toolkit/ZuiMenu.cs) -- a SHARED toolkit capability via a new `.Search(placeholder, maxBodyHeight)` builder call, since ZuiPopover.Place only clamps a panel's position, never its height, so an unbounded menu silently runs off the bottom of the window with real rows invisible below the fold. Filters Item/IconItem rows by label substring; a Section header hides itself once every item under it is filtered out.
2. Wired `.Search()` into the Shaper mock's add-effect menu, and grew the mock's effect catalog from 7 to the REAL measured distribution (T-0114: 20 buffer-free / 7 buffer-padded / 13 needs-sheets / 1 stuck = 41 total) via a new parametrised ShaperMockGenericEffect, so the menu is now genuinely stress-tested at real scale, not just described as needing it.
3. Grew the HeightField preset picker from 8 to 64 mock presets (stand-in for the real 245) and gave it its own filter field + max-height ScrollView (inline, not a ZuiMenu popover, so it needed its own small solution).

Found and fixed a real bug while verifying: ZuiMenu.Item() captured the current section at fluent-chain-build time, but Section() only updates the current section inside its OWN deferred row-builder (which runs at Show() time) -- so every item's recorded section was always null, and no section header ever hid during a filter. Fixed by deferring the capture into Item()'s own lambda too. Verified via direct structural measurement (not just screenshots, which had repeated timing artifacts under rapid programmatic driving): 40 effect items filter to exactly 3 on 'blur' with exactly 1 section left visible; 64 presets filter to exactly 4 on 'cobble'; both clear back to full counts.
