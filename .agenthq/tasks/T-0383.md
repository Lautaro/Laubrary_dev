## Description

**Owner-diagnosed (2026-09-21), root cause confirmed by reading the code — two related bugs, one shared fix pattern.** The project has a single global "guide" asset, `Assets/Packages/Laubrary/Runtime/PixelScale/PixelScaleProjectSettings.cs` (`pixelsPerUnit`, default 16; `targetResolution`, default 320x200) — the whole point of it is to keep every piece of pixel art in the game rendering at the same apparent pixel size, avoiding mixels. It already works correctly in ONE place: `PixelScaleCamera` (attached to the real camera in `Assets/Mirage/MirageStage.unity`) reads it and computes `orthographicSize = targetResolution.y / (2 * pixelsPerUnit)` — confirmed correct, do not touch this part.

**Bug 1 (deeper, higher priority): `Pyre.pixelsPerUnit` (`Runtime/Pyre/Pyre.cs:1195`, per-asset field, defaults to a hardcoded 16f) is baked DIRECTLY into every frame's real Unity `Sprite.pixelsPerUnit` at bake time** (`PyreRenderer.cs:5178`, `Sprite.Create(tex, ..., pivot, spec.pixelsPerUnit)`). This is not a preview-only setting — it is the actual, permanent PPU of every sprite that Pyre asset ever produces. It is NEVER synced to `PixelScaleProjectSettings.Instance.pixelsPerUnit` — a Pyre authored before a project-wide PPU change keeps its old baked value forever, so two Pyres authored at different times (or copied from a different project) can render their pixels at genuinely different apparent sizes side by side in the same recipe. This is the real root cause; Bug 2 is a visible symptom of the same shape one layer up.

**Bug 2 (what the owner actually noticed): `MirageView.displayPixelsPerUnit` (`Runtime/Mirage/MirageView.cs:25`, defaults to a hardcoded 16f) is used to normalize how big a spawned Pyre/Chunk renders in Mirage's preview** (`Runtime/Mirage/MirageRig.cs:224/232`), and is likewise never read from `PixelScaleProjectSettings.Instance.pixelsPerUnit` — `ChunkWindow.Preview.cs`'s `PreviewInMirage(spec)` creates a fresh `MirageView` via `CreateInstance`, which just takes the hardcoded C# default. If the project's real PPU differs from 16, the (correctly-framed, per Bug 1's non-issue here) camera and the (wrongly-normalized) preview sprite disagree, and a Pyre renders far too large/small relative to what the simulated screen should show — this is what the owner saw as "pyres look way too high-resolution for their small sizes."

**Fix — the SAME pattern for both, matching T-0356's already-established "Auto" precedent (`PyreBlast.blastSecondsAuto` in `Runtime/Chunks/Capabilities/PyreBlast.cs` — read that for the exact shape to copy):**
1. `Pyre.pixelsPerUnit`: add a `pixelsPerUnitAuto` bool (default **true**, including for existing/legacy assets — same "the old behaviour was a bug nobody picked on purpose" reasoning T-0356 used, since two Pyres silently disagreeing on PPU is not a state anyone authored deliberately). When Auto, the field is read-only and tracks `PixelScaleProjectSettings.Instance.pixelsPerUnit` at bake time (`PyreRenderer.cs`'s frame-building path, wherever `spec.pixelsPerUnit` is currently read for `Sprite.Create`) and in the editor UI (`PyreWindow.cs` — find where `pixelsPerUnit` is currently exposed). Off is a genuine, rare, deliberate per-asset override (e.g. an intentionally hi-res glow/particle layer under low-res sprites) — keep it, don't remove the field, just fix its default source.
2. `MirageView.displayPixelsPerUnit`: seed it from `PixelScaleProjectSettings.Instance.pixelsPerUnit` at every creation site (`ChunkWindow.Preview.cs`'s `PreviewInMirage`, and any other place a `MirageView` is `CreateInstance`'d — grep for it) instead of the hardcoded `16f` default. The existing "Display PPU" field in `MirageWindow.cs` stays exactly as-is as a per-view override — just fix what it starts at.
3. Decide and document: does Bug 1's fix make Bug 2 moot in the common case (a freshly-baked Pyre's own sprite PPU would already match the global setting via Auto, so Mirage's separate normalization would agree even with its old hardcoded default)? If so, say so explicitly — but fix Bug 2 anyway regardless, since an EXISTING/legacy Pyre (baked before this fix, or with Auto turned off) still needs Mirage's own normalization to independently agree with the project setting, not assume every Pyre it's shown is already correct.
4. Verify: a Pyre baked with the project at PPU 16, and a second baked (or simulated) as if the project were at PPU 32, both previewed in Mirage — confirm they now render at consistent, correctly-scaled apparent pixel sizes rather than disagreeing.

Read `D:\AgentGuide\ui-rules.md` and the laubrary skill's `references/ui-layout-rules.md` before touching any UI (the Auto toggle placement in `PyreWindow.cs`).
