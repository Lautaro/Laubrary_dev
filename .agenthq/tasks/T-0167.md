Follow-up fix on commit 0e2b166194ac103b9ba8e09750cd1df93a4118b7 (feat/shaper), addressing the PM's probe run.

(1) ExplosiveJetForm NaN crash -- root-caused to ExplosiveJetProgram.Rep (Runtime/Pyre/Forms/Kiln/Jet/ExplosiveJetProgram.cs, was lines 480-484): `bis = cenDa + span * Math.Round((da - cenDa) / span, ...)` divides by `span`, which is `2 * PlateGeom's p.half` and `p.half = Min(s.live.spread, 180) * PI/180` -- `spread` is a real, legitimately-animatable ZUIValue (tooltip: 'Half-angle of the emission arc, degrees (180 = a full disc)'), and my probe's forced Curve (0,0)->(1,1) makes it evaluate to exactly 0 at phase 0. span=0 -> (da-cenDa)/span is Infinity or NaN (0/0 when da==cenDa) -> Math.Round/Math.Sign on that NaN throws exactly `ArithmeticException: Function does not accept floating point Not-a-Number values` (Math.Sign(double) throws that specific message on NaN input; Math.Sign is called on the resulting dphi at ExplosiveJetProgram.cs line ~508/516/670). This is a REAL evaluation-path bug, not a probe artifact: any author dialling Spread down to 0 (static or animated) on Detonate/Backdraft/etc. (any variant with fracture.chance>0 and pieces>=2, i.e. every default variant) would crash identically inside real Pyre too, nothing Shaper-specific. Fixed by guarding the division with the same Math.Max(x, 1e-6) epsilon pattern every other division in this file already uses (e.g. `invShrink`, `Warp`'s `Math.Max(reachPx,1.0)`); at span~0 the puffs collapse onto one bisector (da ~ bis, dphi ~ 0), the sane degenerate answer for a needle-thin burst.

(2) JetForm/RadialJetForm rendered identically across phase 0/0.5/1 despite every dial forced to Curve. Root cause: JetFormBase.Render (Runtime/Pyre/Forms/Kiln/Jet/JetFormBase.cs, was line 113) computes its own internal loop clock as `ctx.frameIndex / (double)Math.Max(1, ctx.frameCount)` -- NOT ctx.life -- and feeds that into program.Frame(...), which drives puff birth timing, the domain-warp scroll, everything phase-dependent in the actual draw. This is deliberate for a REAL multi-frame Pyre clip: frameIndex ranges 0..N-1 so frameIndex/frameCount never reaches exactly 1 even on the last frame, which is what keeps a looping clip from visibly stuttering (ctx.life's own convention, frameIndex/(frameCount-1), DOES hit exactly 1.0 on the last frame, which would phase-equal frame 0 under Kiln's Mod1 wrap and duplicate a frame every loop). But PyreFormCompositeSource passes a constant (frameIndex=0, frameCount=1) since the bridge has no real frame timeline -- only a single requested phase01 per Render call -- so the formula degenerated to 0/1=0 on every single call regardless of what phase the Shaper actually asked for, freezing every phase-driven draw in the whole jet family. Fixed with `ctx.frameCount > 1 ? ctx.frameIndex / (double)ctx.frameCount : ctx.life` -- real multi-frame Pyre usage (frameCount>1) is byte-identical to before (untouched branch); the no-real-timeline host case (frameCount<=1, exactly PyreFormCompositeSource's case) now reads ctx.life, which does carry the Shaper's actual phase. Not touched: PyreFormCompositeSource.cs itself -- the bug was structural in the shared engine, per the PM's own diagnosis pointer, not fixable at the bridge without a synthetic frameCount hack that would also perturb ArcBurst's per-frame RNG reseed (ArcBurstForm.cs:470 seeds bolt rerolls off ctx.frameIndex) in an unreviewed way; fixing JetFormBase directly is the smaller, more targeted change.
