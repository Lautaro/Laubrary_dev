Decisions taken without asking (per the standing rule):
- Form field ids: a new base `FldForm = -1000`, slot s ⇒ `FldForm - s` (negative ids never collide with the positive modifier/fire blocks, and -1000.. is far below the -2..-58 singles). Migrated forms additionally get `EvalRaw(value, fieldId)` so they can keep their LEGACY negative ids (-32..-58) — that is what keeps an already-authored Min-Max dial drawing the same random on a migrated asset; new forms use slots only.
- The core algorithm files keep their names (`PlusInferno`/`PlusForkBlast`) but take a plain params struct instead of `PyrePlusLayer`; the form classes fill that struct from their own fields. After the legacy deletion (7b) both algorithm files MOVE into `Forms/Kiln/` so the core carries zero Inferno/ForkBlast code. (Inferno is not a Kiln algorithm, but the brief names `Forms/Kiln` as the one family template for both migrations — logged, not worth a second asmdef for Phase 1.)
- The form section draws with `ZuiReflect.FlowFields` (not `BuildFields`): zui.md says prefer it for cards, and the hand-written Inferno/Fork boxes already packed 2 dials per row — stacking 40 dials one per row would be the space-economy violation the UI Guide names.
- Swarm-only dials (Inferno's Mutation/Heat stacking/Character drift+jitter) get a tiny `[PlusSwarmOnly]` attribute the drawer skips when the layer's swarm is off — a dead control would otherwise sit in the card.
- The swarm-instance record (`PlusSwarmInstance`) is built for every form layer with swarm on, carrying the renderer's own x/y (canvas px, live spin+scale applied), own life (incl. die-together), spawnLife, index, orientDeg, zNorm, sizeMul, brightMul — forms convert to NDC/clamp `start` themselves with the same arithmetic, so the migrated output stays byte-identical.
