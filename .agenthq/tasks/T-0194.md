**Owner (2026-09-02 evening):** "The rendering is visibly slow. It wasn't like that in Pyre. Each time I change the slightest thing the preview pane lights up. Is it necessary to recalculate everything if I disable a layer? It wasn't like that before. Could Burst be an improvement?"

**Cause (PM reading):** `Editor/Shaper/ShaperPreviewFrameCache.cs` (T-0165) is a whole-frame pixel cache; every `Change`/`Val` invalidates ALL frames, so a layer toggle, a Z offset, or a global SpriteFX edit re-resolves every layer of every frame (~30 ms/frame × 16). Pyre caches per LAYER by content key (`Runtime/Pyre/PyreLayerKey.cs`, `PyreLayerCache.cs`, `Editor/Pyre/PyreWindow.FrameCache.cs`): editing one layer re-renders one layer and re-composites the rest; a layer toggle is composite-only. Nothing in Shaper is Burst-compiled — the evaluator and fill resolver are managed per-pixel loops.

**Do, in this order, measuring each step with a committed temporary probe you delete afterwards (report ms/frame before/after on the demo document and a 4-layer 16-frame document):**
1. **Per-layer resolved-buffer cache** keyed by `ShaperNodeIdentity`-style content hash of the layer (its tree, fill, border, height, mask source identity, per-layer SpriteFX, lifetime, phase): editing layer A re-resolves only A across frames; toggling enable, changing Z offset, layerSpacing, background, document SpriteFX, or the light rig re-composites/re-lights from cached layer buffers without re-resolving. Keep bake == preview (the baker may reuse the same cache path). Reuse the existing `ShaperFrameCache`/`ShaperCachedEvaluator` design where it fits (T-0115 built node-level distance caches that nothing consumed).
2. **Only the on-screen frame renders synchronously**; other frames refill in the background as today, but the tick strip must only flash for frames that actually re-resolve — a composite-only change must not turn the strip yellow.
3. **Burst** the hot loops that the design already shaped for it: the SDF evaluator's block fill and the fill resolver's paint tile (`ShaperEvaluator.FillTile`, `ShaperFillResolver.PaintTile`), with a managed fallback when Burst is unavailable; determinism must be bit-identical to the managed path (probe: hash every frame both ways).
4. Say which Pyre-checklist rows (4.2, 4.3, 7.7, 8.14–8.17) now read Same.

**Verify (temporal, by probe and by eye):** drag a dial on a 4-layer document — the preview follows within one frame and the transport keeps playing; toggle a layer — no re-resolve, strip does not flash; numbers in the handover; screenshots; CHANGELOG; commit by path.

### 2026-09-02T17:37:15Z — agent — in_progress -> done
The preview used to throw away every rendered frame on every edit, so hiding a layer cost the same as redrawing the whole document. It caches each LAYER's resolved buffer by content now, the way Pyre has for a long time, so an edit re-renders only what it changed and everything else is re-composited from buffers already in hand.

On a four-layer, sixteen-frame document at 96x152: hiding a layer went from 65.2 to 5.2 ms a frame, recolouring the background from 89.8 to 7.6, and moving one dial on one layer from 89.8 to 26.4 - with 48 layer-cache hits and 16 misses, which is exactly the one layer that changed and none of the others. A cold render costs 1% more for the hashing, which is what buys every later edit. The picture is byte-identical to the old path on every frame, verified by hashing both ways.

The tick strip and the filmstrip stopped flashing for edits that do not re-resolve anything. Invalidation now re-keys each resident frame instead of dropping them all: a frame whose picture did not change is left alone, a frame that changed but needs no re-resolve is re-composited on the spot, and only the rest are dropped for the background pre-baker to refill. Yellow ticks now mean something is genuinely recomputing.

The bake reads the same cache as the preview, so 'the bake is what the preview showed' holds because there is one store rather than because two paths happen to agree - and a layer that stands still across sixteen frames is resolved once instead of sixteen times.

Burst is NOT done, and the reason is not time. The profile says the SDF block fill is at least 45% of a layer's cost, so Burst is aimed at the right place - but the inner loop calls Mathf.Pow/Sin/Cos/Atan2, and Burst does not promise bit-identical results for those against Mono. This task's own contract asks for bit-identity with the managed path, and a side-by-side Burst path cannot give it for any shape that uses them (NGon, Star, every smooth blend). The two honest ways forward - run everything through Burst and accept a one-time re-bake of existing sheets, or Burst only the programs with no transcendental primitive - are both your call, not an implementer's. That decision matters more now than it did, because the layer cache's correctness rests on a hit being byte-identical to a miss.

Two things found while measuring that are not this task's and are not fixed: the demo document cannot render at all (its ArcBurst layer throws inside Pyre's supersampler), and its asset is sitting modified in the worktree with one layer's height reference nulled. **Technical details:**
COMMIT 5572f210 on feat/shaper (9 files, +710/-34). The CHANGELOG line for this landed inside T-0196's commit 3c8cd27e, which staged the whole file.

NEW Runtime/Shaper/ShaperLayerKey.cs (ShaperLayerKey + ShaperLayerKeys) - the content key of a layer's painted buffer, a reflection walk mirroring Runtime/Pyre/PyreLayerKey.cs:108-222. It EXCLUDES enabled, name, contributesToPicture, startFrame, endFrame and id: those decide WHETHER a layer paints, never what its buffer holds, which is exactly what makes a toggle composite-only. It INCLUDES the document part (canvas, pixelSize, seed, the whole lightRig), the layer index (ShaperLightCompiler.BindLayer is index-addressed), phase01, and baseZ from ShaperHeightCompiler.LayerBase - the height and light stages compile against that float (ShaperLightCompiler.cs:492), so two base planes are two different pictures. A masked layer folds its source's content key and lifetime one level deep; the source is read unmasked (ShaperLayerMask.SourceIsReadUnmasked) so no cycle is representable.

NEW Runtime/Shaper/ShaperLayerBufferCache.cs - key -> {dst (4 floats/sample, post-mask, post per-layer SpriteFX), height (1/sample)}, which is exactly what ShaperDocumentRenderer.CompositeDepth reads. LRU against a float budget (8M floats = 32 MB) rather than an entry count, because an entry's size is the canvas. Store() copies rather than adopts: ShaperRenderBufferPool hands the same ShaperFillBuffers back for the same layer index next frame, and the per-layer effect path writes into one scratch shared by every later layer, so adopting either would leave stored entries aliasing a buffer about to be overwritten.

CHANGED Runtime/Shaper/ShaperDocumentRenderer.cs - RenderPhaseInto/RenderPhase/RenderFrame/RenderFrameInto take an optional ShaperLayerBufferCache; null keeps every existing caller byte-for-byte. The layer walk hoists baseZ above the resolve and takes the key AFTER ShaperCompositeDef.FitTree, because FitTree writes the derived bake box into the composite nodes it walks - keying the unfitted tree would key a state the document holds only on the first render after a load. On a hit it skips Resolve, BindLayer, BindSolids, PaintTile, the mask and the layer's own effects, and composites the stored arrays. ShaperLightCompiler.CompileDocument is now lazy, so a frame whose layers all hit compiles no light program at all.

CHANGED Editor/Shaper/ShaperPreviewFrameCache.cs - owns the layer cache. Invalidate(ShaperDocument) sorts each resident frame into unchanged (kept untouched), changed-but-every-contributing-layer-resident (re-rendered IN PLACE, which with the cache warm is a composite and an encode, bounded by MaxRecompositeMilliseconds = 12f), or dropped. CanRecomposite asks whether every contributing layer's key is already in the store, which is precisely the question 'does this frame re-resolve'. The no-argument Invalidate() remains the unconditional reset for a document swap or a canvas/frameCount change.

CHANGED ShaperPreviewStage.InvalidateFrameCache and ShaperFilmstrip.Invalidate pass the document through. ShaperBaker.BakeSheet renders through a bake-local layer cache and buffer pool.

ONE DESIGN POINT WORTH KEEPING: the key memo is rebuilt on EVERY render and never carried across one. A first version memoized it while the document object and layer count were unchanged, and a probe that edited a dial and re-rendered then scored 64 hits where it should have scored 48 - a stale key made a changed layer look unchanged, which for a render cache is the only failure that matters. The memo now survives only in the invalidation SCAN (ShaperLayerBufferCache.BeginPass), which asks about keys without rendering anything. The rebuild costs 0.22 ms for four layers against ~21 ms to resolve one.
