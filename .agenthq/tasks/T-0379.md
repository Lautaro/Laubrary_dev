## Description

**Owner request (2026-09-20):** "For all LauAsset browser windows, by the button that ends with delete, add a filter search bar." A general Laubrary-wide feature, not tied to any specific tool.

**What "LauAsset browser window" means here:** every editor window built on one of the two shared AssetKit bases — `ZuiAssetWindow<T>` (`Assets/Packages/Laubrary/Editor/AssetKit/ZuiAssetWindow.cs`, the current UI Toolkit base — Chunks, Pyre, BackSplash, Cartographer, PropWindow, TilesetBuilderWindow, Choreographer, DotGen, Larder, LatheMoldWindow, LatheWindow, SpriteCatalogWindow, MirageWindow, SpriteFxStackWindow, TapestryWindow, TextSplashWindow, ZoeWindow/WeaponDefWindow, and any other current subclass) and `LaubraryAssetWindow<T>` (`Assets/Packages/Laubrary/Editor/AssetKit/LaubraryAssetWindow.cs`, the older IMGUI base, still in use by some tools). **Add this in the shared base class(es), not per-tool** — every subclass gets it automatically, matching "for all LauAsset browser windows" in one change.

**"The button that ends with delete"** identifies the toolbar to add it to: the top asset-chrome toolbar every one of these windows already has (`BuildToolbar()` in `ZuiAssetWindow.cs` — `New, Browse, [Duplicate, Rename, Delete when an asset is open]`, ending with `Z.Flexible()`; the IMGUI base's equivalent row in `LaubraryAssetWindow.cs` around line 163-172). This distinguishes it from any tool-specific secondary toolbar (Tags, Views, Sections) that some windows also have.

**What it should actually filter — read this carefully before just wiring up an empty text field:** the only thing in these windows with multiple items to search is the **browser grid** — `BuildBrowser()` (`ZuiAssetWindow.cs:405-436`, `_browse` list of every `T` asset in the project) and its IMGUI counterpart `DrawBrowser()` (`LaubraryAssetWindow.cs:240`). Wire the toolbar's search field to filter `_browse` by a case-insensitive substring match on `item.name` before it's laid out into cells/rows. The field lives in the toolbar (always visible, stable position per the owner's instruction), but it only has visible effect while the browser grid is showing (`asset == null || browsing`) — while editing a specific asset it can just sit there empty/inert, ready for the next time Browse is opened. Real motivating case already on record: T-0344's UC1 walk (`workspace/T-0344/WALK.md`, finding F13) found the shared Pyre browser has 32 entries including near-duplicate and typo'd names — exactly what this should make fast to cut through.

**Build:**
1. Read the UI Guide FIRST — `D:\AgentGuide\ui-rules.md`, then the laubrary skill's `references/ui-layout-rules.md` (hard gate, this project's standing rule) — before writing any control.
2. Add a text field to `BuildToolbar()`'s row (after `Delete`, before or after the existing `Z.Flexible()` — use your UI judgment per the guide for where it reads best; a reasonable width, not a Flexible-consuming full-width field crowding the buttons) using `Z.TextInput` if the ZUI toolkit's text-field control fits (the CLAUDE.md notes a plain text-input field is a known current ZUI gap — check `references/zui.md` for what actually exists before assuming; if there truly is no ZUI text field, note it as a raw-fallback case the way the CLAUDE.md's "ZUI gaps" section describes, don't silently invent one either way without checking first).
3. Store the filter string in the window (transient, not `[SerializeField]` — it's UI state, not asset data, and doesn't need to survive a domain reload).
4. In `BuildBrowser()`, filter `_browse` (or a filtered copy built from it) by the search string before building cells — empty string = no filtering, unchanged behavior.
5. Do the equivalent in `LaubraryAssetWindow.cs`'s `DrawBrowser()`/toolbar for the IMGUI base — same behavior, IMGUI controls (a `GUILayout`/`EditorGUILayout` text field is correct there, that base doesn't use ZUI).
6. Tooltip on the field (this project's standing rule: every control gets one, written as the effect). Something like "Filter the library below by name."
7. Verify on at least two real tools that use each base (e.g. Chunks or Pyre for `ZuiAssetWindow<T>`; whichever real tool still uses the IMGUI base for `LaubraryAssetWindow<T>` — check which ones do before assuming) — type a partial name, confirm the grid/list narrows correctly, clear it, confirm everything comes back.

Editor rights: YES if you use Coplay/unity-mcp for verification (screenshot the filtered grid on a real tool) — check whether those MCP tools or the Unity CLI (port 7800, `D:\UNITY\Laubrary Dev`) are actually available first rather than assuming; recent sibling tasks found the MCP tools down and used the Unity CLI successfully instead.
