### 2026-08-24T07:18:06Z — agent — in_progress -> done
Envelope graphs (the little curve editors used all over the tools) now let you delete points down to just 1, instead of getting stuck at 2 or (in one variant) letting you delete all the way to nothing. With only 1 point left, the whole graph is a flat, straight line at that point's height, and that point can be dragged anywhere on the graph.
**Details:**
How to use this: in any ZUI envelope editor, keep deleting points (double-click a point, or select and press Delete) and it will now correctly stop at 1 point instead of either getting stuck early or vanishing entirely. That last point can be moved anywhere. If you want a second point back, click on the flat line and it adds one back in, same as any normal envelope.

Not yet verified: this was checked by directly driving the underlying control code inside the live Unity editor (deleting down, confirming the flat line, confirming the point is freely draggable) rather than by physically clicking through a mouse in an open tool window, since there wasn't a specific tool screen open to click through live.
**Technical details:**
Two parallel envelope controls share this fix: the older IMGUI one at Assets/Packages/Laubrary/Zui/Scripts/Editor/ZUIEnvelope.cs and the newer UI Toolkit one at Assets/Packages/Laubrary/Zui/Toolkit/ZuiEnvelope.cs.

IMGUI control had NO minimum-point guard at all (double-click-to-remove and Delete-key could empty the list to 0); added `points.Count > 1` guards at both removal sites. UI Toolkit control's `minPoints` default was hardcoded to 2; changed to 1 (every current caller in ZuiValueControl.cs uses the default, so this is a real behavior change, not just an opt-in).

Both controls' `anchorsLocked` option (used to force-lock first+last points regardless of their own editState) was unconditionally locking index 0/Count-1 -- for a 1-point list that's the SAME index, so it would have frozen the sole point. Fixed both to only apply anchorsLocked when Count > 1.

IMGUI-only gap: `HitLine` (used to detect a click on the curve to insert a new point) requires 2+ points to define a segment, so a 1-point envelope's visually-flat line was never clickable to add a 2nd point back -- added a small dedicated click-to-add band (in ZUI.cs's point-down handler, right before the HitLine call) that activates only when points.Count == 1, mirroring the existing insert logic. The UI Toolkit control didn't need this fix -- its double-click-to-add already works anywhere in empty space regardless of point count.

Runtime evaluation (`ZUIEnvelopeEvaluator.Evaluate`) already correctly returned `points[0].value` for a 1-point list regardless of query time, and both controls' paint/draw code already rendered a flat line spanning the whole domain for 1 point -- no changes needed there.

Verified in the live Unity editor via Coplay execute_script: instantiated a real ZuiEnvelope with 2 points, removed one (succeeded), attempted to remove the last one (correctly refused), confirmed ZUIEnvelopeEvaluator returns the flat value at arbitrary times, and used reflection to confirm StateOf/EffectiveState return Editable for the sole point under anchorsLocked=true (and still correctly lock endpoints when 2+ points remain, so no regression there). check_compile_errors clean throughout, confirmed against Application.dataPath resolving to this project. One caller of anchorsLocked=true exists in the codebase (Assets/Packages/Laubrary/Zui/Scripts/Editor/Zhowcase.cs, a ZUI showcase/demo, not a production tool) -- not touched, benefits from the same fix automatically. Assets/Packages/Laubrary/Editor/Zounds/EditorWindows/SpectrumView/AudioSpectrumView.cs pins its envelope's first/last points to Y-only (X locked at time 0/duration) via its own per-frame PinEndpointsYOnly helper, independent of anchorsLocked -- left untouched since that's Zounds' own domain-specific design (audio envelope must span the full clip), not the generic ZUI Envelope control in scope here; flagging in case a future task wants that Zounds-specific behavior reconsidered too.
