## Description

Owner wants Zounds (and the Klip editor) to expose parameters that code can drive at runtime, not just what a human sets in the editor. The exact idea, in his words:

A value 0 to 1, with bindings set up in the Zounds or Klip editor, that code can control through a "token" — a runtime object carrying named values. Each controllable binding has a string id. Code sends a token; if a binding's string id is found among the token's values, that binding is set to the matching value. Examples: the volume or pitch of a specific track inside a ZEQ, the amount of an FX chain, a whole group of FX parameters.

A second idea he raised and then worked through out loud, worth carrying into the plan as-is: instead of (or alongside) direct value-setting, let a whole Zound or Klip be saved as a labelled "snapshot" of its full parameter state, and have code fade the live instance toward a named snapshot. He initially proposed sending a 0 to 1 blend amount, then caught the problem himself: a lerp needs both a start and an end, and a bare 0 to 1 number has no way to express "start from wherever the sound already is right now." His own fix: send a duration instead — from wherever the instance currently sits, glide toward the named snapshot over X milliseconds. Carry this reasoning into the plan explicitly, including why the simpler 0 to 1 version doesn't work.

**Owner's explicit priority order, don't skip or reorder it:** UI comes first. Before any engine work starts, he wants a way to SHOW, with mock UI, that a user can be given clear visual feedback when a parameter is being driven by code rather than by hand. His concern: during runtime, with values changing from code, a person looking at the Zounds editor needs to be able to tell what's actually going on — otherwise it's confusing. He explicitly said to reason about when that feedback should show (not necessarily always) rather than assume one answer. Only once that UI question has a real answer does the engine/binding work begin.

**What this task should produce:** a thorough research pass plus a plan, written as a strategic analysis in plain language — explicitly NOT code, not an implementation spec, not full of class names. Cover: prior art for parameter-automation UI in other audio tools if useful context, the two control shapes above (token-bound direct values, and snapshot-glide-by-duration) and how they'd coexist, what "showing a code-driven value is different from a human-set value" should look like in the editor (with mock UI, i.e. sketches/wireframes/described mockups, not implementation), and a recommended plan of attack in phases with UI first. Flag that this is a big refactor of Zounds' data model and runtime, and say so plainly rather than downplaying it.

Recommendation in brief:
1. UI first. Three tiers tied to real state. A quiet, permanent control chip names the game control on every exposed parameter. While a sound plays, a static code-coloured band shows a value code LEFT different from the hand-set one (the 'held' state that a show-only-while-moving design would lose). A pulse and a target tick show only while values are in motion. Nothing live shows when idle (T-0446 rule kept). Dragging a driven slider works like a DAW's touch mode: the hand wins while held, and code resumes on release. A new Game Controls section shows each control's live value, how long it has been held or 'never sent', and what it drives. Glides show as a filling progress bar on the destination snapshot and ghost ticks travelling on each changed parameter. 'Watching N of M' appears when several instances play. ASCII mock-ups are in the doc.
2. Engine. A game control is a new modulator kind whose signal comes from code, so it reuses bindings, depth, combine modes and the existing live overlay, and composes with LFOs instead of fighting them (today a direct live write to a modulated parameter is refused). A snapshot glide moves the RESTING value under all bindings, so the two shapes never compete for one slot. The owner's reasoning for a duration over a bare 0-1 blend is carried in full; Unity mixer snapshots and Wwise states work the same way.
3. Flagged as a big refactor: positional parameter addressing must become stable identity; a new external-signal modulator with smoothing and apply-at-play-start; Zequence/Klip-level values made bindable; snapshots; glides on the audio thread with no managed code; a two-way display channel.
Naming clash: 'token' already names the play handle, so the doc proposes 'game control / control values' for the owner's idea; owner to confirm.
6-phase plan. Phase 1 is UI only, driven by an in-window fake-game test panel, and the owner signs off the look before any engine work. 7 owner questions at the end of the doc. Left OPEN for the owner to read and react.

- Multi-instance display: summary only; per-instance drill-down deferred.
- Modifier ZPOC range: a modifier's depth is always bounded (0 to 1 of the control's travel), so a maximum always exists. Proposed modes Set (the strongest binding follows the value, the others keep their proportion) and Scale. Add was dropped, because it can only raise the depth and Set covers it.
- Code modifier re-explained with a worked helicopter example. Pitch's x0.1 to x4 limits are chosen, not natural; defaulting pitch and speed to the Ratio scale (the middle means unchanged) handles that.
- Replayable tokens. A token keeps its settings across runs, and each run has its own randomness. This dissolves the ended-token and empty-result questions. Keep the old play calls unchanged for compatibility (about 45 checks for 'returned nothing' in this project alone).
- Global ZPOC values: the token's value first, then the global value, then the authored value.
- One universal track model (a Klip is track 0) plus an Enabled toggle: silent and never chosen, and round-robin memory stays safe.
- Snapshots: Default adopted as an ordinary snapshot. Four kinds of setting handled separately: continuous values glide; effect on/off fades; choices switch at the glide's midpoint; settings that size memory apply from the next run. The value-or-range setting model is confirmed against the code, with additions (modifier settings belong in snapshots; a run remembers its draws so returning to Default lands where it started).
- ZPOC ids reuse the Zound name matching rule. Dots are NOT stripped today, which is flagged.
- Waveform topic (verified): enabling a volume curve inserts a real, visible Gain effect; pitch and time curves bind to the sound's built-in pitch and speed. The waveform view already draws all three curves at once; make it an explicit-selection multi-curve view that also draws the combined result. The source read position is cheap to expose; answers given for repeats, the Looper crossfade and time-stretch look-ahead. This ties to deciding an envelope's time axis.
