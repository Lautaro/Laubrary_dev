DotGen has a window. Laubrary/DotGen opens a document the way Pyre opens a blast: browse the ones in the project or make a new one, and it arrives as a working composition rather than an empty frame — a generator system that shows nothing on its first screen teaches nothing about itself. The picture sits beside the dials with the shared backdrop behind it, so a design can be judged against the surface it will really sit on rather than against a black square.

The left pane holds what a person does to a whole document and what they do to one piece of it. The Frame block owns the seed, the resolution, the colours drawn behind and around the composition, and the two whole-document actions: draw a different seed, or write the picture out as a PNG at exactly the size shown. Under it, the hierarchy is the navigation — every row says which placement it uses and how many dots it is making right now, so the tree answers "where is the weight of this picture" without selecting anything. The commands beside it add a child sized for whatever its parent hands out, move it among its siblings, copy it with everything below it, or remove it; each is one undo away, and none of them apply to the root, which cannot be moved, copied or deleted. Selecting a row fills the Generator block with that generator's own area — its shape, its size, which of its nine points sits on the thing it is attached to, and, for a child, how many of its parent's dots it appears on at all.

The picture zooms 25 to 800 per cent toward the cursor, pans by dragging, and fits again on a double-click or the 0 key, with a legend naming which colour of dot came from which generator. Nothing about looking at a document is saved into it.

One real defect came out of building on top of the pipeline: every picture was being drawn upside down. The generator maths measures downward from the frame's top edge — that is what makes an area anchored Bottom grow upward — but the finished raster was being handed to the texture and to the PNG bottom row first, so both the preview and the export came out mirrored and every anchor meant its opposite. It is corrected once, where a rasterised frame becomes an image, so preview and export can never disagree about it.

Four blocks — Placement, Selectors, Mutators, Drawers — are present but empty. That is the shape of the remaining work rather than an omission: the window is fully operable without them, and each is now one self-contained job against a written contract.

DECISIONS I MADE (owner away, nothing waited on him):

1. THE RENDERER WAS DRAWING EVERY PICTURE UPSIDE DOWN, AND I FIXED IT IN THE RUNTIME rather than compensating in the window. Measured, not guessed: a root area anchored Top evaluates to cy = 0.25 (the pipeline is y-down from the frame's top edge, which is what makes DotAnchor.Bottom grow an area upward) and rendered into the BOTTOM quarter of the texture, because a Color32 buffer is read bottom-row-first by BOTH SetPixels32 and EncodeToPNG. So the export was mirrored too - it could not be papered over in the preview. DotGenRenderer's buffer overload now ends with a single FlipRows pass, at the one point both the texture path and the PNG path share. Verified after: Top -> mean texture row 47.5 of 64. This is a change to W1.1's committed file; W1.1's measured counts (308/32) are unaffected by an orientation flip and still reproduce exactly.

2. SELECTION IS NOT AN UNDO STEP. selectedGeneratorId is document data (the window reopens on it) so it is written with SetDirty, but without Undo.RecordObject - recording it would make Ctrl+Z walk back through clicks instead of through changes.

3. FRAME SIZE DOES NOT REBUILD THE SECTION. The brief said "MicroSlider with rebuild-on-commit"; that idiom exists for a control whose RANGE is derived from the edited value (Pyre's Bug-1), and nothing in DotGen has one. It re-renders live like any other dial, and the readouts follow because they refresh from the evaluation rather than from the edit.

4. THE WHEEL-ZOOM EXPONENT IS RESCALED TO UNITY'S DELTA UNITS. The reference's exp(-deltaY x 0.0015) assumes a browser's ~100-per-notch deltas; Unity reports ~3, which would have made the wheel imperceptible. The constant is 0.05, so one notch is the same 0.86x/1.16x step it is in the reference. Transliterated, not redesigned.

5. A TREE ROW IS TWO LINES (row + a subtle metadata line), matching the reference's own row, rather than one dense line. At the 360px pane a placement name plus two counts plus the generator name does not fit beside each other at any indent depth.

6. "Reset to demo" CARRIES NO ELLIPSIS, matching the asset chrome's own "Delete": the confirmation is a courtesy (the reset is undoable), not a second place where the real choice gets made. "Export PNG..." does carry one - it opens a save panel.

7. WritePng(path) AND ApplyDemoReset() ARE SPLIT OUT of the two dialog-owning commands, so the write and the restore can be exercised without a modal panel. That is how both were verified here, and it keeps the tested path the real one rather than a copy of it.

8. DUPLICATE USES A REFLECTION DEEP-COPY (new file DotGenClone.cs), not JsonUtility. JsonUtility serialises a [SerializeReference] list by the field's declared (abstract) type, so a round trip would lose every concrete module. The clone reads each value's real type, shares UnityEngine.Object references (a texture a fill points at is one asset), and passes through anything it cannot construct rather than failing the whole duplicate.

9. THE FOUR MODULE SECTIONS SHIP EMPTY, with no placeholder text. On-screen instruction text is against the rulebook, and the honest intermediate state is an empty section whose contract is written in code above the stubs.

=== THE GIZMO HOOK (W2.3) ===
DotGenWindow.Preview.cs declares:
  partial void DrawGizmos(Rect frame, float scale);
called on Repaint ONLY, AFTER the frame texture is blitted. W2.3 creates DotGenWindow.Gizmos.cs with:
  namespace Laubrary.DotGen.Editor { public partial class DotGenWindow { partial void DrawGizmos(Rect frame, float scale) { ... } } }
No other file needs an edit. Binding verified live (throwaway second file compiled, hook called twice on repaint, file deleted). An unimplemented partial method call is removed by the compiler, which is why the shell ships with no gizmo file.

COORDINATE CONVENTION - the frame is normalized (0,0) = frame TOP-LEFT, (1,1) = bottom-right, y increasing DOWNWARD (matching the reference, and what makes DotAnchor.Bottom grow an area upward). Use the window's mapping, never your own arithmetic:
  Vector2 FrameToScreen(float x, float y);
  Vector2 FrameToScreen(Vector2 p);
  Rect  frameRect;    // the unit frame's on-screen rect (square)
  float frameScale;   // frameRect.width - points per frame unit; multiply any normalized LENGTH by this
Both are refreshed on EVERY event, not only on Repaint, so a hit test during a drag agrees with the last draw.
Read the evaluation through:
  public DotGenResult Result { get; }   // null until the preview has repainted once
Result.order is hierarchy order; Result.For(gen) gives areas / baseDots / finalDots / traces. Never re-run the pipeline from a gizmo. Modes: doc.gizmoMode (Hovered/Selected/All/Off); targets: hoveredModuleId / selectedModuleId / doc.selectedGeneratorId. Per POC 13.1 the Generator Area gizmo stays limited to the SELECTED generator even in All mode.
