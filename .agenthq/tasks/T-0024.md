## Description

Found while migrating ProtoGuy's Legs/Upper animation data into the standard Lauminary system (see T-0025).
This is a REAL, reproducible correctness bug in `LauminaryRepo`, not specific to that migration — it can
corrupt any lauminary's baked frames whenever many animations get added to the same draft in quick succession.

### Root cause

`LauminaryRepo.SaveAnimationToDraft` calls `RebuildDraft`, which calls
`LauminaryBuilder.BuildVersionAssets` — and `BuildVersionAssets` unconditionally re-bakes **every** animation
currently in `draft.animations`, not just the one just added. Each bake writes to a per-animation atlas path
(`Atlases/<anim>.png`), keyed by animation NAME — so an animation that's already in the draft gets its atlas
PNG **overwritten and reimported again** every time a LATER `SaveAnimationToDraft` call runs for a different
animation. Calling `SaveAnimationToDraft` once per animation in a tight loop (19 times, for ProtoGuy's Legs)
means most animations get rebaked-and-reimported many times over in rapid succession, with no time between
writes for Unity's AssetDatabase to fully settle.

**Confirmed via isolated testing** (all in a throwaway scratch script, not committed):
- `AtlasBaker.Compose` (in-memory) — correct, byte-exact, alone or with all 8 walk frames together.
- `AtlasBaker.Bake` (writes+imports+slices once) — correct, exact match to source.
- `LauminaryAtlasPacker.Pack` — correct, even packing all 19 real animations together in one call.
- The SAME data run through the REAL pipeline (`SaveAnimationToDraft` called once per animation, 19 times in
  a loop) — corrupted: some frames baked nearly empty, others with roughly double their real pixel content.
  Symptoms only appeared once repeated overwrite-of-the-same-path was actually exercised; every individual
  stage is provably correct in isolation.

This points at an AssetDatabase reimport race/staleness issue specific to writing+reimporting the SAME sprite
sheet path repeatedly within one synchronous span, not a math bug in any of the baking/packing code. Not
root-caused further (would need instrumenting AssetDatabase's own import pipeline, out of scope for tonight).

### The practical workaround (already applied for T-0025)

Don't call `SaveAnimationToDraft` per-animation when importing/authoring many animations at once. Instead,
set `draft.animations` directly (batch) and call `LauminaryBuilder.BuildVersionAssets` ONCE at the end. This
produced byte-exact-verified results for all 35 ProtoGuy animations (19 Legs + 16 Upper).

### Real risk to existing usage

A normal user adding animations one at a time through the Laumination Builder UI (each save = one real user
action, with real wall-clock time between them) is far less likely to hit the tight-loop failure mode — but
it's not proven safe either, just less likely to trigger whatever the underlying race actually is. Worth
someone actually root-causing this properly at some point (instrument `TryGetPixels`'s forced-readable
reimport path, or the `AssetDatabase.ImportAsset(..., ForceSynchronousImport)` + `LoadAllAssetsAtPath` sequence
in `AtlasBaker.Bake`, across repeated calls to the same path) rather than just working around it via batching.
