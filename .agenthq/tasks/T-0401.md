A Vector meta-layer can now be told to aim only in 16 (or any 2-64) evenly-spaced directions. Turn on 'Snap Angle' in the Laumination Builder's Vector panel and the arrow detents between the allowed angles while you drag it, so a muzzle direction can no longer land between divisions. Off by default; every vector you already painted, and Pyre's anchor tool, are completely unaffected.
**Details:**
Where: the Laumination Builder's Vector-layer panel, one row directly under 'Allow Length' - a 'Snap Angle' toggle plus a 'Divisions' slider that defaults to 16. The slider is greyed out until the toggle is on, so nothing on the panel moves when you switch it. It is per layer and per lauminary: turning it on for ProtoGuy New's Muzzle layer changes nothing anywhere else. The ring is measured so that 16 divisions puts up, down, left and right exactly on it, matching the 16 facings the body's own sprites use and matching the 'EvenAim' technique's ring exactly. It only affects what you aim from now on - frames already painted keep their direction until you re-aim them. The 0-degree start is what you asked for; a custom start angle is already plumbed through in code (an unused offset parameter) and is a one-line follow-up whenever you want it.

Also fixed, not asked for: committing a new version of an animation (or duplicating one) was silently throwing away every Vector meta-layer - the painted origins and directions all vanished and the layer came back as an empty Shape layer. You were minutes from painting 16 muzzle vectors straight into that trap, so it is fixed in a separate commit.
**Technical details:**
Commit 08fcb52e (T-0401) + 28b7f67f (the adjacent data-loss fix), branch dev.

Zui/Toolkit/ZuiVectorMarker.cs: Options.angleSnapDivisions (0 = off, default) and a public SnapDirection(dir, divisions, offsetDeg = 0). Applied inside Handle()'s dragMode == 2 branch on the same line that writes d.direction, so the snapped value exists from the first moved pixel - the host writes it straight to vf.direction and repaints, hence visible detenting mid-drag rather than a correction on release. The click-to-place initial direction is snapped too. Rounding mirrors EvenDirectionsAimer.Resolve verbatim (nearest multiple of 360/n from East); 0 mismatches over 720 angles against that formula.

Runtime/Launimator/MetaLayer.cs: vectorSnapAngle (false) + vectorSnapDivisions (16), [Range(2,64)]. Nothing at runtime reads either - ZonedAnimationPlayer untouched.

Editor/Launimator/LauminationBuilderWindow.cs: VectorOptions passes the snap only when the layer opted in; BuildVectorLayerUI gains the toggle + Z.SliderInt in one WrapRow, slider SetEnabled(snapOn), Refresh() on the toggle and Dirty() on the slider (Refresh mid-drag would destroy the slider).

Editor/Launimator/LauminaryRepo.cs (separate commit): CopyAnimation now copies mode, vectorFrames (deep-cloned), vectorAllowLength and the two snap fields, plus a null guard on frames. It previously copied only id/color/frames, so CommitNewVersion / DuplicateDraftAnimation / Duplicate / the draft-heal path all destroyed Vector layers. T-0400 hit the `mode` half of this and restored it by hand.
