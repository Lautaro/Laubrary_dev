## Description

Changing a sound's time-stretch **while it is playing** — pitch-independent speed as a live control.

**Owner decision, 2026-09-27: deferred. Not part of the effect-chain port.** Finish and validate the chain port first. This is filed so the idea is not lost, not so it gets picked up next.

### Why this is not a port, and was never a lost capability

The chain port was framed as bringing back three capabilities the stripped branch had lost. Two of them genuinely were lost and are now back. This one was not lost, because it never existed:

- The part of the chain that reads a sound has exactly **two** inputs, pitch and gain. There is no speed or stretch input, in this lineage or any other.
- The time-stretching the package does have is a **whole-sound transform**: given a sound and some stretch settings it produces a new, longer or shorter sound, caches it, and hands that back to be played normally. It runs before playback and never per block.

So stretched sounds **already play correctly** through the new native path, because the stretcher hands out an ordinary sound and the new path plays ordinary sounds. That half needs nothing but a listening check.

### What building it would actually involve

A per-block stretcher running on the audio thread inside compiled code, keeping its own analysis window and overlap state for every playing sound. Either the granular or the overlap-matching approach the offline stretcher already implements, restructured so that it produces output incrementally rather than in one pass over a whole sound, and so that all of its state lives in native memory sized up front.

Two things make it materially harder than anything in the chain port:

1. **It is comparable in size to the entire chain port**, rather than a step within one.
2. **It would be the first part of this engine with no reference to check against.** Every other piece was verified by rendering the same thing two ways and comparing samples. There is no existing per-block stretcher to compare a new one to, and the offline one is not an equivalent — it is allowed to look at the whole sound at once, which is exactly the freedom the realtime one does not have. So its correctness would have to be established some other way, and that needs deciding before any code is written.

### Before starting this, settle one thing

**Which reading of the original request was meant?** "Stretched sounds must still play" is already true and needs only a listen. "A sound's stretch must be changeable while it plays" is this task. The two differ by roughly the whole of this task's cost, so it is worth one sentence of confirmation rather than an assumption.
