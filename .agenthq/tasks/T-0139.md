## Description

T-0126's design doc (SHAPER-UI-VISION-AND-DESIGN.md) left 6 items OPEN FOR OWNER (J4). Re-examined each: #1 (window min size) was already resolved in T-0132. #5 (engine-promotion sequencing) and #6 (stuck-effect hosting) are genuine owner scheduling/priority calls, left open. But #3 (colour-as-envelope feasibility) and #4 (swarm native-eligibility dynamism) turn out to be answerable TECHNICAL questions, not taste calls -- the design doc itself asked them as 'confirm whether X' questions. Resolved both by reading the real engine source directly:

#4 -- CONFIRMED dynamic, not static: IShaperSwarmNativeSource.SupportsNativeSwarm (ShaperSwarmDef.cs) is 'checked by the compiler on EVERY compile, never assumed from the interface alone -- a source may be able to batch only below some internal limit, or only once some other asset is assigned.' The mock currently models this as a fixed bool per generator TYPE (ShaperMockGeneratorEntry.SupportsNativeSwarm), which misrepresents the real engine's own stated design. Fix: make the mock's native-swarm check depend on generator PARAMS (authored state), not just which generator is selected, and correct the swarm badge's tooltip/copy to describe eligibility as checked live rather than a fixed fact about the generator type.

#3 -- CONFIRMED feasible: ZuiGradient (Assets/Packages/Laubrary/Zui/Scripts/Runtime/ZuiGradient.cs) already ships a life-phase-sampled colour ramp with animatable hue/saturation/brightness/contrast/phase transforms, already used by Pyre's SpriteFx layer for colour-over-lifetime. It is architecturally the right, already-proven mechanism for 'a Shaper fill colour that varies over life' -- reuse, not invention. This is still a REAL ENGINE change (a Shaper fill's plain Color fields would need to become ZuiGradient-wrapped, same category of change as the float->ZUIValue promotions already done for other dials), not something the mock alone can finish -- but the mock should DEMONSTRATE the pattern on at least one representative colour field, proving it out the same way other envelope-ready fields already are, rather than leaving every colour permanently static with no example.

Two of the six open design questions from the original plan turned out to be things I could actually go check, rather than things only you could decide -- so I checked them and fixed the mock to match reality.
**Details:**
1) Whether a shape can use the fast 'native' swarm mode used to be shown as a fixed yes/no per shape type. Turns out the real engine checks this live and it can depend on how many copies you're scattering -- so the mock now genuinely does that too (works up to 32 copies for the one shape that supports it, then honestly falls back and says why).
2) Whether a color can smoothly change over an object's lifetime, the way a slider already can, was an open 'not sure if this is even possible' question. It is possible -- there's already a working color-over-time tool elsewhere in the toolkit (used for particle effects), so I wired one example color on the new Solid shapes through it to prove it works, rather than just saying it probably would.
**Technical details:**
Assets/ShaperMock/Editor/ShaperMockWindow.cs: NativeSwarmAvailable now takes swarm state, not just the node, and checks a new NativeSwarmCapacity=32 constant against s.count (distinct from the existing SimulationHardCap=6, which is a different real concept -- a stateful-simulation source with no native path at all). Badge tooltip/label updated to state eligibility is checked live. Assets/ShaperMock/Editor/ShaperMockSolids.cs: ShaperSolidDef.edgeGlowColour changed from Color to ZuiGradient (Assets/Packages/Laubrary/Zui/Scripts/Runtime/ZuiGradient.cs), wired via Z.Gradient + OnBeforeMutate for Undo. Verified live: count=10 -> 'active (Native: Orb)', count=50 -> live capacity-exceeded message; edgeGlowColour confirmed ZuiGradient type with a working ZuiGradientControl rendering in the Solid card. Committed b56a9e58 on dev.
