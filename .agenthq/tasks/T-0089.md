## Description

Zoe,Lauminator, combat system.

The idea of Laubrary is to create all 2d sprite based game functionality that a game can need among what could possible be reasonable to generalise. 

On top of this both laubrary engine AND ui should be extendable. Typical functionality like aiming, direction facing, projectile firing, movement, player controlling and more all these when taken care of by Laubrary have to be in a modular way. So that bespoke game native solutions can be used in place but more importantly so that laubrarys solutions are not hardcoded and future optional solutions grows what laubrary can offer rather than bloats it.

We also need the system to be open to different gameplay. If we hardcode a fire event when player fires a gun into zoe, that spawns a pyre muzzle then we cant have different muzzles depending on gun or a power up etc...

Not sure how to do this but events like getting hit or dying will rarely be just one event. The same zoe can be hit in different ways and die in different ways. This is very complex but we need to put in all effort necessary to map out what scope off flexibility we need.

For this to work, the first solutions we design now have to be just as modular even if they are alone for the moment.

I am mostly worried regarding the health of this policy around systems that has to do with characters, agents and combat. Zoe, laumination and chunks/pyre for the visuals.

What is your thurough analysis.

Give me an exhaustive report but keep it TLDR and ELI5. I am not interested in code examples or references to classes or methods. Assume the reader only has access to what is seen in the editor and not the code itself.
