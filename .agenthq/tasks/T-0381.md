## Description

**Owner request (2026-09-20), three related asks on the shared inline "pick a LauAsset" control** (`LauAssetElement.cs` — the chip used everywhere a field references a LauAsset, e.g. the Blast field on a Chunks Pyre Blast card picking a Pyre asset):

1. **A visible "open in its editor" affordance, not just right-click — AND fix why it's greyed out for Pyre specifically.** `LauAssetEditors.Open(asset)` / `LauAssetEditors.CanOpen(asset)` already exist (a global registry, keyed by CONCRETE type, that every LauAsset-authoring tool registers into via its own `*EditorLink.cs` `[InitializeOnLoad]` class) — `LauAssetElement.ShowContextMenu` already calls it via an "Edit" item, but ONLY on right-click, AND the owner found it greyed out for the exact case that motivated this whole task: picking a `Pyre` directly into a Chunks Blast field (`IChunkEffectSpawner`-constrained). **Root cause, confirmed:** `Assets/Packages/Laubrary/Editor/Pyre/PyreSpawnSourceEditorLink.cs` registers Open/Create for `PyreSpawnSource` (a thin wrapper around a Pyre) but there is NO `LauAssetEditors.RegisterOpen<Pyre>(...)` anywhere in the codebase — grep confirms every other picked type (`BackSplash`, `ChunkSpec`, `MirageView`, `WareSpec`, `Choreography`, `SpriteChunkAnimation`, `LazorShape`, `SpriteCatalog`, `SpriteFxSpec`, `LauminaryVersion`, `Zoe`, `WeaponDef`, `AmmoDef`, `TextSplash`, `PyreSpawnSource`) has one, `Pyre` itself does not. Since `Pyre` implements `IChunkEffectSpawner` directly (`Runtime/Pyre/PyreChunksDirect.cs:33`) it can be picked straight into that slot without going through the wrapper at all — which is exactly what a real recipe does (see the owner's own "Rose Blast Plus"/"Explotion Twirl Plus" picks) — so `CanOpen` correctly (if unhelpfully) returns false for the single most common case in this field. **Fix this as part of T1 below**: add a `RegisterOpen<Pyre>(PyreWindow.OpenFor)` (and `RegisterCreate<Pyre>` if Pyre doesn't already have an inline-create story — check `AssetLibrary<Pyre>` first) — either into `PyreSpawnSourceEditorLink.cs` or a new sibling `PyreEditorLink.cs` matching every other tool's pattern. Then wire the visible button (below) so it's discoverable as an actual icon, not hidden behind a context menu: **use a pen/pencil icon** — the owner asked for "the typical pen," so ZUI already has one: `"pencil"` is a registered icon name (`ZuiGallery.cs:178` uses it for its own Rename demo, via `.IconItem("pencil", ...)`) — use that exact icon, don't invent a new asset.
2. **Private (embedded sub-asset) support for any LauAsset type, wherever applicable.** A recipe (e.g. a Chunks recipe) often needs a bespoke Pyre or similar asset that only that one recipe will ever use — cluttering the shared Pyre browser with one-off assets that make no sense to reuse or edit elsewhere. This is NOT a new idea — it already exists, fully built and Undo-safe, for exactly ONE hardcoded case: `Assets/Packages/Laubrary/Editor/Zoetrope/ZoetropeWindows.cs` (T-0371) has `IsPrivateChunks`, `MakeChunksPrivate`, `MakeChunksPublic`, `FindSparePrivateChunks` — a `ChunkSpec` embedded as a sub-asset (`AssetDatabase.AddObjectToAsset`) inside a Zoe's own `.asset` file, invisible to the shared Chunks browser, editable only via an inline "Edit" button on that one row. **Read that code in full first** (lines ~520-680), including its documented Undo-safety contract (the comment block above `MakeChunksPrivate`, ~line 577) — that contract is exactly right and must be preserved, not reinvented. The job here is to LIFT this pattern out of its one Zoe-specific hardcoded site and generalize it into `LauAssetElement.cs` itself, so it applies automatically everywhere the chip is used, for whatever LauAsset type is being picked, with whatever the CURRENT window's own edited asset is as the natural "owner" to embed into.
3. **Convert Private→Public and Clone (current or a newly-picked public asset) into a new private embedded copy**, as buttons on the chip/its context menu — same semantics as `MakeChunksPrivate`/`MakeChunksPublic` already have (carries over the source's tuning via `EditorUtility.CopySerialized`, no shared reference between the two afterward, reuses a matching spare copy instead of piling up duplicates on repeated switches). Also confirm (it likely already is, but verify and make it explicit/guaranteed) that a private/embedded sub-asset is excluded from `AssetLibrary<T>.Enumerate()` / the shared browser grid for every LauAsset type, not just the one Zoe/Chunks case — check what actually filters sub-assets out today and whether it's general or ChunkSpec-specific.

**Read first:** `D:\AgentGuide\ui-rules.md` and the laubrary skill's `references/ui-layout-rules.md` (hard gate before any UI control), and `~/.claude/skills/laubrary/references/authoring.md` if it documents chip/picker conventions. `LauAssetElement.cs`'s own header comment references `LAUASSET_PICKER_SWEEP.md` and the "no inline button row stealing a row of width; a reference reads as a chip; everything besides picking lives on a right-click context card" rule that motivated the CURRENT chip-only design — the owner's ask for a visible Edit button is a deliberate exception to that rule (discoverability matters more here than the row-width purity it was chasing), so don't quietly revert to a full button row; add the minimum visible affordance the ask needs (e.g. a small icon-button beside the chip, shown only when `CanOpen` is true) without undoing the rest of that design.

**Details:**
1) PENCIL. Every LauAsset chip now draws a small pencil icon-button beside it whenever the value it holds has an authoring tool registered. The right-click Edit stayed. It is one 20px square, only when there is something to open, so the chip design the picker sweep landed on is intact - no button row came back.

2) THE GREYED-OUT EDIT, fixed at the root. LauAssetEditors is keyed by CONCRETE type; only PyreSpawnSource (the three-field wrapper) was ever registered, while a real Chunks Blast field holds a Pyre directly (Pyre implements IChunkEffectSpawner itself). So the single most common value in that field was the one value whose Edit was dead. New Editor/Pyre/PyreEditorLink.cs registers Open (PyreWindow.OpenFor) + Create for Pyre, matching every other tool.

3) PRIVATE COPIES, FOR ANY TYPE. The 'a bespoke ChunkSpec that lives inside this Zoe's file' feature is now Editor/AssetKit/LauPrivateAsset.cs, parameterised over the asset TYPE and the OWNER, wired into the chip itself. A Chunks recipe can keep its own bespoke Pyre; a Zoe its own SpriteFx stack; and so on. A latching icon-toggle beside the chip switches Public <-> Private; Make private / Make public / Clone / Clone from... sit on the right-click card. Clone always embeds a genuinely NEW copy under an unused name; the plain switch still reuses a matching spare so toggling back and forth never piles up duplicates.

4) WHO THE OWNER IS. Tools that build a chip by hand pass it (ChunkWindow.AssetPicker, every LauAssetElement.Build in ZoetropeWindows). Everything else picks it up from LauAssetElement.OwnerScope, which ZuiAssetWindow.BuildUI sets around its subclass's body build - so a REFLECTED reference field in any asset tool gets private copies for free. The scope is synchronous and restored in a using, so a chip built outside it simply offers no private actions; it can never embed into the wrong asset.

5) THE ZOE SITE WAS PORTED, not duplicated. 215 lines of Zoe-specific private-asset code are gone from ZoetropeWindows.cs, including its 'Public | Private' MiniRadio, which the latching icon replaces at a third of the width. W Disc Zoe B's two EXISTING private ChunkSpecs from T-0371 still read as private, with no migration.

ONE THING TO SAY OUT LOUD: this is a broad visible change. Every LauAsset chip in every asset window now shows a private latch (and a pencil where one applies). That is what 'for any LauAsset type, wherever applicable' means, but if it reads as too much furniture on rows that will never want a private copy, say so and it can be narrowed to call sites that opt in.
