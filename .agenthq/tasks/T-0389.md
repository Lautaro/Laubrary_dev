## Description

**Owner request (2026-09-21), while reviewing UC4's real-context setup.** Noticed the Zoe Hit reaction's effect entry is labelled "Pyre + Chunks," assumed (correctly, it turns out) that this reads as a leftover/wrong grouping — an effect should only play a Pyre OR a Chunks burst, not both bundled into one ambiguous entry type.

**Root cause, fully traced — this is real and confirmed, not a misunderstanding on the owner's part:**

`PyreChunksFx` (`Runtime/ZoetropePyre/PyreChunksFx.cs`, editor label "Pyre + Chunks") has TWO independently-optional fields, `blast` (a direct Pyre) and `chunks` (a ChunkSpec) — a row shows this generic class-name label regardless of which fields are actually populated. **Grepped every real (non-demo-test) asset in the project that uses this type:**

- `Assets/Zoetrope/Floating Disc.asset` (the owner's real character) — `blast: {fileID: 0}` (empty), `chunks:` set. **Chunks-only, mislabelled "Pyre + Chunks."**
- `Assets/Zoetrope/Hero Gun.asset`, `Assets/Demos/ProtoGuyDemo/ProtoGuy.asset`, `ProtoGuy Scattergun.asset`, `ProtoGuy EvenAim.asset`, `ProtoGuy FreeAim.asset` (weapon muzzle flashes) — `blast:` set, `chunks: {fileID: 0}` (empty). **Pyre-only, correctly single-purpose already — these need NO changes, leave them alone.**

**Every real usage in the whole project already uses this type as one-or-the-other, never both.** The "combined" capability exists in the code but is never actually exercised anywhere real — exactly matching the owner's instinct that this is architectural leftover, not a real design need.

**The fix already exists and was already built for exactly this reason — it just wasn't adopted on existing rows.** `SpawnChunkFx` (`Runtime/ZoetropePyre/SpawnChunkFx.cs`) is a dedicated, Chunks-only effect type, and its own header comment says so explicitly: *"the Chunks-only counterpart of the bundled PyreChunksFx (which STAYS), promoted to a first-class palette effect."* It is a strict functional superset for the chunks-only case — confirmed: it samples the SAME live palette (`ZoeLiveSampler.SampleColours(ctx.Renderer, 6)`, same default count 6) and forwards the same live sprite override, PLUS extra scalar-based sizing (`baseScale`/`scalePerAmount`, defaulting to 1/0 which is byte-behaviourally identical to `PyreChunksFx`'s fixed-size debris).

**Do:**
1. Find every Zoe/effect-carrying asset in the project with a `PyreChunksFx` entry where `chunks` is set and `blast` is empty (Chunks-only usage) — this includes `Assets/Zoetrope/Floating Disc.asset` (the owner's real character — read `.agenthq/workspace/ChunksEditor/PROGRAMME_RULES.md` and every "never touch the owner's real assets" caution in this project's memory before touching it; the owner explicitly asked for this one, but still be surgical: touch ONLY the specific effect entry, verify with `git diff` before committing, nothing else about that file should change) and the UC4/5/6 demo copies this session already built (`UC Floating Disc (walk copy).asset`, `UC Disc Enemy B.asset`).
2. For each, convert that entry from `PyreChunksFx` to `SpawnChunkFx`, carrying the `chunks` reference over losslessly. Leave `sampleLauminaryColours`/`sampleCount` at their defaults (true/6) unless the source `PyreChunksFx` row was somehow configured differently (it wasn't — that type has no such toggle, it always sampled).
3. **Do NOT touch any `PyreChunksFx` row where `blast` is set** (Hero Gun, ProtoGuy's weapons) — those are correctly single-purpose Pyre-only rows already; converting them to anything would be a regression, not a fix.
4. Decide, and say which you chose: leave `PyreChunksFx`'s dual-field capability in the code as-is (it's dead-but-harmless, matches the class's own "which STAYS" comment — i.e. it may be intentionally kept for a rare future Pyre-only-with-fallback-Chunks case) vs. proposing its removal as a separate follow-up (do NOT remove it yourself without asking — that's an API-surface decision, not a data-migration one).
5. Verify each migrated row still plays a real Chunks burst with live colours identically to before — re-run the same real-hit verification T-0388 already built for UC4 (ProtoGuyDemo, both enemies) to confirm nothing regressed, plus a spot-check that the owner's real Floating Disc (wherever it's actually used in a real, non-demo scene, if any) still fires its Hit effect correctly.
6. Commit, by path, only the specific files touched.

DECISION (todo T3): PyreChunksFx is left in the code EXACTLY as-is — not removed, not deprecated. This was a data migration, not an API change. Its dual-field capability is now unexercised by any asset in the project, which makes retiring it a reasonable follow-up, but that is an API-surface call for the owner.

MECHANISM — worth knowing for any similar migration: these are [SerializeReference] MANAGED references, not script-GUID references. PyreChunksFx's own script GUID (5d107c3b5da9d8249b3c864e00187e7d) appears in none of these assets. The migration is a {class: PyreChunksFx} -> {class: SpawnChunkFx} edit inside the asset's trailing RefIds block, plus swapping the data fields. Each entry's rid was kept, so the ReactionFx.fx pointer that references it never moved.

TYPE COMPATIBILITY: the holding field is declared [SerializeReference] public IEffect fx in Runtime/Zoetrope/ReactionFx.cs (widened from ICombatFx to IEffect by an earlier slice). SpawnChunkFx implements IEffect, so it is accepted — independently confirmed by the fact that the same fx field on Floating Disc's death row already held a SpawnChunkFx before this change.

BEHAVIOURAL PARITY: both types' Apply(EventContext) call ZoeLiveSampler.SampleColours(ctx.Renderer, 6) — SpawnChunkFx's sampleCount default of 6 is the same constant PyreChunksFx hardcoded — and forward ZoeLiveSampler.LiveSprite(ctx.Renderer) as the burst's sampleSourceOverride. SpawnChunkFx's extra sizing defaults to baseScale 1 / scalePerAmount 0, so ResolveScale returns exactly 1 and Apply skips the container scale write entirely at 1 — not even a redundant transform write is added. The dropped blastFps and sortingOrder were blast-only fields, inert with no blast. So T-0388's live-colour proof is unaffected.

SIDE EFFECT, harmless: SpawnChunkFx implements IEventParamUser (Position | Direction | Scalar), which PyreChunksFx does not, so the Zoe event editor will now also offer these rows a Scalar param. PyreChunksFx's IEffectOrientationHint was blast-derived and returned nothing with no blast, so nothing is lost there.
