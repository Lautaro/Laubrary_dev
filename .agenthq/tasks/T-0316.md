## Description

**Filed by T-0313 (A27, ninth structural pass). Measured live at HEAD ae66d31c; write-up in `workspace/T-0313/A27-NINTH-PASS.md` sec 2.3, dumps `out/unreachable-shaper-reach2.txt`, `out/unreachable-pyre-reach2.txt`, `out/tab-Layers.txt`, `out/tab-Canvas.txt`.**

Read as `focusable == false` on DRAWN leaf controls, so this is not the ordinary "a disabled control cannot be focused" case:

| window / state | leaf controls | not focusable | which |
|---|---|---|---|
| Shaper, demo doc, layer 0, window 1400 | 144 | **10** | 8 x `ZuiValue2DControl`, 1 x `ZuiMicroMinMax`, 1 x `ZuiPad` |
| Pyre, Torch layer, 1 column | 54 | **9** | 9 x `ZuiMicroMinMax` |

Confirmed by a LIVE traversal, not only by the flag: dispatching `NavigationMoveEvent(Next)` - the event UI Toolkit turns Tab into - through Shaper's Layers card visits 18 of its 20 leaf controls and jumps `+ Add layer` -> `Height` straight past `Lifetime`, never landing on `Direction XY`. (The Canvas card, by contrast, is 5 of 5 reached, in reading order - ordering is not the problem, existence of a focus target is.)

**The Pyre nine are the dials T-0312 created.** `Root spread`, `Root height`, `Tongue climb / peel / width / length / life`, `Ember rise`, `Ember size` were `Z.MinMax` - a `MinMaxSlider` plus two `FloatField`s, i.e. focusable AND typeable - and are now `Z.MicroMinMax`, which carries no field of any kind. That swap fixed a real 8.4-27.6px overflow per dial and should not simply be reverted; but it also removed typed entry and keyboard access from every reflected `[Range] Vector2` field (13 exist in `Runtime/**`), and that cost was not measured at the time.

**The shape of the answer is already in the package:** the scalar sibling `ZuiMicroSlider` carries a `FloatField _numField` (`Zui/Toolkit/ZuiMicroSlider.cs:33`) - it is compact AND focusable AND typeable. `ZuiMicroMinMax` carries none.

Not prescribing the fix (programme rule 6). Facts a fix must satisfy: MicroMinMax's width budget is what made it the right control (150px, two per row); `ZuiValue2DControl` and `ZuiPad` are spatial drag controls with the same gap; and nothing here has been driven with a real keyboard - the traversal was an event dispatched into the panel.

Scope: `Zui/Toolkit/ZuiMicroMinMax.cs`, `ZuiValue2DControl.cs`, `ZuiPad.cs`. No serialized data changes.

CHANGELOG: ZUI: MicroMinMax, Pad and Value2D can now be reached and driven by keyboard (Tab to focus, arrow keys to nudge, Shift for the alternate handle/coarse step), closing the gap the MicroMinMax swap opened.

All three controls (Zui/Toolkit/ZuiMicroMinMax.cs, ZuiPad.cs, ZuiValue2DControl.cs) carried no field of any kind, so `focusable` was never set and Tab skipped straight over them (confirmed live in T-0313's traversal: Layers card jumped `+ Add layer` -> `Height`, past `Lifetime`/`Direction XY`). Fixed by setting `focusable = true; tabIndex = 0;` on each control itself (matching the existing ZuiEnvelope precedent for a custom-painted focusable element), adding a shared `.zui-kbd-focus:focus { outline-color: var(--zui-accent); outline-width: 2px; }` rule to ZuiToolkit.uss (no such focus-ring class existed before; this is new, reusing the toolkit's existing --zui-accent highlight colour rather than inventing a new one), and wiring a KeyDownEvent handler on each that arrow-nudges the value through the SAME mutate path the pointer drag already uses:
- ZuiMicroMinMax: Left/Right nudges whichever handle a pointer last grabbed (a new `_lastHandle` field, defaulting to Low, updated from OnDown's existing Low/High/Both classification whenever it isn't Both); Shift targets the OTHER handle. Each press wraps one `OpenGesture()`/`SetValues(notify:true)` cycle, same as the double-click-reset path.
- ZuiPad: arrows nudge the Vector2 by a fraction of its own Rect range (2%, 10% with Shift); goes through the exact same `OnChanged` event SetFromLocal already fires (this control never had a separate onBeforeMutate hook, so nothing to route around). A left-click now also calls `Focus()` so a mouse user lands on Tab order at the point they last touched.
- ZuiValue2DControl: focusable lives on the OUTER control (not the inner Plot2D, which Build() tears down and recreates on every fold/mode change and would drop focus on the first edit). Arrows nudge the source's Static value, or in curve mode the point named by a new `_focusIndex` field (updated whenever Plot2D's OnPointerDown grabs or creates a point); Shift is a coarser step. Routes through the existing `Mutate()` helper (OnBeforeMutate/OnChanged pair), then calls the same `Build()` refresh ResetToDefault/the menu already use. A new TrickleDown PointerDownEvent handler calls `Focus()` on any click anywhere in the control (plot, numeric fields, fold label) so a mouse user's next Tab lands here too; a native field's own click still re-focuses itself afterward as UI Toolkit does by default.

Mouse/pointer behaviour is unchanged except the two explicit `Focus()` additions noted above (ZuiPad's click, Value2D's trickle-down click) — those are additive (a previously-unfocusable element gaining focus on click), not a change to any existing drag/click math, clamping, or event consumption.

Did NOT touch ZuiReflect.cs, ZuiSectionToggleBar.cs, or any window file, per card scope. No serialized data changes; no new controls, concepts, or menu items.
