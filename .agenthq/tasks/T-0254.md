**Technical details:**
Why halfExtentX/Y/bakeWidth/bakeHeight were NOT deleted outright, verified in source:
- ShaperCompiler.cs reads def.halfExtentX/halfExtentY/bakeWidth/bakeHeight directly at EmitNativeSwarm (~625-628) and EmitComposite (~1000-1003), plus derives box/support-box maths from the resulting baked/raster values at multiple further lines (775-909). That is a dozen-plus read sites, not the zero the card's 'verify no other reader' implied.
- ShaperCompiler.Compile(...) takes no canvas width/height/pixelSize parameter at all, and its own doc comment states the signature is 'Kept EXACTLY as shipped ... because the field audit and every existing caller use it.' The ONLY channel by which the canvas-fitted box reaches the compiler today is these four instance fields, written by ShaperCompositeDef.FitTree/FitTo immediately before compile (ShaperDocumentRenderer.RenderPhaseInto:289, then ShaperFillResolver.Resolve -> ShaperCompiler.Compile on the same node objects).
- Deleting the fields would need Compile()'s signature widened (breaking the 'kept exactly as shipped' contract) and every call site between RenderPhaseInto and EmitComposite/EmitNativeSwarm re-plumbed to carry canvas dims down -- out of proportion for a code-only task that cannot compile-verify the change.
- What IS safe and done: [NonSerialized] on all four fields removes them from the ASSET data (the part of 'authored surface' that can leak stale data across sessions) while leaving ShaperCompiler's read path untouched -- FitTo always runs before Compile within one render pass, so the NonSerialized default is never actually read by the compiler; only a real render's freshly-fitted value ever is.
- Confirmed the removal is cache-safe even without the fields' hash contribution: canvasWidth/canvasHeight/pixelSize are already mixed directly into every layer's key via ShaperLayerKey.DocumentPart(doc), so a canvas resize invalidates the render cache through that path regardless of whether the composite box is separately hashed (the old ShaperNodeIdentity mechanism the class doc used to cite for this no longer exists -- proposal #1 was already executed by a prior wave; the stale reference was corrected).
