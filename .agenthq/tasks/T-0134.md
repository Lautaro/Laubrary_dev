## Description

User feedback after reviewing screenshots: 'vertical space is precious, use horizontal space -- don't put 3 sliders stacked vertically, they will probably fit horizontally, at least 2' and 'Shaper will be a dense workbench, assume the user gives it the whole screen -- make sure the UI can make good use of receiving more width, not just produce ridiculously long sliders.' Also asked to see the generator/modifier add-menu UX for a huge list.

PM (this session) audited and fixed directly: ShaperMockWindow.cs (Canvas 4-field row, light-rig dial rows 4-per-row instead of 4 stacked pairs, extrusion/bevel 6-per-row, lighting-response 6-per-row, swarm 4-per-row with the previously-orphaned single Lifetime-stagger slider folded in, N-gon/Star primitive dials packed) and ShaperMockFillControl.cs (Texture/IndexedStrip/TapestrySteel/HeightField bodies packed tighter). Confirmed no stretched sliders anywhere (every control already had an explicit width; the issue was purely under-packing, not stretching). Bumped the window's initial split width from 400 to 560 so the packing payoff is visible without the user having to discover the drag-to-widen affordance first. Verified live at both the 820x520 minimum and a 1500x900 wide window that packed rows correctly wrap down / expand across.

Still open / needs an owner decision, not resolved this pass: the add-effect/add-generator popover (ZuiMenu) is a flat, narrow (~190px), single-column, non-searchable list -- fine for the mock's small stand-in catalogs (7-9 items) but will not scale gracefully to the real engine's 41-effect catalog, let alone a 245-entry preset library (which the design doc already separately plans a thumbnail grid for). Whether ZuiMenu should grow a search/filter box as a shared capability, or whether effects/generators specifically need a different browsing UI, is an open design question -- flagged for the owner rather than silently decided.
